# CS167 知识库总览（Introduction to Distributed Systems）

> **文档性质说明**：Berkeley CS167（分布式系统导论）已多年未开课，公开讲义停留在 2000 年代初。本文以其官方课程目录（网络结构与 Internet 路由、消息传递与 RPC、进程迁移、分布式文件系统与缓存一致性、可靠/可用/可扩展服务器设计、Internet 安全）为骨架，用至今有效的经典分布式系统知识体系填充，结构对标现代分布式课程（MIT 6.824、新 Berkeley CS162 后段）。概念可靠，"当年讲义的具体编排与项目"无法还原。

## 8+1 总览卡

1. **课程定位**：研究"多台独立机器通过网络协作，对外表现得像一个系统"时产生的问题。单机 OS 的同步与故障在多机条件下全部被放大——没有共享内存、没有全局时钟、故障是部分的。
2. **四个核心目标（CAP 与日常权衡的源头）**：**可扩展性**（加机器就能扛更多负载）、**可用性**（部分故障时仍服务）、**可靠性**（结果正确、数据不丢）、**透明性**（访问位置/并发/故障/迁移对用户尽量隐藏）。
3. **三大障碍**：**异构**（不同硬件/OS/网络，靠中间件与标准协议屏蔽）、**不可靠网络**（延迟无界、丢包、乱序、分区）、**部分故障**（机器可能只是"慢"，你无法确知它死没死——这是分布式一切困难的根源）。
4. **两大通信范式**：消息传递（显式 send/recv，最朴素）→ 远程过程调用 RPC（伪装成本地调用的消息往返，主流工程接口）。
5. **两个经典战场**：分布式文件系统（NFS 的无状态 vs AFS 的整文件缓存，理解一致性取舍的最佳案例）与 可扩展可靠服务器集群（分层、复制、负载均衡、故障转移）。
6. **核心思维**：一切设计决策都是在"延迟、带宽、故障模型、一致性强度"四个维度上做权衡；没有免费的透明性，只有限定场景下成立的折中。
7. **三道门槛**：RPC 语义（at-least-once/at-most-once/exactly-once 与幂等）、分布式共享状态的一致性模型（强一致 vs 最终一致的谱系）、复制与缓存的失效/更新协议。
8. **本课的"反直觉"结论**："Exactly once"在不可靠网络上不可实现，工程上只能做到"效果上一次"（幂等 + 去重）；服务器状态越少越可靠（NFS 故意无状态，崩溃恢复极简单）；缓存提升性能的同时制造一致性问题——客户端缓存是分布式文件系统设计分歧的分水岭；网络分区发生时，一致性与可用性必须二选一（CAP），不存在两者兼得的系统；"两台机器对同一时间达成一致"都需要协议（NTP 也只是近似同步）。

**一句话**：CS167 教的是"把故障当作常态而非异常后，如何用复制、冗余、重试与弱化承诺，在一组随时可能挂掉的机器上构建可用服务"。

# 第一部分：目标、模型与权衡

## 1. 分布式系统的目标
- **可扩展性 scalability**：增加机器数能近线性提升容量/吞吐；瓶颈分析——服务端状态、共享数据、同步点往往是扩展杀手。
- **可用性 availability**：系统在部分组件故障时仍能响应；用冗余（复制）换取。
- **可靠性 reliability / 正确性**：不丢数据、不返回错误结果；通常用"确认 + 持久化 + 重试"组合。
- **透明性 transparency**（访问/位置/迁移/复制/故障/并发的透明）：目标是"像用单机一样用分布式系统"，但透明性有性能代价，多数系统只承诺其中一部分。

## 2. 故障模型（设计前必须先说清假设）
| 模型 | 行为 | 难度 |
|---|---|---|
| Crash 故障 | 节点停机，停前行为正确 | 最容易（服务端集群的主要假设） |
| Omission 故障 | 节点活着但漏收/漏发消息 | 中（网络分区、消息丢失） |
| Timing 故障 | 响应超出时限但最终会答 | 中（无法区分慢与死） |
| Byzantine 拜占庭 | 节点可任意行为甚至恶意撒谎 | 最难（需 BFT 协议，多数互联网系统不假设） |

- **失败检测的根本困境**：超时只能得到"疑似死亡"；心跳间隔短→误判且费带宽，长→发现慢。**租约 lease** 是标准折中：租约期内授权有效，到期未续约才视为故障。
- **网络分区 partition**：两边都活着但无法通信——比单机宕机更危险，因为双方都可能继续对外服务并各自修改数据。

## 3. CAP 与 PACELC（决策语言）
- **CAP**：一致性 C（强一致，读到最新写）、可用性 A（每个请求都收到非错误响应）、分区容忍 P——跨广域网的系统 P 无法放弃，**分区时只能在 C 与 A 之间选**。
  - CP：分区时拒绝部分请求保正确（如多数派共识系统）。
  - AP：分区时继续服务，事后合并（如 DNS、早期 Dynamo 风格）。
- 注意：CAP 只在分区窗口内构成二选一，非分区时可同时优化 C 与 A；不要把 CAP 当日常借口。
- **PACELC 细化**：If P(artition) choose A or C；**Else**（正常运行时）choose L(atency) or C(onsistency)——平时也要在延迟与一致性间取舍。

# 第二部分：通信抽象

## 4. 消息传递
- **最底层范式**：send(dest, msg) / recv()；网络层服务选择——UDP（无连接、快、不保序，适合查询/组播/实时）或 TCP（字节流、可靠有序，但有连接与队头阻塞成本）。
- **阻塞 vs 非阻塞**：阻塞 send 简单但并发度低；非阻塞 + **select/poll/epoll 多路复用**让单线程管理大量连接（高并发服务器经典模型，事件驱动的开端）。
- **消息边界责任在应用**：TCP 是字节流，必须自行成帧（长度前缀 / 定长 / 分隔符）。
- **请求-响应关联**：异步请求要用 request ID 把回复匹配回调用方。

## 5. RPC（课程核心机制）
### 5.1 工作结构
1. 接口定义 IDL：声明远程过程名、参数与返回类型（如早期 Sun RPC 的 .x 文件；现代 gRPC 的 .proto）。
2. 客户端 stub：把参数序列化（marshalling，处理字节序/对齐/异构表示）成消息，发请求，等回复，解包。
3. 服务器 stub：收消息、反序列化、调用真正的服务函数、把结果序列化发回。
4. 对程序员看起来就是普通函数调用——这是 RPC 的全部卖点：**通信透明性**。

### 5.2 RPC 伪装不了的四件事（透明性的失败）
1. **延迟高几个数量级**：本地调用纳秒级，网络毫秒级——不能当本地函数随意细粒度调用。
2. **会失败**：本地调用要么执行要么进程崩；RPC 可能超时、可能重复执行、可能"执行了但回复丢了"。
3. **无共享地址空间**：传不了指针，只能传值；复杂结构要序列化。
4. **部分失败语义模糊**：超时后调用方无法确知操作是否发生。

### 5.3 三种调用语义（必考核心）
- **at-least-once（至少一次）**：没收到回复就重试；可能执行多次。**要求操作幂等**——同一请求执行 1 次和 N 次效果相同（如"把余额设为 100"幂等，"余额加 10"不幂等；支付要靠业务唯一单号去重）。
- **at-most-once（至多一次）**：服务器用请求 ID 去重，重复请求直接拒绝/返回缓存结果；保证不重复，但可能一次都没执行。
- **exactly-once（恰好一次）**：不可靠网络 + 服务器可能崩溃的条件下**无法真正实现**；工程上的"exactly-once"是 **effectively-once**：at-least-once 传输 + 幂等处理 + 持久化去重表，让"效果"恰好一次。消息系统（Kafka 事务、端到端去重）同理。
- 至少一次的配套：重试要有**超时预算 + 退避（exponential backoff + 抖动）**，否则故障期重试风暴把恢复中的服务再次打垮。

## 6. 消息队列与发布订阅
- 相比 RPC 的**同步与时序耦合**，队列让生产者与消费者在时间、空间、速率上解耦； broker 暂存消息（削峰填谷）。
- 语义谱系：at-most-once（发了就忘）/ at-least-once（ACK 后才删，可重复消费）/ effectively-once（幂等 + 事务/去重）。
- 顺序保证通常只在单分区/单键内成立——"全局有序"与"水平扩展"直接冲突。

## 7. 组播
- 一对多发消息；IP 组播靠组地址 + 组播树（课程概念级）。
- 可靠组播的难题：ACK 内爆（所有接收者同时回 ACK 打爆发送方）——用 NAK 抑制、层级 ACK 聚合缓解；消息全序/因果序需要额外协议。

# 第三部分：进程迁移

## 8. 进程迁移是什么、为什么难
- **动机**：负载均衡（热点机器上的进程迁走）、容错（故障机前迁移）、数据局部性（迁到数据所在处）、管理（停机维护）。
- **基本流程**：在源端挂起进程 → 传送进程状态（代码、数据、栈、寄存器、OS 资源表）→ 目的端重建并恢复执行。
- **难点（透明性的重灾区）**：
  - 打开的文件、网络连接、待处理信号、挂起的 I/O 如何在新机器重建？
  - 未完成的消息、其他节点持有的旧地址（"残余依赖 residual dependency"）怎么办？
  - 迁移期间进程不可用的窗口；迁移传输量与运行时间的竞争（进程可能迁完又变了）。
- **现代回响**：虚拟机迁移（VM live migration，迁移整个 VM 状态、共享存储配合 pre-copy 迭代传输脏页）、容器漂移、移动计算的会话迁移——本质都是同一组问题换了抽象层。
- 工程现实：细粒度进程迁移在通用系统中基本失败（透明迁移成本太高），胜利的是粗粒度的 VM/容器迁移与无状态服务重调度（K8s 直接杀 Pod 在别处重建，不迁状态）。

# 第四部分：分布式文件系统（课程最核心案例）

## 9. NFS：无状态服务器的胜利
- **设计目标**：异构 UNIX 机器间透明共享文件；服务器崩溃必须能快速恢复。
- **关键决策：服务器无状态**——不记录"哪个客户端打开了什么文件、读到第几个字节"。每次请求自带全部上下文（文件句柄、偏移、长度）；读/写是显式位置操作而非维护共享文件指针。
- **收益**：服务器崩溃重启后客户端只需重试，无需恢复会话状态；服务器可横向无状态扩展；客户端故障也不污染服务器。
- **代价与妥协**：
  - 无状态 → 无法维护打开文件语义（删除正在使用的文件等行为与本地 UNIX 语义不同）。
  - 性能靠客户端缓存，但无状态服务器不主动通知缓存失效 → 每次操作带缓存属性（时间戳），服务器比对决定是否可用；客户端周期性校验（TTL/validation），可能读到短暂过期数据。
- **协议分层**：NFS 跑在 Sun RPC 上，早期用 UDP + 幂等操作配合重传（NFS 操作设计为幂等是 at-least-once 语义的经典实践），现代走 TCP。

## 10. AFS：整文件缓存 + 回调失效
- **不同假设**：局域网快、文件少被多人同时写、大多数访问是读——优化方向是**大幅减少与服务器的交互**。
- **机制**：
  - 打开文件时把**整个文件**缓存到本地磁盘，之后所有读写在本地副本进行；关闭时若改过，整文件写回。
  - **callback（回调）机制**：服务器记录谁缓存了该文件；任何人修改时，服务器通知所有缓存者作废（invalidate callback）；callback 有效期内客户端直接用缓存，零校验流量。
  - 客户端故障/网络断开：callback 状态可能丢失 → 服务器在超时或恢复时让客户端重新验证。
- **语义结果：session semantics（会话语义）**——文件最后关闭者覆盖；一个进程内自己的写自己立即可见，但别的进程/机器在文件关闭前看不到更新。这与 UNIX 的"写立即可见"语义不同，但换取了巨大性能。
- **NFS vs AFS 的本质**：无状态 + 逐块 + 客户端轮询验证（NFS）vs 服务器维护回调状态 + 整文件粒度 + 主动失效（AFS）——一致性强度、服务器状态、网络流量三者的经典权衡。

## 11. 现代延伸（理解谱系而非考古）
- **GFS（Google 文件系统）**：假设大文件、顺序追加为主、故障是常态、带宽比延迟重要——单 Master 存元数据、多 chunkserver 存数据、每块多副本、租约管理主副本、原子追加。
- **对象存储（S3 风格）**：放弃文件系统 POSIX 语义，只给 GET/PUT 整个对象 + 键值命名 + 跨多副本冗余；弱语义换无限扩展与高耐久——"弱化承诺换取可扩展性"的当代版本。
- **一致性取舍规律**：语义越接近单机文件系统（POSIX），扩展与高可用越难；语义越弱（不可变对象、追加、最终可见），规模越大。

# 第五部分：缓存、复制与一致性

## 12. 缓存的一致性设计
- **缓存层级**：客户端本地（AFS/NFS、浏览器、移动端）→ 代理/CDN → 服务器内 buffer cache。越靠近用户收益越大，一致性维护越难。
- **两大策略族**：
  - **失效法 invalidate**：写时通知所有副本删除旧值；网络消息少（一次失效通知），但失效后读要重新拉取。AFS callback 属此类。
  - **更新法 update/write-through**：写时把新值推给所有副本；读永远快，但写放大、冷副本也被迫更新。
- **租约式校验**：副本带有效期（TTL/lease），期内可信，过期重新验证——允许"有限时间内的不一致"换流量节省（DNS、HTTP cache、NFS 同构）。
- 客户端缓存的**写策略**：write-through（同步写穿，安全但慢）、write-back（延迟写回，快但有丢数据/冲突窗口，AFS 关文件才写回属此类）。

## 13. 一致性模型谱系（重要：不是只有"一致/不一致"两档）
| 模型 | 承诺 | 代价 / 场景 |
|---|---|---|
| 严格/线性一致 linearizability | 写一旦完成，所有后续读（实时顺序）都见新值，操作如同瞬时按全局顺序生效 | 最强，需共识/多数派，延迟最高 |
| 顺序一致 sequential | 所有进程看到相同的操作全序，但不与真实时间绑定 | 比线性一致弱，仍较贵 |
| 因果一致 causal | 有因果关系的操作顺序一致，并发操作可各看各的 | 协作类应用常用甜点 |
| 最终一致 eventual | 停止写入后副本最终收敛，中间可读到旧值 | DNS/对象存储/购物车类，可用性最高 |
| 读己之写 / 单调读 | 会话级保证（用户自己看到自己的更新等） | 客户端体验兜底，可与最终一致叠加 |

- 选型问：用户能否容忍旧值？容忍多久？同一用户呢？（很多业务只需"读己之写 + 最终一致"）。

## 14. 复制与副本协议
- **为什么复制**：提高可用性（挂一个还有副本）、降低读延迟（就近读）、抗数据丢失。
- **被动复制（主从 primary-backup）**：所有写到主，主同步/异步到从；读可走从（可能旧）。
  - 复制方式：同步（等所有副本确认，慢但不丢）/ 异步（主确认即可，快但主挂可能丢已确认数据）/ 半同步（至少一个从确认）。
- **主动复制（多主/无主）**：任意副本可接写，需冲突检测与解决（时间戳/向量时钟/最后写胜 LWW/应用层合并）。
- **两阶段提交 2PC（跨节点原子提交）**：协调者先问所有参与者"能否提交"（prepare 投票），全 yes 才发 commit。
  - 问题：协调者在第二阶段崩溃会让参与者**阻塞等待**（占有锁不释放）；参与者在 prepare 后必须持锁——可用性差，是 CP 类协议。
  - 3PC 试图用超时解阻塞，但引入新假设且无法覆盖网络分区，工程上少见；现代系统多用共识（Raft/Paxos）管理元数据与选主。
- **选主与脑裂**：主故障需重新选主；分区时可能出现两个主（脑裂）→ 靠**多数派投票（quorum）**保证同一时刻只有一个主：N 个节点需 ⌈N/2+1⌉ 同意。
- **读写 quorum**：写需 W 个副本确认、读访问 R 个副本，W+R>N 时读到的集合必含最新值——在一致性、读延迟、写延迟、可用性间旋钮式权衡（Dynamo 风格）。

# 第六部分：可扩展可靠服务器设计

## 15. 扩展方式
- **垂直扩展 scale-up**：买更大的机器——有上限且贵，但简单（无分布式一致性问题）。
- **水平扩展 scale-out**：加更多普通机器——理论无限，但必须解决：无状态化、数据分区、负载均衡、故障转移。
- **应用层无状态化原则**：把会话/状态下沉到共享存储（数据库/缓存）或客户端（token），应用服务器变成可随意增删的"牲口"——现代云原生架构的第一原则，正是 NFS 无状态思想的延伸。

## 16. 数据分区
- **按范围分区**：键区间分配（如用户 ID 0–1M）；支持范围查询，但易热点（顺序写打爆一个分片）。
- **按哈希分区**：hash(key) mod N；均匀但失去范围查询能力。
- **一致性哈希**：节点与键都映射到环上，键顺时针归属最近节点；增删节点只影响相邻一段，避免取模扩容时全量数据迁移——缓存集群/分布式哈希表的经典设计；引入虚拟节点改善负载不均。
- 二次索引、跨分片事务是分区系统的主要复杂源（用 Scatter-Gather、异步索引、Saga 等模式应对）。

## 17. 负载均衡
- **层次**：L4（按连接四元组，IP/端口级转发，便宜）vs L7（按 HTTP 内容路由，可按 URL/头/cookie 决策）。
- **策略**：轮询、加权轮询、最少连接、一致性哈希（会话保持）、就近/延迟路由。
- 健康检查：主动探活 + 被动摘除；防止"雪崩"——节点刚恢复时被瞬时流量打垮（慢启动放量）。

## 18. 故障、级联失效与雪崩
- **单点故障 SPOF**：任何没有冗余的组件（包括负载均衡器、注册中心、数据库主）都是；冗余 + 自动故障转移。
- **级联失效**：一台慢/挂导致上游超时堆积线程 → 上游也被拖垮 → 层层蔓延。
  - 对策：超时（必须有！无超时的 RPC 是资源泄露）、重试预算与退避抖动、**熔断器 circuit breaker**（错误率超阈值直接快速失败，给下游喘息）、限流（令牌桶/漏桶）、降级（返回缓存/简化结果）、舱壁隔离（线程池/连接池按依赖隔离）。
- **惊群 / 缓存击穿**：热点 key 过期瞬间大量请求同时打到后端 → 提前刷新 / 单飞去重（singleflight）/ 锁。
- **雪崩**：大量缓存同时失效或整体缓存层故障 → 随机 TTL、多级缓存、限流保底。

## 19. 可用性量化
- **MTTF**（平均无故障时间）/ **MTTR**（平均修复时间）；可用性 A = MTTF/(MTTF+MTTR)。
- 几个九：99.9%（年停 8.76 小时）、99.99%（52 分钟）、99.999%（5.26 分钟）。
- 串联系统可用性相乘（每跳 99.9%，10 个依赖串联就掉到 99%）——依赖越多越要靠超时/降级/冗余兜底。
- **冗余可靠度直觉**：两台年故障 1% 的机器双活（任一活着即可）≈ 99.99%——冗余把独立故障概率从 p 压到 p²。

# 第七部分：Internet 安全

## 20. 威胁模型与密码学构件
- **四类攻击**：窃听（机密性）、篡改（完整性）、重放（录制旧消息重演）、冒充/中间人（身份）。
- **三类构件**：
  - 对称加密（共享密钥，快，问题在密钥分发）：AES。
  - 公钥密码（加密用公钥、解密用私钥；签名反过来——私钥签、公钥验）：RSA/ECC。
  - 密码学哈希（定长指纹、单向、抗碰撞）：SHA 族；HMAC 给消息加带密钥的认证标签。
- 组合关系：加密保机密性，MAC/签名保完整性与来源认证，二者都要（只加密不认证会被 padding oracle 等攻击）。
- **重放防御**：nonce（一次性随机数）+ 时间戳 + 服务端去重。

## 21. PKI 与 TLS
- **公钥的信任问题**：拿到"服务器公钥"本身可能被调包（中间人）→ 需要可信第三方背书。
- **PKI**：CA（证书机构）用自己的私钥给"域名↔公钥"的绑定签名形成证书；浏览器/OS 预装根 CA 公钥；信任链：根 CA → 中间 CA → 站点证书。
- **TLS 握手要点**：协商版本与密码套件 → 验证服务器证书（PKI）→ 用非对称密码安全交换会话密钥 → 之后全部用对称加密通信（非对称只在握手用，因为慢）；现代 TLS 1.3 把往返压到 1-RTT。
- **认证 vs 授权**：认证证明"你是谁"（密码/MFA/令牌/Kerberos 票据——后者演示了如何用可信第三方避免把密码发给每个服务）；授权决定"你能做什么"（ACL/能力/角色）。
- **电商/支付信任模型**：商家不应看到卡号（支付网关/令牌化）、交易抗抵赖靠签名、争议靠审计日志；安全是端到端系统问题（TLS 保护传输，保护不了被拖库的明文密码——还要加盐哈希存储）。

## 典型项目类型（以现代等价项目为准）

1. **RPC 框架 / 键值客户端**：在不可靠信道上实现带超时、重试、幂等去重的 RPC；难点：区分"执行了但回复丢了"、去重表持久化、退避策略。
2. **分布式键值存储**（MIT 6.824 风格的现代对应物）：基于 Raft 的多副本 KV——分片、复制、故障转移；难点：处理重复客户端请求、配置变更期间的一致性。
3. **分布式文件系统简化版**：客户端缓存 + 无状态/有状态服务器对比实现，观测不同一致性策略下的行为；难点：callback 失效与客户端断连恢复。
4. **高可用 Web 服务**：无状态应用层 + 负载均衡 + 主从数据库 + 缓存；注入节点/网络故障，验证故障转移、超时熔断、缓存击穿防护。
5. **安全实验**：抓包观察明文协议、实现/分析简单签名协议、TLS 证书链验证、重放攻击演示。

## 方法论卡片

### 卡片 A：设计任何分布式交互先问的六问
1. **故障假设**：节点只会 crash 还是可能撒谎（crash vs Byzantine）？网络可能分区吗？
2. **调用语义**：这个操作需要哪种？能设计成幂等吗（用业务唯一 ID）？
3. **超时之后**：重试多少次、退避多久、重试期间副作用是什么？
4. **状态归谁**：这个状态放客户端、协调者还是数据节点？崩溃后怎么重建？
5. **一致性强度**：读到多旧的数据可以接受？谁必须看到自己的写？
6. **扩展瓶颈**：加一台机器，哪个共享资源/同步点不会跟着线性增长？

### 卡片 B：幂等性改造清单
- 写操作天然幂等：SET（赋值）、DELETE（再删一次结果相同）、PUT 整个资源。
- 非幂等操作改造：客户端生成唯一请求 ID（订单号/幂等键）→ 服务端持久化"已处理 ID → 结果"映射 → 重复请求直接返回原结果（结果要留存到业务时效之后）。
- 数据库层：唯一索引兜底重复插入；乐观锁（版本号 CAS）兜底重复更新。

### 卡片 C：一致性方案选择树
```
要求"写入后所有读者立即见新值"？
├─ 是 → 线性一致：主从同步复制或共识系统，接受写延迟与分区时不可用
└─ 否，但有因果关系不能乱（评论回复、协作）
     ├─ 是 → 因果一致（向量时钟/版本追踪）
     └─ 否，只需最终收敛
          ├─ 同一用户需看到自己的更新 → 最终一致 + 读己之写（写后读主/会话钉主）
          └─ 连这也不需要（DNS、对象标签、CDN）→ TTL/租约即可
```

### 卡片 D：服务器韧性模式对照
```
故障形态              防御机制
下游调用挂起不返回     超时（第一原则，无超时一切免谈）
超时引发重试风暴       重试预算 + 指数退避 + 随机抖动
下游持续出错          熔断器（快速失败，半开探测恢复）
流量超过容量          限流（令牌桶/漏桶）+ 降级
一个依赖拖垮全部线程   舱壁隔离（独立线程池/连接池）
热点 key 失效         singleflight 单飞去重 + 提前续期
缓存层整体挂          多级缓存 + 限流保底 + 随机 TTL 防同时过期
主节点故障            心跳/租约检测 + 多数派选主防脑裂
```

### 卡片 E：NFS 与 AFS 的权衡一页纸
| 维度 | NFS | AFS |
|---|---|---|
| 服务器状态 | 无状态 | 有状态（callback 注册） |
| 缓存粒度 | 块 | 整个文件 |
| 失效通知 | 客户端带属性轮询验证 | 服务器主动 callback invalidate |
| 一致性语义 | 接近 UNIX（短周期校验） | 会话语义（关闭才传播） |
| 崩溃恢复 | 极简单（重试即可） | 需处理 callback 丢失/重建 |
| 适用环境 | 通用、跨广域、异构 | 局域网、读多写少、整文件访问 |
| 现代对应 | NAS、无状态云服务、S3 思想源头之一 | 协作缓存、CDN 失效推送、离线优先文档 |

### 卡片 F：CAP/可用性事故复盘框架
1. 故障期间到底发生了"分区"还是"节点挂"？系统实际选择了 C 还是 A？
2. 故障转移期间是否有"双主"窗口（脑裂）？凭什么机制保证只有一个主（租约/多数派/fencing token）？
3. 已返回客户端成功的数据丢了吗（同步 vs 异步复制）？
4. 故障恢复后冲突数据怎么合并的？
5. 超时设置、重试预算、熔断阈值在事故中起了正作用还是反作用？

## 学习路径建议

1. **先建立"部分故障"世界观**：反复练习"请求发出后可能发生的所有结局"（成功、丢请求、执行成功丢回复、执行两次、服务器死、网络死两边活着）——RPC 三语义是所有后续内容的语言。
2. **以分布式文件系统为主线案例**：NFS/AFS 把缓存、状态、一致性、崩溃恢复、幂等全串起来了；读懂这两者的分歧，现代对象存储/CDN/协作软件都是同一谱系。
3. **一致性模型按谱系学**：不要背定义，给每个模型找一个真实产品对应（线性一致=etcd/ZooKeeper 写、最终一致=DNS/S3、会话语义=AFS/离线文档）。
4. **服务器设计部分对照生产经验**：你 `interview/技能详解/` 里的消息队列、Redis、微服务、金融级一致性专题就是本节的工业实现；学完概念回头看那些组件的选型理由会完全透明。
5. **进阶路径**：本课只到 2PC/选主思想；要深入共识与容错，下一步是 MIT 6.824（Raft、复制日志、分片）以及 Lamport 时钟/向量时钟等时序工具。
