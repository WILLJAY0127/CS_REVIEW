# CS162 知识库总览（Operating Systems and Systems Programming）

## 8+1 总览卡

1. **课程定位**：CS162 是伯克利的操作系统与系统编程课。本质是"管理硬件、向上层提供干净抽象，并在并发与故障两个客观敌人面前保证正确与高效"。
2. **三大核心主题**：**并发（Concurrency）**、**资源管理（Resource Management）**、**抽象与边界（Abstraction / Protection）**；后期加入分布式入门（RPC、MapReduce）。
3. **四个基本抽象**：进程（私有地址空间上的执行体）、线程（进程内共享地址空间的执行流）、地址空间（虚存营造的私有内存幻象）、文件（持久化字节容器）。
4. **贯穿全课的"三个分离"**：机制与策略分离（mechanism vs policy）、策略与实现分离、用户态与内核态分离（mode bit + 系统调用）。
5. **两大客观敌人**：**非确定性**（线程交错顺序无穷，测试覆盖不完）与 **故障**（崩溃可发生在任意两条指令之间，磁盘可静默损坏）。
6. **核心思维**：正确性不靠"跑了一万次没出错"，而靠不变量（invariant）与临界区原子性；性能不靠直觉，而排队论/工作负载/Amdahl 量化。
7. **三道门槛**：锁与条件变量的正确配合、地址翻译与 TLB/缺页全流程、崩溃一致性（fsck / journaling / RAID）。
8. **本课的"反直觉"结论**：加锁不是越多越好（死锁、串行化）；线程安全不等于"每个方法加锁"（复合操作仍可交错）；`read()`/`write()` 是会被信号打断、可能短读短写的内核调用，不是普通函数；空闲内存是浪费——OS 主动拿它做 page/buffer cache；MapReduce 把"故障是常态"写进编程模型，而非当作异常处理。

**一句话**：CS162 教的是"在一个随时可能交错、随时可能断电的世界里，如何设计出让人放心依赖的抽象层"。

# 第一部分：系统调用、内核结构与进程

## 1. 用户态 / 内核态与系统调用
- **特权级**：硬件提供 mode bit；内核态可执行特权指令（改页表、开关中断、操作设备寄存器），用户态不能。
- **系统调用是受控入口**：用户程序执行特殊陷入指令（ecall/syscall/int 0x80，依 ISA）→ 硬件切模式、跳到中断向量表中注册的内核入口 → 内核按编号分发 → 返回时切回用户态。
- **trap / interrupt / fault 的区分**：
  - interrupt：异步外部事件（磁盘完成、时钟、网卡）。
  - trap/syscall：同步、主动的陷入。
  - fault/exception：同步、指令引发（缺页、除零、非法访问），可能可恢复（缺页）也可能不可（段错误）。
- **内核结构**：宏内核（一切在内核地址空间，快但出错即崩）vs 微内核（只留最小内核，文件系统/驱动都是用户进程，靠 IPC，稳但慢）；现代主流多为宏内核 + 模块化。

## 2. 进程与地址空间
- **进程 = 一个地址空间 + 一个或多个线程 + OS 维护的元数据（PCB）**。
- 地址空间布局（低→高）：text（代码）、data/bss（全局）、heap（向上长，brk/mmap 控制）、mmap 区、stack（向下长）、内核空间（用户不可见）。
- **进程的意义**给每个程序"独占一台机器"的幻象：私有内存、独立的文件描述符表、独立的用户身份与资源记账。

## 3. fork / exec / wait 模型（UNIX 灵魂）
- `fork()`：创建子进程，**复制地址空间语义**（现代靠 COW 实现）；返回值区分父子（父收 PID，子收 0）。fork 后父子执行同一代码、从同一位置继续。
- `exec(path, args)`：用新程序**替换**当前进程的代码与数据，PID 不变、打开的 FD 默认保留（除非 close-on-exec）。
- `wait(pid)`：父进程回收僵尸子进程（zombie），获取退出状态；不 wait 的子进程结束后变僵尸，父进程退出后由 init 收养回收。
- 典型组合 `fork + exec + wait` = shell 启动外部命令；`fork` 后两进程各有一份 FD 表副本，因此重定向要在 exec 前 `close + open/dup2`。
- **孤儿**：父先死，子被 init 收养；**僵尸**：子已死但父未 wait，占用 PID 表项。

## 4. IPC 与信号
- **管道 pipe**：内核中的字节缓冲区，一端写一端读，写满阻塞 / 读空阻塞；shell 的 `|` 就是管道 + FD 重定向。
- **信号 signal**：异步软件中断（SIGINT、SIGKILL、SIGSEGV、SIGCHLD…）；可注册 handler，但 handler 可在任意指令点打断主流程——handler 里只能调 async-signal-safe 函数，且必须考虑主流程数据正在修改一半。
- 其他：消息队列、共享内存（最快，绕过内核拷贝，但同步责任在用户）、socket（可跨机）。

# 第二部分：线程与同步（课程心脏）

## 5. 为什么需要线程
- 多进程隔离好但：创建慢、切换贵、共享数据难。
- **线程 = 进程内独立的执行上下文（栈、寄存器、PC、线程局部存储），共享代码、堆、打开文件表**。
- 用途：利用多核并行；让慢速 I/O 与计算重叠；事件循环之外的另一种并发编程结构。
- **用户级线程**：库调度、内核看不见，切换极快、不进内核，但一个线程阻塞于系统调用则整个进程被阻塞。
- **内核级线程**：内核调度，可在多核上并行、系统调用只阻塞一个线程；切换贵。现代实现多为 M:N 或 1:1（Linux NPTL 是 1:1）。

## 6. 竞态、临界区与不变量
- **竞态条件**：结果取决于指令交错顺序。经典案例：两个线程同时执行 `counter++`（load → add → store 三步，可交错丢更新）。
- **临界区**：访问共享资源、必须互斥执行的代码段。
- **临界区三要求**：
  1. **互斥 mutual exclusion**：至多一个线程在临界区内。
  2. **进展 progress**：没人用时想进的人能进，不能死等。
  3. **有限等待 bounded waiting**：想进的人不会饥饿无限久。
- **纪律**：用不变量描述正确性（如"计数器 == 已完成任务数"），临界区的进入退出保证不变量在区外恒成立。

## 7. 锁的实现与层次
- **高层抽象：mutex**（lock/unlock），不可获取时阻塞、由调度器挂起，无竞争时很快。
- **底层实现**：
  - **禁用中断**：只在单处理器、内核短时临界区可用；多核无效，且用户态无权关中断。
  - **自旋锁 spinlock**：基于原子指令忙等；适合持锁极短（等待成本低于挂起/唤醒），多核可用；单 CPU 上持有锁的线程若被抢占，其他核空转。
  - **两阶段锁**：先自旋少量次数，拿不到再睡眠——现实常见折中。
- **原子指令**：test-and-set、compare-and-swap(CAS)、load-linked/store-conditional——锁与无锁结构的硬件根基（61C 原子指令在多处理器语境的应用）。
- **评价**：正确性（三要求）、公平性、性能（无竞争开销、竞争下的伸缩性、缓存行抖动）。

## 8. 条件变量（最难用对的原语）
- 解决"锁只能表达互斥，不能表达等待条件"的问题。
- 三个操作：`wait(cv, lock)`（原子地释放锁并睡眠，被唤醒后重新拿锁才返回）、`signal`（唤醒一个）、`broadcast`（唤醒全部）。
- **铁律 1：wait 必须放在 while 循环里判断条件，不能用 if**。
  - 原因：虚假唤醒（spurious wakeup）合法存在；被唤醒到重新拿锁之间条件可能又被别的线程改没了（Mesa 语义）。
- **铁律 2：signal 时持不持锁？** 持锁 signal 简单但可能让被唤醒者立刻又阻塞在锁上（Hobson 选择问题）；先 unlock 再 signal 通常更高效，但须保证代码组织仍正确。
- **两种语义**：Hoare（信号者让道，条件醒来时必为真，可用 if）vs Mesa（只保证"条件可能成立"，必须 while 重查）——pthread/Java 都是 Mesa 语义。
- 模式：生产者-消费者（缓冲区非空 / 非满两个条件变量）、等待资源、join（线程等线程）。

## 9. 信号量 semaphore
- 一个整数 + 等待队列；`P/wait`（值 >0 则减 1，否则阻塞）、`V/post`（值加 1，唤醒一个等待者）。
- **初值决定用途**：
  - 初值 1 → 互斥锁。
  - 初值 0 → 等待信号 / 会合（join、前驱后继排序，线程版拓扑序）。
  - 初值 N → N 个许可的资源池（限并发）。
- 生产者-消费者用两个信号量 + 一个互斥信号量可完整实现。
- 条件变量与信号量在表达力上多数情形等价，但条件变量更适合"谓词等待"。

## 10. 经典并发问题（用于检验原语掌握）
- **生产者-消费者**：共享有界缓冲区；两个条件变量或两个信号量；注意先放数据再发信号、先申请空槽再生产。
- **读者-写者**：读读共享、写写/读写互斥；读者优先会饿死写者，写者优先或公平队列可解。
- **五个哲学家**：朴素"先拿左叉再拿右叉"可循环等待死锁；解法：限制最多 4 人就坐 / 一人反向拿叉 / 用全局排序（资源分层）破坏循环等待。

## 11. 死锁
- **四个必要条件（同时满足才可能死锁）**：
  1. 互斥（资源不可共享）
  2. 持有并等待（拿着 A 等 B）
  3. 不可抢占（锁不能被强行夺走）
  4. 循环等待（等待图成环）
- **应对策略**：
  - **预防**：破坏任一条件——资源一次性申请（破坏 2）、可抢占（破坏 3）、**全局资源排序按序加锁（破坏 4，工程最常用）**。
  - **避免**：运行时判断分配是否安全——Banker 算法（保守、需预知最大需求，少用于通用系统）。
  - **检测与恢复**：建资源分配图，周期查环，找到后杀进程/回滚（数据库常用）。
  - **忽略**：鸵鸟策略（多数通用 OS 的选择，死锁概率低于代价）。
- **活锁 livelock**：没人阻塞但都在互相让步、整体无进展（如冲突重试双方同步退避）；靠随机退避避免。

## 12. 并发出错的常见模式（Pintos / 面试高频）
- 复合操作误判原子性：`if (!map.containsKey(k)) map.put(k, v)` 两步之间可插入。
- check-then-act、read-modify-write 两类原子性违例。
- 锁保护错对象：用了不同的锁实例（this 锁 vs 类锁）、锁了不可变包装却改内部数组。
- 信号丢失：signal 发生在 wait 之前（没在持锁状态下检查谓词）。
- 嵌套加锁顺序不一致 → 循环等待死锁。
- 回调 / 重入：持锁时调用外部代码（可能反向加锁）。

# 第三部分：调度

## 13. 指标与工作负载假设
- **CPU 利用率 / 吞吐**：单位时间完成作业数。
- **周转时间 turnaround** = 完成 − 到达；**等待时间**；**响应时间 response** = 首次运行 − 到达。
- 公平性（相对占比、是否饿死）与可预测性。
- 关键区分：批处理（只关心周转/吞吐）vs 交互式（响应时间优先）；任务是否可抢占、I/O burst 还是 CPU burst。

## 14. 经典算法
| 算法 | 规则 | 优点 | 缺点 |
|---|---|---|---|
| FCFS | 先到先服务，非抢占 | 简单 | 护航效应，短作业排长作业后 |
| SJF | 最短作业先（非抢占） | 平均等待最优 | 需预知时长；可能饿死长作业 |
| STCF/PSJF | 剩余最短者抢占 | 响应更好 | 仍需预测；上下文切换开销 |
| RR 时间片轮转 | 每作业跑一个 quantum 后到队尾 | 响应公平、无饥饿 | quantum 大小两难：太小切换开销大，太大退化 FCFS |
| MLFQ 多级反馈队列 | 多个优先级队列，短作业/频繁让出者升级，耗满片者降级 | 不需预知时长，兼顾交互与吞吐 | 规则复杂、需防愚弄与饥饿（周期性提权） |
| 优先级调度 | 按静态/动态优先级 | 可表达重要性 | 优先级反转（高优先级等低优先级持有的锁，中优先级长期占 CPU）；优先级继承可缓解 |

- Linux CFS 概念：按虚拟运行时间 vruntime 选最小者，红黑树组织，目标是"完全公平"的比例份额。
- **多处理器**：负载均衡（push/pull migration）、缓存亲和性（迁移破坏热 cache）、全局 vs 每核队列。

# 第四部分：虚拟内存（OS 策略层）

## 15. 缺页异常处理全流程
1. MMU 翻译虚地址 → 查 TLB → 查页表，PTE valid=0 → 触发 page fault 陷入内核。
2. 内核保存故障指令地址与原因，在 VMA/段信息中查该地址是否合法。
   - 不合法（未映射/违反权限）→ SIGSEGV。
   - 合法但页不在内存 → 进入分页流程。
3. 找空闲物理帧；没有则执行**置换**（见算法）。
4. 从磁盘（swap 区或可执行文件/映射文件）读入该页（阻塞当前进程，调度别的进程）。
5. I/O 完成后更新 PTE（PPN、valid、权限、dirty），刷新/使 TLB 失效。
6. 从故障指令返回并**重新执行**该指令——此时翻译成功，进程无感。
- **关键认知**：缺页是正常控制流而非错误；进程的堆/栈可"延迟分配"（首次触碰才建页）；程序可用内存 > 物理内存。

## 16. 置换算法
- **OPT（最优，离线）**：换出未来最久不用的页；不可实现，是比较上界。
- **FIFO**：换入最早的页；简单，但有 **Belady 异常**（帧数增多缺页反而增多）。
- **LRU（最近最少使用）**：换出最久未访问的页；利用时间局部性，效果接近 OPT。
  - 精确 LRU 需每次访问更新时间戳（昂贵）；近似实现：
    - **Clock/第二次机会**：引用位 + 环形扫描，遇 1 清 0 跳过，遇 0 换出。
    - 增强 Clock 同时用 dirty 位优先换干净页（省写盘）。
- **工作集与抖动**：常驻集小于工作集时频繁换页（thrashing）；对策：局部置换、缺页频率反馈、 admission control（内存不够就不让更多进程跑）。
- **按需调页 + 预取**：纯 demand 只在缺页时取页；预取相邻页利用空间局部性。

## 17. 虚拟内存的高级用法
- **COW（写时复制）**：fork 不复制物理页，父子共享只读页；任一方写时触发保护故障，内核复制该页——把 fork 从 O(内存) 降到 O(页表)。
- **mmap**：把文件映射进地址空间，访问文件如同访问内存；页在首次访问时从文件调入，脏页由 OS 负责回写；是共享库、大文件处理、零拷贝的基础。
- **共享内存 IPC**：多进程映射同一物理帧。
- **page/buffer cache 统一**：空闲内存不空闲——缓存磁盘块；分配压力到来前缓存可被回收，因此"free 很少"往往是健康状态。

# 第五部分：文件系统与崩溃一致性

## 18. 文件系统接口与实现
- **抽象层次**：文件（字节流，OS 不解释内容）→ 目录（名字 → inode 映射的特殊文件）→ 文件系统（挂载在路径树上）。
- **inode**：文件元数据（大小、属主、权限、时间戳、数据块指针数组）；数据块寻址：直接块 + 间接块 + 二级/三级间接块（经典 UNIX 结构），小文件快、大文件可扩展。
- **FD 与打开文件表**：`open` 在进程 FD 表建项，指向系统级打开文件表（含 offset），再指向 inode；fork 后父子共享同一打开文件表项（共享 offset），dup 同理；独立两次 open 各有独立 offset。
- **目录操作**：create/link/unlink/mkdir；`unlink` 只删目录项，inode 的 linkcount 归零且无人打开才释放数据——"先打开再 unlink"可造匿名临时文件。
- **权限**：rwx 三组（属主/组/其他）+ UID/GID；一切皆文件的设计让设备也走同一接口。

## 19. 磁盘与 FFS
- 机械磁盘代价 = 寻道（毫秒级，主导）+ 旋转 + 传输；随机访问比顺序慢约百倍——文件系统布局的核心矛盾是**局部性**。
- **FFS（Berkeley Fast File System，课程经典案例）**：
  - 柱面组/块组：把 inode 与数据放同组，减少寻道。
  - 大块（block）+ 碎片（fragment）：大块提吞吐，碎片存小文件尾部省空间。
  - 长文件名目录、预留空间等策略。
- SSD 时代寻道消失，但擦除/写入放大、FTL、TRIM 成为新主题（课程通常点到）。
- **磁盘调度**：FCFS / SSTF（最近磁道）/ SCAN（电梯算法）/ C-SCAN；由设备/控制器负责程度依系统而异。

## 20. 崩溃一致性（CS162 最有思维含量的一节）
- **问题**：一次逻辑操作（如创建文件）要写多个磁盘位置（inode 位图、inode、目录项）；崩溃可发生在任意两次写之间 → 重启后状态不一致。
- **三种状态**：inode 标了已用但数据未初始化；目录项指向未分配 inode；位图与实际不符。

### 方案一：fsck（事后修复）
- 重启后全盘扫描：位图 vs inode 实际占用对账、目录项 vs inode 链接计数对账、修复孤儿/损坏。
- 缺点：整个文件系统不可用直到扫完（TB 级磁盘无法接受）；无法恢复已损坏的用户数据，只能"修到自洽"。

### 方案二：日志 journaling / write-ahead log（事前保证）
- 先把"要做的修改"整体写入只追加的日志并落盘（含事务结束标记 TxE），再写真正的位置（checkpoint），最后可释放日志。
- 崩溃恢复：日志中有完整 TxE → 重放（redo，可能重复，要求幂等）；无完整 TxE → 整个事务丢弃。
- **数据日志（data journaling）**：数据+元数据都进日志，写两次但安全；ext3/ext4 默认 **有序模式 ordered**：先把数据直接写到位并落盘，再只给元数据记日志，兼顾安全与性能。
- 关键点：**先写日志后写 checkpoint 的顺序必须由强制刷新（fsync/barrier）保证**，否则磁盘写缓存重排会使日志形同虚设。

### 方案三：其他流派
- **Soft updates**：仔细排列写顺序，使磁盘上的结构永不自相矛盾（实现极复杂）。
- **Copy-on-Write（WAFL/ZFS）**：从不原地修改，写新版本到新块、原子切换根指针（与原子 rename 同思想）；天然带快照。
- **原子 rename**：`rename` 保证 crash 后要么旧名要么新名，永无中间态——很多"原子配置更新/写临时文件再 rename"技巧的根基。

## 21. RAID（多盘的性能与可靠性）
| 级别 | 组织 | 容量 | 读 | 写 | 容错 |
|---|---|---|---|---|---|
| RAID 0 | 条带 | 100% | 快 | 快 | 无 |
| RAID 1 | 镜像 | 50% | 快（可分工） | 双写 | 坏 1 盘 |
| RAID 4 | 条带 + 专用校验盘 | (n−1)/n | 快 | 小写要读旧数据旧校验算新校验，校验盘瓶颈 | 坏 1 盘 |
| RAID 5 | 校验轮转分布各盘 | (n−1)/n | 快 | 小写有"写惩罚"（4 次 IO），无热点盘 | 坏 1 盘 |
| RAID 6 | 双校验 | (n−2)/n | 快 | 更贵 | 可坏 2 盘（重建窗口内再坏也安全） |

- **小写代价公式（RAID 4/5）**：新校验 = 旧校验 ⊕ 旧数据 ⊕ 新数据 → 4 次磁盘 IO。
- RAID 不是备份：误删、火灾、勒索软件同时毁掉所有盘；备份的核心是**离线 + 历史版本**。

# 第六部分：I/O、安全与分布式入门

## 22. I/O 三种方式
- **轮询 polling**：CPU 反复查状态寄存器；简单但浪费，适合极快设备或软实时。
- **中断驱动**：设备完成时发中断，CPU 期间可做别的；中断频繁时（高速网卡）上下文切换成本压垮 CPU。
- **DMA**：设备控制器直接在内存与设备间搬数据，完成后只发一次中断；大数据传输主流。

## 23. 安全与保护
- 内核是可信计算基（TCB）；系统调用边界必须校验所有用户传入参数（指针是否属于该进程、长度、权限）。
- 最小权限原则；setuid 机制的历史教训；缓冲区溢出攻击（栈上数据覆盖返回地址）与防护（栈金丝雀、ASLR、NX/DEP）。
- 安全 ≠ 可靠：权限模型防不了有合法权限的恶意/失误操作。

## 24. 分布式入门（CS162 后段，也是 CS167 的入口）
- **为什么难**：并发（多机）、部分故障（网络/机器可挂但你不知道）、没有全局时钟、没有共享内存。
- **RPC 语义**（重试与故障的组合）：
  - **at-least-once**：重试保证执行但可能重复 → 服务端操作必须幂等。
  - **at-most-once**：靠请求 ID 去重，保证不重复但可能没执行。
  - **exactly-once**：本质上"effectively once"——靠去重 + 幂等/事务在效果上实现，网络本身无法承诺。
- **失败检测 = 超时 + 心跳**；超时无法区分"对方死了"与"网络慢"，这是所有共识/选主问题的根源。
- **NFS 风格无状态服务**：服务器不记客户端状态，每次请求自带全部上下文，崩溃恢复简单、可平滑迁移（CS167 重点案例）。
- **MapReduce**：编程模型（map → shuffle → reduce）把分布式最难点（故障重试、数据本地性、负载均衡）交给框架；worker 挂了由 master 重算任务（确定性重算即可，因为中间结果可重建）——把容错做成默认而非例外。

## Pintos 四个项目方法论（Berkeley 经典实验）

> Pintos 是教学用极简 OS 内核，四个 project 逐周加功能。具体函数名与测试点以当学期 handout 为准，以下是结构与难点。

### Project 1：线程（Thread）
- **内容**：alarm clock（让线程睡到指定时刻，不能忙等）、优先级调度 + 优先级捐赠（解决优先级反转）、高级调度（MLFQ 风格）。
- **难点**：
  - `timer_sleep` 必须把线程挂到等待队列并在时钟中断里统一唤醒，禁止自旋。
  - 优先级捐赠可能多级（A 等 B 的锁，B 又等 C）→ 递归捐赠；释放锁时恢复原优先级。
  - 所有共享调度队列的访问都要关中断或持锁。

### Project 2：用户程序（Userprog）
- **内容**：参数解析、系统调用（process control / 文件操作）、虚拟内存布局加载、多道程序。
- **难点**：
  - syscall 参数来自用户内存，**必须逐个校验指针有效性**，否则用户进程可读写内核。
  - 父进程 wait 子进程的退出状态要妥善保存（子死后状态留存到父收走）。
  - FD 表管理、进程终止时关闭所有文件、文件锁的粒度（Pintos 要求全局文件锁还是每文件锁依测试而定）。

### Project 3：虚拟内存（VM）
- **内容**：补充/完善页表、lazy load、栈增长、swap、mmap、页帧回收（clock 算法）。
- **难点**：
  - 区分三类缺页：栈自动增长、可执行文件页（从文件读）、swap 页（从 swap 读回）。
  - 脏页换出要写 swap、干净页直接丢弃（文件页可重新读入）。
  - 页表访问本身在中断上下文，锁的嵌套顺序必须全局统一，否则死锁。

### Project 4：文件系统（File System）
- **内容**：extent/二级索引支持大文件、子目录、动态增长、buffer cache + 时钟置换、（进阶）日志与崩溃恢复。
- **难点**：
  - buffer cache 要有同步保护（多线程并发读写块）、脏块回写、淘汰策略。
  - 路径解析逐级查目录、`.`/`..`、目录项的增删原子性。
  - 可选的 journaling 直接对应第 20 节：先写日志再 checkpoint。

## 方法论卡片

### 卡片 A：写同步代码的标准流程
1. 列出所有共享数据（哪些字段被 ≥2 个线程访问？）。
2. 写出必须恒成立的不变量（用一句话 + 一个等式描述）。
3. 划分临界区：哪些操作必须在一把锁内原子完成？
4. 等待条件用条件变量 + **while 重查谓词**；先改状态再 signal。
5. 多把锁时画锁的获取顺序图，全局统一加锁顺序防死锁。
6. 自检：线程在临界区**中间被抢占**时，区外线程能否看到非法状态？若能，临界区划小了。

### 卡片 B：锁 / CV / 信号量选择
```
只需要互斥                     → mutex
需要"等到谓词成立"              → mutex + condition variable（while 循环 wait）
需要许可池 / 严格先后顺序        → semaphore（初值 = 许可数；排序初值 0）
读多写少                       → 读写锁，但警惕写者饥饿
多变量的复合原子更新            → 粗粒度一把锁先做对，再拆锁提性能
```

### 卡片 C：地址翻译与缺页题走查
1. 拆虚地址 = VPN + offset；查 TLB → 命中直接得 PFN。
2. TLB miss 走页表（多级时逐级查，每级都是一次物理访存）。
3. PTE valid=1 → 得 PFN，拼物理地址；valid=0 → 进缺页流程。
4. 缺页：合法否 → 有空闲帧否（无则置换：用引用位/dirty 位决策）→ 从文件/swap 读入 → 更新 PTE 与 TLB → 重启指令。
5. 算效访存时间：TLB 命中率走快路径，未命中叠加页表遍历，缺页再叠加磁盘 I/O（差约 10⁵ 倍，缺页率是主导项）。

### 卡片 D：调度计算题步骤
1. 画甘特时间轴，标出每个作业的到达、运行区间、I/O、完成点（注意是否可抢占）。
2. 周转 = 完成 − 到达；等待 = 周转 − 服务；响应 = 首次运行 − 到达。
3. RR 题逐 quantum 推进队列；MLFQ 题记录每个作业在各队列的配额与升降级。
4. 对比时报告平均值并指出公平性/饥饿，而不只是一个指标。

### 卡片 E：崩溃一致性分析模板
1. 找出该逻辑操作涉及的所有磁盘写（位图？inode？数据块？目录项？）。
2. 枚举每次写之后崩溃的状态，判断哪些会自相矛盾。
3. 无防护：标出哪些状态 fsck 能修、哪些数据已丢。
4. 有 journaling：画 timeline——TxB → 数据/元数据日志 → TxE（落盘）→ checkpoint；任意点崩溃给出恢复动作。
5. 追问：写缓存可能重排吗？哪里需要 barrier/fsync？

### 卡片 F：系统设计中的机制与策略自问
- 这部分是机制（做什么的能力）还是策略（决定怎么做）？
- 能否把策略留在用户层/配置里，内核只提供通用机制？（vmsplice、io_uring、调度类的演进都是这个方向）
- 抽象泄漏了吗？用户是否被迫知道页大小、磁盘块大小、时间片长度才能正确使用？

## 学习路径建议

1. **先建立"双敌人"视角**：并发与故障。之后每个机制都问——它在防哪类交错？在防哪个崩溃窗口？
2. **同步部分必须做题+画图**：线程交错时序图、资源分配图、条件变量的等待/唤醒序列；Pintos P1 是试金石。
3. **虚存部分以"一次访存的完整生命"为锚**：从 C 代码的虚地址 → TLB → 多级页表 → 缺页 → 置换 → 重启指令，能默画全流程图。
4. **文件系统抓住崩溃一致性主线**：fsck → journaling → COW 是一条"修复 → 预防 → 结构革新"的演进史，比背 inode 字段重要。
5. **分布式章节是接口课**：RPC 语义、超时失败模型、MapReduce 容错思想学透，再进 CS167 会非常顺。
6. **C 语言前提**：指针、struct、函数指针不熟练会被 Pintos 拖死，建议先用 61C 的 C 部分打底。
