# 架构推演：电商下单系统从 0 到 1

> **问题驱动的架构设计完整演示**
> 
> 从「最简单能跑的版本」开始，一步步遇到问题、一步步解决问题。
> 每一步都讲清楚：痛点是什么 → 有哪些方案 → 选了什么 → 代价是什么。

## 一、先给约束条件（架构不能脱离约束）

| 约束项 | 初始规模 |
|--------|---------|
| 日订单量 | 1000 单/天（小项目起步） |
| 并发 | 高峰期 10 QPS |
| 团队 | 2 个后端开发 |
| 上线时间 | 2 周 |
| 预算 | 服务器 2 台（一台应用+数据库，一台备用） |

## 二、V1.0 最简单能跑的版本

### 设计方案

```
┌──────────────┐
│   用户下单    │
└──────┬───────┘
       │ HTTP 同步调用
       ▼
┌──────────────────────────┐
│      单体 Java 应用       │
│  OrderService             │
│  ① 创建订单               │
│  ② 扣减库存               │
│  ③ 扣减余额（支付）        │
│  ④ 发送短信通知           │
└──────────────┬───────────┘
               │ 读写
               ▼
        ┌─────────────┐
        │   MySQL     │
        └─────────────┘
```

### 核心代码（伪代码）

```java
@Service
public class OrderService {
    
    @Transactional
    public OrderResult createOrder(OrderRequest req) {
        // ① 创建订单
        Order order = new Order(req);
        orderMapper.insert(order);
        
        // ② 扣减库存
        inventoryMapper.decrease(req.getSkuId(), req.getCount());
        
        // ③ 扣减用户余额（假设钱包支付）
        walletMapper.decrease(req.getUserId(), req.getAmount());
        
        // ④ 发短信通知
        smsService.send(req.getPhone(), "下单成功！");
        
        return new OrderResult(order.getId());
    }
}
```

### 评估：这个版本有什么问题？

| 维度 | 状态 | 潜在问题 |
|------|------|---------|
| 能不能跑？ | ✅ 能跑 | 10 QPS 完全无压力 |
| 开发速度？ | ✅ 2 周搞定 | 单体开发效率高 |
| 有没有坑？ | ⚠️ 先记下来 | 后面流量涨了会出问题 |

**没问题就上线！先跑起来再说。架构不是设计出来的，是演进出来的。**

## 三、V1.1：流量涨了，第一个坑来了

### 痛点场景

> 业务发展了，日订单涨到 1 万单，高峰期 100 QPS。
> 
> **用户投诉**：下单好慢啊，经常转圈圈，偶尔还超时。

### 问题诊断

我们来测一下，一次下单要花多久：

```
下单流程耗时分析：
  ① 创建订单：     10ms
  ② 扣减库存：     10ms
  ③ 扣减余额：     10ms
  ④ 发短息通知：   500ms  ← 问题在这！
─────────────────────────
  总计：          530ms

短信服务是第三方的，网络不稳定，有时甚至要 2s！
用户 = 一直等短信发完，才能拿到下单成功的响应。
```

### 为什么会这样？

因为我们的流程是**同步阻塞**的：

```
用户 → 创建订单 → 扣库存 → 扣钱 → 发短信（等500ms） → 返回成功
                          ↑
                     这里白白等了500ms！
```

**问题本质**：发短信这件事，**不需要用户等**。
用户只关心订单有没有成功，不关心短信是现在发还是 1 秒后发。

### 方案选择

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 同步里开线程 | 短信部分另起一个线程发 | 改代码最少 | 线程管理麻烦，服务器重启会丢 |
| B. 本地异步队列 | 存到内存队列，后台线程发 | 比 A 稍好 | 进程挂了消息全丢 |
| **C. 引入 MQ** | 下单完扔消息到 MQ，消费者发短信 | 持久化、不丢消息 | 增加复杂度 |

### 决策：引入 MQ（消息队列）

```
┌──────────────┐
│   用户下单    │
└──────┬───────┘
       │ HTTP（现在只等 30ms 了！）
       ▼
┌──────────────────────────┐
│      单体 Java 应用       │
│  ① 创建订单 10ms          │
│  ② 扣减库存 10ms          │
│  ③ 扣减余额 10ms          │
│  ④ 发送消息到 MQ 1ms ✨   │ ← 变快了！
└──────────────┬───────────┘
       │写入   │
       ▼       ▼
  ┌────────┐ ┌─────┐
  │ MySQL  │ │ MQ  │ ─────┐
  └────────┘ └─────┘      │ 异步消费
                            ▼
                      ┌───────────┐
                      │ 短信消费者 │ → 发短信
                      └───────────┘
```

**关键改动**：

```java
public OrderResult createOrder(OrderRequest req) {
    // ①②③ 不变
    orderMapper.insert(order);
    inventoryMapper.decrease(req.getSkuId(), req.getCount());
    walletMapper.decrease(req.getUserId(), req.getAmount());
    
    // ④ 改成：发消息到 MQ，不等结果
    mqProducer.send("sms_topic", new SmsMsg(req.getPhone()));
    
    return new OrderResult(order.getId());  // 现在 30ms 就返回了！
}
```

### 效果 + 代价

| 收益 | 代价 |
|------|------|
| 下单耗时：530ms → 30ms，用户体验暴涨 | 增加了 MQ 组件 |
| 短信失败不影响下单主流程 | 要处理：消息会不会丢？会不会重复发？ |
| 以后要加「发邮件」「推APP通知」，直接加消费者就行，主流程不改 | 需要有人懂 MQ 运维（但初期可以用云厂商托管版） |

## 四、V1.2：又涨了，第二个坑：数据库读压力

### 痛点场景

> 日订单 5 万，越来越多人刷商品详情页、查订单列表。
> 
> **DBA 报警**：MySQL CPU 80%，大部分是 SELECT 查询。

### 问题诊断

```
数据库压力分析：
  写操作（下单/扣库存）：500 QPS  ← MySQL 完全扛得住
  读操作（商品详情/订单查询）：5000 QPS  ← 问题在这！

  读:写 = 10:1

  大家反复刷同样的热门商品，同样的 SQL 反复查数据库，
  每次都走磁盘 IO，数据库被读操作拖垮了。
```

### 方案选择

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 数据库读写分离 | 主库写，从库读 | 逻辑改动少 | 增加数据库服务器，主从同步有延迟 |
| B. 加本地缓存（Caffeine） | JVM 内存里缓存热门数据 | 快，不需要额外组件 | 多实例缓存不一致，容量有限 |
| **C. 加 Redis** | 集中式缓存，存热点数据 | 通用方案，容量大，多实例共享 | 增加组件，要处理缓存一致性 |

### 决策：引入 Redis 做热点缓存

```
                    ┌──────────────┐
                    │   用户查商品   │
                    └──────┬───────┘
                           │
                           ▼
            ┌──────────────────────────┐
            │      单体 Java 应用       │
            │                           │
            │  先查 Redis 有没有？      │
            │       │                   │
            │   有? │ 直接返回 ✨ 1ms   │
            │   无? │ 查 MySQL 10ms     │
            │       │ 同时写回 Redis    │
            └───┬───────────────────┬──┘
                │ 读缓存 miss 时读    │ 写
                ▼                    ▼
          ┌─────────┐          ┌──────────┐
          │  Redis  │          │  MySQL   │
          └─────────┘          └──────────┘
```

**代码改动**：

```java
public ProductDetail getProductDetail(Long skuId) {
    // 1. 先查缓存
    String key = "product:" + skuId;
    ProductDetail cached = redisTemplate.get(key);
    if (cached != null) {
        return cached;  // 缓存命中，1ms 返回
    }
    
    // 2. 缓存没命中，查数据库
    ProductDetail db = productMapper.selectById(skuId);
    
    // 3. 写回缓存（加过期时间，防止脏数据）
    if (db != null) {
        redisTemplate.set(key, db, 30, TimeUnit.MINUTES);
    }
    return db;
}
```

### 效果 + 代价

| 收益 | 代价 |
|------|------|
| 热门查询：MySQL 10ms → Redis 1ms | 要处理**缓存一致性**（商品改了价格，缓存怎么办？） |
| 数据库压力大幅下降 | 缓存穿透 / 击穿 / 雪崩（后面专题讲） |
| 再涨 10 倍读流量也不怕 | 要维护 Redis（初期用云托管版就行） |

## 五、V1.3：再涨，第三个坑：库存超卖

### 痛点场景

> 搞秒杀活动，限量 100 件，最后卖出了 150 件，超卖了 50 件！
> 
> **老板震怒**：谁写的扣库存代码？

### 问题复现

原来的扣库存代码：

```java
// ❌ 错误代码（并发场景下超卖）
public void decrease(Long skuId, int count) {
    // 1. 先查库存
    Inventory inv = inventoryMapper.selectBySkuId(skuId);
    int remain = inv.getCount();  // 假设查到剩 1
    
    // 2. 判断够不够
    if (remain < count) {
        throw new BizException("库存不足");
    }
    
    // 3. 更新库存（问题：这里的 remain 是之前查的，可能已经被别人扣了！）
    inventoryMapper.updateCount(skuId, remain - count);
}
```

**时间线（两个线程同时进来）**：

```
时间轴     线程A                      线程B
  T1    查询库存=1
  T2                              查询库存=1
  T3    判断 1>=1，准备扣
  T4                              判断 1>=1，准备扣
  T5    更新库存 = 1-1 = 0
  T6                              更新库存 = 1-1 = 0

结果：两个用户都抢到了，库存从 1 变成 0
      实际卖出 2 件，但库存只有 1 件 → 超卖！
```

### 方案选择

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 数据库行锁（悲观锁） | `SELECT ... FOR UPDATE` | 简单，不超卖 | 吞吐量下降，可能死锁 |
| **B. 乐观锁（版本号）** | 加 version 字段，CAS 更新 | 性能好，无死锁 | 冲突时用户要重试 |
| C. Redis 分布式锁 | 用 Redis 锁同一 sku | 灵活 | 增加 Redis 依赖，要处理锁过期 |
| D. Redis 预扣库存 | 库存放 Redis 里，先扣再落库 | 性能最高 | 复杂，要处理 Redis 和 DB 双写一致性 |

### 决策：先上乐观锁（简单且够用）

**改造 SQL**：

```sql
-- ❌ 原来：不判断版本号，谁都能改
UPDATE inventory SET count = #{newCount} WHERE sku_id = #{skuId}

-- ✅ 改为：加版本号校验（CAS 思想）
UPDATE inventory 
SET count = count - #{count}, version = version + 1
WHERE sku_id = #{skuId} 
  AND count >= #{count}   -- 数据库层面直接判断够不够
  AND version = #{oldVersion}
```

**Java 代码**：

```java
public void decrease(Long skuId, int count) {
    int maxRetry = 3;  // 冲突时最多重试 3 次
    for (int i = 0; i < maxRetry; i++) {
        Inventory inv = inventoryMapper.selectBySkuId(skuId);
        if (inv.getCount() < count) {
            throw new BizException("库存不足");
        }
        
        // 更新时带版本号，返回影响行数
        int rows = inventoryMapper.decreaseWithVersion(
            skuId, count, inv.getVersion()
        );
        
        if (rows == 1) {
            return;  // 更新成功
        }
        // rows == 0：被别人抢先了，重试
    }
    throw new BizException("手慢了，稍后再试");
}
```

### 效果 + 代价

| 收益 | 代价 |
|------|------|
| 再也不会超卖了 | 高冲突时用户要重试（「手慢了」提示） |
| 不引入新组件，纯数据库搞定 | 秒杀场景（1万并发抢1件）扛不住，要上 Redis 方案 |
| 逻辑清晰 | |

## 七、回头看：这就是架构！

### 我们都做了哪些架构决策？

| 决策 | 解决的痛点 | 代价（复杂度增加） |
|------|-----------|------------------|
| V1.0 单体架构 | 小规模快速上线 | 后期扩展能力有限 |
| V1.1 引入 MQ | 短信慢阻塞主流程 | 消息丢失 / 重复消费问题 |
| V1.2 引入 Redis | 数据库被读压垮 | 缓存一致性问题 |
| V1.3 乐观锁 | 超卖问题 | 高冲突秒杀场景性能不够 |

**这不是架构是什么？**

- 每一步决策都**有明确的问题驱动**（不是为了炫技上组件）
- 每一步都**知道代价是什么**（不是加组件就完了）
- 组件选型**匹配业务规模**（初期不搞微服务、不搞集群）

### 对比「空泛架构课」会怎么教？

| 空泛的教 | 实际的架构演进 |
|---------|--------------|
| 「先上微服务、注册中心、网关」 | 单体先用着，够用不拆 |
| 「MQ 集群部署 + 持久化参数」 | 为什么要用 MQ？（解决同步阻塞） |
| 「Redis 哨兵 + 集群」 | 为什么用 Redis？（扛读压力） |
| 「分布式事务 TCC」 | 有没有必要？（先乐观锁够用） |

## 八、思考题：下一步怎么办？

假设业务又涨了 100 倍，现在日订单 500 万，QPS 10 万：

1. 单体会不会因为改一个 bug 就要整个重启？ → 要不要拆微服务？
2. 单库 MySQL 写入 1 万 TPS 快顶不住了？ → 分库分表？
3. 秒杀 Redis 乐观锁也顶不住了？ → Redis Lua + 预扣库存？

> 💡 这些都不是现在要解决的。**架构是演进出来的，不是设计出来的。**
> 
> 提前过度设计 = 花冤枉钱 + 增加复杂度 + 开发变慢。

## 九、核心心法

```
架构 = 痛点 → 方案 → 权衡 → 代价

每一次加组件都要问自己：
  1. 我现在遇到的具体痛点是什么？
  2. 有没有更简单的方案（不加组件）能解决？
  3. 如果加组件，代价是什么？我能不能承受？

记住：
  没有银弹，只有权衡。
  够用就是最好的架构。
```
