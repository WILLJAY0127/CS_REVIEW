# 00. 本质追问：构建工具到底是个啥？

> 核心问题：它就是个管依赖的，为啥和编译有关？边界在哪里？

---

## 一、先回到原点：没有构建工具时，编译是什么样的？

假设你有一个**纯 Java 小项目**，只有两个文件：

```
project/
├── src/
│   ├── A.java    ← 主类，依赖 B
│   └── B.java    ← 工具类
└── lib/
    └── log4j-1.2.17.jar   ← 你想加个日志库
```

### 第 1 步：不用任何依赖，纯手写 javac

```bash
# 进入 src 目录，编译所有 .java 文件，输出到 out/
cd src
javac A.java B.java -d ../out/
```

编译完，`out/` 目录下会出现：
```
out/
├── A.class
└── B.class
```

**注意：javac 做了什么？**
- 读 .java 文件，按语法翻译成字节码
- 检查 A.java 里引用的 B 是不是也在输入里
- 输出 .class 文件

### 第 2 步：加一个外部依赖 log4j

A.java 里写了 `import org.apache.log4j.Logger`，编译命令变成：

```bash
# 告诉 javac：外部的类去哪里找（-cp = classpath）
javac -cp "../lib/log4j-1.2.17.jar" A.java B.java -d ../out/
```

**现在编译需要两个输入：**
1. 你自己写的源码 `.java`
2. 你依赖的库 `.jar`（classpath 指定）

### 第 3 步：再加第二个依赖，版本还冲突

现在你又想加一个工具库 `commons-io`，它内部**也依赖了 log4j**，但版本是 `log4j-1.2.14`。

手动编译变成：

```bash
# 你得先搞清楚：commons-io 需要 log4j 1.2.14，你自己想用 1.2.17
# 到底放哪个版本的 jar？手动做选择...
# 假设你选了 1.2.17，然后手动下载所有依赖、手动排序 classpath

javac -cp "../lib/log4j-1.2.17.jar;../lib/commons-io-2.11.0.jar" A.java B.java -d ../out/
```

### 第 4 步：再加测试、加资源、打包成 jar

```bash
# 编译测试代码（还要加 junit.jar）
javac -cp "../lib/log4j-1.2.17.jar;../lib/junit-4.13.2.jar;../out" test/TestA.java -d ../out-test/

# 手动复制资源文件
copy src\config.properties out\

# 手动打 jar 包（还要写 MANIFEST.MF）
jar cfe myapp.jar A.class -C out/ .

# 然后部署？手动 copy 到 Tomcat/webapps/
```

**到这里你会发现一个铁三角的麻烦：**

```
编译 = 源码 + 依赖 + 输出目录
  ↑          ↑         ↑
  |          |         └─ 每次可能变
  |          └─ 版本会冲突、会传递引入、要手动下载
  └─ 每次都要敲同样的命令、流程固定
```

## 二、构建工具的本质：替你搞定这个铁三角

### 构建工具 = 三件事的自动化

```
┌─────────────────────────────────────────────┐
│              构建工具的边界                    │
│                                             │
│  1. 依赖管理 = 自动下载、自动解冲突、自动放对位置 │
│  2. 构建流程 = 自动编译、自动测试、自动打包      │
│  3. 约定规范 = 规定你代码放哪、资源放哪          │
│                                             │
├─────────────────────────────────────────────┤
│  它不管的事情：                               │
│  - 你的业务代码怎么写                         │
│  - JVM 怎么运行 .class                       │
│  - 你用哪个 IDE                              │
│  - 你的 Git 分支策略                         │
└─────────────────────────────────────────────┘
```

**一句话：构建工具是"代码变成可运行产品"这条流水线的大管家。**

### 那为什么和编译有关？

因为**编译是这条流水线的第一个、也是最核心的环节**：

```
源代码 .java
    │
    ▼  编译（javac）
字节码 .class
    │
    ▼  打包（jar/war）
归档文件
    │
    ▼  部署
可运行产品
```

编译的前提是**依赖正确**——你 import 了一个类，javac 必须能找到它。所以：
- 依赖管理 → 是为了让编译能跑通
- 编译 → 是为了让测试能跑
- 测试 → 是为了让打包有意义
- 打包 → 是为了让部署有东西可发

**构建工具不是只管依赖、也不是只管编译，它管的是"从源码到产品"整条链。**

## 三、从 Ant → Maven → Gradle：三代演进动机

### 第一代：Ant（2000 年）

Ant 本质是个**shell 脚本的替代品**，用 XML 写：

```xml
<project name="myapp">
  <!-- 手动写每一个步骤 -->
  <target name="compile">
    <javac srcdir="src" destdir="out" classpath="lib/log4j.jar;lib/junit.jar"/>
  </target>
  <target name="test" depends="compile">
    <junit classpath="out;lib/junit.jar"/>
  </target>
  <target name="package" depends="test">
    <jar destfile="myapp.jar" basedir="out"/>
  </target>
</project>
```

**Ant 的问题：你什么都要自己写**——目录结构、classpath、依赖下载方式、每个 target 的依赖关系。团队间没有共识，A 项目这样组织，B 项目那样组织。

### 第二代：Maven（2004 年）

Maven 看到了：**90% 的 Java 项目目录结构都长一样**，编译→测试→打包的流程也都一样。

所以 Maven 的核心贡献：

| 改进 | 具体做法 | 解决的问题 |
|------|----------|-----------|
| **约定目录** | `src/main/java`, `src/test/java`, `target/` 写死 | 不用自己写 javac 的 srcdir/destdir |
| **生命周期** | compile → test → package → install 写死 | 不用自己写 target 依赖关系 |
| **自动依赖下载** | 配个 GAV 坐标就自动下载、自动放 classpath | 不用手动找 jar、不用手动写 classpath |
| **传递依赖** | A 依赖 B，B 依赖 C → C 自动进来 | 不用手动算依赖树 |

### 第三代：Gradle（2013 年）

Gradle 看到了：Maven 虽然好，但**太死板**。

| Maven 的痛点 | Gradle 怎么解决 |
|-------------|----------------|
| 想改个编译参数？要写复杂插件 | DSL 直接配置，改起来灵活 |
| 每次全量编译，改一个文件重新编所有 | **增量构建**：只编改过的和依赖它的 |
| XML 写起来啰嗦 | Groovy/Kotlin DSL 写起来像写代码 |
| 固定流水线，没法并行 | **DAG 任务依赖**，能并行执行 |

## 四、构建工具的边界再画清楚

```
┌────────────────────────────────────────┐
│           JDK / JRE（运行时）            │
│  javac 编译 → java 运行 → jvm 管理内存   │
└─────────────── ▲ ─────────────────────┘
                │ 构建工具产生 .class 文件给 JDK
┌───────────────┴────────────────────┐
│         构建工具（Maven / Gradle）    │
│  下载依赖 → 编译 → 测试 → 打包 → 发布  │
└─────────────── ▲ ─────────────────────┘
                │ 输入是你的 .java 和配置
┌───────────────┴────────────────────┐
│          你写的源代码                  │
└────────────────────────────────────┘

构建工具 = JDK 之上的"工程化增强层"
它本身不编译字节码，它是去调用 javac / java，
并帮你搞定 javac 需要的所有条件（依赖在 classpath 上、输出目录存在等）
```

### 所以你平时的命令到底干了啥？

```bash
# Maven
mvn compile
# → Maven 先读 pom.xml 里的 <dependencies>
# → 下载所有依赖到 ~/.m2/repository
# → 组装 classpath（依赖 jar + target/classes）
# → 调用 javac，把 src/main/java 编译到 target/classes
# → 完事

mvn test
# → 先执行 compile（default 生命周期前面的阶段）
# → 再编译 src/test/java 到 target/test-classes
# → 加上 test scope 的依赖（junit 等）
# → 调用 junit 跑测试

mvn package
# → 先执行 compile 和 test
# → 把 target/classes + 依赖 jar（可选）+ 资源文件 打成 .jar/.war
```

---

## 五、一句话总结

> **构建工具 = 把"手动敲 javac + 手动下载 jar + 手动打 jar"这堆重复劳动，用声明式配置（pom.xml / build.gradle）变成一键执行的东西。**
>
> 它的边界：只管**"从源码到可运行文件"**这条链上的事，不管 JVM 内部怎么跑、不管你业务怎么写。
