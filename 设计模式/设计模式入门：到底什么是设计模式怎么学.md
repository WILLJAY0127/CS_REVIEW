# 设计模式入门：到底什么是设计模式？怎么学？

> **写给 Java 后端、喜欢代码随想录「问题先行」风格的程序员**
> 
> 先解决最大困惑：为什么学了模式反而代码更难用？应该按什么顺序学？

---

## 一、灵魂一问：设计模式到底是什么？

### 一句话定义

> 设计模式 = 工程代码里的「算法题最优解模板库」。

**用算法类比（你最熟悉的）**：

| 领域 | 遇到的痛点 | 成熟解决方案 |
|------|-----------|-------------|
| 算法（LeetCode） | 在有序数组里找数，两层循环超时 | 二分查找模板（O(log n)） |
| 工程代码 | 一大坨 if-else 判断不同支付方式，加新支付要改原代码 | 策略模式（开闭原则，不加 if） |

**核心共性**：
- 都是别人踩了无数坑总结出来的 **「最佳实践模板」**
- 都有 **适用前提**（二分：有序；策略：算法/规则频繁变化）
- 都有 **代价**（二分：边界容易错；策略：类变多）

> 🔑 **关键纠正**：设计模式不是「高级炫技」，是「踩坑总结」。
> 
> 你不会「为了用二分而用二分」，同样也不应该「为了用策略而用策略」。

## 二、为什么很多人学完反而写烂代码？

### 核心病根：学的顺序反了！

| ❌ 烂学习顺序（大多数人） | ✅ 正确学习顺序 |
|--------------------------|----------------|
| 1. 先背策略模式的 UML 图、角色名字 | 1. 先写代码：一坨 if-else 加支付方式 |
| 2. 背代码模板 | 2. 感受痛点：加一个微信支付要改 5 处 |
| 3. 找地方强行套模式 | 3. 想怎么重构能少改？ |
| 4. 代码越来越复杂（过度设计） | 4. 哦！这个重构方案就叫「策略模式」 |

### 用你熟悉的类比

```
❌ 学算法如果也乱序：
  先背「左闭右开」模板
  然后见到数组就写 while left <= right
  → 结果明明遍历就行的 O(n) 题被写得稀碎

✅ 正常顺序：
  先暴力 → 发现超时
  想怎么优化 → 发现每次能砍一半搜索空间
  哦！这就叫二分查找
  然后再学习左闭右闭/左闭右开的边界写法
```

**设计模式也是一样：先有痛点，再有模式！**

## 五、强制学习方法论（每个模式都要走一遍）

> **就像你学算法：先暴力 → 再优化 → 再背模板**

### 每个模式的 5 步学习法

```
第 1 步：场景
  → 给一个真实业务场景（比如：3 种支付方式，马上要加第 4 种）

第 2 步：不用模式写一版
  → 一坨 if-else，马上感受「加第 4 种要改原代码」的痛苦

第 3 步：引入模式重构
  → 把 if-else 拆成策略类
  → 【标记代码】：哪些是稳定代码（不会变的），哪些是可变代码（新加支付）

第 4 步：回答三连问
  Q1：这个模式隔离了哪块变化？
       （策略：隔离「具体算法/规则实现」）
  Q2：用什么手段隔离的？
       （策略：抽象 PaymentStrategy 接口，稳定依赖抽象）
  Q3：代价是什么？什么时候别用？
       （类变多；如果只有 2 种支付且以后不加，别用）

第 5 步：写 5 行总结笔记
  → 不用画 UML，不用记角色名，记上面 3 个答案即可
```

## 六、第一个模式入门：策略模式（完整示范）

> 就用你最熟悉的「支付场景」演示 5 步法。

### 第 1 步：场景

```
需求：
  支持 3 种支付：支付宝、微信、银行卡
  下周要接入：苹果支付、PayPal
```

### 第 2 步：不用模式写一版（感受痛点）

```java
// ❌ 反模式：一坨 if-else
public class PayService {
    
    public void pay(String type, BigDecimal amount) {
        if ("alipay".equals(type)) {
            // 50 行支付宝逻辑
            AlipayClient client = new AlipayClient(config);
            client.pay(amount);
            log.info("支付宝支付：{}", amount);
        } 
        else if ("wechat".equals(type)) {
            // 50 行微信逻辑
            WechatPayClient client = new WechatPayClient(config);
            client.doPay(amount);
            log.info("微信支付：{}", amount);
        }
        else if ("bank".equals(type)) {
            // 50 行银行卡逻辑
            BankPayClient client = new BankPayClient(config);
            client.transfer(amount);
            log.info("银行卡支付：{}", amount);
        }
        // 加第 4 种：又要在这里加 if...
        // 加第 5 种：继续 if...
        // 修改一处，所有支付代码都在一个文件里，容易改错！
    }
}
```

**痛点清单**：

| 问题 | 说明 |
|------|------|
| 违反开闭原则 | 新增支付方式 → 必须修改原有 PayService（有改错风险） |
| 代码膨胀 | 一个方法几百行，不同支付全揉在一起 |
| 测试痛苦 | 改微信支付，要回归所有支付方式 |
| 团队冲突 | 3 个人同时加 3 种支付，全改同一个文件 → Git 冲突 |

### 第 3 步：引入策略模式重构

```
┌─────────────────────────────────────────────────────┐
│  【稳定层】永远不改动                                  │
│                                                      │
│  // 抽象边界：所有支付都实现这个接口                    │
│  interface PaymentStrategy {                          │
│      void pay(BigDecimal amount);                     │
│  }                                                    │
└──────────────┬──────────────────────────────────────┘
               │ 依赖
               ▼
┌─────────────────────────────────────────────────────┐
│  【稳定层】PayService 只依赖抽象接口，不依赖具体实现    │
│                                                      │
│  @Service                                             │
│  public class PayService {                            │
│      private Map<String, PaymentStrategy> strategies; │
│                                                      │
│      public void pay(String type, BigDecimal amt) {   │
│          strategies.get(type).pay(amt);  // 一行搞定！│
│      }                                               │
│  }                                                    │
└─────────────────────────────────────────────────────┘

        ┌──────────────────────────┐
        │ 【可变层】加新支付，只加类！│
        │                          │
        │  AlipayStrategy implements PaymentStrategy  │
        │  WechatStrategy implements PaymentStrategy  │
        │  BankStrategy   implements PaymentStrategy  │
        │  ApplePayStrategy implements...（新增不碰原有代码）│
        └──────────────────────────┘
```

**代码**：

```java
// ✅ 稳定抽象（接口）
public interface PaymentStrategy {
    void pay(BigDecimal amount);
}

// ✅ 可变实现：支付宝（新增只加类）
@Component("alipay")
public class AlipayStrategy implements PaymentStrategy {
    @Override
    public void pay(BigDecimal amount) {
        AlipayClient client = new AlipayClient(config);
        client.pay(amount);
        log.info("支付宝支付：{}", amount);
    }
}

// ✅ 可变实现：微信
@Component("wechat")
public class WechatStrategy implements PaymentStrategy {
    @Override
    public void pay(BigDecimal amount) {
        WechatPayClient client = new WechatPayClient(config);
        client.doPay(amount);
        log.info("微信支付：{}", amount);
    }
}

// ✅ 稳定主体：PayService（加新支付不需要改这里！）
@Service
public class PayService {
    // Spring 自动把所有 PaymentStrategy 实现注入成 Map
    @Autowired
    private Map<String, PaymentStrategy> strategies;

    public void pay(String type, BigDecimal amount) {
        PaymentStrategy strategy = strategies.get(type);
        if (strategy == null) {
            throw new BizException("不支持的支付方式");
        }
        strategy.pay(amount);  // 一行！
    }
}
```

### 第 4 步：回答三连问

| 问题 | 策略模式答案 |
|------|-------------|
| **隔离了什么变化？** | 「具体支付方式的实现逻辑」 |
| **用什么隔离的？** | `PaymentStrategy` 接口作为抽象边界 |
| **代价？什么时候别用？** | 类变多；如果只有 2 种支付、确定不会加第三钟，别用，直接 if-else 更简单 |

### 第 5 步：5 行总结

```
策略模式 = 把 if-else 里的每一分支，拆成独立策略类
抽象接口 = 稳定边界
策略实现 = 被隔离的可变逻辑
适用：算法/规则可能频繁增加时
别用：规则很少、确定不变（过度设计）
```

## 七、语言选择建议（匹配你的技术栈）

### ✅ 初学用 Java

| 为什么适合初学 | 说明 |
|---------------|------|
| 显式接口 | `interface` 和 `implements` 让「稳定边界」物理可见 |
| 强类型 | 编译器帮你守住抽象契约，不会乱传 |
| 和你的工作重合 | 后端写业务天天用，学完直接落地 |

> 💡 **学习阶段原则**：越啰嗦、结构越显性的语言，越适合看清楚边界。
> 
> 结构学明白后，再用 Python/Go 重写同一批模式，你会发现「很多模式在简洁语言里根本不需要那么多重的写法」——这是第二层认知升级。

### ❌ 初学别用 Python

- 鸭子类型可以跳过接口，代码短，但「边界被藏起来了」
- 新手只看到「可以跑」，看不到「抽象作为稳定屏障」的价值
- 学完 Java 版回头看 Python 版，5 分钟就能看懂

## 八、完整学习路线（按时间规划）

### 📅 阶段 1：地基（1 周）

**目标**：搞懂设计原则，知道「模式为什么会长这样」

| 天 | 内容 | 验收 |
|----|------|------|
| D1 | 学 SOLID 原则，重点：开闭原则、里氏替换、依赖倒置 | 能用自己的话讲出「什么是开闭原则」 |
| D2 | 看小林 coding「设计模式概述」章节 | 能回答「原则和模式是什么关系」 |
| D3 | 想 3 个项目里被改吐的场景（到处 if-else、继承爆炸） | 写在笔记里，后面对应找模式 |

### 📅 阶段 2：逐个研习（核心，2~3 周）

**目标**：第一梯队 13 个模式，每个都走 5 步法

- 按「创建型 → 结构型 → 行为型」顺序
- 每周学 4~6 个，不要一天塞太多
- **每学一个就回到项目里找：哪里能用上？**（不需要马上改，先标记位置）

### 📅 阶段 3：横向对比（1 周）

很多模式长得像，但作用维度不同，容易混淆，做一个对比表：

| 容易混淆的组 | 核心区别 |
|-------------|---------|
| 装饰器 vs 代理 | 装饰：叠加功能；代理：控制访问权限 |
| 策略 vs 模板方法 | 策略：用组合替换整块算法；模板：用继承固定骨架，开放步骤 |
| 适配器 vs 桥接 | 适配：解决已有接口不兼容；桥接：事前设计多维度解耦 |
| 工厂方法 vs 策略 | 工厂：解决「怎么造对象」；策略：解决「怎么执行算法」 |

### 📅 阶段 4：去套路化（长期，工作中自然形成）

放下名词，拿到需求直接问：

1. **未来这块哪里会变？**（预判变化）
2. **我该划一条什么抽象边界？**（接口/抽象类）
3. **有没有现成模式匹配？**（不要硬找，有就用上）
4. **代价我能承受吗？**（类数量、调试复杂度）

## 九、避坑清单（90% 的人会踩）

| 坑 | 症状 | 正确姿势 |
|----|------|---------|
| **为了模式而模式** | 简单逻辑写了 5 个类，别人看不懂 | 确定未来会变化才上模式；不变就写直白代码 |
| **模式套娃** | 一个功能 3 个模式叠加，没人能看懂 | 一个场景通常一个模式就够；复杂场景最多两层 |
| **死背 UML、角色名** | 面试背得溜，实际不会用 | 记「解决什么问题、隔离什么变化、代价」三要素 |
| **忽略代价** | 以为用了模式就是优秀代码 | 每个模式都有代价，每次都想：「不值得？直接 if-else」 |
| **一开始就微操** | 新项目前 3 天全在画模式类图，写了 0 业务 | **先写直白代码跑起来，第一次出现变化时再重构** |

## 十、最终心法

> **算法 = 用最少的时间空间解决计算问题**
> 
> **设计模式 = 用最少的后续修改成本解决工程问题**
> 
> 二者都是「先有痛点，再出方案」，顺序不能反。

```
设计模式不是银弹，
    只是前人踩坑留下的地图。

         /  \~~~/  \
```
