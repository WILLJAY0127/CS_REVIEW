# 一、角色与转型

## Q1. 你技术这么强,为什么从开发转 TPM?

**标准答法**:我不是放弃技术,是**扩大技术价值的半径**。做架构/开发,我影响一个系统;在香港项目里我发现大量项目失败不是技术方案不行,而是协同、边界和节奏出了问题——这类问题纯技术岗没有足够权责去解决。我喜欢的事一直没变:把复杂的东西抽象、组织、组装成可运转的体系;代码系统是一种体系,交付组织也是。

**连环追问**:

- "做 TPM 不写代码,不可惜吗?" → 我从没完全离开技术:规则引擎、AI 集成、资金链路的关键决策我都在场;我是能替团队判断技术风险的 TPM。
- "是不是写不动了/卷不动年轻人了?" → 不是。恰恰是我技术最能打的这几年,才有资格做技术型项目管理;工程师愿不愿意和你说实话,取决于你懂不懂他在做什么。
- "TPM 和架构师你到底想做哪个?" → 在我的理解里不矛盾:架构师设计系统,TPM 让系统被交付出来。我的目标位置是"懂架构的业务域交付负责人"。

**死亡点**:说"写代码太累/不想加班/想转管理轻松点"——立刻挂。

**挂项目**:香港 App(角色)+ 断点平台(体系)+ 核验中台(关键技术决策没放手)。

## Q2. TPM、架构师、Tech Lead、传统 PM 的区别?

**标准答法(一张表讲清)**:

| 角色 | 核心目标 | 视角 |
|---|---|---|
| 传统 PM | 任务按期交付 | 单次项目、时间轴 |
| Tech Lead | 团队技术方案与代码 | 向内、团队 |
| 架构师 | 技术模型/选型/演进 | 系统生命周期 |
| TPM | 跨团队复杂项目交付 | 向外、多团队协同 |

一句话:传统 PM 管"任务",TPM 管"**跨团队的技术依赖与结构性障碍**";架构师"画图纸",TPM"让多团队按图纸把楼盖出来"。

**追问**:"那 TPM 和 PMO 呢?" → PMO 管流程制度与项目组合视图;TPM 对具体项目/项目集的交付结果负责。

## Q3. 做了 TPM 以后还写不写代码?

**标准答法**:不再承担日常业务开发,把时间让给协同和风险;但我给自己定了纪律:**关键方案评审必须在场、每年至少亲手做一个小项目(内部工具或个人产品)**——技术手感是"技术型 TPM"的护城河,丢了就退化成传声筒。

**追问**:"不写代码怎么判断工程师说的工期真假?" → 不只听他说,看任务拆解粒度、历史速率、依赖清单;关键节点验交付物;我有 10 年实操,常见注水点我清楚。

## Q4. 你没有正式 PM title,凭什么能做 TPM?

**标准答法**:Title 是公司给的,完整的项目管理实践是我自己跑出来的。香港项目里没有专职 PM,我事实上承担了从需求澄清、范围控制、跨地域排期、风险台账到两地 UAT 的全部 TPM 职责并按期交付;能力要求可以逐条对 JD,结果可以被追问。

**追问**:"那为什么公司不给你 title?" → 小团队一岗多责很常见,title 没跟上但权责是实的;我不认为一个 title 比一次跨地域按期交付更有说服力。

**死亡点**:支支吾吾、把"参与"说成"主导"——被问汇报关系和团队规模时立刻露馅。

# 二、项目深挖

## Q5. 香港项目你具体管了什么?团队多少人?汇报给谁?

**标准答法(3 分钟骨架)**:

- 规模:【真实团队人数】;我直接汇报【内地研发负责人】,虚线对齐香港业务负责人;
- 权责:内地技术侧统一接口人 + 项目经理(兼技术负责人);
- 管什么:需求澄清与差异清单、范围冻结、核心/渠道排期、里程碑与风险台账、两地 UAT、上线保驾;
- 结果:按期上线 + 区域接入 SOP。

**连环追问**:

- "管过预算吗?" → 诚实:没有独立预算权,但参与人力工时与渠道费用评估;这是我下一步要补的(学 EVM)。
- "项目周期多长?" → 【真实】;并能说出各里程碑实际耗时。
- "有几个里程碑延期了?为什么?" → 必须真实;有延期不扣分,讲清怎么追回来的才加分。

**死亡点**:数字前后不一致(周期/人数/功能数),面试官会用你的简历交叉问。

## Q6. 两地最大的冲突是什么?怎么解决的?(必须真实)

**标准答法(用 Q15.3 模板,带选项升级)**:

- 冲突:【真实:某保全项规则差异 / 渠道能力 / 核心接口缺失】;
- 分歧本质:香港业务方要【体验/本地惯例】,核心团队受限于【改造成本/排期】;
- 我的动作:**不带着问题升级,带着选项升级**——给出三个方案(完整改造/折中方案/分期上线)配工期和影响,让业务方拍板取舍;
- 结果:选了【方案】,按期交付,教训写进 SOP。

**追问**:"业务方坚持选最贵的方案但不给排期呢?" → 把三角约束(范围/时间/资源)摆清楚,结论走书面;我负责让选择的代价被看见,不替业务承担模糊承诺。

**死亡点**:讲不出具体冲突细节,只会说"沟通后解决了"。

## Q7. 需求变更怎么控?业务方强行加需求怎么办?

**标准答法**:

1. 预防:需求冻结点 + 范围基线;所有需求走清单,口头不认;
2. 拦截:变更必须走评审,我输出"影响评估"(工期/资源/关联模块/风险),让提变更的人看见代价再决策;
3. 分流:小变更吸收进迭代,大变更换范围或进下期,绝不在不变计划的情况下偷偷加;
4. 留痕:变更结论书面确认。

**追问**:"对方是你领导/大客户,压你怎么办?" → 对上:同步影响和选择题,不当面顶也不默默扛;对客户:商务边界内灵活、边界外走变更流程。关键是**让做决定的人承担决定的后果,而不是项目组**。

**挂项目**:香港差异清单 + 冻结点(手册 Q15.4)。

## Q8. 核心团队不配合排期,你怎么推?

**标准答法**:

1. 先理解对方约束:他们为什么排不进(KPI/人力/风险);
2. 降低对方成本:契约先行 + mock 联调,把他们需要做的改造收敛到最小;
3. 换协同方式:接口能复用的不新增,非关键路径后置;
4. 推不动再升级:先双方技术层达成事实共识,再拉双方主管对齐,带着数据和选项开会。

**死亡点**:只会"找领导压"——低级且透支关系。

## Q9. 断点平台为什么"先立标准再建平台"?推不动怎么办?

**标准答法**:没有统一口径,数据就是垃圾进垃圾出——节点定义和错误码不统一,看板上的漏斗和归因没人敢信,平台就是摆设。所以标准是因、平台是果。

**推动路径(四步)**:样板流程先跑通并拿出收益(满期领取)→ starter + 注解把接入压到半天 → 架构评审 checklist 制度化 → 数据反哺业务方(他们也要转化数据),从"要我接"变"我要接"。

**追问**:"业务线就不按标准传怎么办?" → 宽容策略(failCode 降级存裸码)保证不阻断,但数据治理周报里标脏;先让数据可用,再逐步收紧;同时错误码注册纳入上线卡点。

## Q10. 讲一个你推动跨团队"改变现有工作方式"的完整例子

**标准答法(STAR,推荐断点平台)**:

- S:各线口径不一、断点靠猜、优化无依据;
- T:我想一次性解决"问题发现机制",而不只是交付一个看板;
- A:复盘历史项目定标准 → 建平台 → 样板 → 低接入成本 → 评审制度化;
- R:4 业务线、10+ 流程、80+ 节点接入,转化 +15%,周级→天级。

**追问**:"这是你一个人做的?" → 如实区分:标准是我牵头拉各方对齐,平台研发有团队参与;我的核心价值是定义规则和持续推动共识,不抢功也不背虚名。

# 三、情景与方法

## Q11. 项目进行到一半发现赶不上 deadline,你怎么办?

**标准答法(顺序不能乱)**:

1. 先确认事实:偏差多大、在关键路径还是支线、剩余工作量重估(找一线工程师核实,不找负责人传话);
2. 恢复进度:并行化、砍非关键范围、补资源、调顺序——先评估每条的真实代价;
3. 做决策:范围/时间/资源三角必须动一个,**带着选项和影响尽早向上同步,绝不压到最后**;
4. 留教训:为什么计划阶段没识别?更新风险台账和估算基线。

**连环追问**:

- "领导说'我不管,必须按时'?" → 我接受结果,但需要范围或资源配合;把选择题做精确(砍哪三项、加几个人、各自影响什么质量),请领导拍;口头硬扛是对项目最不负责。
- "加班能追回来吗?" → 短期可以,长期加班降低质量反而制造返工;我的选项里加班只作为短期手段。

**死亡点**:瞒着不报、最后两天才爆;或直接说"催大家加班"。

## Q12. 两个团队为责任边界扯皮,你怎么处理?

**标准答法**:

1. 先还原事实:争议的具体动作是什么、涉及哪个接口/数据、历史上谁在做;
2. 找共同目标:对业务/项目的影响是什么,把"谁背锅"转成"怎么让业务跑通";
3. 给过渡方案:短期先明确一个 owner 兜底(哪怕不完美),不让业务停摆;长期边界走架构/流程固化;
4. 必要时升级:带着"事实 + 两个方案 + 建议"让上级定,不当传声筒。

**追问**:"双方级别都比你高?" → 靠事实和业务影响说话,不靠级别;先私下各自沟通找共识空间,再开小会定。

## Q13. 你怎么识别和管理风险?风险台账长什么样?

**标准答法**:

- 识别:项目启动时按"技术/依赖/资源/合规/外部(厂商/渠道)"逐项过,关键路径上的依赖是重点;风险靠一线信息,不靠会议感觉;
- 台账字段:风险描述、类别、概率、影响、等级(红黄绿)、责任人、应对措施(规避/减轻/转移/接受)、截止时间、当前状态;
- 节奏:周更 + 红色风险随时报;闭环必须看到结果。

**连环追问**:

- "举一个你提前识别并规避的风险"(香港:核心接口若不能按期交付 → 提前锁定契约 + mock 联调,把等待时间变成并行开发)。
- "风险真的发生了呢?" → 直接切应急预案;预案不是文档,事先约定触发条件和动作。

**死亡点**:台账只有"已跟进"没有责任人和结果。

## Q14. AI 项目不确定性高,你怎么做计划和度量?

**标准答法**:管理 AI 项目不是催进度,是**管理不确定性**。

- 计划:目标路径化而非线性排期——准确率从 62 到 88 拆成三段(检索治理 / Prompt 与拒答 / 闭环迭代),每段有明确指标门槛;
- 度量:500+ 评测集,任何知识库/Prompt/模型变更自动回归,用指标证明"好了",而不是"感觉好了";
- 节奏:双周迭代 + badcase 周分析;高不确定性部分先做 spike 验证再排正式计划;
- 兜底:超时/失败降级转人工,业务连续性不押在模型上。

**追问**:"准确率目标没达成但 deadline 到了?" → 按场景分级:高准确率场景暂不全量、保持灰度或人工兜底;上线与否看业务可接受的错误成本,这是业务决策不是技术硬扛。

## Q15. 多个项目抢同一批资源,你怎么排优先级?

**标准答法**:

1. 统一口径:让所有项目用同一套标准陈述(业务价值/紧急度/风险/不可替代性);
2. 决策框架:价值 × 紧急 × 风险,关键资源向关键路径倾斜;
3. 机制:优先级会集体决策、结论书面,我不私下承诺任何一方;
4. 执行:被砍项目做好相关方预期,不是"不做了"是"什么时候做"。

**追问**:"两个老板意见不一致?" → 提供共同的数据底座和方案对比,推动他们在同一会议上决策;我不站队,我守流程。

## Q16. 项目上线出了事故,你的处理流程?

**标准答法**:

1. **止血优先**:回滚/降级/切流,先恢复服务,不在事故现场争论根因;
2. 定位:按监控黄金四指标 + 日志/链路快速锁定范围;
3. 通报:第一时间同步状态和影响面,定时更新;
4. 修复与恢复:验证后再放量;
5. 复盘:对事不对人,5why 到根因,action 带人和截止时间;管理责任我承担,让团队敢暴露问题。

**连环追问**:

- "回滚不了怎么办?" → 上线前就必须有回滚预案(开关、兼容版本);真回滚不了就降级 + 热修,这也是为什么上线 checklist 强制回滚方案。
- "事故是你协调失误导致的?" → 直接认,复盘讲清怎么改;甩锅一次,信任清零。

**挂项目**:缴费平台连续 3 年零 P0/P1 的保障体系(压测/开关/监控/值班)。

## Q17. 向上汇报,领导只要结论,业务方要细节,怎么平衡?

**标准答法**:分层信息——对上给**结论 + 选择题 + 需要的决策**(风险和影响不隐瞒),不把过程倒给领导;对业务给细节、口径和时间点;同一个事实、不同包装。坏消息尽早说,承诺留 buffer。

**追问**:"项目一切正常,汇报什么?" → 同步里程碑达成、风险趋势、需要提前协调的依赖;汇报不是报平安,是管理预期。

## Q18. 你怎么做复盘?举一次复盘改变后续做法的例子

**标准答法**:复盘固定四问:目标是什么、实际发生了什么、差异为什么、下次怎么做(action 可执行)。

**例子**:香港项目早期依赖口头沟通,出现理解偏差返工 → 复盘后确立"接口契约书面化 + 关键结论邮件确认",并进了区域 SOP;后续联调偏差明显减少。一句话:**写下来比说清楚重要。**

**追问**:"复盘 action 落地不了?" → action 必须有人、有时间、进跟踪板;下次复盘第一件事检查上次 action,否则复盘是空转。

# 四、软性收口

## Q19. TPM 工作最让你有成就感的是什么?

**标准答法**:不是某次准时上线,是**我搭的体系自己转起来了**——SOP 被后续区域复用、看板让问题在客户投诉前被发现、团队按统一语言协作。一次性交付的成就感很短,体系化资产持续产生价值,这是我最想要的。

**死亡点**:答"团队氛围好/不用写代码/把活分出去很轻松"。

## Q20. 你做 TPM 最大的短板是什么?

**标准答法**:我目前的交付经验集中在中型规模、单区域,缺少超大项目集(多部门、几十人协同)的锤炼——这是我来大平台的原因;另外预算管理我只有参与经验,正在系统补 EVM。短板我都有明确的补救路径,而不是停留在自评。

**死亡点**:编一个"太追求完美"的假短板;或爆出性格硬伤(不爱沟通/脾气急还不收敛)。

# 五、附录

## 5.1 高压压力连环链(模拟连续 8 问)

> 面试官从"香港项目"切入一路追到底,提前把整条链走熟:

```
Q1 香港 App 你具体做了什么?
 → 项目经理兼技术负责人:需求/范围/排期/风险/UAT 全负责
Q2 没有专职 PM 经验,凭什么敢接?
 → 我有 10 年技术底子,且项目里没有别的人选;权责是实的、结果可验证
Q3 两地最大的冲突?
 → 【真实冲突】;带三个选项升级,让业务拍板
Q4 项目这么小,有什么技术含量?
 → 我不拼规模,拼复杂度维度:跨地域/新市场/合规/多渠道,外加 SOP 沉淀
```
