# 一、分布式事务四种方案对比（务实取舍，不背定义）
> 核心原则：**能不用分布式事务就不用；优先业务补偿，其次事务消息；TCC、Saga只在复杂流程用，AT尽量谨慎**

|方案|原理|优点|痛点|适合场景|
| ---- | ---- | ---- | ---- | ---- |
|本地消息表（业务表+消息表同库）|主业务和消息记录在同一个本地事务；后台任务轮询消息表投递|最简单、稳定、无中间件绑定|轮询有延迟，要做幂等、防重复投递|订单创建后发通知、积分、流水，最推荐|
|RocketMQ事务消息|半消息，确认本地事务完成后再对外可见；回查状态|不需要额外建消息表，实时性更好|强绑定RocketMQ；回查逻辑容易漏写；事务状态管理复杂|下单、支付通知链路|
|TCC（Try-Confirm-Cancel）|Try：资源预留；Confirm：确认提交；Cancel：回滚释放|高性能，无锁，适合高并发|每个业务都要写三套接口，侵入业务代码；Cancel幂等、空回滚、悬挂问题非常容易踩坑|资金、账户、资产类核心流程|
|SAGA（长事务）|拆分多个本地事务，正向执行；失败按顺序反向补偿|适合长流程，无锁|补偿逻辑写起来繁琐，补偿失败会造成数据不一致；很难隔离|长链路编排：订单→库存→物流→退款|

> 避坑：Seata AT 是侵入最低的，但依赖全局锁，高并发下容易锁等待、吞吐暴跌，**不要随便给全链路上AT**。
> 一句话判断：不是钱流转，优先本地消息表；是资金短流程，TCC；超长审批流转，Saga。

# 二、幂等设计（分布式绕不开，很多雪崩、资损根源就是没做好）
## 什么时候一定会遇到重复请求
- MQ重复消费（网络ACK丢了）
- 客户端重试、网关重试、RPC重试
- 多活、切换机房，流量切过去，请求重复投递

## 四种幂等实现（按推荐优先级）
1. **唯一业务单号（最优）**：订单号、支付流水号，唯一key，执行前先查是否已处理。适合支付、订单。
2. **Token令牌机制**：前端先拿一次性token，提交带上token，token使用即作废；适合表单提交、防重复下单。
3. **状态机控制**：订单只允许【待支付→已支付】单向流转；状态已经流转，再次收到消息直接丢弃。非常适合订单系统。
4. **数据库唯一索引**：唯一约束兜底，最简单粗暴，防止脏数据。

> 重要区分：
> 幂等 ≠ 不重试；幂等是**允许重试，多次执行结果和一次一样**。
> 非幂等接口（扣减库存、扣款）绝对不能配置自动重试。

# 三、超时、重试、退避的落地规范（写在服务治理规范里）
1. 超时设置：**链路层层设置超时，总超时 < 上游超时**
   例：网关超时3s → 订单RPC超时2s → 库存RPC超时1s；防止上游已经超时，下游还在疯狂跑。
2. 重试三要素：
   - 只对幂等接口重试
   - 最大重试次数（一般2~3次封顶）
   - 指数退避 + 随机抖动（Jitter），防止同一时刻大量请求一起重试，形成重试风暴
3. 禁止：循环重试、同步链路无限重试、批量接口重试。
> 一个经典故障：下游抖动，所有客户端同时重试，流量直接翻3倍，直接雪崩。抖动Jitter就是打散这个峰值。

# 四、连接池治理（很多人忽略，但高负载故障大户）
连接池包括：DB连接池、Redis连接池、RPC连接池、HTTP连接池
- 连接不是越大越好：MySQL单实例连接数上限有限，连接过多会导致上下文切换、锁竞争，吞吐量反而下降
- 核心配置：最小空闲、最大连接、连接超时、空闲连接回收
- 现象：连接池耗尽的典型表现：请求卡在获取连接这一步，RT飙升，但是CPU不高
- 最佳实践：
  - 核心链路、非核心链路**分开连接池（舱壁思想）**
  - 监控：活跃连接数、等待队列长度、等待超时次数
  - 告警：等待队列持续堆积，优先限流，而不是盲目调大连接池

# 五、热点治理体系（不止热点key，还有热点用户、热点商品）
分层策略：
1. 发现层：中间件监控自动识别高频key；业务埋点识别热点UID
2. 拦截层：网关对热点uid做单机限流、排队
3. 缓存层：
   - 热点key拆分（key分片）
   - Caffeine本地缓存兜底，绕开Redis集群
   - 热点独立Redis实例，不和普通流量混部
4. 业务层：热点资源独立集群，隔离部署
> 易错：热点key永不过期只是手段，**热点流量本身要隔离**，不然Redis集群分片被打挂，影响其他业务。

# 六、变更治理SOP（80%故障根源，适合写稳定性建设）
变更分级：
- P3变更：配置、文案、开关（低风险）
- P2变更：普通业务代码上线、非核心索引
- P1变更：核心服务、数据库DDL、主从切换、中间件参数、分库分表
- P0变更：大促窗口、核心存储变更，冻结，特殊审批

强制规则：
1. 所有变更必须有**回滚方案**，回滚时间预估
2. 灰度比例：0.1% → 5% → 20% → 100%，每一步观察指标（错误率、RT、SLA）
3. 变更窗口期：避开业务高峰；核心变更放在低峰
4. 变更冻结：大促、重大活动前冻结P1/P0变更
5. 变更失败判定：指标超过阈值，**自动回滚，不人工慢慢排查**
> 很多团队踩坑：灰度放了5%，指标轻微异常，选择继续观察，最后扩散成P0。

# 七、可观测的避坑：告警设计（告警风暴是稳定性杀手）
## 告警分类
- 预警（warning）：缓慢上涨，给人时间准备，比如缓存命中率缓慢下降、磁盘使用率75%
- 故障告警（critical）：已经影响业务，必须立刻处理，错误率突增、SLA跌破阈值、主库宕机
## 告警铁律
1. 告警必须**可行动**：收到告警，知道做什么；“JVM内存高”不如“订单服务JVM堆内存持续>90%，建议扩容/回滚”
2. 去重、降噪：同一根链路故障，只发根因告警，下游依赖告警收敛合并
3. 告警分级，不同级别不同通知渠道：预警钉钉，P0电话+短信
4. 告警要定期清理：长期不处理的告警直接删掉，告警墙不能有“习惯无视”的告警

# 八、容量规划 & 水位体系（不是压测一次就完事）
核心公式：
> 安全水位 = 峰值流量 / 扩容上限；预留冗余（一般预留30%~50%冗余）
> 扩容上限 = 压测得到的安全上限（不是极限打崩的极限值）

水位分成：
- 绿色：正常负载
- 黄色：预警，准备扩容、准备限流预案
- 红色：触发限流，保护核心链路
> 误区：压测压到系统崩溃的值当成上限；真实容量上限是**指标不恶化、没有大量超时错误**的最大QPS。
> 容量还要考虑：流量的热点倾斜，不是均匀流量；部分节点负载不均（热点打在少数实例）。

# 九、混沌工程（不是随便杀进程）
混沌注入的顺序（由轻到重）
1. 注入延迟、丢包（模拟网络抖动，最常用）
2. 杀掉单个Pod实例（验证负载均衡、摘除健康节点）
3. CPU、内存打满（模拟实例过载）
4. 故障整个机房（只在演练，线上极少）
混沌目标：验证**预案是否生效，而不是把系统搞崩**
> 很多团队混沌只是玩，没有指标校验：注入故障之后，看SLA、错误率、降级开关有没有正常触发。

# 十、故障应急SOP（一线值班直接背）
固定顺序，不要乱：
1. 确认告警是不是真故障（不是监控误报）
2. 止血优先：限流、降级、回滚、切流量、切换主库
3. 止血之后，保留现场（保留日志、线程栈、堆快照，不要急着重启）
4. 定位根因（链路追踪、慢日志、指标）
5. 恢复业务，通知上下游
6. 复盘，沉淀预案、监控、巡检项

口诀：**先恢复，后定位；先止血，后取证；不带着故障继续上新**

# 十一、几个高频冷门但很硬核的面试问题+答案
## 1. 怎么处理“读多写少”和“写多读少”架构差异？
读多写少：多级缓存、CDN、读写分离、从库扩容；写是瓶颈，写库少扩容。
写多读少：缓存慎用（缓存失效冲击大）；分库分表打散写压力；优先队列削峰；避免大量读请求和写争抢资源。

## 2. 什么是读写分离的延迟问题怎么处理？
主从同步延迟，刚写完立刻去从库查，读到旧数据。
方案：
- 强一致性读路由到主库
- 业务容忍短暂不一致（大部分）
- 记录写时间，按延迟阈值动态路由

## 3. 什么是流量染色？
全链路压测、线上灰度用：给一部分请求打上染色标记，流量隔离，压测数据不会进到真实业务，影子表、影子库。
> 非常适合全链路压测，不会污染生产数据。

## 4. 影子库/双写是什么？
影子库：真实流量同步复制一份到影子库，用来做压测、验证SQL、索引变更，不影响线上。
双写：同时写两个库，多用于数据迁移、分库分表平滑迁移，验证数据一致性。
