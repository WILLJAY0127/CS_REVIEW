3. **倒推逻辑**：每个"我执行了某命令 / 改了某参数"的动作，都必须能回答"凭什么这么做"——这个"凭什么"就是要补的知识点。
4. **知识四类**：JMM 与并发（可见性/锁/线程池）、JVM 内存（堆/元空间/直接内存/栈）、GC（分代/收集器/日志）、工具链（JDK 自带 + Arthas + async-profiler + MAT）。
5. **权威锚点分三级**：S 级 = 规范与一手文档（JLS / JVMS / JEP / 官方 Javadoc）；A 级 = 公认经典书；B 级 = 官方工具文档与行业规范。准备时以 S/A 为准，B 级补操作细节。
6. **版本基线**：JDK 8 与 JDK 17 双轨——大量公司仍在 8，面试新问法以 17 为准；**CMS 已在 JDK 14 移除（JEP 363）**，再把 CMS 当主力答案会暴露知识陈旧，正确说法是"用过 CMS，知道它为什么被 G1/ZGC 取代"。
7. **三个生产必开的开关**：`-XX:+HeapDumpOnOutOfMemoryError`（OOM 现场自动留证）、GC 日志（JDK 9 后统一日志开销很小，应常开）、核心服务的线程池队列水位监控。
8. **与简历措辞的对应**：每修完一类事故，才允许在简历保留对应措辞——修过堆泄漏才能写"OOM 排查"，调过 GC 参数并给出前后指标才能写"GC 调优"，否则删词。

# 一、沙盘一：CPU 持续 100%

## 五段式推演

### 1. 现象

- 监控告警：\[某实例] CPU 使用率持续 100%（不是瞬时尖峰），接口 P99 RT 从 \[80ms] 抬到 \[1s+]，但内存、GC 指标表面正常。
- 关键判断：**CPU 100% 是症状不是病因**，先区分是"业务线程在算"还是"GC 线程在回收"还是"JIT 编译线程"，三者排查路径不同。

### 2. 排查命令（JDK 8/17 通用链路）

```bash
# 第一步：定位高 CPU 的 Java 进程
top

# 第二步：看该进程内哪个线程吃 CPU（-H 显示线程）
top -Hp <pid>

# 第三步：把高 CPU 的十进制线程号转成十六进制（jstack 里的 nid 是十六进制）
printf '%x\n' <tid>

# 第四步：dump 线程栈，按 nid 定位该线程在干什么
jstack <pid> | grep -A 30 'nid=0x<hex_tid>'
# 或直接用 arthas：thread <tid> / thread -n 5（CPU 占用前 5 的线程栈）

# 第五步：若高 CPU 的线程名是 GC 线程（如 "GC thread#xx"），转向 GC 排查
jstat -gcutil <pid> 1000        # 每秒一次看 YGC/FGC 次数增速与各区占用

# 第六步（深度）：生成火焰图，看 CPU 到底烧在哪个方法
# async-profiler（生产低开销，事实标准）
./profiler.sh -d 30 -f cpu.html <pid>
```

- 栈顶状态判读：`RUNNABLE` 且栈顶在业务方法 = 在真算；栈顶在 `Unsafe.compareAndSwap*` / `AbstractQueuedSynchronizer` = CAS 自旋竞争；GC 线程高 = 转沙盘三；`C1/C2 CompilerThread` 短时高是正常 JIT，持续高另查（代码热点频繁失效等）。

### 3. 根因（四种高频类型）

1. **死循环不退出**：典型是自写标志位 `boolean running = true`，工作线程读、另一线程改——没有 `volatile`/同步，工作线程可能永远看不到更新（JIT 还可能把读取直接提升成寄存器常量），循环不再退出。
2. **灾难性正则回溯**：用 `(a+)+b` 类嵌套量词模式直接 `String.matches(用户输入)`，长输入触发指数级回溯，一个请求把一个核钉死。
3. **锁/CAS 激烈竞争**：热点计数用 `synchronized` 或 `AtomicLong`，高并发下大量线程自旋/空转（`AtomicLong` 在极端竞争下 CAS 失败重试本身烧 CPU）。
4. **Full GC 连环触发**：GC 线程占满 CPU，业务线程反而拿不到时间片——表面是 CPU 问题，实质是 GC 问题。

### 4. 修复

- 死循环：标志位改 `volatile boolean`，更规范的做法是响应中断（`Thread.interrupted()` / 可中断的阻塞方法），停止逻辑可测试。
- 正则：Pattern 预编译为静态常量；限制输入长度；Java 侧无回溯超时（`Matcher` 不支持中断），高风险输入放独立有界线程池隔离，或换 RE2/J 等线性时间引擎。
- 热点计数：`AtomicLong` → `LongAdder`（分段累加，竞争时摊到 Cell 数组）；能上无锁结构就缩短临界区；真要锁就减小粒度。
- GC 导致的：转沙盘三处理。

### 5. 事后加固

- 监控：CPU 使用率 + load average 双告警，区分"用户态 CPU"与"内核态/GC"；容器内用容器视角指标（`container_cpu_usage`，不要看宿主机）。
- 工具： Arthas 预装到基础镜像，免去故障时临时安装。
- 流程：代码审计加入"用户输入直接进正则"、"自写线程可见性标志位"两个检查项。

# 二、沙盘二：OOM（四种类型分开打）

> OOM 不是一个病，是四个不同的病。报错信息不同、工具不同、修法不同。**看到 OOM 先读异常全文**，这是全部排查的起点。

## 五段式推演

### 1. 现象与分型

| 异常信息                                                   | 病位        | 典型场景                                                  |
| ------------------------------------------------------ | --------- | ----------------------------------------------------- |
| `java.lang.OutOfMemoryError: Java heap space`          | 堆         | 内存泄漏；或堆真的不够（缓存无界、一次性查全量）                              |
| `OutOfMemoryError: Metaspace`（JDK 8+）                  | 元空间（本地内存） | 动态生成类失控：CGLIB、频繁反射代理、热部署、脚本引擎                         |
| `OutOfMemoryError: Direct buffer memory`               | 堆外直接内存    | Netty/NIO 使用不当；受 `MaxDirectMemorySize` 约束，与 `-Xmx` 无关 |
| `OutOfMemoryError: unable to create new native thread` | 栈/线程资源    | 线程数撞 `ulimit -u`/内核 `pid_max`；常见于无界线程池 + 任务全阻塞        |

### 2. 排查命令

```bash
# 前置（生产必开，OOM 瞬间自动留现场，事后任何工具都不如 dump 本身）
# -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump/

# 现场还活着：先快速看对象直方图（只看类名与数量，不 dump 全堆）
jmap -histo:live <pid> | head -50          # JDK8
jcmd <pid> GC.class_histogram              # JDK9+ 推荐

# 主动 dump（会触发 Full GC，注意对业务的影响）
jcmd <pid> GC.heap_dump /data/dump/heap.hprof    # JDK9+ 首选
jmap -dump:live,format=b,file=heap.hprof <pid>  # JDK8

# MAT 打开 hprof：Leak Suspects 报告 → Dominator Tree →
# 对可疑对象 "Path to GC Roots → exclude weak/soft references"
# 看到一条从静态字段/运行中线程到业务对象的强引用链 = 泄漏路径成立

# Metaspace 型：看类加载统计
jcmd <pid> VM.classloader_stats
jcmd <pid> GC.class_stats | sort           # 需配合 -XX:+UnlockDiagnosticVMOptions

# 线程数型
jstack <pid> | grep -c 'java.lang.Thread.State'
ulimit -u                                   # 当前用户最大进程/线程数
cat /proc/sys/kernel/threads-max
```

### 3. 根因（按分型）

- **heap space — ThreadLocal 泄漏**：线程池线程长期存活，ThreadLocal 的 Entry 键是弱引用、值是强引用；只 set 不 remove，线程不死 → value 对象链永不回收。这是"测试环境没事、线上越跑越胖"的经典原因。
- **heap space — 静态集合当缓存**：`static Map` 只 put 不淘汰；或自研缓存没有 size/TTL 上限。
- **heap space — 一次性加载**：XXL-Job/批处理 `selectList` 全量装载结果集，数据随业务增长最终超过堆（对应简历里的"批量代扣"场景）。
- **Metaspace**：每次请求新建 ClassLoader 加载动态类且不卸载（ClassLoader 泄漏会导致它加载的所有类无法卸载）。
- **Direct buffer**：Netty 中手动分配 ByteBuf 未 release，或 DirectByteBuffer 回收依赖 Cleaner/Full GC，堆积速率超过触发 GC 的阈值。
- **native thread**：下游卡死导致池内线程全阻塞，框架继续 new 线程（用了无界的 `newCachedThreadPool`）直到 OS 拒绝。

### 4. 修复

- ThreadLocal：`finally { threadLocal.remove(); }`；线程池场景尤其强制。
- 缓存：换 Caffeine，**必须**声明 `maximumSize` 与 `expireAfterWrite/Access`；缓存容量纳入容量评估。
- 批处理：游标/分页流式处理（ResultSet fetchSize、MyBatis Cursor、keyset pagination），批大小按单批内存占用 × 并发数反推；配合分片。
- Metaspace：设置 `-XX:MaxMetaspaceSize`（不设默认只受进程内存限制，泄漏时晚发现）；修复 ClassLoader 持有链。
- Direct：设置 `-XX:MaxDirectMemorySize`；Netty 遵守 ByteBuf 释放责任（池化用 release/引用计数），监控直接内存用量。
- 线程型：见沙盘四——有界线程池 + 下游超时，系统层调 `ulimit -u` 只是止血不是根治。

### 5. 事后加固

- `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=<大容量独立盘>` 全量服务标配。
- 堆使用率分档告警（70%/85%），不要等 OOM 才发现。
- 代码审查项：static 集合、ThreadLocal、`Executors` 无界工厂、全量查询、动态类生成。
- 容器环境明确堆/元空间/直接内存/Native Memory 四笔账，`-Xmx` 之外预留足够容器内存（JVM 非堆内存约占堆的 20–40%，具体实测）。

# 三、沙盘三：频繁 Full GC 与长 STW

## 五段式推演

### 1. 现象

- 接口 RT 出现周期性毛刺（每隔几分钟一批请求超时），曲线与 GC 暂停时间吻合；`jstat` 看到 FGC 次数快速增长，单次 FGCT（Full GC 累计耗时）拉长；老年代回收率越来越低。

### 2. 排查命令

```bash
# 实时看各代占用与 GC 计数（列含义：S0/S1 Survivor，E Eden，O Old，M Metaspace，
# YGC/YGCT Young GC 次数/总耗时，FGC/FGCT，GCT 总耗时）
jstat -gcutil <pid> 1000

# GC 日志（排障信息量最大的单一来源，两种版本都会）
# JDK8：-XX:+PrintGCDetails -XX:+PrintGCDateStamps -XX:+PrintGCApplicationStoppedTime
#       -Xloggc:/data/log/gc.log -XX:+UseGCLogFileRotation -XX:NumberOfGCLogFiles=5 -XX:GCLogFileSize=20M
# JDK9+（统一 JVM 日志，JEP 158）：
#   -Xlog:gc*,safepoint:file=/data/log/gc.log:time,uptime,level,tags:filecount=5,filesize=20m

# 现场命令（17）
jcmd <pid> GC.heap_info          # 堆布局、region 使用
jcmd <pid> VM.flags              # 实际生效参数（含默认值，排查"参数没生效"）

# 怀疑泄漏：dump + MAT（路径同沙盘二）；怀疑大对象：直方图按大小排序
jmap -histo <pid> | sort -k 3 -n -r | head -30
```

- 判读顺序：先看 Full GC 后**老年代是否降下来**——降不下来 = 泄漏（转沙盘二）；能降但很快又满 = 大对象/过早晋升/吞吐型问题（本沙盘继续）。

### 3. 根因

1. **内存泄漏**：最常见，Full GC 只是泄漏的症状（老年代回收曲线只涨不跌）。
2. **大对象直接入老年代**：巨型数组/大字符串/超大集合，Eden 放不下直接分配老年代，几次就压满（G1 中为 humongous 对象，连续 region 占用，还可能引发并发标记提前启动）。
3. **显式** **`System.gc()`**：代码或第三方库（历史上的 RMI、部分 NIO 直接内存回收路径）触发，Full GC 与流量无关、时间点诡异。
4. **过早晋升 promotion**：Survivor 太小或晋升年龄阈值过低，存活但短命的对象涌进老年代。
5. **元空间扩容**：JDK 8 下 Metaspace 扩容默认可能引发 Full GC。
6. **（JDK8 时代）CMS concurrent mode failure / promotion failed**：并发标记速度跟不上分配速度，退化为串行 Full GC——答题价值在于知道这是 CMS 被淘汰的原因之一。

### 4. 修复（按根因）

- 泄漏：修泄漏，不要用调参数掩盖。
- 大对象：代码层拆解（流式、分页、限制单次大小）；G1 调大 region（`-XX:G1HeapRegionSize`）让 humongous 阈值相应提高；评估时关注 humongous region 占比。
- 显式 GC：JDK8 用 `-XX:+ExplicitGCInvokesConcurrent`（显式触发走并发收集，避免 Serial Full）或 `-XX:+DisableExplicitGC`；JDK9+ 显式 System.gc() 默认即走并发收集器周期。
- 过早晋升：调 SurvivorRatio / MaxTenuringThreshold（JDK8 Parallel/CMS 语境），用 `jcmd <pid> GC.heap_info` 与日志中年龄分布（`-XX:+PrintTenuringDistribution`）确认，不要拍脑袋。
- 元空间：`-XX:MetaspaceSize` 设到稳态值，避免运行期扩容；`-XX:MaxMetaspaceSize` 兜底。
- 收集器选择（结论式）：JDK 17 默认 G1，适合多数服务（大堆、可设停顿目标 `-XX:MaxGCPauseMillis=200`）；超大堆 + 极低延迟诉求评估 ZGC（JEP 377 转正）/Shenandoah（JEP 189）；**不再以 CMS 为答案**。
- 任何调优一次只改一个参数，前后用同一份压测脚本对比 GC 日志指标。

### 5. 事后加固

- GC 日志生产常开（JDK9 统一日志、带滚动，磁盘开销可控）。
- 告警：Full GC 频率（如 10 分钟 ≥1 次）、单次 STW 时长、老年代 Full GC 后占用率。
- 容量基线：上线前压测产出"对象分配速率、晋升速率、稳态堆占用"三个数，参数以数据为准。

# 四、沙盘四：线程池队列堆积

## 五段式推演

### 1. 现象

- 依赖的某下游服务 RT 升高 → 本服务接口大面积超时；Tomcat 工作线程被打满；dump 中大量线程卡在 `ThreadPoolExecutor$Worker.run → LinkedBlockingQueue.take()` 或下游 HTTP 调用上；严重时堆持续膨胀直至 OOM。

### 2. 排查命令

```bash
jstack <pid> > t.txt
# 统计线程状态分布与线程池名（自己的池必须有业务可读的线程名前缀）
grep 'java.lang.Thread.State' t.txt | sort | uniq -c
grep -A 5 'pool-.*-thread' t.txt | grep -E 'at (com.业务|java.util.concurrent|http)' | sort | uniq -c | sort -rn | head

# arthas 快速版
thread -n 5          # CPU 视角（堆积时 CPU 往往不高，帮助排除沙盘一）
thread --state WAITING
thread -b            # 找阻塞其他线程的线程（死锁/独占锁视角）

# 池的运行时指标（代码中需暴露）：活跃数/队列深度/已完成任务数/拒绝计数
# getActiveCount() / getQueue().size() / getCompletedTaskCount()
```

### 3. 根因

1. **用了** **`Executors`** **无界工厂**：`newFixedThreadPool` / `newSingleThreadExecutor` 底层是无界 `LinkedBlockingQueue`，下游变慢时任务无限堆积 → 队列里每个任务还持有请求对象引用 → 先吃堆再 OOM；`newCachedThreadPool` 则是线程数无界，走向 native thread OOM。
2. **不懂池的真实运转规则，参数拍脑袋**：核心线程数、队列、最大线程数的交互与直觉相反（见下方规则）。
3. **下游慢调用拖垮公共池**：快慢任务共用一个池，慢任务占满全部工作线程（队头阻塞的池化版本）。
4. **拒绝策略反打**：`CallerRunsPolicy` 把任务退给调用线程执行，若调用方是 Tomcat 线程，等于反压到入口线程池——无人接盘时全链雪崩；`Discard*` 策略静默丢任务，资金类场景是事故。
5. 线程数估算错误：把"IO 密集型 = 2N"当公式，实际应按等待/计算时间比估算并压测校准。

### 4. 修复

- **一律** **`new ThreadPoolExecutor(...)`** **显式构造**（行业规范出处见锚点），七参数逐一交代依据：
  `corePoolSize / maximumPoolSize / keepAliveTime / workQueue(有界) / threadFactory(带业务前缀名) / handler`。
- 牢记官方 Javadoc 的运转规则（与多数人直觉相反）：
  1. 当前线程数 < corePoolSize → 直接新建核心线程（哪怕有空闲线程）；
  2. ≥ corePoolSize → 任务**先入队列**；
  3. **队列满了**才新建非核心线程直到 maxPoolSize；
  4. 达到 maxPoolSize 且队列仍满 → 执行拒绝策略。
     → 用无界队列时 maxPoolSize 永远不生效（队列不可能满），这是 Executors 工厂被禁的核心原因。
- 隔离：按依赖建独立池（快接口与慢 LLM/外部接口分池，对应简历 AI 项目的线程池隔离），拒绝策略与超时各自配置。
- 必配下游超时（连接/读超时分别设）与熔断，池解决不了"下游永远不返回"。
- 线程数：按 Little 定律式估算 `线程数 ≈ 核数 × (1 + 等待时间/CPU时间)`，再压测找拐点；队列容量按"可接受的峰值积压 × 单任务内存"反推。

### 5. 事后加固

- 每个自定义池暴露四个指标到监控：activeCount、queue.size、completedTaskCount、拒绝计数（用 Micrometer 包装即可），队列水位告警。
- 线程名前缀（`ThreadFactoryBuilder().setNameFormat("ai-fetch-%d")`），否则 jstack 里全是 `pool-13-thread-2` 无法归属。
- 压测剧本必须包含"下游注入延迟/故障"，验证池行为与拒绝策略，而不是只压正常路径。

```bash
jcmd <pid> GC.heap_info               # 堆布局（G1 region 详情）
jcmd <pid> GC.class_histogram         # 对象直方图（替代 jmap -histo）
jcmd <pid> GC.heap_dump /x/x.hprof    # 主动 dump（替代 jmap -dump）
jcmd <pid> VM.classloader_stats       # 类加载器统计（Metaspace 泄漏）

# ---- Arthas（交互式，生产先在测试环境练熟）----
arthas-boot.jar →
  dashboard          # 线程/内存/GC 一屏总览
  thread -n 5        # CPU Top5 线程栈
  thread --state BLOCKED
  thread -b          # 阻塞其他线程的线程
  trace <类> <方法>  # 方法内调用链耗时
  watch <类> <方法> '{params,returnObj,throwExp}' -x 2
  profiler start; profiler stop --format html   # 内置 async-profiler 火焰图

# ---- JFR：低开销持续记录，生产事后回放 ----
jcmd <pid> JFR.start name=rec settings=profile duration=5m filename=/x/r.jfr
# 用 JMC 打开 .jfr

# ---- 必开启动参数（JDK17 基线，按服务裁剪）----
# -Xms 与 -Xmx 设相同值（避免运行期扩缩堆）
# -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump
# -Xlog:gc*,safepoint:file=/data/log/gc.log:time,uptime,level,tags:filecount=5,filesize=20m
# -XX:MaxMetaspaceSize=256m -XX:MaxDirectMemorySize=512m   # 按实测给
# -XX:+ExitOnOutOfMemoryError   # 容器化部署时让编排系统快速重启，可选策略
```

# 八、把沙盘替换成真实故事：填空模板

> 四个沙盘对应四类故事。每经历一次真实事故，当天就按此模板落一份归档（记忆会快速衰减）。**模板要求每个空都有具体值，填不出空的部分说明经历不完整，不能进简历。**

```markdown
### 事故类别：[ CPU 100% / 堆OOM / Metaspace / Direct / 线程数OOM / Full GC / 线程池堆积 ]

1. 背景（三句话内）
   - 系统与职责：[什么系统，我负责什么模块]
   - 时间与规模：[年月]，[实例数/QPS/数据量的量级]
   - 技术版本：[JDK 版本、收集器、容器/虚机]

2. 现象（只写监控与用户反馈，不写猜测）
   - 告警内容与触发时间线：[哪个指标，阈值，持续多久]
   - 影响面：[多少实例/接口/用户/资金量级，有没有资损]

3. 排查（命令 + 看到的关键证据，顺序就是当时动手的顺序）
   - 命令 1：[实际命令] → 关键输出：[什么数值让你做出下一步判断]
   - 命令 2：……
   - 定性证据：[dump/日志/火焰图中哪一条链路锁定根因]

4. 根因（代码/参数层面的确定原因，能指到具体提交或配置）
   - 直接原因：[哪段代码/哪个参数]
   - 为什么测试没发现：[数据量、并发度、时长哪一个条件线上才具备]

5. 修复（止血与根治分开写）
   - 止血：[重启/限流/回滚，几点几分，多久恢复]
   - 根治：[代码或参数改动，为什么这样改]
   - 验证：[压测/灰度中哪个指标从 X 变到 Y]

6. 事后加固（这一段决定故事的"高级感"）
   - 监控：[新增了什么告警/指标，阈值依据]
   - 参数/规范：[沉淀了什么启动参数、代码审查项、组件使用规范]
   - 复盘与推广：[是否横向排查了其他服务，产出什么文档]
```

**真实性自检三问（答不出就不要用这个故事）**：

1. 当时 `VM.flags` 里关键参数的实际值是多少？
2. 修复前后 GC/RT 指标的具体数字对比？
3. 止血操作是你做的还是同事做的？你在其中的确切角色？
