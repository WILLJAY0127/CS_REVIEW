# 第一部分:并发编程攻防

## A1. 讲讲 volatile,它能保证原子性吗?

**标准答法(结论先行)**:volatile 保证两件事——**可见性**(写立即刷主内存、读强制从主内存,底层是内存屏障 + 缓存一致性协议 MESI)和**禁止指令重排序**;但**不保证复合操作的原子性**,比如 `volatile int i; i++` 仍然线程不安全,因为 i++ 是读-改-写三步。

**连环追问**:

- Q:既然不能保证原子性,什么场景用 volatile?
  - A:① 状态标志位(`boolean running`,一个线程写、其他线程读);② DCL 单例里禁止对象半初始化被看到;③ JUC 里 AQS 的 state 不是 volatile 装饰而是专门类,但 ConcurrentHashMap 的很多属性直接 volatile。
- Q:volatile 和 synchronized 区别?
  - A:volatile 是轻量级的变量级约束,不阻塞、不保原子;synchronized 是锁,互斥执行、三者(原子/可见/有序)都保但开销大。
- Q:什么是 happens-before?和 volatile 什么关系?
  - A:它是 JMM 给程序员的"可见性承诺":volatile 写 happens-before 后续对该变量的读;此外还有监视器锁规则、线程 start/join 规则、传递性等。**意思是前一个操作的结果对后一个可见,不是说时间上先发生**。
- Q:`volatile boolean running = true` 为什么不用锁也安全?
  - A:单次 boolean 读写本身原子,volatile 补上可见性即可,这是最轻的正确方案。

**死亡点**:说"volatile 能保证 i++ 安全";或把 happens-before 理解成"代码书写顺序"。

## A2. synchronized 的锁升级过程讲一下

**标准答法**:对象头 Mark Word 里存锁状态,锁只能**单向升级**(竞争加剧时膨胀):

1. **无锁**:Mark Word 存对象 hashCode、分代年龄;
2. **偏向锁**:第一个线程进入,把线程 ID 记进 Mark Word,之后该线程重入只需比对 ID,**连 CAS 都不做**;出现第二个线程竞争时撤销偏向;
3. **轻量级锁**:竞争线程在栈帧建锁记录(Lock Record),CAS 把 Mark Word 指向自己的锁记录;拿不到就**自旋**等待(赌对方很快释放);
4. **重量级锁**:自旋失败/竞争激烈,膨胀为操作系统互斥量(monitor),未抢到的线程进入 EntryList **阻塞挂起**,涉及用户态/内核态切换,开销最大。

**连环追问**:

- Q:为什么要分这么多级?直接用重量级锁不行吗?
  - A:大部分锁生命周期内**根本没有竞争**(经验数据:多数锁只被一个线程用)。分级是用不同成本匹配不同竞争程度:无竞争时偏向锁近零成本,短竞争时自旋避免挂起,真激烈才付阻塞代价。
- Q:自旋一定好吗?
  - A:自旋占 CPU。锁持有时间短,自旋划算;持有时间长,空转浪费 CPU,所以自适应自旋(由 JVM 据历史成功率调整),最终膨胀。
- Q:偏向锁有什么争议?
  - A:维护成本高(撤销要等安全点、和 hashCode 存储冲突),**JDK 15 起偏向锁默认禁用并逐步废弃**。面试答出这句=跟过新版本。
- Q:synchronized 锁的是什么?
  - A:实例方法锁 this、静态方法锁 Class 对象、同步块锁括号里的对象;本质都是锁对象头的 monitor。
- Q:synchronized 和 ReentrantLock 怎么选?
  - A:见 A8。先答一句:能用 synchronized 就用(JVM 层持续优化、自动释放不会死锁),需要可中断/超时/公平/多条件变量时才用 ReentrantLock。

**死亡点**:说锁可以降级(HotSpot 在批量操作里有特殊的 bulk rebias/revoke,但面试语境答"单向升级"即可,别展开说错);把偏向锁说成"一直偏向某个线程,第二个线程永远抢不到"。

**挂项目**:可以引到"我们支付回调防重用的是 Redisson 分布式锁 + 数据库唯一索引,JVM 锁只用于单机内的短临界区"——把话题导向 A5/技能 5。

## A3. 讲讲 AQS,ReentrantLock 是怎么基于它实现的?

**标准答法**:AQS(AbstractQueuedSynchronizer)是 JUC 同步器的骨架,核心三样:

1. **volatile int state**:同步状态(重入次数/许可数/读写锁里高低 16 位分工);
2. **CAS 修改 state**:保证争抢原子;
3. **CLH 变体双向队列**:抢不到的线程封装成 Node 入队,前驱释放后唤醒后继。

ReentrantLock:lock 时 CAS 抢 state(0→1)并记录独占线程;重入则 state+1,unlock 一次 -1,归零才真正释放。

**连环追问**:

- Q:公平锁和非公平锁区别?为什么默认非公平?
  - A:公平锁入队前先看队列里有没有等待者(hasQueuedPredecessors),严格 FIFO;非公平锁允许新线程直接插队 CAS。默认非公平因为**公平锁唤醒有延迟(要 park/unpark 调度),插队能趁持有者刚释放的空档直接拿到锁,吞吐高**,代价是可能队头线程饿死概率增加。
- Q:线程在队列里是什么状态?怎么被唤醒?
  - A:Node 有 CANCELLED/SIGNAL/CONDITION/PROPAGATE;入队后把前驱状态设为 SIGNAL,自己 park 阻塞;前驱释放时 unparkSuccessor 唤醒它再 CAS 抢。
- Q:CountDownLatch / Semaphore / ReentrantReadWriteLock 怎么用 AQS?
  - A:Latch 和 Semaphore 用**共享模式**(tryAcquireShared/tryReleaseShared,state 是计数/许可);读写锁 state 高 16 位读计数、低 16 位写计数。
- Q:为什么 AQS 用双向队列不用 CLH 原始单向?
  - A:需要从尾部取消节点(CANCELLED)、需要前驱指针管理 SIGNAL,单向做不到;AQS 是 CLH 的变体。
- Q:Condition 的原理?
  - A:每个 Condition 维护一个单向等待队列,await 时释放锁并转移节点进去 park,signal 时挪回同步队列重新竞争。

**死亡点**:只背"有个队列"答不出 state 语义和公平性实现细节;不知道 AQS 是模板方法模式(tryAcquire 由子类实现)。

## A4. CAS 有什么问题?ABA 怎么解决?

**标准答法**:CAS(Compare And Swap)是"我认为值是 A,是就换成 B"的原子指令(Unsafe → CPU 的 cmpxchg)。三个问题:

1. **ABA**:值从 A→B→A,CAS 认为没变。用版本号(AtomicStampedReference)或布尔标记(AtomicMarkableReference)解决;
2. **自旋开销**:失败一直重试占 CPU,高竞争下不如直接挂起;
3. **只能保证一个变量原子**:多变量要用 AtomicReference 打包,或加锁。

**连环追问**:

- Q:AtomicInteger 和 LongAdder 区别?高并发计数选哪个?
  - A:AtomicInteger 所有线程 CAS 同一个 value,高并发下自旋失败多;**LongAdder 用 Cell 数组分散热点**,各线程 CAS 不同 Cell,求和时汇总——高并发递增场景 LongAdder 吞吐高,但 sum() 不保证瞬间精确;要精确值(如生成序号)用 AtomicXxx,要高吞吐计数(如 QPS 统计)用 LongAdder。
- Q:i++ 在字节码层面是什么?
  - A:iload、iinc(?注意:iinc 只用于局部变量自增,字段是 getfield→+1→putfield)——字段 i++ 是三次内存操作,中间可插线程切换。
- Q:CAS 底层怎么保证原子的?
  - A:多核下 cmpxchg 指令带 lock 前缀锁缓存行/总线,MESI 保证;Java 层 Unsafe 是 native 方法。
- Q:乐观锁和 CAS 什么关系?
  - A:数据库乐观锁(version 字段 + UPDATE WHERE version=?)是同样思想在数据库层面的实现——**直接挂你的缴费单状态机**:`UPDATE ... WHERE id=? AND status='待支付'`,影响行数=0 即并发冲突。

**挂项目**:"我们资金单据不依赖分布式锁保证正确性,而是状态机 + 条件更新(数据库版 CAS),影响行数判定;锁只是减少无效竞争。"

## A5. 线程池原理讲一下,你们线上线程池参数怎么定的?(★ 主战场)

**标准答法(先讲运转流程)**:ThreadPoolExecutor 7 个参数:corePoolSize、maximumPoolSize、keepAliveTime、workQueue、threadFactory、handler,外加任务提交流程——

1. 线程数 < core:开核心线程执行(即使有空闲核心线程也开,除非预热);
2. core 满:进队列;
3. 队列满:开到 max;
4. max 也满:执行拒绝策略。

四种拒绝策略:AbortPolicy(抛异常,默认)、CallerRunsPolicy(提交线程自己跑,天然降速)、DiscardPolicy(静默丢弃)、DiscardOldestPolicy(丢队头)。

**连环追问(这题至少 5 层,逐层接)**:

- Q:为什么阿里规范禁止 Executors 创建线程池?
  - A:FixedThreadPool/SingleThread 用**无界 LinkedBlockingQueue**,任务堆积会 OOM;CachedThreadPool 最大线程 Integer.MAX_VALUE,无限开线程也会 OOM。必须手动 new ThreadPoolExecutor 用**有界队列**。
- Q:参数怎么定?
  - A:先分任务类型:**CPU 密集** core≈N+1;**IO 密集** core≈N×(1+等待/计算时间),实践中靠压测定——压出 QPS、RT、CPU、队列水位的关系曲线再定,公式只给初值。核心数、队列容量、拒绝策略三者是一组权衡:队列大→抗突发但积压无感知;队列小→快速失败好监控。
- Q:队列里任务堆积了怎么发现?
  - A:线程池必须可监控:暴露 activeCount、queue.size、completedTaskCount、拒绝次数到 Prometheus + 告警;线程名带业务前缀(threadFactory),jstack 一眼知道是谁家的池。
- Q:拒绝策略选了什么?
  - A:按业务:AI 取数池用 CallerRuns——LLM 慢、调用方是 Web 线程,让调用方自己跑等于背压降速,比静默丢数据安全;支付类异步任务不能丢,拒绝后进 MQ 兜底/持久化重试。**严禁默认 Abort 又不监控**。
- Q:核心线程能回收吗?线程池能动态改参数吗?
  - A:allowCoreThreadTimeOut(true) 核心线程也回收;setCorePoolSize/setMaximumPoolSize 运行时可调——大促前调大、事后缩回,配合配置中心动态推送。
- Q:一个任务在池里抛异常会怎样?
  - A:execute 提交的异常冒泡到 UncaughtExceptionHandler;submit 提交的异常被包进 Future,不 get 就被吞——**这是经典事故源**,要么统一 afterExecute 记录,要么用 Future 必须 get。
- Q:线程池怎么关闭?
  - A:shutdown(不接新任务,跑完存量)→ awaitTermination 等 → shutdownNow(发中断信号);池里有调远程的任务要正确响应 InterruptedException,不能吞中断。

**死亡点**:

- 只会"CPU 密集 N+1、IO 密集 2N"这种背参数,追问压测数据就卡;
- 不知道任务先入队还是先开到 max(这是执行顺序题,答错=没看过源码);
- 项目里线程池没有名字、没有监控、拒绝策略默认——一追就露馅。

**挂项目(必须能展开 2 个真实池)**:

1. **AI 取数池**:Chatflow 预取节点并行拉取多投连账户数据,自定义池(core【按真实】、有界队列、CallerRuns、线程名 `ai-fetch-`、独立于 Web 容器池);LLM 慢调用再做**线程池/信号量隔离**,防止慢调用雪崩主站。
2. **批量代扣分片任务**:XXL-Job 分片广播,每片游标分页 + 有界批大小,任务内不使用大线程池并发打核心(核心有承载上限),并发度与核心/渠道约定。

## A6. ThreadLocal 原理?为什么会内存泄漏?

**标准答法**:每个 Thread 持有 ThreadLocalMap,key 是 ThreadLocal 对象(**弱引用**)、value 是线程私有值(**强引用**)。线程池线程长期存活 → 如果用完不 remove,value 一直被强引用;即便 key 被回收变成 null entry,value 也拿不到又收不走 → 泄漏 + 下一个复用到该线程的任务读到脏数据。

**连环追问**:

- Q:key 为什么设计成弱引用?
  - A:ThreadLocal 对象本身生命周期可能结束(局部变量),弱引用保证 ThreadLocal 实例能被回收;但 value 泄漏问题仍在,所以规范是**必须在 finally 里 remove**。
- Q:你们项目哪里用了 ThreadLocal?怎么保证不踩坑?
  - A:用户上下文(userId/token 透传)、traceId、Dify 工具调用的会话态;统一在拦截器/过滤器 afterCompletion 里 remove;异步线程切换用 TaskDecorator 或 TransmittableThreadLocal 显式传递。
- Q:父子线程怎么传?
  - A:InheritableThreadLocal 只在**创建子线程时**拷贝,线程池复用线程时不会更新;阿里 TTL(TransmittableThreadLocal)解决线程池场景,在任务提交时捕获、执行时回放。
- Q:ThreadLocal 和 synchronized 解决的是同一个问题吗?
  - A:相反方向:synchronized 是"数据共享但串行访问"(以时间换安全);ThreadLocal 是"每线程一份数据"(以空间换隔离),根本不共享。

**挂项目**:AI 工具 Webhook 强调"userId 取自会话态、不信模型参数"——会话态就是网关鉴权后放 ThreadLocal/请求上下文,拦截器出口清理,可顺带讲 TTL。

## A7. CountDownLatch、CyclicBarrier、Semaphore、CompletableFuture 怎么选?

**标准答法(一句话辨析)**:

- **CountDownLatch**:一个/多个线程等 N 个计数归零,一次性,不能复用(发车:所有人上车 → 开车);
- **CyclicBarrier**:N 个线程互相等齐再一起走,可 reset 复用(团建:人到齐合影,再来一轮);
- **Semaphore**:N 个许可的资源池,acquire/release(限流、保护下游);
- **CompletableFuture**:异步编排,thenApply/thenCombine/allOf,做并行调用聚合。

**连环追问**:

- Q:并行调用 3 个接口汇总结果怎么写?超时怎么办?
  - A:`CompletableFuture.supplyAsync(任务, 专用线程池)` 三个 + `allOf().get(timeout)`;每个子调用自己也要有超时,**一个慢不能拖死整体**,异常用 exceptionally 给默认值;get 外层线程要处理 TimeoutException。
- Q:CompletableFuture 默认用什么线程池?有什么坑?
  - A:不传 executor 用 ForkJoinPool.commonPool(并行度=CPU-1),所有任务共享,**有阻塞 IO 会拖住整个 JVM 的并行流/其他用法**——必须传业务自定义池。
- Q:Semaphore 限流和 Sentinel 区别?
  - A:Semaphore 是单机 JVM 内信号量;全局限流要 Redis/令牌桶中心组件,入口流控用 Sentinel。

**挂项目**:AI 取数层并行拉多账户、多保单数据用 CompletableFuture + 专用池编排,任一账户查询失败不影响其他账户,聚合层标记缺失。

## A8. 锁这么多,实际怎么选?(综合对比题)

**标准答法(给决策框架,不要背优缺点表)**:

1. 先问:**锁什么?跨不跨 JVM?** 跨进程(多实例)→ Redis/数据库层面;单机内 → 往下;
2. 临界区短、无特殊要求 → **synchronized**(JVM 优化到位、自动释放);
3. 要可超时/可中断/公平/多条件队列 → **ReentrantLock**;
4. 读多写少 → **ReentrantReadWriteLock** 或 **StampedLock**(乐观读,但不可重入、编程复杂);
5. 计数器/状态位优先 CAS 原子类,高并发热点用 LongAdder;
6. 资金正确性 → 不靠锁,靠**数据库唯一索引 + 状态机**。

**连环追问**:

- Q:读写锁有什么坑?
  - A:写锁饥饿(读一直来写拿不到,可用公平模式)、锁不能升级(读锁中拿写锁会死锁,但写可降级为读)。
- Q:分布式锁和本地锁能同时用吗?
  - A:典型组合:本地锁减少 Redis 竞争 + Redisson 跨实例互斥;但要讲清本地锁只在单 JVM 有效,正确性仍在分布式锁/DB。
- Q:synchronized 在 JDK6 后做了哪些优化?
  - A:偏向锁、轻量级锁、自旋自适应、锁消除(逃逸分析)、锁粗化(循环外合并)。

## A9. HashMap 为什么线程不安全?ConcurrentHashMap 原理?

**标准答法**:

- HashMap:JDK7 并发扩容头插法可能形成环形链表(JDK8 改尾插规避了环,但仍有 put 覆盖、size 不准问题),结论就是并发下行为未定义;
- ConcurrentHashMap 1.8:**数组 + 链表/红黑树**,put 时对**桶数组头节点 CAS + synchronized 锁单个桶**,锁粒度从 1.7 的 Segment 细化到桶;size 用 baseCount + CounterCell 分散计数(思想同 LongAdder);**不允许 key/value 为 null**(并发下无法区分"没有"和"存了 null")。

**连环追问**:

- Q:为什么 CHM 不允许 null 而 HashMap 允许?
  - A:二义性:get 返回 null 到底是不存在还是值为 null?单线程可以用 containsKey 再查,并发下两次调用之间状态会变。
- Q:CHM 的 putIfAbsend/computeIfAbsent 能解决什么?
  - A:check-then-act 复合操作原子化;**经典坑:computeIfAbsent 的 mappingFunction 里再对同一个 map 做修改可能死循环/重入问题**,以及 JDK8 老版本有递归建桶 bug,别在函数里干重活。

**挂项目**:断点平台/AI 会话缓存里本地缓存结构选择——短生命周期用 CHM,跨实例共享必须 Redis,别用本地 Map 存全局状态。

## A10. 手写线程安全单例(DCL)

**标准答法**:

```java
public class Singleton {
    private static volatile Singleton instance; // volatile 必须有
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {                  // 第一次检查,避免每次加锁
            synchronized (Singleton.class) {
                if (instance == null) {          // 第二次检查,防止重复创建
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**连环追问**:

- Q:为什么必须 volatile?
  - A:`new Singleton()` 不是原子操作:分配内存、初始化、引用指向三步,重排后可能引用已非空但对象未初始化,另一个线程拿到半初始化对象;volatile 写屏障禁止这个重排。
- Q:更推荐哪种写法?
  - A:**枚举单例**(天然防反射、防反序列化重建)或静态内部类 holder(类加载锁保证懒汉式线程安全),DCL 是面试用、工程上优先枚举/holder/Spring Bean。
- Q:Spring 的 Bean 默认是单例,线程安全吗?
  - A:单例 ≠ 线程安全。无状态 Bean 安全;有成员变量态就不安全,请求数据走方法参数/ThreadLocal,不要放字段。

# 第二部分:实战场景攻防(挂项目)

## B1. AI 取数:多个投连账户并行查询,你怎么设计?

**标准答法(分层讲)**:

1. 入口校验(保单归属、userId 取自会话);
2. CompletableFuture 列表,每个账户一次查询任务,提交**专用有界线程池**;
3. 每个任务独立超时 + exceptionally 降级(单账户失败标缺失,不拖垮整答);
4. `allOf().get(总预算时间)` 兜底;
5. 历史重数据(收益 5 年/净值 3 年)按需加载,不在并行列表里;
6. 线程池参数来源:账户接口 RT、峰值会话量压测;监控队列水位和拒绝率。

**连环追问**:全在一个池里吗?——不,LLM 调用与取数调用分池(慢快隔离,舱壁模式);QPS 翻三倍先坏哪?——先看下游接口承载,其次队列、连接池;怎么降?——信号量限流 + 语义缓存(命中率约 30%)。

## B2. 线程池打满导致接口雪崩,讲一个事故(五段式模板,用真实经历填)

1. **现象**:某时段【接口 RT 飙升/告警】,jstack 发现【某池】线程全 WAITING 在【下游调用】,队列【几千】;
2. **排查**:监控定位 active=max、queue 持续不降 → 下游【核心/渠道】变慢导致任务持有线程时间变长;
3. **根因**:池没有按依赖隔离(和别的业务共用)、无超时/超时过长、无队列水位告警;
4. **修复**:按依赖拆池(舱壁)、下游调用强制超时、CallerRuns 背压、补四项监控;
5. **加固**:容量压测把"下游 RT 翻 3 倍"作为固定故障场景,预案进演练。

> 没有真实事故不要编,可以说"在线上压测/预发演练中发现过该风险并提前治理",但简历写了"排查实战"就必须准备至少一个真事。

## B3. 怎么保证一段"查询 + 计算 + 更新"代码的线程安全?

**标准答法**:先问清楚**原子性边界和数据在哪**:

- 单 JVM、内存数据:加锁或 CAS;
- 数据库数据:**优先数据库层解决**——`UPDATE t SET val=val+? WHERE id=? AND version=?`(一条语句原子),不要"查出来在 Java 里加完再写回";
- 跨服务/跨库:状态机 + 唯一约束 + 消息补偿,对账兜底。

**挂项目**:缴费回调"查单 → 判定 → 落账"绝不做成 read-modify-write,而是唯一索引 + 条件更新一步到位。

## B4. 三个线程轮流打印 ABC(编码题)

**标准答法**:至少会一种——ReentrantLock + 三个 Condition 唤醒下一个;或 Semaphore(许可 1/0/0 轮转);或 synchronized + wait/notifyAll + state 取模。
**追问点**:为什么用 notifyAll 不用 notify(notify 可能唤醒错条件的线程导致假死);线程怎么优雅停止(中断标志位、响应 InterruptedException)。

## B5. 异步任务里怎么传 traceId 和用户上下文?

**标准答法**:线程池包装 TaskDecorator/RunnableWrapper,提交时捕获 MDC + 上下文,run 前 set、finally clear;跨 MQ:在消息 Header 放 traceId,消费端恢复 MDC;TTL 用于线程池复用。
**挂项目**:全链路 traceId:Gateway → Feign(RequestInterceptor)→ MQ Header → 日志(SkyWalking 也可,讲成互补:基础设施走 SkyWalking,业务字段自己透传)。

# 第三部分:JVM 攻防

## C1. JVM 运行时数据区讲一下,哪些线程私有?

**标准答法**:

- **线程私有**:程序计数器(当前字节码行号,唯一不会 OOM 的区)、虚拟机栈(栈帧:局部变量表/操作数栈/动态链接/返回地址)、本地方法栈;
- **线程共享**:堆(对象主体)、方法区(JDK8 后是 Metaspace,在**本地内存**,存类元信息、常量池、静态变量)。

**连环追问**:

- Q:栈上会存对象吗?
  - A:理论上可能(逃逸分析 + 标量替换,对象拆成基本类型放栈上),但 HotSpot 没有真正"栈上分配对象",是标量替换的效果——答到这程度即可,别说死。
- Q:JDK8 为什么把永久代换成 Metaspace?
  - A:永久代大小固定、容易溢出(动态代理/CGLib 生成类多了就 PermGen OOM);移到本地内存受机器内存约束,还便于 JRockit 合并。
- Q:对象创建过程?
  - A:类加载检查 → 分配内存(指针碰撞/空闲列表,TLAB 优先)→ 零值初始化 → 设对象头(Mark Word/类型指针)→ 执行 `<init>`。
- Q:对象怎么访问?
  - A:句柄(引用稳定,GC 移动对象只改句柄)vs 直接指针(HotSpot 用,快一次寻址)。

## C2. 怎么判断对象可以回收?什么是 GC Roots?

**标准答法**:早期引用计数法(解决不了循环引用)→ 现在**可达性分析**:从 GC Roots 出发不可达的对象可回收。GC Roots 包括:虚拟机栈中引用的对象(局部变量)、静态变量、常量、本地方法栈 JNI 引用、活跃线程等。

**连环追问**:四种引用?
- 强引用(打死不回收)、软引用(内存不足才回收,适合缓存)、弱引用(下次 GC 必回收,ThreadLocalMap 的 key)、虚引用(只为回收时收到通知,管理堆外内存 DirectByteBuffer)。

**追问**:可达就一定不回收吗?——不可达的对象若重写了 finalize 且未被执行过,会进 F-Queue 等最后一次自救(重新被引用),但 finalize 早已不推荐(执行不保证、成本高),JDK9 弃用。

## C3. 垃圾收集算法与常用收集器

**标准答法**:

- 基础算法:标记-清除(碎片)、标记-整理(无碎片但移动成本)、复制(空间换时间,新生代用);
- 分代:朝生夕灭 → 新生代用复制(Eden:S0:S1=8:1:1);老年代存活率高 → 标记整理/清除;
- 收集器演进:Serial/Parallel(吞吐量优先)→ CMS(低停顿)→ G1(可预测停顿,Region)→ ZGC/Shenandoah(亚毫秒级)。

**连环追问**:

- Q:对象什么时候进老年代?
  - A:大对象(超 PretenureSizeThreshold 直接进,避免在新生代来回复制)、年龄到阈值(默认 15)、动态年龄判定(Survivor 中同龄对象总和超 Survivor 一半)、Minor GC 后 Survivor 放不下、分配担保。
- Q:Minor GC / Major GC / Full GC 区别?
  - A:Minor 回收新生代;Full 回收新生代+老年代+方法区,停顿最长,要尽量避免;Major 这个词含义不统一,面试中确认口径。
- Q:什么时候触发 Full GC?
  - A:老年代空间不足、Metaspace 不足、空间分配担保失败、显式 System.gc()(不保证执行)、并发失败(concurrent mode failure,CMS)。

## C4. CMS 和 G1 详细对比(高频)

**标准答法**:

| 维度 | CMS | G1 |
|---|---|---|
| 布局 | 物理分代(新/老年代) | Region 化,逻辑分代,每个 Region 可动态角色 |
| 算法 | 标记-清除(有碎片) | 复制为主(Region 间拷贝,基本无碎片) |
| 停顿模型 | 低停顿,但不可预测 | **可设 -XX:MaxGCPauseMillis,按收益选回收集合** |
| 阶段 | 初始标记/并发标记/重新标记/并发清除 | 类似并发标记 + 筛选回收(Remembered Set 跟踪跨 Region 引用) |
| 坑 | concurrent mode failure → Serial Old 兜底(长停顿)、浮动垃圾 | 小堆 Region 管理开销大,大堆(6G+)优势明显 |

**连环追问**:

- Q:你们用的哪个?为什么?
  - A:按真实情况。推荐答法:服务堆 4~8G、JDK8/11 普遍用 G1,目标停顿 200ms 内;CMS 在 JDK9 废弃、JDK14 移除——体现版本认知。
- Q:G1 还有 Full GC 正常吗?
  - A:不正常。G1 正常只有 Young GC/Mixed GC,退化为 Full GC(单线程 Serial GC 做兜底)说明调优失败:巨型对象太多、IHOP 触发太晚、堆太小。
- Q:ZGC 了解吗?
  - A:染色指针 + 读屏障,停顿与堆大小无关(亚毫秒),适合超大堆低延迟;JDK15 生产可用,JDK17+ 分代 ZGC。我们规模暂不需要,但关注。

## C5. 类加载与双亲委派

**标准答法**:加载 → 验证 → 准备(静态变量赋零值)→ 解析 → 初始化(静态块、赋初值)→ 使用 → 卸载。类加载器层级:Bootstrap(rt.jar)→ Ext/Platform → App;双亲委派:收到加载请求先委托父加载器,父加载不了自己才加载——防止核心类被篡改、避免重复加载。

**连环追问**:

- Q:哪些场景打破双亲委派?
  - A:JDBC/SPI(核心类接口在 Bootstrap,实现在 classpath,用线程上下文类加载器反向加载)、Tomcat(每个 webapp 独立 ClassLoader 先自己加载,实现应用隔离)、热部署(OSGi/自定义)。
- Q:一个类什么时候初始化?
  - A:new、静态方法调用、反射、初始化子类先初始化父类、main 类;被动引用(通过子类访问父类静态字段、定义数组、final 常量)不初始化。

## C6. 线上 CPU 100% 怎么排查?(命令题,必须滚瓜烂熟)

**标准答法(Linux 五板斧)**:

1. `top` 找 CPU 最高的 Java 进程 PID;
2. `top -Hp <pid>` 找进程内 CPU 最高的**线程** TID;
3. `printf '%x\n' <tid>` 转十六进制;
4. `jstack <pid>` 导出线程栈,搜 nid=0x... 的线程,看它在执行哪段代码;
5. 常见根因:死循环、正则回溯、频繁 Full GC(GC 线程吃 CPU,此时要转 GC 排查路径)。

**连环追问**:Windows 怎么办?——任务管理器/Process Explorer 找线程,或直接 Arthas;`thread -n 3` 一条命令列出最忙 3 个线程的栈。Arthas 还能 `watch` 看方法入参返回值、`trace` 看耗时分布、`profiler` 生成火焰图——**工具答到 Arthas 是加分项**。

## C7. 线上 OOM 怎么排查?OOM 有哪几种?

**标准答法**:先分清是哪种 OOM,方向完全不同:

| 类型 | 含义 | 典型根因 |
|---|---|---|
| Java heap space | 堆放不下 | 内存泄漏(集合只进不出、静态缓存、ThreadLocal 未 remove)、一次性加载大数据 |
| GC overhead limit | GC 花了 98% 时间回收不到 2% | 同上,堆已经快满的前兆 |
| Metaspace / PermGen | 类元数据 | CGLib 动态生成类、类加载器泄漏 |
| Direct buffer memory | 堆外内存 | Netty/ByteBuffer 未释放、-XX:MaxDirectMemorySize 太小 |
| unable to create new native thread | 线程数达系统上限 | 线程池无界创建;要查 ulimit -u |
| StackOverflowError | 栈深度超限 | 递归无出口、循环依赖的方法调用 |

**排查套路**:`-XX:+HeapDumpOnOutOfMemoryError` 必须提前配(出事时自动 dump)→ MAT/jprofiler 分析 dominator 树找最大占用 → 看 GC Roots 引用链定位谁持有;临时手段是加内存,但**加内存是止血不是治病**。

**挂项目(核心锚点)**:批量代扣早期如果一次性 select 全量代扣单(几百万行)到内存就会 heap OOM;改造:XXL-Job 分片 + 游标分页(`id > lastId limit n`),每批几百条处理完即回收;批大小按压测定;同时 dump 开关常备。

**连环追问**:内存泄漏和内存溢出区别?——泄漏是该回收的被持有(因),溢出是装不下了(果);泄漏积累必然溢出。怎么发现泄漏?——堆使用量单调上涨、Full GC 后老年代不回落。

## C8. Full GC 频繁怎么排查?

**标准答法(按路径走)**:

1. 先看 GC 日志/监控:Full GC 频率、每次老年代回收前后大小——**回收后老年代仍很高 = 有对象活着不走**(泄漏/缓存);回收后很低但很快又满 = 分配速率过大(大对象/年轻代太小);
2. `jstat -gcutil <pid> 1s` 看各代涨速和 GC 次数;
3. `jmap -histo:live <pid>`(谨慎,会触发 Full GC)或 dump 后 MAT 看对象排行;
4. 常见根因:大对象直接进老年代、缓存无淘汰、内存泄漏、Metaspace 动态类过多、显式 System.gc()、JVM 参数不合理;
5. 修复:根因修复 + 参数调整(如 G1 区域大小、年轻代比例)。

**连环追问**:

- Q:频繁 Minor GC 但对象很快进老年代?
  - A:看年龄分布,可能 Survivor 太小、动态年龄晋升;调大 Survivor、控制大对象。
- Q:接口偶发卡顿怎么和 GC 关联?
  - A:拿时间点对 GC 日志(停顿发生时刻)和慢请求时刻;G1 可用安全点日志(jvm 里停顿不只 GC,还有安全点)。

## C9. 你们 JVM 参数怎么配的?

**标准答法(给真实模板,数字按机器调)**:

```
-Xms4g -Xmx4g                    # 堆固定,避免动态扩缩
-XX:+UseG1GC -XX:MaxGCPauseMillis=200
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump/
-Xlog:gc*:file=/data/log/gc.log  # JDK9+ 统一日志(JDK8 用 -XX:+PrintGCDetails)
-XX:+AlwaysPreTouch              # 启动时摸一遍内存页,避免运行时缺页
```

**追问**:Xmx 和 Xms 为什么设一样?——运行时扩堆会影响停顿和容器限额判断,生产固定;容器里还要注意 `-XX:MaxRAMPercentage`,K8s limit 与堆外内存(Metaspace + Direct + 线程栈 + JVM 本身)要留余量,否则容器 OOMKilled 而不是堆 OOM。

## C10. 项目实战:批量代扣为什么要游标分页?(高频挂项目题)

**标准答法**:

1. `LIMIT 1000000, 500` 深分页要扫描前 100 万行再丢弃,越往后越慢,且百万对象加载有 OOM 风险;
2. 游标 `WHERE id > #{lastId} ORDER BY id LIMIT 500`,走主键索引,每页成本恒定;
3. 配合 XXL-Job 分片:每个实例只处理 `id % 分片数 = 自己序号` 的范围,水平扩展;
4. 批大小权衡:太小 → 网络/调度次数多;太大 → 单批耗时长、失败重试成本高;压测定值;
5. 幂等兜底:任务可能重跑(执行器宕机转移),每批处理必须幂等(状态机条件更新)。

**追问**:数据中间有删除导致漏数据?——状态驱动比 id 驱动更稳(按待处理状态扫描并加更新时间窗口),具体按真实实现答,讲出取舍。

# 第四部分:死亡压力连环题(模拟高压追问)

> 这部分按真实面试节奏设计:面试官从一个点连续追 5~7 层,每层答不好都会降档。每题给"追问链"和"保命答法"。

## D1. "你们支付防重是怎么做的?"——一条链追到死

```
Q1 支付回调重复了怎么办?
 → 渠道流水号唯一索引 + Redisson 锁 + 缴费单状态机三重幂等
Q2 锁和唯一索引,谁保证正确性?
 → 唯一索引 + 状态条件更新;锁只是减少无效竞争,锁失效(主从切换)钱也不会错
Q3 那为什么还要加锁?
 → 用户网络重试时快速失败/快速返回,减少唯一键冲突异常和下游核心压力;是优化不是正确性
Q4 状态机怎么实现的?
 → UPDATE ... WHERE id=? AND status='待支付';影响行数 0 就查回当前状态返回,不抛错让用户再付
Q5 两台机器同时收到回调呢?
 → 行锁保证两个 UPDATE 串行,一个 1 行一个 0 行;Redisson 先挡一道
Q6 钱收了但入账核心失败呢?
 → 本地消息表 + MQ 重试 + XXL 主动查单 + 日终三方对账,四层兜底
Q7 这些都失效了呢?
 → 对账必然发现长短款,差异工单 + 人工应急通道;资金在渠道/平台账上不会凭空消失
```

**保命要点**:被追到极端时不要嘴硬,落到"对账兜底 + 资金不会丢 + 有应急通道"。

## D2. "线程池参数你怎么定的?现在线上是多少?"

- 错误答法:"核心 10、最大 20"(背的,一问依据就死);
- 正确姿势:报出真实数字 + **推导过程**(任务类型 IO 密集 → 初始按 N×(1+W/C)→ 压测调整:目标 CPU 70%、P99 RT 达标、队列无持续堆积)+ 配套(拒绝策略、监控指标、告警阈值、大促调过几次)。
- 追"凭什么是 70% 不是 90%":留 buffer 给突发和 GC,容量规划按水位线不是按打满。
- 追"利特尔法则知道吗":并发数 = 到达率 × 平均处理时间(L = λ × W),用它校验线程池/排队容量是否合理——答得出直接拉满。

## D3. "线上突然大面积超时,你怎么定位?"——综合排查链

```
1. 看监控黄金四指标:流量突增?错误率?RT?饱和度(CPU/内存/线程池)?
2. RT 涨但 CPU 不高 → 大概率在等:下游变慢(DB/Redis/HTTP)、GC 停顿、锁竞争、网络
3. jstack 抓 3 次间隔几秒 → 看大量线程卡在同一个调用 → 锁定下游或锁
4. 是 GC 停顿 → 转 GC 日志路径;是下游慢 SQL → slow log/执行计划
5. 止血优先:降级/切流/扩容,再定位根因
6. 事后:复盘 5why + action 带人和时间
```

**评分点**:先止血再查因、有命令、有监控、有顺序,而不是"看日志"(初级答案)。

## D4. "synchronized 和 ReentrantLock 性能现在还有差距吗?"

- JDK6 后 synchronized 优化后两者吞吐接近,**选型不再以性能为主要依据**,以功能需求(公平/可中断/超时/多条件)和代码安全(自动释放)为准。
- 追"什么叫锁消除/锁粗化":逃逸分析证明对象不逃逸 → 加锁无意义直接去掉;循环内反复加锁 → 粗化到循环外。
- 追"String.intern() 当锁有什么坑":常量池全局共享,不同业务锁同一字符串互相阻塞;锁对象要用私有 final Object。

## D5. "ThreadLocal 你们用在用户上下文,线程池异步任务里用户信息丢了,怎么回事?"

- 线程池线程不是请求线程,ThreadLocal 天然不传递;InheritableThreadLocal 只在线程创建时拷一次,池化线程复用导致拿到的是旧任务的上下文(既会丢又会串)。
- 解法:Runnable 包装器提交时快照、执行时 set + finally remove;或 TTL。
- 追"不清理会怎样":脏数据 + 内存泄漏双杀。这题答完整 = 并发基础 + 工程意识同时过关。

## D6. "给你一个 100 万数据的导出任务,OOM 了怎么改?"

```
错误:一次性查 100 万到 List → 拼装 Excel → OOM
改法:
1. 查询:游标/keyset 分页或 MyBatis 流式查询(Cursor),按批拉取
2. 写入:SXSSFWorkbook 流式写盘(只保留窗口行),或直接写 CSV
3. 结构:任务异步化(提交导出 → MQ/XXL 执行 → 文件传 OSS → 通知下载),不占 Web 线程
4. 资源:限流(同时导出数)、文件过期清理、大导出走独立线程池
```

挂你的断点平台/运营后台场景即可,思路同批量代扣。

## D7. 压力下的几个一句话送命题

| 题目 | 保命答案要点 |
|---|---|
| wait 和 sleep 区别? | wait 来自 Object、释放锁、要在同步块里被 notify;sleep 来自 Thread、不释放锁;wait/notify 必须持有同一 monitor |
| 死锁怎么排查? | jstack 会直接打印 found one deadlock;jconsole/Arthas;预防:固定加锁顺序、超时 tryLock |
| 为什么线程栈里大量 BLOCKED? | 等 synchronized 监视器锁;等 ReentrantLock 显示 WAITING(parking)——jstack 状态不同,别搞混 |
| parallelStream 能用在 Web 项目吗? | 慎用:共享 commonPool,阻塞 IO 拖垮全局;要并行就用自定义池的 CompletableFuture |
| 异步线程里异常不见了? | submit 的异常在 Future 里;要 afterExecute 统一记或显式 handle;池外无感知=事故 |
| JDK 版本?用过新特性吗? | 按真实:17 的 record/sealed/模式匹配/虚拟线程(了解:轻量线程适合大量阻塞 IO,不是银弹,pin 住载体线程等坑) |
