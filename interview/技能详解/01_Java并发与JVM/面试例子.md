一、JVM 务实场景题（5 题）
题 1
题干：线上服务白天正常，每到晚上 20 点之后，接口 RT 间歇性抖动，监控看 GC 次数变多，没有 OOM。你第一步看哪些指标？会用哪些工具？怎么判断根源是年轻区压力、老年代碎片，还是堆外直接内存？
考察目标：GC 指标链路、工具选型、区分不同卡顿来源，不背收集器理论
参考答案
先看监控大盘核心指标：GC 停顿时间、Young GC 频率、晋升速率、老年代占用变化、堆内存走势、CPU。
工具优先 Arthas，其次 jstat、GC 日志；必要时 jmap、jhat。
判断逻辑：
如果 Young GC 频繁、每次回收后年轻区下降明显，晋升不多 → 新生代分配压力大，短对象疯狂创建；
Young GC 不多，但 Full GC / Concurrent GC 变多、老年代涨得快、回收后下降有限 → 老年代碎片或者对象泄漏；
堆内存占用稳定，但是进程总内存持续上涨、GC 日志看不到异常 → 优先怀疑堆外内存，Netty、ByteBuffer、第三方 native 库是高发区。
拿到现场优先保留 GC 日志，不要直接重启。
题 2
题干：某个接口单次请求会加载一批数据放到 List，压测的时候 Young GC 暴涨，业务上又必须拿到这批数据。你有哪些优化方向，各自有什么代价？
考察目标：优先代码优化，而不是上来调 JVM 参数；理解对象生命周期
参考答案
优先代码层面：
分页 / 游标分批返回，不要一次性全加载；代价：接口要改造，前端 / 调用方适配；
流式读取，边读边处理，不把全部数据放进 List；代价：处理逻辑要改成流式，不能依赖随机访问；
对象复用、对象池，避免频繁创建销毁临时对象；代价：实现复杂，容易出现对象状态污染，维护成本上升；
把大集合拆成小集合，处理完及时释放引用，帮助 GC 回收；
最后才考虑调整新生代大小。调大新生代能缓解，但会抬高单次 YGC 停顿，机器内存占用更高，属于兜底方案，不是首选。
题 3
题干：线上突然 OOM，报错 java.lang.OutOfMemoryError: Java heap space，拿到告警，你的操作顺序是什么？什么时候抓堆快照，什么时候不能直接重启？
考察目标：故障处置顺序，理解现场价值，知道 dump 的副作用
参考答案
先看告警面板：QPS 有没有突增、是不是流量暴涨，先区分是正常流量还是泄漏；
如果业务允许短暂停服 / 流量不大：优先抓堆快照（jmap 或者 Arthas），保留现场；
如果是核心链路、流量很大，dump 会 STW，加剧业务雪崩：优先先限流、降级，保障业务可用，再找低峰期抓快照；
不要上来直接重启：重启会清空堆，丢失泄漏现场，后面很难定位；
拿到快照之后，重点看：最大的对象、是谁持有这个引用、引用链，判断是瞬时大对象、内存泄漏，还是资源上限不够。
题 4
题干：我们准备把 G1 换成 ZGC，你会先评估什么？哪些业务场景下，换 ZGC 收益很小甚至有坑？
考察目标：理解收集器取舍，破除 ZGC 万能的误区
参考答案
评估清单：
JDK 版本，ZGC 不同版本稳定性、特性差异；
现有服务的痛点：是不是对 STW 停顿敏感；
内存开销：ZGC 标记有额外内存开销，相同堆大小，ZGC 会占用更多内存；
依赖：有没有 native 库、JNI、特殊 Agent，兼容性风险；
压测验证：相同流量下，RT、CPU、内存、GC 停顿对比。
不适合换 ZGC 的场景：
业务本身分配速率很低、GC 停顿本来就很短，对延迟不敏感；资源很紧，机器内存余量很小；老版本 JDKZGC 不稳定。这种场景换了收益几乎没有，还引入新风险。
题 5
题干：有同事说：这个服务直接把 Xmx 拉满，给最大堆，GC 就好了。你同意吗？你会怎么跟他解释？
考察目标：纠正 “堆越大越好”，理解大堆长尾风险
参考答案
不同意。堆不是越大越好。
堆大，能容纳更多对象，减少 GC 触发频率；但是一旦触发 GC，需要扫描回收的对象更多，最坏停顿时间会被放大，长尾 RT 风险上升。
堆大小要匹配业务的分配速率、对象晋升模型，同时给系统、堆外内存、其他进程预留空间。
比如一台 16G 机器，全给 Java 堆，Netty 堆外内存、系统缓冲区没空间，很容易进程 OOM。
核心思路：够用即可，配合监控 GC 停顿，而不是直接拉满。
二、并发务实场景题（6 题）
题 1
题干：下单接口并发进来出现超卖。你的排查思路是什么？数据库方案、Redis 分布式锁方案各自适用场景和坑点？什么时候干脆不用锁？
考察目标：并发安全选型，知道锁有成本，不是所有场景都要加锁
参考答案
先确认：超卖是并发竞争导致，先看业务一致性要求。
数据库方案：
乐观锁（版本号 / 条件更新），update stock set num=num-1 where id=xx and num>0。优点：简单，不需要额外组件；缺点：高并发下大量失败，重试多，数据库压力大。适合中等并发、强一致场景。
悲观锁 for update：锁粒度大，容易堵，并发一高就卡死，尽量少用。
Redis 分布式锁：
优点：性能高，适合高并发；坑点：锁超时、任务执行超过锁时长、主从切换丢锁、续约失败。必须做好防丢、自动续期，释放锁用 lua 脚本。
不用锁的场景：业务允许弱一致，比如非核心库存、统计类，最终一致即可，或者流量极低，冲突概率几乎为 0。
优先顺序：数据库条件更新 > Redis 锁 > 悲观锁。
题 2
题干：线程池处理异步任务，上线一段时间，任务大量堆积，接口超时。你怎么定位？核心参数怎么评估，有哪些容易踩的坑？
考察目标：线程池监控、队列、拒绝策略，理解无界队列的灾难
参考答案
定位顺序：
看监控：活跃线程数、队列长度、任务平均耗时、拒绝数量；
判断原因：任务处理太慢（下游慢）、线程数不够、队列阻塞；
看拒绝策略：Abort 会抛异常，Discard 直接丢任务，业务感知不一样。
参数评估：
CPU 密集：核心线程≈CPU 核心数；IO 密集：可以放大，看下游 RT；
严禁无界队列，流量上来队列无限膨胀，直接 OOM。
坑：很多人直接 Executors.newCachedThreadPool/newFixedThreadPool，自带无界队列，线上大忌；
必须埋点监控队列堆积，队列长度告警，提前发现。
题 3
题干：同一个定时任务多实例部署，重复执行。你有哪些方案？各自缺点？
考察目标：分布式调度并发控制，高频业务问题
参考答案
方案 1：分布式锁（Redis/ZK），抢到锁才执行；缺点：锁过期时间不好设，如果任务执行超过锁时长，依然会重复跑；需要续约。
方案 2：调度中心（XXL-Job、Airflow），由中心负责分发，只分配给一个实例；缺点：引入中间件，运维成本上升。
方案 3：数据库执行记录表，任务开始前插入唯一记录，唯一索引防重复；缺点：数据库压力大，时间窗口要做好，清理旧数据。
没有完美方案，核心看集群规模、任务重要性。简单小服务优先 Redis 锁；核心定时任务优先分布式调度平台。
题 4
题干：缓存更新逻辑：先删缓存，再更新 DB。高并发下会出现什么问题？怎么改？有没有完美方案？
考察目标：读写竞争，理解缓存一致性的取舍
参考答案
问题：线程 A 删缓存，还没更新 DB；线程 B 进来读到旧 DB，把旧数据写回缓存 → 缓存永久脏数据。
优化：延时双删。先删缓存，更新 DB，等待一段时间，再删一次缓存。
但是它不是完美方案：等待时间不好控制，极端场景依然有概率脏数据；而且会多一次缓存操作。
强一致性场景，不能依赖缓存，直接读库；缓存本身就是为性能牺牲一致性的组件。
题 5
题干：MQ 消费服务，消息重复投递是常态，你怎么保证业务幂等？幂等 key 怎么选？
考察目标：分布式并发最真实的问题，比锁更常见
参考答案
幂等核心：同一个业务标识，只执行一次。
幂等 key 优先选业务唯一标识：订单号、支付流水号，不要用 MQ msgId（重发时 msgId 可能变）。
实现方案：
数据库唯一索引：插入成功才执行，冲突直接跳过；适合简单新增；
状态机：根据业务状态流转，已经处理过的直接 return；适合订单、支付；
Redis 记录已处理标识，设置过期时间；适合高并发，但是要考虑 Redis 宕机丢失。
优先数据库方案，可靠性最高。天然幂等操作（查询）不用额外处理。
题 6
题干：一段代码加 synchronized 之后，RT 明显涨了。你怎么判断是锁竞争激烈，还是锁本身太重？有哪些优化思路？
考察目标：锁优化先定位，而不是上来就换锁
参考答案
先定位：看锁等待时间、锁持有时间。
持有时间很长：不是竞争大，是锁里面逻辑慢，锁范围太大；优先缩小锁范围，把无关代码移出锁；
等待时间很长，持有很短：大量线程抢同一把锁，竞争激烈；
优化思路：
缩小锁粒度；
分段锁，把一把大锁拆成多把；
读写分离，读多写少换成 ReentrantReadWriteLock；
评估是否允许弱一致性，用 CAS 无锁方案；
如果写非常频繁，读写锁也会降级，这时候无锁收益有限。
三、综合架构题（3 题）
题 7
题干：线上同时出现 CPU 高、GC 频繁、线程大量 WAITING。你的排查顺序是什么？怎么区分是 GC 导致 CPU 高，还是业务死循环导致 CPU 高？
考察目标：综合故障排查，区分 GC 和业务代码问题
参考答案
先看 GC 指标：GC 占 CPU 比例，如果 GC 线程占用大量 CPU，就是 GC 压力；
拿线程栈：jstack，看 RUNNABLE 线程，有没有死循环、不停创建对象的代码；WAITING 一般是锁等待、阻塞在下游；
区分：业务死循环 CPU 高，GC 频率不一定暴涨；GC 压力高，GC 线程 CPU 占比很高，伴随大量对象分配回收。
顺序：先看 GC 大盘 → 线程栈 → 堆快照 → 链路追踪看下游耗时。
题 8
题干：想做本地缓存，多线程读写。你会用什么？ConcurrentHashMap 有什么它解决不了的并发问题？
考察目标：对容器并发边界的理解
参考答案
基础多线程读写优先 ConcurrentHashMap。
但是它只能保证单个节点原子性，复合操作不原子：比如先 get，判断不存在再 put，这两步中间会被其他线程插入，依然有竞态；
还有缓存过期、缓存淘汰、批量读写、缓存击穿，这些都不是 CHM 本身能解决的。
场景简单：CHM；需要过期、淘汰，用 Caffeine；强一致复合操作，还是要加锁。
题 9
题干：很多人说尽量避免锁，用无锁方案。什么时候你不会优先上无锁？
考察目标：取舍思维，不盲目追无锁
参考答案
写占比很高、CAS 失败率极高，大量自旋，CPU 飙升；
业务逻辑复杂，不是简单计数，复合状态变更；无锁代码极难写，容易藏 bug，维护成本高；
业务对可读性、可维护性要求高，团队水平参差不齐；
并发量本身不大，锁竞争很低，加锁开销很小，无锁收益几乎看不到。
无锁适合简单的计数、标记，读多写少的场景。复杂业务，清晰的锁方案，往往比炫技无锁更稳妥。
