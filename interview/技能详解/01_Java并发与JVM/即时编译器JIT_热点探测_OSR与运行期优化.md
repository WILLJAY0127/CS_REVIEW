# 0. 问题场景：压测为什么要"预热"？

压测时有一条铁律："先空跑一遍，把 JVM 预热了再统计数据。"

问题是：**代码一行没改，为什么第二遍跑得比第一遍快？**

答案在即时编译器——第一遍执行走的是**解释执行**（逐句翻译字节码，慢）；某段代码被执行到一定次数后，JVM 把它**编译成本地机器码并缓存**，之后直接跑机器码（快）。所谓"预热"，预热的就是这个过程。

不预热直接测，测到的是解释器的速度，不是 JVM 的真实性能；用手写计时循环做微基准，还可能被 JIT 把代码"优化没了"——这就是微基准必须用 JMH 的根本原因。

## 8+1 总览卡

1. **本质**：JIT（Just-In-Time Compiler）= 运行期把热点字节码编译成机器码并缓存的组件，与解释器协同构成 HotSpot 的"混合模式"（`-Xmixed`，默认）。
2. **为什么需要它**：纯解释执行太慢；纯 AOT 预编译（C/C++）失去跨平台性，且用不上运行时信息。JIT = "跨平台的启动能力" + "接近本地的峰值速度"。
3. **编译粒度**：以**方法**为单位（体量适中、边界清晰、优化上下文够用）；OSR 的编译对象是"方法 + 指定循环入口"，产物仍覆盖整个方法体。
4. **热点探测**：方法调用计数器 + 回边计数器，超阈值分别触发**标准编译**与 **OSR 编译**；计数器有**热度衰减**（半衰期约 30 秒），防止冷代码永久占用编译资源。
5. **分层编译**（JDK 8 起默认开启）：级别 0 解释 → 1/2/3 为 C1 各档 → 4 为 C2；典型路径 0 → 3 → 4，兼顾启动速度与峰值性能。
6. **C1 vs C2**：C1 编译快、优化浅（守"响应时间"）；C2 编译慢、优化深（守"峰值性能"）；JDK 10 起可选纯 Java 写的 Graal（JEP 317）。
7. **王牌优化**：方法内联（优化之王）、逃逸分析 → 锁消除 / 标量替换、公共子表达式消除、循环展开、去优化。深度优化本质都是**投机**，靠运行时 profiling 情报下注，猜错就回退解释器。
8. **核心因果链**：解释器兜底 → 编译可在后台线程异步进行（`C2 CompilerThread`）→ 编译不占用用户响应时间、时间预算宽裕 → 敢做烧时间的深度优化 → 本地代码质量更高。

**一句话**：解释器保证"能跑起来"，JIT 负责"跑得快"——它赌"少数代码占多数执行时间"（二八定律），把编译资源全押在热点上。HotSpot 这个名字本身就是"热点"的意思。

# 一、三种执行策略：翻译模型类比

| 策略 | 类比 | 优点 | 缺点 |
|---|---|---|---|
| **AOT**（C/C++） | 整本书出版前全部译成中文 | 读者读得飞快 | 只服务中文读者（失去跨平台）；出版后无法根据"读者实际怎么读"调整 |
| **解释器** | 同声传译，逐句翻译 | 任何读者立刻能听（启动快、跨平台） | 每句都现场翻译，每次都慢 |
| **JIT** | 传译员把客人反复要求的话写成便利贴贴在墙上 | 热点内容直接指墙（接近本地速度） | 便利贴需要时间积累（预热成本） |

**关键洞察——JIT 有一项 AOT 永远做不到的超能力：基于运行时真实数据做优化。**

- 它知道哪个分支真的走得最多（分支预测）；
- 它知道某个虚方法在运行期是否只有一个实现（类层次分析，于是敢做激进内联）；
- 假设失效时，还能撕掉便利贴重来（去优化）。

这就是为什么 JIT 的峰值性能理论上可以**反超**静态编译器。静态编译器面对的是"死"的程序文本，JIT 面对的是"活"的执行剖面（profile）。

# 二、解释器与编译器的协同：双工作台流水线

套用"双工作台流水线模型"：

- **解释器工作台**：订单一来立刻开工（启动快），但每件都手工逐件加工（慢）；
- **编译器工作台**：收到"这个零件订单量巨大"的通知（热点探测）后，花时间做一套模具（编译耗时），之后模具冲压（机器码执行，飞快）；
- **协作方式**：模具做好之前解释器顶上；做好之后订单切到冲压机。编译在后台线程**异步**进行，业务线程不会被编译阻塞。

两个极端都不可取，对比即可反推出混合模式的必要性：

- **纯解释执行**：第一行代码立刻能跑（响应时间最优），但每条字节码都现场翻译，执行性能最差；
- **纯预编译**：跑得飞快（性能最优），但必须等编译完才能启动（响应最差），且永远用不上运行时信息。

混合模式的本质分工：**解释器负责"立刻能跑"，编译器负责"越跑越快"。**

# 三、热点探测：两个计数器与两种编译

HotSpot 不采样、不猜测，用计数器精确找出热点：

| 计数器 | 计数对象 | 超阈值后触发 |
|---|---|---|
| **方法调用计数器** | 方法每被调用一次 +1 | **标准即时编译** |
| **回边计数器** | 循环体往回跳一次 +1 | **OSR（栈上替换）编译** |

- 非分层模式下，Server 端方法调用计数器默认阈值为 10000 次（`-XX:CompileThreshold`）；
- **热度衰减**：计数器值有半衰期（约 30 秒，`-XX:CounterHalfLifeTime`），一段时间没被调用的代码热度减半——防止"历史热度"让冷代码永久占用宝贵的编译资源；
- 编译请求是异步排队的：计数器超阈值只是"提出编译申请"，后台编译线程忙不过来时申请会排队，期间解释器继续执行。

## 两种编译的对比

| | 标准即时编译 | OSR 编译（栈上替换） |
|---|---|---|
| **触发条件** | 方法被**频繁调用**（方法调用计数器超阈值） | 方法内**有效循环次数很多**（回边计数器超阈值） |
| **替换时机** | **下一次**调用该方法时直接执行编译版 | **当下这一次**执行中，循环回跳到入口时切换到编译版 |
| **跑道模型** | 老顾客下次光顾，直接上快车道 | 正在慢道上跑圈的选手，跑到半路直接切进旁边快车道，**不用退回起点重新跑** |

# 四、OSR：人在跑道上，鞋换成钉鞋

OSR 为什么必须存在？看这个场景：

```java
public static void main(String[] args) {
    long sum = 0;
    for (int i = 0; i < 10_000_000; i++) {  // 大循环
        sum += i;
    }
}
```

main 方法一辈子只被调用 **1 次**——按"方法调用次数"探测，它永远是冷代码，这个一千万次的大循环只能解释执行到底。

加上"回边计数器"后，JVM 发现：**方法本身不热，但循环体热得发烫**。于是在栈上把"正在解释执行的方法帧"直接替换成编译版，从下一个循环回跳点开始跑机器码。

**"栈上替换"名字的由来**：被替换的是还留在虚拟机栈上、正在执行中的那个帧——人还在跑道上，鞋已经换成钉鞋了。

# 五、分层编译：5 个级别

JDK 8 起默认开启（`-XX:+TieredCompilation`），不再需要手动选 Client / Server 模式：

| 级别 | 执行方式 | 说明 |
|---|---|---|
| 0 | 解释执行 | 起步阶段，顺带收集基础信息 |
| 1 | C1 编译，无 profiling | 编译最快，给生命周期极短的方法"收尾"用 |
| 2 | C1 编译，少量计数 | 折中档 |
| 3 | C1 编译，完整 profiling | 绝大多数方法的过渡态，为 C2 攒情报 |
| 4 | C2 编译 | 峰值性能终点站 |

典型晋升路径：`0 → 3 → 4`。

- **C1（Client 编译器）**：编译快、优化浅——守"程序响应时间"这一头；
- **C2（Server 编译器）**：编译慢、优化深——守"峰值执行性能"这一头；
- 级别 3 的完整 profiling 就是"解释器 / 低级编译器与高级编译器协同"的具象化：低级层边跑边帮 C2 踩点（分支频率、类型剖面），C2 拿情报做投机优化。

# 六、JIT 王牌优化（面试重点）

## 6.1 方法内联——"优化之王"

把被调方法的方法体直接"抄"进调用点：

```java
private int add(int a, int b) { return a + b; }

int r = add(1, 2) + add(3, 4);
// 内联后等价于：
int r = (1 + 2) + (3 + 4);   // 进一步常量折叠，可能直接编译成 10
```

消除方法调用开销（压栈、传参、跳转）只是表象；**本质是打通优化边界**——不内联，常量传播、死代码消除等后续优化全部跨不过方法边界。这是它被称为"优化之王"的原因：大部分优化都以它为前置条件。

默认规则：普通方法 ≤ 35 字节码才内联（`-XX:MaxInlineSize`），热点方法可放宽到 ≤ 325（`-XX:FreqInlineSize`）。

## 6.2 逃逸分析 → 锁消除 / 标量替换

```java
public String concat(String a, String b) {
    StringBuffer sb = new StringBuffer();  // sb 从不逃出本方法
    sb.append(a).append(b);
    return sb.toString();
    // JIT 分析结论：sb 永远只被当前线程看见
    // → append 内部的 synchronized 全部消除（锁消除 / 同步消除）
    // → sb 对象甚至可能被拆散成基本量直接放栈上（标量替换，GC 压力归零）
}
```

注意：逃逸分析是 JDK 6u23 起默认开启，但它是"分析"而非"承诺"——分析本身消耗编译时间，收益依赖后续优化是否成立。栈上分配在 HotSpot 中并非真的把对象放进栈帧，而是通过标量替换拆散后消解掉对象。

## 6.3 去优化——猜测失败时的回退

JIT 通过类层次分析（CHA）做激进假设："目前整个程序里 `foo()` 只有一个实现类 → 敢内联 + 虚方法转直接调用"。一旦运行期又动态加载了新的实现类、破坏假设，**已编译代码立即作废，回退解释器重新观察、重新编译**（`Uncommon Trap`）。

这完美解释了并发学习中的经典陷阱（与 [实战推演与权威锚点.md](file:///d:/myfile/CS_REVIEW/interview/技能详解/01_Java并发与JVM/实战推演与权威锚点.md) 沙盘一"CPU 100%"的死循环根因互证）：

```java
static boolean stop = false;   // 非 volatile

// 线程A: while (!stop) { }
// 线程B: stop = true;
```

JIT 发现循环体内没有任何代码修改 `stop`，激进优化后把 `!stop` 提升成寄存器常量 `true`（循环提升 /  hoisting），循环永远退出不了。这就是"不写 volatile 导致死循环"在 **JIT 层面的物理解释**；规范层面的依据则是 JMM：无 happens-before 关系时，一个线程的写不保证对另一线程可见。

## 6.4 深度优化为什么存在：一条因果链

```
解释器兜底（编译没好之前业务照样执行）
    ↓
编译可以丢给后台线程异步做（jstack 里的 C2 CompilerThread0/1）
    ↓
编译耗时不再占用用户响应时间 → 编译时间预算宽裕
    ↓
敢用"重分析、高耗时"的深度优化（逃逸分析、CHA、循环展开、向量化……每一项都烧编译时间）
    ↓
输出的本地代码质量更高
```

**反面印证**：C++ 静态编译器面临同样权衡——优化越激进，每次改代码后的重新编译越久、开发效率越差，必须在"编译耗时 vs 优化深度"间妥协。JIT 把这笔时间账甩到了运行期的后台线程，用一个随时可用的解释器解开了静态编译器的时间枷锁。

**正面加分项**：解释器 / C1 在执行时顺便收集运行时情报，C2 拿到情报才敢下注——这是 JIT 峰值性能能反超静态编译器的根本原因。

> 一句话背诵版：**解释器的兜底让 JIT 获得了"花得起时间"的权利，而"花得起时间"正是深度优化得以存在的物质基础。**

# 七、经典段落逐句拆解

> 出处：《深入理解 Java 虚拟机》第 11 章"早期（运行期）优化"。这段是混合模式思想最凝练的总结，下面逐句拆解。

> 原文："HotSpot 虚拟机的热点代码探测能力可以通过执行计数器找出最具有编译价值的代码，然后通知即时编译器以方法为单位进行编译。"

- "以方法为单位"是工程上的甜蜜点：整个程序为单位 → 一次编译太慢、启动等不起；单条语句为单位 → 没有上下文，内联等优化无法施展。方法体量适中、边界清晰、优化上下文充足。

> 原文："如果一个方法被频繁调用，或方法中有效循环次数很多，将会分别触发标准即时编译和栈上替换编译（On-Stack Replacement，OSR）行为。"

- 两种热点、两个计数器、两种编译，一一对应（见[第三节](#三热点探测两个计数器与两种编译)表格）：
  - 频繁调用 → 方法调用计数器 → 标准编译（下次调用生效）；
  - 循环次数多 → 回边计数器 → OSR（本次执行中途切换）。

> 原文："通过编译器与解释器恰当地协同工作，可以在最优化的程序响应时间与最佳执行性能中取得平衡。"

- 响应时间与峰值性能是天平两端：解释器保启动响应，编译器保长期性能，分层编译是这套思想在 JDK 8+ 的工业化实现。

> 原文："而且无须等待本地代码输出才能执行程序，即时编译的时间压力也相对减小，这样有助于引入更复杂的代码优化技术，输出质量更高的本地代码。"

- 含金量最高的一句，即 [6.4 的因果链](#64-深度优化为什么存在一条因果链)。读这段老文字时可以直接映射：**"编译器与解释器协同"在今天的实现就是 Tiered Compilation（0 → 3 → 4）**。

# 八、实操：亲眼看见 JIT 工作

```bash
# 1. 看哪些方法被编译、编译到哪一级
java -XX:+PrintCompilation MyApp
# 输出示例：
#   127   85       4       java.lang.String::length (6 bytes)
#    ↑毫秒时间戳  ↑编译级别(4=C2)  ↑方法              ↑字节码大小

# 2. 看内联决策（为什么这个方法没被内联，会直接打印原因）
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining MyApp

# 3. 对照实验：强制纯解释执行，通常比混合模式慢一个数量级
java -Xint MyApp     # 纯解释
java -Xmixed MyApp   # 混合模式（默认）
```

- `jstack <pid>` 的线程列表里能看到 `C2 CompilerThread0` —— 印证编译是后台异步线程做的；
- 在 [实战推演与权威锚点.md](file:///d:/myfile/CS_REVIEW/interview/技能详解/01_Java并发与JVM/实战推演与权威锚点.md) 沙盘一中：`C1/C2 CompilerThread` 短时 CPU 高是正常 JIT 现象（启动预热期），**持续**高才需要另查（代码热点反复失效、频繁去优化重编译等）；
- 微基准必须用 **JMH**，`@Warmup` 注解控制预热轮次，本质就是等分层编译晋升到级别 4 后再计时。

**版本注记（2025 视角）**：

- JDK 8：分层编译默认开启，是今天绝大多数线上 JVM 的行为基线；
- JDK 9：引入实验性 AOT（jaotc，JEP 295）；JDK 17 移除（JEP 410）——静态 AOT 路线在 HotSpot 主线被放弃；
- JDK 10：Graal 作为实验性 JIT（JEP 317），可用 `-XX:+UseJVMCICompiler` 替换 C2；
- 前沿：Project Leyden（提前优化、改善启动）与 GraalVM Native Image（封闭世界假设下的真正 AOT）在重新定义"静态/动态"的边界——Native Image 的代价是放弃部分运行时投机优化能力，与本篇第一节的权衡表一脉相承。

# 十、面试问法速查

| 问题 | 答题骨架 |
|---|---|
| JVM 为什么不直接编译成机器码执行？ | 跨平台 + 类加载的动态性 + 运行时信息可做静态编译器做不到的投机优化；用解释器兜底解决启动问题 |
| 热点代码是怎么探测出来的？ | 双计数器（方法调用 / 回边）+ 热度衰减，非采样式精确计数 |
| 标准编译和 OSR 的区别？ | 触发器不同（调用计数器 vs 回边计数器）；生效时机不同（下次调用 vs 本次循环回跳点中途切换） |
| 为什么叫"栈上替换"？ | 替换的是还留在虚拟机栈上、正在执行中的解释帧 |
| 方法内联为什么是"优化之王"？ | 消调用开销只是表象，打通方法边界让常量传播等优化得以进行才是本质 |
| 为什么压测要预热？ | 分层编译 0→3→4 需要调用次数积累，未预热测到的是解释执行耗时 |
| JIT 为什么敢做激进优化？ | 解释器兜底 + 后台异步编译 → 时间压力小；profiling 提供运行时情报；有去优化机制兜底猜错 |
| 手写循环计时为什么不准？ | 预热不充分、OSR 干扰、死代码被消除、循环提升——用 JMH |
| C2 CompilerThread CPU 高正常吗？ | 启动预热期短时高正常；持续高查频繁去优化 / 代码反复失效，与 GC 线程高区分开 |
