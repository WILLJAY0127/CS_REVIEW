# 技能 8:数据驱动与流程标准化 — 断点分析平台

> 对应手册:第 14 章(项目四连环问)、第 16.4 节(设计题)
> 这项证明你不只是写需求的人,而是能"发现问题、统一语言、推动别人改"的人——TL/专家岗的核心信号。

## 一、简历原句

> 主导业务流程断点分析平台建设(全链路节点埋点 → 漏斗转化与失败归因 → 驱动流程优化),推动各业务线流程节点、错误码、埋点口径标准化,用数据驱动转化率提升。

## 二、能力信号

1. **先立标准再建平台**:没有统一口径的数据是垃圾进垃圾出——标准化是因,平台是果;
2. **零侵入架构能力**:注解 + 拦截器上报,业务方接入成本半天;
3. **数据链路选型**:MQ + ClickHouse 而不是 MySQL/ES,讲得清为什么;
4. **治理闭环**:看板不是终点,"失败码 → 责任系统派单 → 优化 → 回看"才是;
5. **推动力**:让 4 条业务线改埋点、改错误码,靠的是样板和低接入成本,不是行政命令。

## 三、知识地图

### 3.1 标准节点模型

| 字段 | 说明 |
|---|---|
| flowType | 流程类型(投保/保全/续期/满期领取/理赔) |
| nodeCode | 节点编码(统一命名规范:业务-模块-环节) |
| result | 成功/失败/取消 |
| failCode | 统一错误码字典(OCR/人脸/要素/支付/核心/网络 分类) |
| cost | 节点耗时 |
| channel | 渠道(App/H5/柜面) |
| traceId/bizId | 串人、串单 |

- 上报方式:**自定义注解 `@FlowNode` + AOP/拦截器自动上报**,异常也上报(无侵入);前端同口径埋点;
- 容错:上报失败只记本地日志/异步重试,**绝不阻断业务主流程**;failCode 未登记降级存裸码,宽容不阻断;
- 异步语义:事件先本地存/MQ,削峰且解耦。

### 3.2 错误码字典(标准化的灵魂)

- 全局分段:`OCR-1xxx`、`FACE-2xxx`、`ELEMENT-3xxx`、`PAY-4xxx`、`CORE-5xxx`;
- 每个错误码:含义、归属系统、用户侧文案、是否可重试——**同一个失败不能在 A 系统叫"系统异常"、B 系统叫"交易失败"**;
- 字典中心统一注册,新错误码不登记不允许上线(架构评审 checklist 卡点)。

### 3.3 数据链路

```
注解埋点 → 事件 → RocketMQ(削峰)→ ClickHouse(明细)
                                     ↓ XXL-Job 按天/小时聚合
                漏斗转化率 / 节点成功率 / 失败 TOP / 耗时 P90
                                     ↓
                        ECharts 看板 + 周报 + 优化工单
```

选型问答:
- **为什么 ClickHouse 不用 MySQL?** 千万级事件/天,写多读少、列存高压缩、聚合快;MySQL 做这种宽表聚合一会就慢;明细天然按天分区,过期直接 drop partition。
- **为什么不用 ES?** ES 擅长搜索,10 层 terms 嵌套聚合有桶上限风险且成本高;纯分析场景列存库更合适。
- **为什么不用 Flink 实时?** 业务节奏是日/小时级运营,实时价值有限、运维成本高;XXL-Job 定时聚合是约束下的务实选择。(会讲"不做什么"比堆技术高级。)

### 3.4 治理闭环与案例

- 周报自动产出各流程 TOP 断点,按 failCode 归属系统直接派单,治理后回看转化率;
- 四个真实案例:
  1. **港澳台证件 OCR 模板缺失** → 断点集中在 OCR-FAIL → 推动补模板 → 该类客户断点 -60%;
  2. **活体阈值过高,老年客户反复失败** → 年龄分层阈值 + 引导 → 通过率 +20%(反哺项目三);
  3. **某银行卡支付失败集中** → 银行通道问题 → 切流;
  4. **满期金额确认页流失高** → 接 AI 问答解释金额构成 → 下降。
- 结果:10+ 流程、80+ 节点,转化 +15%,问题发现周级 → 天级。

### 3.5 怎么推动业务线接入(软技能也是技术力)

1. 先拿一个流程(满期领取)跑样板,拿出转化率提升;
2. starter + 注解把接入压到半天,配模板和接入文档;
3. 架构评审 checklist 固化为新流程准入;
4. 数据反哺业务方(他们也想要转化数据),从"要我接"变"我要接"。

## 四、高频追问(详见手册第 14 章)

- "埋点影响主流程性能怎么办?" → 异步 + MQ + 失败宽容;注解切面只做序列化投递,微秒级。
- "数据不准怎么办?" → 统一 SDK 上报保证口径;抽样核对 + 与业务单量对账;宽容策略不阻断但标记脏数据。
- "ClickHouse 数据要更新/删除?" → 明细只追加;错数据通过新版本聚合覆盖;极特殊用 mutation(很重,侧面证明选型契合 append-only)。
- "漏斗怎么定义才不被质疑?" → 与业务方先对齐节点定义和口径,定义即标准;同一流程只认字典中的 nodeCode。
- "这平台和神策/GA 区别?" → 外部产品做通用行为分析强,但内部系统失败码归因、核心/支付/OCR 深度对接、数据合规不出域是自建理由;选型题正反都要能讲。
