# 技能 7:规则引擎与身份核验中台

> 对应手册:第 10.6 节、第 13 章(项目三连环问)、第 16.3 节(设计题)
> 这是你"配置化中台设计"能力的主证据:从"接厂商 SDK"升级成"规则可配、多证件、多厂商、生存/死亡核验"。

## 一、简历原句

> 主导多证件身份核验中台化建设,基于规则引擎实现核验策略配置化(证件类型、核验项组合、分数阈值、活体/生存核验开关按场景可配);支持大陆身份证、港澳台居住证/回乡证/台胞证、护照;覆盖 OCR、二/三要素、活体、人脸比对、生存/死亡状态核验;熟悉个保法下生物信息合规。

## 二、能力信号

1. **配置化思维**:把"变化频率不同的东西"分离——流程骨架在代码里(稳定),策略差异在规则里(常变),这是中台化的核心思想;
2. **选型能力**:QLExpress/决策表 vs Drools 的取舍;
3. **业务理解**:生存核验为什么是保险刚需(满期生存金、年金按人生存给钱),不是炫技;
4. **合规意识**:生物识别信息是个保法敏感个人信息,单独同意/最小必要/限期删除。

## 三、知识地图

### 3.1 规则引擎

| 主题 | 要点 |
|---|---|
| 解决什么问题 | 核验策略因场景/证件类型/渠道而异且经常调整;硬编码 = 改一次发一次版,业务等不起 |
| 决策表 | 行 = 规则(业务场景 × 证件类型 × 渠道),列 = 动作(OCR/要素/活体/比对/生存核验开关 + 分数阈值 + 重试 + 降级);非技术背景也能看懂、可评审 |
| QLExpress | 阿里轻量表达式引擎,处理决策表表达不了的复杂条件(如年龄/风险等级动态阈值);**为什么不选 Drools**:重、学习曲线陡、运维复杂,我们的规则复杂度决策表 + 少量表达式够用,不为用而用 |
| 热生效 | 规则发布 → 推送 Nacos/Redis → 应用监听刷新,零发版;**版本化 + 按渠道灰度 + 一键回滚**(规则配错是运营事故) |
| 执行模型 | 规则匹配(命中决策表行)→ 展开核验项计划 → 责任链依次执行 → 汇总结论;不命中走默认策略并告警 |
| 风险控制 | 规则只能"收紧"不能"放松"到合规线以下;高风险场景(满期给付/大额退保)阈值下限硬编码兜底;规则变更双人复核 + 审计日志 |

### 3.2 多证件适配

| 证件 | 权威通道 |
|---|---|
| 大陆身份证 | 公安人口库(二要素/三要素 + 人脸比对) |
| 港澳台居民居住证 | 可走类似大陆证件通道(有公民身份号码) |
| 港澳回乡证 / 台湾台胞证 | 出入境通道;OCR 模板独立 |
| 护照 | 出入境/护照识别;要素核验能力弱,靠 OCR + 人脸 + 人工补充 |
| 设计模式 | 适配器:统一接口,内部按证件类型路由;新增证件只加适配器,主流程不动 |

### 3.3 活体与真实人脸

- 动作活体(眨眼/摇头/张嘴,随机动作码防脚本固化)+ 静默活体(被动防照片/视频/面具/翻拍);
- 人脸比对输出相似度分,**阈值是风险与体验的权衡**:阈值高=安全但老人/光线差的过不了;分场景配置(满期给付 85、信息变更 75);
- 防攻击延伸:失败计数、高风险客户动态加强动作、设备/IP 维度风控;
- 真实案例(断点平台反哺):老年客户活体失败集中 → 年龄分层阈值 + 交互引导 → 通过率 +20%。

### 3.4 生存 / 死亡核验(保险特色)

- 为什么要:满期生存金、年金给付的前提是"被保人仍然生存";过去要柜面交生存证明,成本高、老年客户难;
- 在线生存核验 = 实名 + 活体 + 人脸比对,证明"此刻是本人在操作",替代柜面证明(法律效力以公司与监管认可的方案为准);
- 死亡核验:对接权威状态数据(如公安状态)+ 理赔场景死亡证明 OCR 辅助;注意口径——**能证明死亡 vs 能证明生存的通道不对称**,死亡信息存在时滞,理赔仍以死亡证明材料为准;
- 凭证:核验通过签发凭证(绑业务流水 + 限时 + 一次性/防重放),下游凭票消费,生物原图不二次传输、限期删除。

### 3.5 稳定性与合规

| 主题 | 做法 |
|---|---|
| 多厂商 | 主备厂商熔断自动切换(成功率 99.0%→99.9%),统一计费对账;适配器屏蔽字段差异 |
| 合规 | 个保法:单独授权(非捆绑同意)、明示目的、最小必要、加密存储/传输、限期删除、全流程审计、DPA 厂商协议;等保;**敏感数据不进日志、不进模型上下文** |
| 开关降级 | 任一核验项可配置降级(如权威库超时:放行 or 阻断按场景风险定),全部动态开关 |

## 五、高频追问(详见手册第 13 章)

- "规则引擎和 if-else 本质区别?" → if-else 是代码要发版、不可运营;规则是数据,可配可审可回滚;但简单稳定逻辑硬编码更好,**别把所有分支都规则化**。
- "规则配错了把阈值改 0 怎么办?" → 高风险阈值硬下限 + 双人复核 + 灰度 + 回滚 + 审计;技术不假设人不犯错。
- "为什么不用 Drools?" → 见上,复杂度不匹配;同时表态了解 Drools 的 rete 推理和适用场景(复杂计费)。
- "厂商挂了会放行欺诈吗?" → 按场景:低风险可降级放行后补审;满期给付类直接阻断/走人工,降级策略本身也是配置。
- "活体照片视频攻击怎么防?" → 静默活体 + 动作随机 + 厂商风控分 + 重放(一次性凭证)多层,不依赖单点。
- "生存核验的法律依据?" → 诚实口径:方案经法务/合规认可,技术满足"本人实时操作"证据链,不等同于官方生存登记;不懂的不装懂。
