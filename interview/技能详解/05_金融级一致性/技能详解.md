## 一、简历原句

> 熟悉保险核心系统对接模式,擅长支付/收付费链路的幂等设计、三方对账(渠道账单 ↔ 平台流水 ↔ 核心应收)、长短款处理、本地消息表与分布式事务;坚持"资金链路笔笔可追溯、差异必有兜底"。

## 二、能力信号(面试官的判断标准)

- 普通候选人讲分布式事务停留在"2PC/TCC/Saga 概念";你要讲**"保险核心这种老系统根本不配合你,工程上怎么把钱做平"**。

## 三、知识地图

### 3.1 保险系统认知(业务语言,先能对话)

| 概念 | 解释 |
|---|---|
| 保险核心 | 承保(出单)、保全(保单变更)、收付费(钱)的老系统,公司的 system of record,稳定压倒一切,接口老旧(可能是报文/批量文件) |
| 保单状态 | 有效 → 宽限期 → 中止 → 终止(失效);复效是中止后恢复;满期/退保/理赔是退出方式 |
| 应收/实收 | 应收=核心按费率算出"该收多少";实收=渠道实际到账;两者差异就是对账对象 |
| 投连账户 | 投资单位数 × 每日单位价格,账户价值日波动,**金额只信核心试算接口** |
| 交互方式 | 同步接口 + 异步回执 + 日终批量文件,三种都要接 |

### 3.2 幂等(单笔不错)

| 层次 | 手段 |
|---|---|
| 入口 | 业务唯一键(缴费单号/渠道流水号);防重复提交(token/状态校验) |
| 并发 | Redisson 锁(减少竞争,非正确性依赖) |
| 落库 | **唯一索引(最终防线)** + 状态机 `WHERE status=?` 乐观锁,影响行数=0 → 查回当前状态返回 |
| 远程 | 核心入账:平台流水号作为幂等号传给核心,依赖核心去重或重复入账后对账冲正 |
| 原则 | 幂等失败时返回"当前真实状态",不能报错让用户重试(用户视角永远成功或处理中) |

### 3.3 最终一致(链路不断)

| 方案 | 适用 | 代价 | 你的用法 |
|---|---|---|---|
| 本地消息表 | 老系统、跨组织、要可审计 | 有投递延迟、要建表和补偿任务 | **主力方案**:缴费回调 → 本地事务(账单+消息表)→ MQ → 核心 |
| 事务消息 | 双方都用 RocketMQ 且接受回查 | 排查不如本地表直观 | 新系统间可用 |
| TCC | 短流程、强一致、资源可预留 | Try 接口改造大,核心不配合 | 保险场景基本不现实 |
| Saga | 长事务(承保多步) | 补偿逻辑复杂、无隔离 | 编排多步业务时了解 |
| 定时补偿 | 任何方案的兜底 | 有延迟 | XXL-Job 扫描处理中单据主动查单/重推 |

关键设计原则:
1. **主链路不绑定 MQ**:用户支付成功的响应只依赖本地落库,核心入账异步化;
2. **状态机只允许单向流转**,每个状态有超时出口;
3. **核心回执重发天然幂等**(按流水号覆盖推进)。

### 3.4 对账(总量对得上)

```
T+1 三方勾兑:
渠道账单(微信/支付宝/银联实际到账)
      ↕ ①
平台流水(我们记录的每笔支付)
      ↕ ②
核心应收/实收(核心系统的账)
差异分类:长款(收了没入账)/ 短款(入账了没收到钱)/ 单边账 / 金额不一致
处理:自动分类 → 差异工单 → 自动查单/重推可自愈 → 不能自愈的人工处理
目标:对账覆盖率 100%,长短款小时级发现
```

- 主动查单:对处理中超时单据主动调渠道/核心查询接口,不等客诉;
- 对账文件解析也要幂等(按对账日期 + 流水唯一);
- 容差规则:利息/手续费尾差要有规则,不能全报差异淹没问题。

## 四、你的项目锚点(缴费平台)

1. **支付回调全链路**:渠道回调 → 验签 → 三重幂等落库 → 本地消息表 → MQ → 核心入账 → 回执驱动状态机;连续 3 年高峰期零资金差错。
2. **批量代扣**:分片调度 + 游标拉取 + 加密文件 + 回执分类重试(余额不足/卡失效转催缴),扣款成功率 +12%。
3. **满期金给付链路**:申请 → 核验中台生存核验 → **核心试算金额(金额红线)**→ 用户确认 → 核心给付 → 转账回执状态机。
4. **防腐层**:核心报文协议(同步/异步/批量)全部收敛在适配层,核心字段变更不蔓延业务层。
5. **Canal 异构**:16 库 64 表后对账查询走 ClickHouse,不打交易库。

## 五、高频追问与死亡点

- "为什么不用 Seata?" → AT 模式要全局锁 + 改数据源,核心是外部老系统进不来;我们的约束是"核心零改造",本地消息表 + 对账是约束下最优解。**答题永远先说约束。**
- "MQ 消息丢了/重复了,钱怎么办?" → 重复靠状态机幂等;丢失靠 XXL-Job 兜底扫描 + 日终对账;双保险。
- "用户扣了钱但系统显示失败?" → 绝不让用户重复支付;状态置处理中 + 主动查单;查单确认已支付则推进,差异进对账;前端给明确预期。
- "对账发现长款怎么处理?" → 先冻结结论、自动查单确认链路状态;能补入账的自动补(走幂等),不能补的走人工审批,严禁技术人员直接调账。
- "支付成功但通知核心一直失败?" → 消息重试到死信 → 告警 + 工单;资金在平台账上不会丢,日终对账必然发现;与核心有应急人工处理通道。
- "分布式事务你选哪个?" → 不背对比表,按"一致性要求 × 对方配不配合 × 流程长短"三维度给结论。
