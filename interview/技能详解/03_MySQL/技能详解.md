## 三、知识地图

### 索引与执行计划

| 知识点 | 深度 |
|---|---|
| B+ 树 | 为什么不是 B 树/哈希(范围查询、有序、高度低 3~4 层);聚簇索引叶子=数据行,二级索引叶子=主键(回表) |
| 覆盖索引 | 索引包含查询所有列,Extra 显示 Using index;**避免回表**是最常用优化手段 |
| 最左匹配 | 联合索引按顺序;范围条件之后的列失效;索引下推 ICP(5.6+) |
| EXPLAIN | type(const/ref/range/index/ALL)、key/rows/**Extra(Using filesort / Using temporary 要警惕)** |
| 慢 SQL 套路 | 看执行计划 → 是不是没走索引(函数/隐式转换/like %xx/OR)→ 回表多不多 → 是否排序超大结果集 |

### 事务与锁

| 知识点 | 深度 |
|---|---|
| 隔离级别 | RU / RC(**互联网常用**) / RR(MySQL 默认) / 串行化;各级别解决什么(脏读/不可重复读/幻读) |
| MVCC | 隐藏字段 trx_id/roll_ptr + undo 版本链 + ReadView;RC 每次查询新建 ReadView,RR 复用——一句话讲清区别 |
| 锁 | 记录锁、间隙锁(防插入,RR 下)、临键锁;**死锁排查**:`SHOW ENGINE INNODB STATUS`、事务顺序一致性原则 |
| 日志 | redo(物理日志,crash recovery,WAL)、undo(回滚+MVCC)、binlog(Server 层,主从/归档);两阶段提交保证 redo/binlog 一致 |
| 乐观锁 | version 或状态字段 `UPDATE ... WHERE status=?`,**看影响行数**——资金单状态流转的标准做法 |

### 分库分表

| 知识点 | 要会讲 |
|---|---|
| 为什么分 | 单表数据量(经验值 500 万~2000 万看行宽)、写入压力、DDL 风险 |
| 分片键 | **保单/流水按 user_id 分 16 库 64 表**:用户维度查询都能命中;代价是运营/对账按非分片键查 → 异构 |
| 分片策略 | 哈希(均匀、扩容难)vs 范围(易扩容、热点);扩容:成倍扩 + 迁移(旧库只迁一半) |
| 全局 ID | 雪花算法(时钟回拨问题)、号段模式(Leaf) |
| ShardingSphere | JDBC 客户端分片;绑定表/广播表;跨片排序分页的坑 |
| 异构 | Canal 订阅 binlog → ES(运营查询)/ClickHouse(对账分析),这是你项目里的真实架构 |

## 四、你的项目锚点

1. **缴费单三重幂等的最后一层**:渠道流水号唯一索引——"唯一索引是幂等的最终防线,应用层锁都会失效,数据库约束不会"。
2. **状态机 + 乐观锁**:缴费/给付单据流转,`WHERE id=? AND status='待支付'`,影响行数=0 即重复/并发请求,直接查回当前状态返回。
3. **16 库 64 表 + Canal 异构**:保单/流水按 user_id 分片;对账和运营查询走 ClickHouse/ES——能讲"分表键选错会怎样、异构延迟怎么对账兜底"。
4. **批量代扣游标分页**:`WHERE id > #{lastId} ORDER BY id LIMIT n`,不用 `LIMIT 100w,1000`(越翻越慢 + 内存风险)。
5. **长事务规避**:支付回调里不直接调核心(慢 + 跨网络),本地落账 + 消息驱动,把大事务切成短事务。

## 五、高频追问

- "RR 一定不会幻读吗?" → 快照读靠 MVCC 没问题;当前读靠临键锁,但先快照读再当前读仍可能看到新行——要会讲边界。
- "索引为什么用 B+ 树不用红黑树?" → 磁盘 IO 以页为单位,树高决定 IO 次数;B+ 矮胖、叶子链表支持范围。
- "分库分表后怎么做分页?" → 归并 + 深分页禁止;产品交互改成上一页/下一页游标。
- "唯一索引和普通索引性能差多少?" → change buffer 对唯一索引无效;但金融场景不省这个。
- "对账 SQL 把库查挂了怎么办?" → 只读从库 + 时间窗 + 异构到 ClickHouse(你的真实答案)。
