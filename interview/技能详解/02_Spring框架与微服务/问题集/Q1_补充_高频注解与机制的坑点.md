# Q1 补充：高频注解与机制的坑点清单

> 定位：Q1 主文讲的是"Bean 怎么被造出来"，本文讲的是"造出来之后，日常用的注解还会在哪翻车"。
> 主线只有一条：**注解本身不干活，是容器（代理 / BPP / 生命周期钩子）替它干活**。理解了这条，下面所有坑都是同一个病的不同症状。

## 概览卡

| # | 主题 | 一句话结论 |
|---|---|---|
| 1 | `@Transactional` / `@Async` / `@Cacheable` 失效 | 注解不干活，**代理才干活**；调用不经过代理 = 白写 |
| 2 | JDK 动态代理 vs CGLIB | 一个要接口，一个要继承；final 类/方法谁也救不了 |
| 3 | `@Autowired` / `@Resource` / `@Inject` | byType 派 vs byName 派，选一个统一用 |
| 4 | 同类型多 Bean：`@Primary` / `@Qualifier` / `@Order` | `@Order` **不管**单个注入选谁，只管集合排序 |
| 5 | `@Bean` 方法互相调用为什么不重复创建 | `@Configuration` 被 CGLIB 增强，方法调用被拦截查容器 |
| 6 | prototype 注入 singleton 的坑 | 装配只做一次，prototype 名存实亡 |
| 7 | `@Value` 注不进 static 字段 | 容器管的是**实例**，不是类 |
| 8 | 启动时执行代码的四个位置 | `@PostConstruct` → `afterPropertiesSet` → `init-method` → `Runner` |
| 9 | `@Lazy` 治循环依赖 | 创可贴：环还在，只是启动期不发作 |
| 10 | `@EventListener` | 拆环正道之一：把"反向通知"从"依赖"里剥离 |
| 11 | BeanFactory vs FactoryBean vs ApplicationContext | 名字最像的三个东西，一个是容器、一个是产 Bean 的 Bean、一个是增强容器 |
| 12 | `@Component` vs `@Bean` | 有自己的类用注解，没源码的类用 `@Bean` |
| 13 | `@Conditional` | Spring Boot "引入 starter 就有 Bean"的开关原理 |
| 14 | 构造器注入为什么被官方推荐 | 把"需要什么"从注解暗处挪到 Java 语法强制检查的明处 |

## 一、代理失效家族：`@Transactional` / `@Async` / `@Cacheable` 是同一个病

### 病根一句话

> **注解只是贴了个标签，真正干活的是代理对象。你的调用必须经过代理，标签才会被读到。**

代理的拦截规则决定了失效清单：

| 失效场景 | 为什么 |
|---|---|
| 自调用 `this.doX()` | `this` 是目标对象本身，不是代理，调用不经过代理 |
| `private` 方法 | 代理是"子类重写 / 接口实现"，私有方法无法被重写 |
| `final` 方法 / `final` 类 | CGLIB 靠继承，final 禁止继承和重写 |
| 自己 `new` 出来的对象 | 没经过容器，根本没有代理存在 |
| 异常被 `catch` 吃掉不抛出 | 事务代理靠"异常抛出"判断回滚，异常没了它以为一切顺利 |
| 抛出 checked 异常 | 默认只对 `RuntimeException` / `Error` 回滚，需 `rollbackFor` 显式指定 |
| `@Async` 方法与调用者在同一个类 | 同上，自调用不走代理，线程池根本不会介入 |

### 检测口诀

**"调用链上有没有代理"三问**：

1. 这个对象是容器给的，还是自己 `new` 的？
2. 调用方拿到的是代理，还是裸对象（`this`）？
3. 方法签名允许被重写吗（非 private / final / static）？

三问有一问答错，注解就静默失效 —— **注意是"静默"，不报错，这才是最坑的**。

## 二、JDK 动态代理 vs CGLIB：为什么有的类代理不了

| | JDK 动态代理 | CGLIB |
|---|---|---|
| 原理 | 运行时生成一个**实现相同接口**的新类 | 运行时生成一个**继承目标类**的子类 |
| 前提 | 目标必须实现接口 | 目标类和方法不能是 final |
| 调用方式 | 接口方法 → 代理 | 父类方法 → 子类重写拦截 |
| Spring Boot 2.x 默认 | 不用 | **默认用它**（`proxyTargetClass=true`） |

为什么 Spring Boot 默认 CGLIB：用 JDK 代理时，生成的代理**只实现接口、不是目标类的子类**，如果你按实现类注入（`@Autowired OrderServiceImpl`）会直接报类型不匹配。CGLIB 代理是目标类的子类，按接口按实现类注入都行，省心。

**推论**：`@Transactional` 打在 final 方法上，CGLIB 无法重写 → 静默失效。这也是"为什么 Spring 的 Bean 最好别写 final"的原因。

## 三、注入三兄弟：`@Autowired` / `@Resource` / `@Inject`

| | 出身 | 查找顺序 | 特点 |
|---|---|---|---|
| `@Autowired` | Spring 亲儿子 | byType → 多个候选再 byName | 有 `required=false`；可标构造器/字段/setter |
| `@Resource` | JDK（JSR-250） | **byName → 找不到再 byType** | 名字来源于字段名或 `name` 属性 |
| `@Inject` | Java 标准（JSR-330） | 同 `@Autowired` | 无 `required` 属性，需引额外依赖 |

经典分歧场景：容器里有两个 `UserDao` 实现。

- `@Autowired` 先按类型找到两个 → 再按字段名匹配，匹配不上就报 `NoUniqueBeanDefinitionException`。
- `@Resource` 先按字段名找，名字对上就用，对不上才看类型。

**工程建议**：团队内统一一种。新项目更推荐**构造器注入**（字段 `final`、依赖一目了然、单元测试不用起容器、循环依赖启动期就炸而不是运行期才发现），此时连注解都可以省（单构造器时 Spring 4.3+ 自动识别）。

## 四、同类型多 Bean：`@Primary` / `@Qualifier`，以及 `@Order` 的经典误解

报错现场：`NoUniqueBeanDefinitionException: expected single matching bean but found 2`

- `@Primary`：给其中一个 Bean 贴上"默认人选"，注入时不点名就用它。
- `@Qualifier("xxDao")`：注入点处点名要谁，优先级高于 `@Primary`。

**高频误区**：以为 `@Order(1)` 能让某个 Bean 在注入时"胜出" —— 不能。

`@Order` 的真实管辖范围：

1. **注入 `List<接口>` 时，控制集合里的顺序**。Spring 会把该类型的所有 Bean 按 Order 排好序一次性注入，这是策略模式落地的标准姿势：

```java
@Service
public class PayService {
    // 支付宝、微信、银联全部按 @Order 排好注入
    private final List<PayChannel> channels;
    public PayService(List<PayChannel> channels) { this.channels = channels; }
}
```

2. AOP 多个切面的先后顺序、过滤器的先后顺序。

一句话：`@Primary` / `@Qualifier` 解决"选一个"，`@Order` 解决"排一排"，井水不犯河水。

## 五、`@Bean` 方法互相调用，为什么不会创建两次

```java
@Configuration
public class AppConfig {
    @Bean
    public A a() { return new A(); }

    @Bean
    public B b() {
        a();              // 看起来又调了一次 a()，会 new 出第二个 A 吗？
        return new B(a());
    }
}
```

答案：不会。`@Configuration` 类本身被 **CGLIB 增强**，`@Bean` 方法被拦截：调用时先查容器"这个 Bean 造过吗"，造过就直接返回一级缓存里的成品，方法体根本不执行。

**反转来了**：把 `@Configuration` 换成 `@Component`（或 `@Configuration(proxyBeanMethods = false)`，即 lite 模式），增强关闭，`b()` 里的 `a()` 就是普通 Java 方法调用 —— **真的会 new 出第二个 A**，而且第二个 A 不在容器里，事务代理全没有。

| | full 模式（默认） | lite 模式 |
|---|---|---|
| 标注 | `@Configuration` | `@Component` 或 `proxyBeanMethods=false` |
| `@Bean` 互调 | 走容器，单例保证 | 普通调用，每次 new |
| 启动成本 | 要生成 CGLIB 子类 | 零增强，启动略快 |
| 适合 | 配置之间有依赖 | 纯声明一批互不引用的 Bean（Spring Boot 自动配置大量使用） |

一句话：**`@Configuration` 的"超能力"是 CGLIB 给的；`@Bean` 方法不是普通方法，是被收编的方法。**

## 六、prototype 注入 singleton 的坑

```java
@Component
@Scope("prototype")
public class ShoppingCart { /* 每个用户一个购物车 */ }

@Service
public class OrderService {          // 单例
    @Autowired
    private ShoppingCart cart;       // 实际只注入了一次！
}
```

单例 Bean 一生只装配一次，`cart` 字段在那一刻被焊死 —— prototype 名存实亡，所有用户共用一个购物车。

解法（按推荐度）：

1. 注入 `ObjectProvider<ShoppingCart>`，用的时候 `getObject()` 现取；
2. 方法上加 `@Lookup`，让 Spring 每次重写该方法去容器取新实例；
3. 多数时候真正的解法是重新想设计：prototype 状态对象往往不该注入，应该作为参数在调用链里传。

一句话：**作用域是"每次取都新建"的承诺，字段注入是"只取一次"的动作，两者天然撞车。**

## 七、`@Value` 的坑：static 注不进，零散值别硬扛

```java
@Component
public class SmsConfig {
    @Value("${sms.key}")
    private static String KEY;   // 永远是 null，不报错
}
```

原因：容器管理的是**实例**，static 属于类，不属于任何实例，属性填充阶段根本不会看它。

修复：把 `@Value` 放到 setter 上，在 setter 里给静态字段赋值；或者干脆别用 static。

进阶：配置项一多，每个字段一个 `@Value` 又散又难测，改用 `@ConfigurationProperties(prefix = "sms")` 批量绑定到一个 POJO —— 类型安全、可校验、IDE 有提示，这是 Spring Boot 配置的正道。

## 八、启动时执行代码的四个位置与顺序

```text
单个 Bean 视角：
@PostConstruct → InitializingBean.afterPropertiesSet → @Bean(initMethod)
                                                          │
容器全局视角：                                             ▼
                              所有 Bean 造完 → ApplicationRunner / CommandLineRunner
```

| 位置 | 粒度 | 此刻能用什么 |
|---|---|---|
| `@PostConstruct` | 单 Bean | 依赖已注入（但**代理还没套**，别在这调自己的 `@Transactional` 方法，见主文故障 3） |
| `afterPropertiesSet` | 单 Bean | 同上，Spring 专有接口，侵入性比注解强 |
| `init-method` | 单 Bean | 同上，常用于不好改源码的第三方类 |
| `ApplicationRunner` / `CommandLineRunner` | 全容器就绪后 | 预热缓存、跑数据检查的正确位置，代理已就绪 |

选型经验：**Bean 收拾自己用 `@PostConstruct`，需要"整个系统都好了"才干的事用 Runner**。两者混用是故障高发区。

## 九、`@Lazy`：循环依赖的创可贴

```java
@Service
public class A {
    public A(@Lazy B b) { this.b = b; }  // 构造器循环依赖也能启动了
}
```

原理：注入点给的不是真 B，是一个 B 的**占位代理**；A 拿着它就能先出生，等第一次真正调用 B 的方法时才去创建 B。相当于把"启动期就要对方"推迟到"运行期才要对方"，绕开了创建死锁。

但注意：**环还在**。`@Lazy` 只是把"启动即报错"变成了"能跑"，和三级缓存一样是兜底不是设计。看到团队里 `@Lazy` 成堆出现，基本等于看到了一沓创可贴 —— 该回去看主文"循环依赖是设计信号"那一节了。

## 十、`@EventListener`：拆环的正道之一

典型坏环：订单完成后要通知积分、通知短信、通知库存 —— `OrderService` 注入三四个下游，下游有时还反过来查订单，环就这么长出来的。

事件解法：`OrderService` 不认识任何下游，只负责喊一嗓子：

```java
@Service
public class OrderService {
    private final ApplicationEventPublisher publisher;

    public void complete(Long orderId) {
        // ... 业务逻辑
        publisher.publishEvent(new OrderCompletedEvent(orderId));
    }
}

@Component
public class PointListener {
    @EventListener
    public void on(OrderCompletedEvent e) { /* 加积分 */ }
}
```

依赖方向从"A → B、B → A 互指"变成"A、B 都面向事件"，环从根上消失。

两个进阶点：

- `@TransactionalEventListener(phase = AFTER_COMMIT)`：**事务提交成功后才触发**。解决"事务回滚了但短信已经发出去了"的经典事故。
- 事件是进程内广播，跨服务请用 MQ，语义相同但别拿 ApplicationEvent 当消息队列用。

## 十一、名字陷阱：BeanFactory vs FactoryBean vs ApplicationContext

三个名字像到面试必考：

| | 是什么 | 一句话 |
|---|---|---|
| `BeanFactory` | **容器本身**的最小接口（`getBean`） | 仓库 + 工厂的抽象 |
| `ApplicationContext` | `BeanFactory` 的增强子接口 | 多了事件、国际化、自动注册 BPP、环境抽象，日常说的"Spring 容器"都是它 |
| `FactoryBean` | **一个会生产 Bean 的特殊 Bean** | 容器里注册的是它，但真正用的是它 `getObject()` 吐出来的东西 |

`FactoryBean` 的经典实例：MyBatis 的 `MapperFactoryBean`。Mapper 是接口没法实例化，MyBatis 就让一个 FactoryBean 在 `getObject()` 里用 JDK 代理现造一个实现塞进容器 —— 你在业务代码里 `@Autowired UserMapper`，拿到的是代理产物，这就是"接口也能被注入"的全部秘密。

面试追问：`FactoryBean` 生产的对象是单例吗？默认是（FactoryBean 内部缓存产物），但可以返回 prototype。

## 十二、`@Component` vs `@Bean`：什么时候用哪个

| 场景 | 选择 | 原因 |
|---|---|---|
| 自己写的业务类 | `@Component` / `@Service` / `@Repository` | 类上贴一个注解完事，配合包扫描自动注册 |
| 第三方库的类（没源码，贴不了注解） | 在 `@Configuration` 里写 `@Bean` 方法 | `new` 的过程你掌控，还能做参数装配 |
| 构造过程复杂（读配置、选实现、多步组装） | `@Bean` 或 `FactoryBean` | 注解表达能力不够，需要"写一段代码来造对象" |
| 想替换/覆盖已有 Bean | `@Bean` + `@ConditionalOnMissingBean` | Spring Boot 自定义自动配置的标准姿势 |

一句话：**有源码用注解，没源码用 `@Bean`，造法复杂用 `@Bean` / `FactoryBean`。**

## 十三、`@Conditional`：Spring Boot "引入 starter 就自动有 Bean" 的原理

为什么 pom 里加了 `spring-boot-starter-data-redis`，容器里就多了 `RedisTemplate`？不是魔法，是一堆条件判断：

```java
@Configuration
@ConditionalOnClass(RedisOperations.class)        // 类路径上有这个类才生效
@ConditionalOnMissingBean(RedisTemplate.class)    // 用户没自己定义才生效
public class RedisAutoConfiguration {
    @Bean
    public RedisTemplate<String, Object> redisTemplate(...) { ... }
}
```

链条是这样的：

1. starter 的 jar 里有一份**自动配置清单**（`META-INF/spring/...AutoConfiguration.imports`）；
2. 启动时 Spring Boot 把清单里的配置类全部加载，但每个配置类头上都挂着 `@ConditionalXxx`；
3. 条件不满足的静默跳过 —— 这就是为什么"没引依赖不报错、引了依赖自动有、自己定义了就用你的"。

面试一句话：**自动装配 = 自动配置清单 + 条件注解过滤 + `@EnableAutoConfiguration` 触发加载。** 学自定义 starter 之前，先吃透 `@ConditionalOnMissingBean`，它是"用户优先于框架"这条设计哲学的直接体现。

## 十四、为什么官方推荐构造器注入

一句话：**字段注入有"半成品窗口期"，构造器注入把这个窗口期交给编译器焊死。**

| 理由 | 展开 |
|---|---|
| 依赖可以 `final` | 字段注入的依赖不能 final（容器要用反射塞值）；构造器注入可以，对象造完即不可变，并发场景天然安全 |
| 消灭 null 窗口期 | 流水线① new 完到③ populateBean 之前，字段注入的对象**字段全是 null**，此时调方法必 NPE（见主文故障 1：构造器里读注入字段为 null）。构造器注入要求"造我之前先把我要的给我"，对象一出生就是完整的 |
| 依赖清单 = 坏味道探测器 | 构造器参数列表就是这个类的"依赖清单"，超过五六个就是设计在报警（呼应主文"循环依赖是设计信号"）。字段注入把依赖藏在类体里，加多少个都无声无息 |
| 循环依赖启动期就炸 | 构造器环走不到 `addSingletonFactory`，三级缓存**救不了**，启动期抛 `BeanCurrentlyInCreationException`——救不了反而是好事：问题在启动时暴露，而不是运行期某个角落悄悄拿到半成品 |
| 单元测试免容器 | `new OrderService(mockRepo)` 直接测，不用起 Spring 容器，也不用反射工具往私有字段里塞 mock |

### 官方态度

- Spring 4.3+：**单个构造器时连 `@Autowired` 都可以不写**，容器自动识别 —— 官方用"最省事"的方式给构造器注入开了绿灯。
- Spring Data 负责人 Oliver Gierke 的《Why field injection is evil》是这场运动的标志性文章，Spring 官方文档从 4.x 起明确建议构造器注入。
- 工程落地标配：Lombok `@RequiredArgsConstructor`，final 字段 + 自动生成构造器，零模板代码。

### 字段 / setter 注入还适用的场景

| 场景 | 方案 |
|---|---|
| 可选依赖（没有也能跑） | 构造器参数用 `ObjectProvider<T>` 或 `Optional<T>`，比 `@Autowired(required = false)` 更显式 |
| 确实要保留的循环依赖（逃生门） | setter 注入或 `@Lazy`，但先问自己三次"这环真的拆不掉吗" |
| `@Bean` 方法 | 依赖写在**方法参数**上，本质就是构造器注入的配置版 |

## 收口：所有坑的同一个根

把本文十四个主题排开看，会发现它们全部收敛到 Q1 的主干上：

| 本文主题 | 收敛到 Q1 的哪个点 |
|---|---|
| 代理失效家族、JDK/CGLIB、`@Lazy` | 初始化阶段 `wrapIfNecessary` 生成代理，调用必须走代理 |
| 注入三兄弟、多 Bean 选择 | 属性填充阶段 `AutowiredAnnotationBeanPostProcessor` 的解析规则 |
| `@Bean` 互调、lite 模式 | `@Configuration` 类自己也是一个被增强的 Bean |
| prototype 注入单例 | 属性填充一辈子只发生一次 |
| `@Value` static、四位置顺序 | 生命周期各阶段的边界：`@PostConstruct` 在填充后、代理前 |
| `@EventListener` | 循环依赖是设计信号的解法篇 |
| FactoryBean、自动装配 | Bean 的注册方式不止注解一种 |
| 构造器注入 | 三级缓存救不了构造器环（启动期炸反而是好事）；依赖声明从注解暗处挪到 Java 语法的明处 |

> 所以复习路径不是"背十四个孤立的坑"，而是：**每次踩坑，先问"这对应生命周期的哪一步、哪条规则"，把坑挂回主干上，它就不会再掉下去。**
