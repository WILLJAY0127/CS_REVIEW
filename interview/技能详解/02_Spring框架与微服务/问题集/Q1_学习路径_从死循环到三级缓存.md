# Q1 学习路径：从"死循环"到"三级缓存"

---

## 先纠正一个顺序问题

感觉是"看不懂三级缓存"，实际是"还没看懂它要解决什么问题"。直接背结论必然忘，因为三级缓存是**答案**，而你对**问题**没有感觉。

理解路径应该是：先撞上死循环 → 自己想出解法 → 发现解法的新缺陷 → 第三级缓存是补丁。走完这一圈就忘不掉了。

## 第 1～2 步：先亲手撞死循环

无循环依赖很简单：`getBean("a")` → 实例化 A → 填充时 `getBean("b")` → 创建 B → 返回 → A 填完 → 初始化 → 成品。

循环依赖就出事了：`getBean("a")` → 实例化 A → 填充时 `getBean("b")` → 实例化 B → 填充时 `getBean("a")` → **一级缓存里没有 A（A 还没创建完）→ 再去创建 A → 无限递归 → StackOverflowError**。

这就是"为什么必须拆三步"的直接后果：A 在填充阶段被回头索取，但它此刻只是个半成品。**问题不是缓存不够，是半成品对外不可见。**

---

## 第 3 步：你自己就能发明二级缓存

解法很自然：A 刚 `new` 出来（还没填充）时，先把它登记到一个"早期引用"表里。B 回头要 A 时，查到早期引用，直接给出去。

```java
Map<String, Object> level1 = new HashMap<>();  // 成品
Map<String, Object> level2 = new HashMap<>();  // 早期引用（你发明的）
```

到这里循环依赖已经被打破了。**所以"两级行不行"的答案是：能解决循环依赖，但会带来新问题**——这正是面试官想听的转折。

---

## 第 4 步：为什么还需要第三级（这是全题的灵魂）

假设 A 上有 `@Transactional`，Spring 会给它生成一个代理对象，调用方必须拿到**代理**，否则事务不生效。

现在有个两难：

- 如果 B 回头要 A 时，你直接给**原始对象** → B 拿到的是裸对象，A 后续所有增强（事务、缓存、异步）全绕过。
- 如果 B 回头要 A 时，你给**提前生成的代理** → 那代理就必须在"半成品阶段"就造出来。可万一这个 Bean 根本没被循环依赖、没人来提前要它，这个代理就白造了（还可能造错，因为 `wrapIfNecessary` 的判断需要 Bean 完整）。

解法：**别存对象，存"生产对象的方法"**。

```java
Map<String, ObjectFactory<?>> level3 = new HashMap<>();  // 工厂
```

- 平时没人要 → 工厂一直躺着，不产生任何代理，正常流程走完后在 `initializeBean` 的 after 阶段统一 `wrapIfNecessary`。
- 真有人来提前要 → 才调用工厂，此刻执行 `getEarlyBeanReference` 生成代理，把结果放进二级缓存。

这就是 `addSingletonFactory` 的真实目的：**把"要不要生成代理"这个决定，从"创建时"推迟到"真正被需要时"**。

配套的还有一个细节：代理生成后会被记录进 `earlyProxyReferences`，后续 `postProcessAfterInitialization` 发现已经代理过，就跳过，保证**代理只生成一次**。

## 第 5 步：手搓 mini 容器（这才是真正"了解"）

这段代码可以直接跑，60 行，没有 Spring 依赖：

```java
import java.util.*;
import java.util.function.*;

public class MiniContainer {

    record BeanDef(Supplier<Object> creator, BiConsumer<Object, MiniContainer> populate) {}

    private final Map<String, BeanDef> defs = new HashMap<>();
    private final Map<String, Object> level1 = new HashMap<>();           // 成品
    private final Map<String, Object> level2 = new HashMap<>();           // 早期引用
    private final Map<String, Supplier<Object>> level3 = new HashMap<>(); // 工厂

    void register(String name, Supplier<Object> creator,
                  BiConsumer<Object, MiniContainer> populate) {
        defs.put(name, new BeanDef(creator, populate));
    }

    Object getBean(String name) {
        Object bean = level1.get(name);
        if (bean != null) return bean;

        Object early = level2.get(name);
        if (early != null) return early;

        Supplier<Object> factory = level3.get(name);
        if (factory != null) {
            early = factory.get();
            level2.put(name, early);
            level3.remove(name);
            return early;
        }

        Object instance = defs.get(name).creator().get();
        level3.put(name, () -> instance);
        defs.get(name).populate().accept(instance, this);
        level3.remove(name);
        level2.remove(name);
        level1.put(name, instance);
        return instance;
    }

    static class A { B b; }
    static class B { A a; }

    public static void main(String[] args) {
        MiniContainer c = new MiniContainer();
        c.register("a", A::new, (o, ctx) -> ((A) o).b = (B) ctx.getBean("b"));
        c.register("b", B::new, (o, ctx) -> ((B) o).a = (A) ctx.getBean("a"));

        A a = (A) c.getBean("a");
        System.out.println(a.b.a == a);
    }
}
```

三个实验，每个都是一次"aha"：

1. **原样跑** → 输出 `true`，循环依赖被打破。
2. **删掉 level3，把 `level3.put(name, () -> instance)` 换成 `level2.put(name, instance)`** → 依然输出 `true`。这证明**两级就够打破循环依赖**。
3. **把工厂改成 `() -> proxy(instance)`**（伪代码，模拟 AOP）→ 会发现依赖方拿到的是代理。把"第三级存在的唯一理由"变成亲手验证过的结论，而不是别人告诉你的。

## 第 6 步：回源码对号入座（只看 5 个位置）

别一上来读整本源码，按这个顺序看，每个只看关键几行：

1. `AbstractAutowireCapableBeanFactory#doCreateBean` —— 只看三个方法调用：`createBeanInstance` / `populateBean` / `initializeBean`，其余全跳过。
2. 同一个类里的 `addSingletonFactory` 和 `getEarlyBeanReference` —— 看它往三级缓存塞的是什么。
3. `DefaultSingletonBeanRegistry#getSingleton(String, boolean)` —— 看三级缓存的三次查找顺序。
4. `AbstractAutoProxyCreator#getEarlyBeanReference` 和 `postProcessAfterInitialization` —— 看 `earlyProxyReferences` 怎么防止重复代理。
5. `doGetBean` 里的 `getSingleton(beanName, () -> createBean(...))` —— 看懂"缓存查询包着创建逻辑"这个结构。

调试怎么看：

- 在 `getSingleton` 打断点，条件设成你的 beanName，然后 IDEA 里 Evaluate 依次看 `this.singletonObjects.keySet()`、`earlySingletonObjects`、`singletonFactories`，能直观看到"半成品什么时候被登记、什么时候升级、什么时候清空"。
- 或者开日志：`logging.level.org.springframework.beans=TRACE`，能看到完整的创建链条。
