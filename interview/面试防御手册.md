## 1. Java 集合与基础

### Q1.1 HashMap 底层原理?为什么线程不安全?

- **结构**:JDK8 数组 + 链表 + 红黑树。默认容量 16、负载因子 0.75;链表长度 ≥ 8 **且**数组长度 ≥ 64 才树化(不足 64 优先扩容),节点 ≤ 6 退化回链表。
- **put 流程**:hash 扰动(`(h=key.hashCode()) ^ (h>>>16)`)→ `(n-1)&hash` 定位桶 → 空桶直接放;否则比较 key(地址/equals),相同覆盖;不同尾插链表;树化判断 → 扩容判断。
- **扩容**:2 倍扩容;JDK8 不用重算 hash,用 `e.hash & oldCap` 判断元素留原位还是移到 `原位+oldCap`。
- **不安全**:JDK7 头插法并发扩容出环形链表导致 get 死循环 CPU 100%;JDK8 尾插解决死循环但并发 put 仍数据覆盖。→ ConcurrentHashMap。

### Q1.2 ConcurrentHashMap 1.7 与 1.8 区别?

- 1.7:Segment 分段锁(默认 16 段),每段一把 ReentrantLock,并发度=段数。
- 1.8:废弃 Segment,**CAS + synchronized 锁桶头节点**,锁粒度更细;红黑树;size 用 baseCount + CounterCell 分散计数。
- 加分:put 时空桶 CAS 无锁插入,非空才锁头节点,锁竞争概率低。

### Q1.3 ArrayList vs LinkedList?

- ArrayList:数组,默认懒创建初始 10,扩容 1.5 倍;随机访问 O(1),尾插均摊 O(1),中间插删 O(n)。
- LinkedList:双向链表,头尾插删 O(1),下标访问 O(n),节点对象额外内存开销。实际几乎不用(数组缓存友好)。

### Q1.4 String 不可变?intern?

- 不可变(char[]/byte[] final + 类 final):可缓存 hash、线程安全、常量池前提。
- intern():JDK7+ 常量池在堆,首次遇到放引用;== 比地址,equals 比值;单线程拼串用 StringBuilder。

## 2. 并发编程

### Q2.1 volatile 解决什么?保证原子性吗?

- 两语义:**可见性**(写完刷主存 + 缓存行失效,MESI)+ **禁止重排**(内存屏障)。
- 不保证原子性:`i++` 仍不安全,原子用 AtomicInteger(CAS)或锁。
- 场景:状态标志位、DCL 单例。
- 挂简历:AI 同事平台的"LLM 服务降级开关"、对账任务启停标志用 volatile,配置中心推送后所有线程立即可见。

### Q2.2 synchronized 锁升级?

- Mark Word 记录:**无锁 → 偏向锁(首个线程 CAS 写线程ID)→ 轻量级锁(CAS 指向栈帧锁记录,失败自适应自旋)→ 重量级锁(ObjectMonitor,挂起线程,用户态转内核态)**。只升不降。
- 设计意图:无竞争/低竞争占绝大多数,分级以最小代价覆盖不同竞争程度。

### Q2.3 synchronized vs ReentrantLock?

- synchronized:JVM 关键字、自动释放、可重入、非公平;ReentrantLock:AQS 实现、finally 手动 unlock、可公平/非公平、可中断 lockInterruptibly、可超时 tryLock、多 Condition。
- 选型:简单同步用 synchronized;要超时/中断/公平/多条件队列用 ReentrantLock。

### Q2.4 AQS 原理?

- `volatile int state` + CAS 更新 + CLH 变体**双向 FIFO 队列**;抢不到 state 的线程封装 Node 入队,park/unpark 挂起唤醒。
- 独占:ReentrantLock;共享:CountDownLatch、Semaphore、读写锁(高16读低16写)。一句话:一个 volatile 变量 + CAS + 一个排队队列,JUC 共同骨架。

### Q2.5 线程池七参数?执行流程?拒绝策略?为什么不用 Executors?

- 七参数:corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。
- 流程:核心线程未满建核心 → 满了入队 → 队满建非核心至 max → 还满走拒绝策略。
- 拒绝策略:Abort(抛异常)、CallerRuns(调用者线程跑,天然背压)、Discard(静默丢)、DiscardOldest(丢队头)。
- 不用 Executors:无界队列/无限线程 → OOM。必须 ThreadPoolExecutor 显式控制。
- 参数:CPU 密集 核数+1;IO 密集 核数×2 或 核数/(1-阻塞系数);**工程上靠压测**:目标QPS×单任务RT 估算,压测调优,监控队列长度与拒绝数。
- 挂简历:① 支付回调/核心回执处理用独立线程池,与查询链路舱壁隔离;② LLM 调用线程池独立隔离 + 限流,防止大模型慢响应耗尽 Tomcat 线程拖垮整站;③ XXL-Job 批量代扣按分片调度。

### Q2.6 ThreadLocal 与内存泄漏?

- Thread.threadLocals 是 ThreadLocalMap,key 弱引用(ThreadLocal 对象)、value 强引用;ThreadLocal 回收后 key=null 但 value 被长生命周期线程(线程池)持有 → 泄漏 + 线程池串数据。
- 规范:finally 里 remove();跨线程池用 TransmittableThreadLocal。
- 挂简历:① 全链路 traceId、② AI 问答的会话上下文(userId、会话ID)、③ 压测标记都用 TTL 跨线程池透传。

### Q2.7 CAS 与 ABA?

- CAS:内存值/期望值/新值,相等才更新,CPU 原子指令。
- 问题:ABA → AtomicStampedReference 版本号;自旋开销 → LongAdder 分段;单变量限制 → AtomicReference。

## 3. JVM

### Q3.1 运行时数据区?

- 私有:程序计数器(唯一无 OOM)、虚拟机栈(栈帧:局部变量表/操作数栈/动态链接/返回地址)、本地方法栈。
- 共享:堆(新生代 Eden:S0:S1=8:1:1 + 老年代)、方法区(JDK8 元空间用本地内存:类元信息、常量池、静态变量)。

### Q3.2 如何判断对象死亡?GC 算法?

- 可达性分析:GC Roots(栈中引用、静态字段、常量、JNI 引用)不可达则回收。
- 算法:标记-清除(碎片)、标记-复制(新生代)、标记-整理(老年代);分代收集。

### Q3.3 CMS vs G1?

- CMS:老年代标记-清除,初始标记(STW)→并发标记→重新标记(STW)→并发清除;并发低停顿,但 CPU 敏感、浮动垃圾、碎片。
- G1:堆划分为 Region(逻辑 Eden/Survivor/Old/Humongous),标记-复制(Region 间复制无碎片),**可预测停顿**(MaxGCPauseMillis,按回收价值排序,Garbage First),SATB 处理漏标。
- 选型:小堆 Parallel/CMS;大堆要可控停顿 G1;亚毫秒停顿 ZGC。

### Q3.4 什么时候 Full GC?

- 老年代不足(大对象、泄漏、晋升快)、元空间不足(动态类加载)、CMS promotion failed/concurrent mode failure、空间担保失败、System.gc()。

### Q3.5 线上排查三板斧(必问)

- **CPU 100%**:top → top -Hp pid → 线程 id 转 16 进制 → jstack 定位线程栈(死循环/正则/频繁GC)。
- **OOM/泄漏**:jmap -dump(或 -XX:+HeapDumpOnOutOfMemoryError)→ MAT 支配树看大对象与引用链。
- **频繁 Full GC**:jstat -gcutil 看代增长 → dump 分析(ThreadLocal 未 remove、静态集合无限长、队列堆积、大对象)。
- 挂简历:批量代扣上线时发现 Full GC 频繁,定位是一次性把百万级代扣明细 load 进内存做分批 → 改游标/分页流式拉取 + 小批量提交解决;类似还有保单导出改 EasyExcel 流式写。

### Q3.6 类加载与双亲委派?打破场景?

- 加载→验证→准备(零值)→解析→初始化(静态赋值/static块)。
- 双亲委派:请求先委托父加载器(Bootstrap→Ext→App),防核心类被篡改 + 避免重复加载。
- 打破:JDBC SPI(线程上下文类加载器反向委托)、Tomcat(webapp 独立 ClassLoader 隔离)、OSGi。

## 4. Spring

### Q4.1 Bean 生命周期?

实例化 → 属性填充(注入)→ Aware 回调 → BeanPostProcessor 前置 → 初始化(afterPropertiesSet/init-method)→ BeanPostProcessor 后置(**AOP 代理在此生成**)→ 使用 → 销毁。

### Q4.2 循环依赖为什么三级缓存?

- 三级:singletonObjects(成品)、earlySingletonObjects(早期半成品)、singletonFactories(ObjectFactory 工厂,lambda 决定是否提前生成 AOP 代理)。
- A 实例化后放工厂 → A 注入 B → B 注入 A 时调工厂拿早期引用(需代理则此时生成,放入二级)→ B 完成 → A 完成。
- 三级的意义:保证 AOP 场景代理对象唯一,代理生成提前且仅一次;二级也能做但需无条件提前代理,Spring 选择工厂延迟决策。
- 边界:构造器注入无法解决(无早期引用)→ setter/字段注入或 @Lazy;prototype 不支持。

### Q4.3 AOP:JDK 代理 vs CGLIB?

- JDK:基于接口(Proxy + InvocationHandler);CGLIB:基于继承(ASM 生成子类),不能代理 final。
- Boot 2.x 起默认 CGLIB。自调用失效、事务失效的根因都是走 this 原对象而非代理。

### Q4.4 事务失效场景?

1. 自调用(this 绕过代理)→ 注入自身/AopContext/拆类;2. 非 public;3. 异常被吞;4. 受检异常没配 rollbackFor;5. 多线程(事务在 ThreadLocal);6. 引擎不支持;7. 传播行为用错(REQUIRED 默认/REQUIRES_NEW 独立/NESTED 保存点)。

### Q4.5 SpringBoot 自动配置?

- @SpringBootApplication = 配置类 + @EnableAutoConfiguration + @ComponentScan;
- AutoConfigurationImportSelector 读取 META-INF/spring.factories(2.7+ 为 AutoConfiguration.imports)中的自动配置类;
- @ConditionalOnClass/MissingBean/Property 按条件装配。约定优于配置。

### Q4.6 SpringMVC 流程?

DispatcherServlet → HandlerMapping 找 Handler+拦截器链 → HandlerAdapter 执行(参数解析器)→ 返回值处理(@ResponseBody 经 HttpMessageConverter 转 JSON;否则视图渲染)。

## 5. MySQL

### Q5.1 为什么 B+ 树?

- 非叶节点只存键 → 扇出大、树矮(千万级 3~4 层、3~4 次 IO);叶子有序双向链表 → 范围/排序友好。
- B 树每节点存数据树更高;哈希不支持范围。挂简历:保单/缴费流水分库分表后单表控制千万级,正是让 B+ 树稳定 3 层。

### Q5.2 聚簇/回表/覆盖/最左前缀/ICP?

- 聚簇索引叶子存整行;二级索引叶子存主键 → 回表;查询列都在索引里即覆盖索引(Using index)。
- 联合索引最左前缀,范围查询右侧失效;ICP(5.6)把 where 条件下推引擎层用索引过滤减少回表(Using index condition)。

### Q5.3 隔离级别与幻读?

- 读未提交/读已提交(RC)/可重复读(RR,InnoDB 默认)/串行化。
- RR 下 **MVCC 快照读** + **临键锁当前读** 解决幻读:普通 select 走一致性视图;for update/update 加临键锁挡插入。

### Q5.4 MVCC?

- 隐藏字段 trx_id、roll_pointer(undo 版本链);ReadView(creatorTrxId、m_ids 活跃列表、min、max)。
- 可见性:trx_id<min 可见;≥max 不可见;区间内在 m_ids 中则未提交不可见,沿版本链回溯。
- RC 每次 select 新 ReadView;RR 首次生成复用。

### Q5.5 InnoDB 锁体系?

- 记录锁(唯一索引等值命中)、间隙锁(开区间防插入,仅 RR)、临键锁(记录+前间隙,默认);唯一索引等值未命中退化间隙锁。
- **行锁加在索引上**:更新不走索引 → 锁不到索引 → 锁全部记录(类表锁)。
- 意向锁(IS/IX 表级,快速判断表上有无行锁)。
- 死锁:等待图检测,回滚代价小者;预防:固定加锁顺序、短事务、RC 减少间隙锁。
- 挂简历:缴费回调更新保单状态时 `where id=? and status=?` 走主键 + 状态条件,锁粒度最小;资金类操作禁止无索引更新。

### Q5.6 redo/undo/binlog 与两阶段提交?

- redo(InnoDB 物理日志,WAL,crash recovery,循环写)、undo(逻辑反向,回滚+MVCC)、binlog(Server 层逻辑日志,复制+归档,追加写)。
- 两阶段提交:redo prepare → 写 binlog → redo commit;崩溃恢复时 prepare 状态看 binlog 完整与否决定提交/回滚,保证 redo 与 binlog 一致(主从一致)。
- 双 1:innodb_flush_log_at_trx_commit=1 + sync_binlog=1,金融场景标配。

### Q5.7 慢 SQL 怎么排查?

- 慢日志/pt-query-digest 聚合 → EXPLAIN 看 type/key/rows/Extra(Using filesort、Using temporary 危险)。
- 优化:联合索引对齐 where+order by、覆盖索引、避免函数/隐式转换/select *、深分页延迟关联;架构层缓存、ES 异构、分库分表。
- 挂案例:运营查"某代理人某时段保单列表",原 SQL 扫描百万行 → (agent_id, status, create_time) 联合索引 + 深分页改游标,P99 从秒级降到 200ms 内;复杂检索走 ES/OLAP。

### Q5.8 分库分表(保单/缴费流水)

- 垂直拆库按业务;水平拆按规则。分片键选**最高频查询维度 + 分布均匀**:C 端 80% 是"我的保单/我的缴费",选 user_id Hash,16 库 64 表,单表千万级。
- 非分片键查询:按保单号点查 → **基因法**,雪花 id 末 6 位嵌入 `user_id % 64`,拿保单号直达分片;运营/对账维度 → Canal 异构 ES/OLAP;字典表广播。
- 路由:`table = userId % 64`,`db = table / 4`;逻辑分片固定 64(2 的幂),扩容只做"表搬家"+双写+校验+切流,不 rehash。
- 代价:跨片事务、跨片聚合、局部唯一、运维复杂 → "能不拆不拆,先索引优化+冷数据归档"。

## 6. Redis

### Q6.1 为什么快?

纯内存;单线程执行命令(无锁/无切换/无并发问题);IO 多路复用(epoll);高效结构。6.0 网络读写多线程、命令执行仍单线程。

### Q6.2 五大数据结构底层?

- String:SDS(O(1) 长度、预分配、二进制安全);List:quicklist(节点为 listpack);Hash/Set:少元素 listpack/intset,多了 hashtable;ZSet:skiplist + hashtable(跳表有序 O(logN) 范围,hash 表 O(1) 取分)。

### Q6.3 持久化?

- RDB:fork 子进程快照(COW),恢复快但丢最后一次快照后的数据,适合备份;
- AOF:追加写命令,everysec 默认(最多丢 1 秒),重写压缩;4.0 混合持久化(RDB 全量+AOF 增量)。

### Q6.4 过期删除与淘汰?

- 惰性删除 + 定期删除(100ms 抽样);
- 淘汰:noeviction(默认报错)/allkeys-lru/volatile-lru/allkeys-lfu/volatile-ttl 等,缓存场景 allkeys-lru。

### Q6.5 穿透/击穿/雪崩?

- 穿透(查不存在的数据):空值短 TTL / 布隆过滤器。
- 击穿(热点 key 过期瞬间):互斥锁 setnx 重建 / 逻辑过期异步刷新返旧值。
- 雪崩(大批同时过期/Redis 宕机):TTL 随机打散、多级缓存(Caffeine)、限流降级、集群高可用。
- 挂简历:产品/条款缓存 TTL 基础值+随机;AI 问答的语义缓存用 Redis,过期策略随知识库版本失效(知识更新主动清缓存)。

### Q6.6 缓存与 DB 一致性?

- Cache Aside:读缓存 miss 查 DB 回种;写**先更新 DB 再删缓存**(删而非更新:并发写顺序不可控会写脏;懒加载避免无效计算)。
- 兜底:延时双删 / Canal 订阅 binlog 异步删 / 定时对账;只保证最终一致,强一致加锁或不走缓存。
- 挂简历:保单详情强一致走 DB;产品、条款、网点等读多写少走缓存;AI 知识库版本更新时主动失效语义缓存。

### Q6.7 分布式锁?看门狗?Redlock?

- 基础:`SET key uuid NX EX 30`,释放用 Lua(判 value 是自己才删)。
- Redisson 看门狗:默认 30s,后台每 10s 续期;业务完主动释放;客户端宕机不续期,到期自动释放不死锁;hash 结构记可重入次数。
- Redlock:N/2+1 独立节点加锁成功才算;争议(Kleppmann:时钟跳跃/GC 停顿下仍可能双持,正确性需 fencing token)。
- 工程:业务锁单 Redis + Redisson 足够;强 CP 用 ZK/etcd。
- 挂简历:① 缴费回调处理防并发重复入账(Redisson 锁保单号);② 保全关键操作(退保)防用户并发提交;③ 统一封装锁组件强制粒度/超时规范。

### Q6.8 哨兵 vs Cluster?

- 哨兵:主从 + 哨兵集群监控与自动故障转移(主观/客观下线、Raft 选 leader、选复制 offset 最大的从)。
- Cluster:16384 槽,CRC16%16384,Gossip 通信,MOVED/ASK 重定向,至少 3 主 3 从。数据量要水平扩展用 Cluster。

### Q6.9 大 key / 热 key?

- 大 key:阻塞主线程、迁移卡顿、网卡打满、集群倾斜;--bigkeys 发现;拆分、压缩、UNLINK 异步删。
- 热 key:本地缓存 Caffeine 兜读;写热点拆 key 副本分散;AI 语义缓存的热点问答同理用本地缓存挡。

## 7. 消息队列

### Q7.1 为什么用 MQ?代价?

- 异步(短信/邮件/核心报文通知非主链路,核心接口 RT 降 70%)、解耦(缴费成功后核心入账、积分、通知各自订阅)、削峰(开门红/批量回执洪峰)。
- 代价:可用性依赖、复杂度(丢/重/顺序/积压)、最终一致。

### Q7.2 怎么保证不丢?

- 生产端:同步发送+重试;关键链路**本地消息表**(业务数据与消息同库事务写入,后台扫描发送,成功标记)或事务消息。
- Broker:同步刷盘 + 同步复制;Kafka acks=all、min.insync.replicas≥2、禁 unclean 选举。
- 消费端:**手动 ACK**,业务成功再确认;失败退避重试,最终死信队列 + 告警 + 对账兜底。
- 挂简历:缴费成功驱动核心入账用本地消息表;所有资金消息消费幂等 + 死信告警 + 日终对账三重保障。

### Q7.3 重复消费/幂等?

- at-least-once 必然重复,消费端幂等:业务唯一键(渠道流水号/保单号)去重表唯一索引、Redis SETNX 判重、状态机合法流转(已处理直接返回成功)。

### Q7.4 顺序消息?

- 局部有序:同一保单/流水号 hash 到同一 queue;RocketMQ MessageListenerOrderly 单 queue 加锁顺序消费(失败阻塞重试不跳过);并发度受 queue 数限制。

### Q7.5 积压怎么办?

- 定位:消费慢(下游 RT/GC/锁)、消费者挂、突增。
- 应急:扩消费者(不超 queue 数,超了先扩 queue)、临时转发多队列 topic 并行消费、毒丸消息跳死信、非核心消息降级丢弃;恢复后补数对账。预防:lag 监控告警。

### Q7.6 事务消息?本地消息表?

- RocketMQ 事务消息:half 消息(不可见)→ 执行本地事务 → commit/rollback;未确认则 Broker 回查(查业务是否存在),默认 15 次。
- 本地消息表:业务表与消息表同库本地事务写入,后台任务扫描未发送消息投递,成功更新状态;不依赖 MQ 事务特性,通用稳妥。
- 挂简历:缴费成功 → 核心入账用本地消息表(核心系统不支持事务消息且是异步回执模式,消息表 + 回执匹配 + 对账最稳)。

### Q7.7 延迟消息?(续期催缴核心场景)

- RocketMQ 开源版 18 个固定延迟等级(1s~2h),原理:延迟消息先进内部 SCHEDULE_TOPIC(每等级一 queue),定时任务扫描到期还原投递。
- 挂简历:续期全周期提醒(缴费日前 7 天/当天、宽限期 60 天节点、中止预警、复效提醒)用延迟消息事件驱动,替代扫表;另留低频扫表兜底防消息极端丢失。

### Q7.8 Kafka 高吞吐?

顺序写 + Page Cache + sendfile 零拷贝 + 批量压缩 + 分区并行 + 稀疏索引。ISR/HW 机制保证 leader 切换不丢已提交消息。

## 8. 分布式

### Q8.1 CAP/BASE?

- 网络分区必然 → P 必选,CP(ZK/etcd,选举时不可用)vs AP(Eureka/Nacos 临时实例,注册中心保可用);BASE:基本可用 + 软状态 + 最终一致。
- 金融口径:资金记账核心走强一致(数据库事务/核心系统自身保证);跨系统外围(平台 ↔ 核心 ↔ 渠道)走最终一致 + 对账兜底——这是金融系统的标准形态。

### Q8.2 分布式事务怎么选?

| 方案 | 一致性 | 侵入 | 适用 |
|------|--------|------|------|
| Seata AT | 强一致(全局锁) | 低 | 短事务、同构;高并发热点行评估锁性能 |
| TCC | 强一致 | 高(空回滚/悬挂/幂等) | 资金、额度 |
| 本地消息表 | 最终一致 | 中 | 跨系统通知,金融最常用 |
| 事务消息 | 最终一致 | 低 | RocketMQ 生态 |
| Saga | 最终一致 | 中 | 长流程(承保→缴费→生效) |

- 简历口径:平台内部短事务用 Seata AT;平台 → 核心入账用本地消息表 + 日终对账;缴费 → 渠道支付用支付状态机 + 回调幂等。
- TCC 三坑:空回滚(Try 未到 Cancel 先到)、悬挂(Cancel 后 Try 才到)、幂等。

### Q8.3 幂等设计?(资金链路必问)

- ① 前端防重 token(Redis Lua GET+DEL);② 数据库唯一索引(渠道流水号 + 业务类型,缴费回调的唯一键);③ 去重表;④ 状态机(待支付→已支付 只能一次,重复回调影响行数 0 即返回成功);⑤ 乐观锁 version。
- 挂简历:缴费回调三重幂等——渠道流水号唯一索引(防同笔回调重复)、缴费单状态机(防跨状态乱序)、Redis 锁(防并发同时处理);核心系统回执报文重发同样以报文流水号去重。

### Q8.4 限流/熔断/降级?

- 限流:固定窗口(临界突刺)、滑动窗口、漏桶(恒定速率)、**令牌桶**(允许突发,Sentinel/Guava 类似);Sentinel 集群限流解决"单机阈值×机器数"总量漂移。
- 熔断三态:closed → open(错误率/慢调用超阈值快速失败)→ half-open(探测)→ closed;降级:非核心功能关闭保核心。
- 挂简历:① LLM 接口按用户/租户限流(大模型按 token 计费,限流即控成本)+ 超时熔断转人工;② 开门红/批量期核心接口限流;③ 人脸厂商调用熔断自动切备用厂商。

### Q8.5 分布式锁选型?

- Redis:高性能、AP、主从切换极端丢锁,适合业务锁;ZK/etcd:临时顺序节点 CP,适合选主/调度协调;MySQL 唯一键/for update 重,适合低频。

### Q8.6 雪花算法?时钟回拨?

- 64 位:1 + 41 时间戳(ms,69 年)+ 10 机器位 + 12 序列(4096/ms);本地生成、趋势递增(B+ 树友好)。
- 回拨:小幅等待追平,大幅报错告警;美团 Leaf 号段+雪花双模式。
- 挂简历:保单号/缴费流水号雪花生成,末 6 位嵌入 `user_id % 64` 分片基因,id 自带路由信息。

## 9. AI 应用工程(LLM / RAG / Dify)— 重点差异化板块

> 2026 年面试的加分项。面试官假设你"真做过",从架构、效果、工程三个角度挖。
> 本项目真实场景:**投连险满期生存金问答**。两条心法:① 讲不清准确率怎么提升 = 没做过;② 金额/数字类答案必须实时查接口、禁止模型生成 = 金融场景的生命线。

### Q9.1 用一句话讲清 AI 同事怎么工作(满期金场景的全链路)

- 离线侧:满期金相关知识(投连险条款、满期生存金给付规则、领取材料与流程、FAQ、账户说明、税收规则)→ 解析 → 切分 chunk → Embedding → 向量库(带 metadata:产品、渠道、生效日期)。
- 在线侧:用户提问(如"我的保单什么时候满期""满期能拿多少钱")→ 脱敏 → **意图分流**:
  - **知识类**(领取条件、材料、流程、税收):RAG 链路——Query 改写/指代消解 → 混合检索(向量 + BM25)→ Rerank 取 Top-K → 拼 Prompt → LLM 生成 → 附引用 → SSE 返回;
  - **数据类**(满期日、投资账户价值、领取进度):Chatflow 调业务工具**实时查询**核心/投连账户系统,数字接口直出,模型只做组织解释;
  - **办理类**("我要领钱"):给出在线领取入口,跳转正式办理流程(核验中台实名+活体+生存核验 → 核心给付);
  - 闲聊/超范围:兜底 + 转人工。
- 一句话:RAG 让模型"开卷考试"回答规则问题,工具调用让模型"查系统"回答数据问题,办理引导把流量变成自助转化。

### Q9.2 为什么选 RAG 不选微调?

- RAG:知识更新分钟级(条款规则常变)、可溯源引用、冷启动快;微调:教风格/格式可以,知识更新要重训、不可溯源;满期金规则随产品和监管变,RAG 天然合适。
- 选型逻辑:知识问答 → RAG;数据查询 → 工具/工作流;流程自动化 → Chatflow;风格化 → 后期可叠加微调。

### Q9.3 准确率 62% → 88% 怎么做到的?(最核心问题)

按"知识在哪个环节丢了"分层治理,每层配满期金场景的真实 badcase:
1. **知识库侧**:① 早期把满期金给付规则 PDF 固定 500 字切块,问"领取要什么材料"召回的是相邻的退保章节 → 改按"章节 + 语义"切分,一个 chunk 讲一件事;② 客服高频问答(FAQ)以问答对入库,不塞长文档;③ 给付比例表/税率表结构化处理不切块;④ metadata 带产品/渠道/生效日期,失效版本不召回;⑤ 业务部门认领知识 owner、文档审核发布。
2. **检索侧**:① 单路向量检索不够,加 BM25 做混合检索(产品名、"满期生存金"等术语精确匹配强);② Rerank 精排(召回 20~30 条取 Top 5),解决"召回了但排序靠后";③ **Query 改写 + 意图区分**:用户说"我的钱什么时候能取",向量召回"退保现金价值"——实际问的是满期领取,改写为"满期生存金/领取条件"再检索;多轮指代消解("那它呢"补全主语);④ FAQ 精确匹配优先。
3. **生成侧**:① Prompt 强制"仅依据知识库与接口数据回答,没有就说不知道并转人工";② 回答附条款引用;③ 低温 0.1~0.3;④ **数字红线:满期金额、账户价值一律来自工具接口返回,Prompt 里明确"金额字段必须原样引用接口数据,禁止计算/估算"**。
4. **闭环侧**:真实咨询日志建 500+ 题评测集(含"该拒答"诱导题),知识库/Prompt/模型变更自动回归;线上点踩 + 转人工进 Badcase 池周会归类——约 40% 是知识缺失(新产品满期规则没入库),推动业务补知识。
- 数字拆解:62→78 靠切分 + 混合检索 + Rerank;78→85 靠 Query 改写 + 拒答策略;85→88 靠 badcase 闭环 + 知识补全。

### Q9.4 chunk 切分策略?

- 太小语义破碎、太大主题混杂;按文档标题层级优先切,语义边界二次切,chunk 间留 50~100 字 overlap;条款天然按"第 X 条"组织按条切;表格结构化;用评测集召回命中率验证不同策略。

### Q9.5 为什么要混合检索(向量 + BM25)?

- 向量擅长语义/口语("钱什么时候能取"→ 满期领取),但对精确术语(产品名、"满期生存金"、比例数字)不敏感;BM25 精确匹配强但不懂同义口语;两路并集 → Rerank 统一精排,融合策略用评测集调。

### Q9.6 Rerank 和 Embedding 召回的区别?

- 召回:双塔模型,query 和文档分别编码,ANN(HNSW)快但粗;Rerank:Cross-Encoder 把 query+chunk 拼一起算相关性,准但慢,只对粗筛几十条做。类比:索引找 30 本书(快)→ 翻目录比对(准)→ 取 5 本。

### Q9.7 Embedding 模型怎么选?

- 中文优化/多语言模型(BGE、m3e 等);看自己业务评测集的召回命中率不看排行榜;模型升级向量空间不兼容,需全库 reindex 版本迁移。

### Q9.8 幻觉怎么控制?满期金场景出过什么事?

- 通用手段:RAG 强约束、引用溯源、低温、低置信拒答转人工、关键实体后处理校验、诱导题测拒答率。
- 本项目最大的幻觉风险:**模型编造金额**——投连账户价值每日波动,模型不可能知道,早期有模型按"演示利益"话术估了个数字,被坐席点踩发现。治理:① 金额类问题强制走工具查询,接口直出;② Prompt 红线"禁止生成任何金额/收益数字";③ 回答后处理正则提取数字,若非来自接口字段则拦截;④ 坐席场景人在回路(AI 给建议+引用,坐席确认后发客户)。
- 态度:答错比答不出危险——保险误导销售有合规责任,宁可转人工不可乱答。

### Q9.9 Query 改写与多轮对话?

- 小模型结合最近 N 轮历史做指代消解 + 改写,输出独立完整检索 query;满期金场景多轮常见:"我那张保单呢"→"保单号 XXX 的满期生存金领取条件";改写失败回退原 query;历史窗口 + 摘要压缩控 token。

### Q9.10 评测体系?指标?

- 500+ 题:真实客服日志按业务分层抽样(满期金咨询 60%、投连账户 20%、领取流程 20%)+ 专家补边界题 + 15% 诱导拒答题;每题标标准答案要点、应引用条款、分类。
- 指标:答案准确率(LLM-as-judge 初评 + 每周 10% 人工双评校准)、引用正确率、拒答率/误拒率、检索召回命中率;业务指标:转人工率、AHT、点踩率、AI 引导领取转化率。
- 发布门禁:任何变更先过回归,指标不劣化才上线;Badcase 周会归类(检索失败/生成错误/知识缺失/系统问题)闭环。

### Q9.11 Dify 是什么?为什么选它?

- 开源 LLM 应用平台:知识库管理、可视化工作流(LLM/知识检索/条件分支/HTTP 工具节点)、应用发布、API+SSE、会话标注后台。
- 对比:自研 LangChain 链路知识库运营/标注后台都要从零做(3 人月+);商业 SaaS 数据出域不合规;Dify 私有化部署开箱即用,人力集中在 Java 集成层和准确率专项。
- 边界认知:Dify 是编排层不是资产;知识库、评测集、Prompt、工具接口都在自己手里,不被绑定。

### Q9.12 对话型 vs 工作流(Chatflow)?本项目怎么用?

- 对话型:开放式知识问答;Chatflow:固定节点编排,确定性可控。
- 本项目主用 Chatflow:入口意图识别节点(知识问答 / 账户查询 / 领取办理 / 闲聊)→ 知识分支走 RAG;数据分支走参数提取(保单号)→ HTTP 工具节点查核心/投连账户 → 查询结果与知识一起进生成节点;办理分支返回领取入口。金融场景优先确定性工作流,不用开放式 Agent 自主决策。

### Q9.13 Java 侧怎么对接 Dify?SSE 怎么做?

- 后端调 Dify Server API(blocking/streaming),前端不直连 Dify(鉴权审计都在 Java);流式:WebClient 收 Dify 的 SSE,后端再 SSE 透传前端做打字机效果;断连走 message detail 拉取。
- 会话:业务 userId ↔ Dify conversation_id 映射存 MySQL;
- 工具回调:Dify HTTP 节点回调 Java Webhook(查保单/查投连账户/查领取进度),这些接口无用户登录态 → 用 `@NoAuth` 白名单注解 + 签名/token + 内网 IP 限制放行,不动全局拦截器;
- 事件解析严格按 Dify 实际事件类型,不臆造字段;LLM 调用独立线程池 + 信号量限流,超时降级转人工。

### Q9.14 工具调用怎么保证安全?

- 白名单:只暴露只读工具(保单状态、满期日、投连账户价值、领取进度、网点);**写操作(领取申请、信息变更)绝不通过 AI**,走正式业务流程 + 人脸/生存核验;
- 越权校验:userId 从会话上下文取,保单归属校验,不信模型传参;
- 出参脱敏:账户金额等字段按角色返回,日志脱敏;
- 全量审计 + 独立限流防循环调用。

### Q9.15 成本怎么控?

- 意图路由:FAQ/闲聊走小模型(约 1/10 成本),复杂推理走大模型;语义缓存(满期金高频问题集中度高,命中率约 30%);Top-K 收紧 + 历史摘要压 token;token 消耗按部门/场景入大盘核算;单问成本降约 60%。

### Q9.16 数据安全与权限?

- 入模脱敏:身份证/手机号/保单号/银行卡正则+NER 掩码;Dify、向量库、模型全内网私有化;知识库按部门 metadata 隔离;全量问答与工具调用审计留痕。

### Q9.17 LLM 挂了/答错了怎么兜底?

- 超时重试 → 切备用模型 → 熔断转人工;坐席场景 AI 永远是"建议 + 引用",人在回路;对客场景转人工入口常驻。

### Q9.18 向量数据库?

- 存向量 + metadata,ANN 检索(HNSW/IVF);Dify 生态 Weaviate/Qdrant/Milvus/PGVector;几十万 chunk 用 PGVector 最省事,百万级以上 Milvus/Qdrant;难点在切分/混合检索/Rerank/评测,不在向量库。

### Q9.19 "满期能拿多少钱"为什么不让模型直接算?

- 投连险满期金 = 投资账户价值(投资单位数 × 最新单位价格),单位价格每日随市场波动,模型训练数据里没有、也不可能实时知道;让模型答数字必然是编造(幻觉),在金融场景就是误导销售风险。
- 正确做法:这类问题由 Chatflow 意图识别后调投连账户系统接口实时查询,**接口返回什么数字,回答里就引用什么数字**,模型只负责解释"这个金额由账户价值构成、如何领取"。同理:领取进度、满期日期全部走接口。
- 一句话:**规则靠检索、数字靠接口、模型只负责表达**。

### Q9.20 咨询 → 办理闭环怎么落地?怎么衡量 AI 的业务价值?

- 落地:意图识别到"领取/办理"类问题 → AI 回答规则后给在线领取入口(带保单上下文预填)→ 跳转领取流程(核验中台实名+活体+生存核验 → 核心试算 → 确认 → 给付);领取进度可回 AI 查询。
- 价值指标(管理面必问):准确率/引用正确率(质量)、转人工率 55%→22%、满期金人工咨询量降 50%、坐席 AHT 降 25%、**AI 引导的线上领取转化率**(埋点统计从 AI 入口进入领取流程的完成率,与断点平台打通)。
- 注意:AI 价值不能只讲"更智能",要讲替代了多少人工、带来多少自助转化、省了多少成本。

## 10. 保险业务与金融级实践(领域面)

> 面试官不懂保险没关系,你要能用大白话讲清业务,再落到技术。领域知识是你区别于互联网候选人的壁垒。

### Q10.1 保险核心系统是什么?你们外围系统怎么和它交互?

- 保险核心系统:保险公司的"账本系统",管保单全生命周期的**承保(投保出单)、保全(变更)、理赔、收付费(记账)**,通常是外购(中科软/易保等)或自研老系统,稳定但技术栈老、改造成本高。
- 外围系统:互联网 App/公众号、经代渠道、客服系统等面向客户的系统,不直接记账,通过**核心接口**做交易、通过**批量文件**(日终对账文件、代扣文件)做批量交互。
- 交互模式三种:① 同步接口(实时查询/简单交易);② 异步交易(外围发申请 → 核心受理后异步回执,通过 MQ 驱动状态机);③ 批量文件(日终对账、代扣, SFTP/接口拉取)。
- 技术要点:**防腐层(ACL)**隔离核心报文/字段/状态差异,核心换版本或字段变更不蔓延业务层;所有交互带报文流水号,重发幂等;核心不可用时外围有降级(受理"处理中",事后补)。

### Q10.2 保全是什么?

- 保单生效后的一切变更服务:联系方式/地址变更、受益人变更、缴费银行卡变更、保额调整(减保)、退保、保单贷款、复效(中止后恢复)、投保人变更等。
- 特点:规则复杂(不同保全项对保单状态、材料、资格有要求)、部分涉及资金(退保打款、贷款)、高风险项需人脸核验 + 电子签名 + 影像材料留档、监管要求可回溯。

### Q10.3 期缴、宽限期、中止、复效?

- 期缴:保费按年/月分期交(对比趸交一次性交清);续期缴费是每年到期交下一期。
- **宽限期**:约定缴费日没交,一般 60 天内补交保单仍有效,出险仍赔;
- **中止(失效)**:宽限期满仍未交,保单效力中止,出险不赔;
- **复效**:中止后一定期限内(通常 2 年)补交保费 + 利息 + 健康告知,可申请恢复效力;超期合同终止。
- 技术映射:这套生命周期就是**保单状态机**;各节点的提醒(缴费日前、宽限期、中止前、复效期)用延迟消息驱动;代扣在宽限期内按策略重试。

### Q10.4 三方对账怎么做?长短款怎么处理?

- 三方数据:① 支付渠道账单(微信/支付宝/银联 T+1 提供,客户实际付了多少钱);② 平台缴费流水(我们自己记的缴费单);③ 核心系统应收/实收(保单该收多少、核心记了多少)。
- 勾兑逻辑:以业务流水号/渠道流水号关联三方,金额一致 → 平账;不一致分类:
  - **长款(平台/渠道收了钱,核心没入账)**:钱收了保单没生效 → 高优先级,自动触发补入账(本地消息表重试)+ 告警,补不了人工工单;
  - **短款(核心入账/显示已缴,渠道没收到钱)**:技术上极少(支付成功才回调),出现说明状态错乱 → 冻结异常单,人工核查;
  - **单边账**:渠道有账单平台无流水(可能支付成功但回调丢失)→ 主动查单(主动调渠道查询接口)补单;平台有流水渠道无账单(可能支付中)→ 等待/关单。
- 机制:T+1 日终批量自动对账,差异自动生成工单 + 飞书告警;高频差异(如回调丢失)用主动查单任务小时级兜底,不等日终。
- 原则:**资金链路笔笔有出处、差异必有工单、处理必有闭环**。

### Q10.5 讲一下一笔缴费的完整资金链路?

```
用户发起缴费 → 风控/校验(保单状态、应缴金额以核心应收为准,不信任前端传金额)
  → 创建缴费单(状态=待支付,渠道流水号占位)→ 调支付渠道下单(微信/支付宝/银联)
  → 用户支付 → 渠道异步回调(可能多次/延迟/乱序)
  → 回调处理:① 渠道流水号唯一索引去重 ② Redisson 锁缴费单防并发
    ③ 验签 + 金额核对(回调金额 = 应缴金额,防篡改)
    ④ 缴费单状态机 待支付→已支付(乐观锁,影响行数0说明已处理,直接返回成功)
  → 本地消息表写入"核心入账"消息(与缴费单状态更新同库事务)
  → 后台任务投递消息 → 核心收付费接口入账 → 核心异步回执匹配 → 缴费单 已支付→已入账
  → 日终:渠道账单 ↔ 平台流水 ↔ 核心实收 三方对账
失败/异常:回调超时未到 → 主动查单定时任务;入账失败 → 消息重试 + 对账补偿;
          用户重复支付 → 渠道侧/平台侧拦截,已支付单发起退款流程
```

### Q10.6 身份核验在保险里怎么用?技术链路?

- 用在哪:投保人实名认证、高风险保全(退保、保单贷款、受益人变更)、**满期生存金/年金给付前的生存核验**、理赔(含死亡核验)、电子签名前的本人确认。
- 链路:证件 OCR(身份证/居住证/回乡证/台胞证/护照,分证件模板)→ 二/三要素核验(按证件类型路由公安人口库或出入境权威通道)→ 活体检测(动作+静默,判定真实人脸,防照片/视频/面具)→ 人脸比对(相似度分数,**阈值按场景规则配置**)→ 生存/死亡状态核验 → 出具核验凭证(绑业务流水)→ 业务放行。
- 关键设计:**核验策略走规则引擎**(场景+证件类型 → 核验项组合/分数阈值/重试/降级,配置化热生效,不硬编码);主备双厂商熔断;凭证一次性防重放。
- 合规(个保法):人脸是**敏感个人信息**,需单独授权(不埋在总协议里)、最小化采集、加密传输存储、核验后限期删除原始生物特征、全流程审计、等保测评。
- 细节深挖见第 13 章连环问。

### Q10.7 金融场景技术选型和互联网有什么不同?

- 一致性优先级高于性能:钱不能错,宁可慢一点/转人工,不能出现资损;最终一致 + 对账是行业标准形态;
- 可追溯/可审计:所有资金、保全操作留痕(谁、何时、改了什么、依据什么),监管检查要能调出来;
- 变更保守:核心系统不轻易动,外围迭代快;灰度、回滚、双人复核;
- 高可用理解不同:保险没有秒杀式突发,但开门红、宽限期末日、批量代扣窗口有明显高峰,且系统在工作日工作时间不能停(柜面依赖)。

### Q10.8 二/三要素、OCR、电子签名简单解释?

- 二要素:姓名 + 身份证号一致性核验;三要素:加人脸/银行卡;四要素再加手机号。
- OCR:身份证/银行卡拍照识别文字,减少手输错误;
- 电子签名:基于可信时间戳 + CA 证书 + 人脸核验意愿确认,电子保单/保全协议签署具备法律效力(电子签名法),替代纸质签字。

### Q10.9 投连险、满期生存金、生存核验是什么?(AI 项目业务基础,必懂)

- **投连险(投资连结保险)**:保费扣除初始费用后进入**投资账户**,按当日单位价格买入"投资单位";账户价值 = 投资单位数 × 最新单位价格,单位价格随投资表现每日波动——**收益不保证、风险客户自担**,和传统险(预定利率保证)的根本区别。
- **满期生存金**:保险期间届满时**被保险人仍生存**,保险公司给付的保险金;投连险的满期金通常等于当时的投资账户价值(部分产品含持续奖金/保证部分)。
- **为什么要"生存核验"**:满期金/年金是"被保人生存才给付",若被保人已身故仍被冒领就是资损;传统方式要柜面或视频做生存证明,线上化后用**实名 + 活体人脸**确认"是本人且本人存活",这就是核验中台的生存核验能力与满期金业务的衔接点。
- **死亡核验**:理赔身故责任时,核验死亡信息(死亡证明 OCR + 权威数据源核对)。
- 客户高频问题:保单什么时候满期?满期能拿多少钱(=实时账户价值,必须查系统)?怎么领、要什么材料?为什么和当年演示利益不一样(投资波动)?领了要不要交税?——这些直接决定了 AI 问答"知识 + 实时数据 + 办理引导"的三段式设计。
- 业务链路(AI 与办理的衔接点):满期前通知 → AI/客服咨询 → 在线领取申请 → 核验中台(实名+活体+生存核验)→ 核心试算账户价值 → 用户确认(电子签名)→ 核心给付 → 银行转账 → 状态回执。

## 11. 项目一:保全与续期缴费平台连环问

### Q11.1 先讲一下一笔缴费从发起到对账的完整链路

直接用 Q10.5 的链路图,补充三个角色:**用户/渠道 → 平台(缴费单状态机)→ 核心系统(账本)**;两个异步点:支付回调(渠道→平台)、核心回执(核心→平台);两道兜底:主动查单 + 三方对账。

### Q11.2 核心系统那么老,你们怎么对接的?为什么要防腐层?

- 问题:核心系统报文格式(定长报文/老 XML/特定字段编码)、状态码、错误码体系和互联网侧完全不同;核心每年有版本升级,字段和接口会变。
- 做法:建独立**适配/防腐模块**,对外暴露面向业务的接口("申请退保""核心入账"),对内负责报文组装、字段映射、错误码翻译、加解密/签名;业务代码里不出现任何核心报文字段。
- 价值:核心升级/换接口只改编排适配层一个地方;业务单测不依赖核心环境(可 mock);不同渠道核心(公司多套核心)可多实现。
- 三种交互模式处理:实时查询同步调;交易类(保全申请、入账)发申请后等异步回执,回执进 MQ 驱动状态机;批量类(对账、代扣)走文件,XXL-Job 定时拉取解析。

### Q11.3 支付回调为什么会重复?怎么保证不重复入账?

- 重复原因:渠道重试策略(我方超时未返回 success,渠道按 15s/1min/5min...重推)、网络重试、人工补推。
- 三道防线(对应 Q8.3):
  1. **渠道流水号唯一索引**:回调落库 `(channel, channel_serial_no)` 唯一,重复回调 insert 冲突 → 直接查询原缴费单状态返回 success(注意:必须给渠道返回成功,否则渠道会一直重推);
  2. **Redisson 锁缴费单**:同一缴费单并发回调(渠道多机重试)串行化;
  3. **状态机乐观锁**:`update pay_order set status='PAID' where id=? and status='WAIT_PAY'`,影响行数 0 说明已处理,幂等返回。
- 回调处理还要:验签(防伪造回调)、金额核对(回调金额=缴费单应缴金额,防篡改/少付)。

### Q11.4 缴费成功了,但核心入账一直失败怎么办?

- 这是"钱收了、保单没生效"的长款场景,处理分层:
  1. **本地消息表**:缴费成功与消息写入同库事务,后台任务扫描未确认消息持续重试投递(指数退避,最多 N 次);
  2. **回执匹配**:核心入账是异步的,回执回来匹配消息标记成功;
  3. **超时告警**:消息超过阈值(如 30 分钟)未确认 → 告警 + 自动工单;
  4. **日终对账兜底**:三方对账自动捞出长款,自动补入账或生成人工工单;
  5. 业务兜底话术:用户端显示"缴费确认中",保单权益以核心到账为准。
- 关键认知:**最终一致 = 重试 + 告警 + 对账,不是放任不一致**。

### Q11.5 主动查单解决什么问题?

- 回调链路可能彻底丢失(回调地址故障、渠道侧异常);定时任务(如每分钟)扫描"待支付超过 N 分钟、已到渠道下单时间"的缴费单,主动调渠道"订单查询接口":渠道显示已支付 → 走和回调一样的入账流程(幂等);显示未支付 → 继续等;超时未支付 → 关单。
- 作用:把"等回调"变成"回调 + 主动查询"双保险,长短款在小时级发现,不等日终对账。

### Q11.6 银行批量代扣怎么做的?

- 业务:续期保费和银行签代扣协议,缴费日批量代扣,不用客户手动操作。
- 链路:XXL-Job 分片调度(按保单号哈希分片到多执行器)→ 每页游标拉取待扣保单(不一次性 load 全量,防 OOM)→ 组装代扣文件(加密)→ 上传银行/SFTP → 银行处理后返回回执文件 → 解析回执:成功 → 走缴费成功流程(幂等入账);失败(余额不足/卡失效/协议失效)→ 记录失败原因 → 宽限期内下一批次重试 / 触发催缴通知。
- 可观测:批次号维度统计总数/成功/失败/金额,失败明细可下载;大批量分批提交、失败不阻断整批。

### Q11.7 续期催缴为什么用延迟消息而不是定时任务扫表?

- 扫表问题:保单量 800 万,为了不漏提醒,扫描间隔要短 → 大量无效扫描(绝大部分保单当天不需要提醒);分库分表后扫 64 张表;提醒时间点多(前 7 天/当天/宽限期/中止前),扫表逻辑复杂。
- 延迟消息:保单生效/进入宽限期时就把各时间点的提醒消息投递(延迟等级 1s~2h 不够长的长延迟用**时间轮/延迟分级转发**或调度平台),到点触发,零无效扫描、天然分布式、失败可重试。
- 兜底:低频扫表(每天扫"当天该提醒但没发提醒记录"的小窗口)防消息极端丢失。

### Q11.8 退保这种涉及打款的保全,系统上怎么防风险?

- 身份强校验:人脸识别 + 短信验证码双因子(项目三能力);
- 资格与金额:退保能拿回的是**现金价值**(以核心计算为准,平台不自行算钱),申请后核心计算返回确认金额,用户确认才提交;
- 状态机:申请中 → 审核(大额/高风险规则转人工)→ 核心处理 → 打款中 → 完成,每个流转留痕;
- 防重复:防重 token + 业务流水唯一索引;
- 打款:走核心收付费/财务系统出款,平台不碰资金;影像材料(证件、签名)归档可回溯;
- 审计:谁在什么设备/IP、核验凭证、操作记录全链路留痕,监管检查可导出。

### Q11.9 分库分表后,对账批量任务怎么跑?

- 对账是离线批处理,不受分片键限制:对账任务按分片并发(64 个表/16 个库并行拉取),或把流水数据 Canal 异构到 OLAP(ClickHouse)/ES 后在异构侧聚合勾兑;
- 日终文件按渠道维度拉取,平台流水按渠道+日期范围查询(走 (channel, pay_date) 索引或异构侧),核心实收走核心对账文件;三方以流水号关联。

### Q11.10 开门红/宽限期末日的高峰怎么扛?

- 保险高峰形态:不是瞬时尖峰,是持续数小时的高水位 + 批量任务并发(代扣回执、核心回执洪峰)。
- 手段:① MQ 削峰,回执全量进 MQ,消费端按核心和 DB 承载限速消费;② 查询链路加缓存(产品、应缴信息);③ 批量任务错峰调度(代扣避开白天柜面时段);④ 压测定容量,核心接口/线程池/连接池水位监控;⑤ 缴费链路降级预案(核心慢时受理"处理中"异步化)。

### Q11.11 这个项目你最有成就感/最难的点?

- 口径建议:**三方对账体系从 0 到 1**——之前靠财务人工 Excel 勾兑,上线后差异小时级发现、自动化工单闭环,连续 3 年零资金差错;难点不在技术多高深,而在把"渠道账单、平台流水、核心应收"三套口径的差异场景(退款、部分支付、跨日、手续费)全部定义清楚并和财务、渠道、核心团队对齐规则。体现技术 + 业务 + 跨团队协调能力(管理岗加分)。

### Q11.12 投连满期生存金领取链路是怎样的?

```
满期前通知(延迟消息) → 用户咨询(AI 同事)→ 点"在线领取"入口
  → 领取申请(校验:保单归属、满期状态、未还保单贷款等)
  → 核验中台按"满期给付"场景规则执行:证件 OCR + 三要素 + 活体 + 人脸比对(高阈值) + 生存核验
  → 核心试算:核心返回账户价值/满期金金额(平台不自行计算金额)
  → 用户确认金额 + 电子签名
  → 核心给付指令(本地消息表驱动,回执驱动状态机)
  → 财务/银行转账 → 转账回执 → 状态机 给付中→已完成
异常:生存核验不通过/比对失败 → 转人工柜面;核心/转账失败 → 重试 + 工单;
      全流程节点事件上报断点平台,统计领取漏斗转化
```
- 关键点:金额以核心为准(平台只展示不计算);生存核验防冒领;状态机 + 消息表保证给付指令不丢不重;断点埋点让"领取卡在哪一步"可观测。

## 12. 项目二:AI 同事(投连满期生存金智能问答)连环问

### Q12.1 你负责什么?一句话讲清架构

- 角色:项目技术负责人,主导选型、架构设计、Java 集成层、准确率专项,带 2 名后端,协调业务/客服/核心团队。
- 四层架构:① 知识层(满期金条款/规则/FAQ,业务维护);② 编排层(Dify:对话型 + Chatflow,私有化);③ 集成层(自研 Java/Spring Boot 3):鉴权、会话、SSE 网关、工具 Webhook、脱敏、审计、限流;④ 渠道层(坐席工作台、客服系统、App/公众号入口)。
- 业务闭环:AI 咨询 → 识别领取意图 → 引导在线领取 → 核验中台生存核验 → 核心给付,领取进度可回查。

### Q12.2 为什么选满期生存金这个场景切入?

- 三高:咨询量高(满期客户集中)、查询成本高(金额随投连账户每日波动,客服要翻多个系统)、标准化程度高(规则明确、知识边界清晰,适合 RAG 冷启动);
- 且业务价值可量化:人工咨询量、AHT、线上领取转化率都能埋点统计——选场景时就想好了"用什么指标证明 AI 有用"。

### Q12.3 "满期能拿多少钱"这种问题 AI 怎么答?(必问)

- 不能让模型答:投连账户价值每日波动,模型不知道实时数字,编数字就是误导销售。
- 做法:Chatflow 意图识别为"账户/金额查询" → 参数提取(保单号,从会话上下文取)→ HTTP 工具节点调投连账户/核心系统接口实时查 → 接口返回的金额字段**原样填入回答模板**,Prompt 红线"金额数字必须引用工具返回,禁止计算估算";模型只负责解释金额构成(账户单位数 × 单位价格)和领取方式。
- 同理:满期日期、领取进度、转账状态全部走工具;规则类(材料、流程、税收)走知识库。一句话:**规则靠检索、数字靠接口、模型只表达**。

### Q12.4 准确率 62%→88% 怎么做到的?(展开 Q9.3,每层配满期金 badcase)

- 知识库:给付规则 PDF 固定切块导致"领取材料"召回退保章节 → 按条款章节切 + FAQ 问答对入库 + 表格结构化 + metadata(产品/渠道/生效日期);
- 检索:"我的钱什么时候能取"向量召回退保现金价值 → Query 改写区分满期领取 vs 退保;混合检索 + Rerank;
- 生成:金额编造红线(接口直出 + Prompt 禁止 + 后处理数字校验);强制引用 + 低温 + 低置信拒答;
- 闭环:500+ 评测集自动回归;周会 badcase 归类,约 40% 是知识缺失推动业务补。
- 数字拆解:62→78 检索侧;78→85 改写+拒答;85→88 闭环+补知识。

### Q12.5 怎么证明准确率提升?评测集怎么建?

- 500+ 题:客服真实会话日志分层抽样(满期金咨询 60%/投连账户 20%/领取流程 20%)+ 专家补边界题 + 15% 诱导拒答题(问知识库没有的产品、诱导编造金额);
- 每题标注:答案要点、应引用条款、是否需工具、分类;
- LLM-as-judge 按 rubric 自动评(要点覆盖、无错误信息、数字与接口一致、引用正确)+ 每周 10% 人工双评校准;
- 发布门禁:知识库/Prompt/模型/工作流变更先过回归,核心指标不劣化才上线。

### Q12.6 幻觉出过事吗?怎么兜底?

- 出过:早期模型按"演示利益"话术估金额、把 A 产品领取规则安到 B 产品;
- 治理:金额接口直出 + 数字后处理校验 + 引用溯源 + metadata 产品过滤 + 低置信拒答;
- 底线:坐席场景人在回路(AI 给建议+引用,坐席确认后发客户);对客场景转人工入口常驻;LLM 超时/报错熔断转人工。

### Q12.7 Java 对接 Dify 的技术细节?

- 后端调 Dify Server API,前端不直连;WebClient 收 SSE 流再 SSE 透传前端做打字机;断连走 message detail 补拉;
- userId ↔ conversation_id 映射存 MySQL;
- 工具 Webhook(查保单/投连账户/领取进度)无登录态 → `@NoAuth` 白名单注解 + 签名/token + 内网 IP 限制,不动全局拦截器;
- 事件解析严格按 Dify 实际事件类型,不臆造字段;LLM 调用独立线程池 + 信号量限流。

### Q12.8 工具调用安全?AI 能不能直接帮用户领钱?

- 不能。工具只有只读查询(保单状态、满期日、账户价值、领取进度);**领取/变更等写操作必须走正式业务流程**(登录态 + 人脸 + 生存核验 + 电子签名),AI 只提供入口跳转;
- 越权校验:userId 从会话取,保单归属校验;出参按角色脱敏;全量审计 + 限流防 Agent 循环调用;工具失败降级纯知识回答 + 转人工。

### Q12.9 成本怎么降 60%?

- 意图路由(FAQ/闲聊走小模型)+ 语义缓存(满期金问题集中度高,命中率约 30%)+ Top-K 收紧 + 历史摘要;token 按部门核算入大盘。

### Q12.10 知识过期/产品版本矛盾怎么办?

- metadata 强制过滤当前有效版本 + 渠道可见;文档审核发布流;Rerank 按生效日期/权威性加权;评测集含新旧版本题防答老条款。

### Q12.11 信息安全?

- 入模脱敏(身份证/保单号/手机号/银行卡正则+NER)、全内网私有化、知识库部门隔离、全量审计留痕。

### Q12.12 重做会改什么?

- 评测前置(第一天就建尺子)、知识运营机制前置(知识 owner + SLA)、多模态预留(条款截图/保单图片问答)、Agent 谨慎开放(确定性工作流优先)。

### Q12.13 怎么看 AI 对后端的影响?(管理面)

- 会用 AI 的后端替代不会用的;后端价值上移到系统设计、一致性、业务抽象、AI 应用工程(评测/灰度/降级/人在回路是新基本功);组内已推 AI 辅助编码与知识沉淀,新人上手周期缩短。

## 13. 项目三:多证件身份核验中台(规则引擎驱动)连环问

### Q13.1 为什么做中台?原来什么问题?

- 四痛点:① 各业务线(投保/保全/满期给付/理赔)各自对接厂商,凭证不通用、重复核验体验差;② 核验策略硬编码——比对分数阈值、要不要活体,改一次发一次版;③ 证件支持不全,港澳台/护照客户无法线上办理;④ 满期金、年金需要生存核验,原来只能柜面做生存证明。
- 中台价值:统一核验能力、统一凭证复用、策略配置化、多证件多通道、合规统一管控。

### Q13.2 完整核验链路(多证件版)?

```
业务场景(投保/退保/满期给付/理赔)+ 证件类型
  → 规则引擎决策:核验项组合(OCR?要素?活体?比对?生存核验?)、分数阈值、重试次数、降级策略
  → 证件 OCR(分证件模板:身份证/居住证/回乡证/台胞证/护照)
  → 二/三要素核验(按证件类型路由权威通道:公安人口库 / 出入境通道)
  → 活体检测(动作+静默,判定真实人脸)
  → 人脸比对(相似度 vs 规则阈值)
  → [满期/年金场景] 生存状态核验;[理赔身故] 死亡核验
  → 签发核验凭证(绑业务流水、限时、签名、防重放)→ 业务方校验放行
```

### Q13.3 规则引擎怎么设计的?(核心问题)

- 决策模型:**场景 + 证件类型 → 规则**,规则字段包括:核验项开关组合(OCR/二要素/三要素/活体/比对/生存核验)、比对分数阈值、失败重试次数、降级策略(是否允许人工复核)、生效渠道;
- 实现:规则用**决策表**存 DB(管理后台可视化配置),发布后推 Nacos/Redis 缓存热生效,执行时按场景+证件查规则;复杂条件(如"65 岁以上 + 满期给付 → 阈值降 2 分并增加引导")用 **QLExpress/Aviator 表达式**;
- 工程保障:规则版本化(可回滚)、按渠道灰度、规则变更走审批 + 评审;规则执行全留痕(命中了哪条规则、阈值多少)。
- 典型配置:满期给付 = OCR + 三要素 + 活体 + 比对(85 分)+ 生存核验;普通信息变更 = OCR + 二要素 + 比对(75 分)。

### Q13.4 为什么用规则引擎?不用 if-else / 为什么不用 Drools?

- 不用 if-else:策略频繁变(监管要求、新场景、阈值调优),硬编码每次发版周期长、风险大;业务方无法参与;
- 规则引擎价值:配置即上线、规则集中可审计(合规要求所有核验策略可追溯)、新人不用读代码;
- Drools vs 自研轻量:Drools 功能全但重、学习成本高、运维复杂;我们的规则维度固定(场景+证件 → 核验项),决策表 + QLExpress 表达式完全覆盖,几百行核心代码,团队好维护——选型按复杂度匹配,不炫技。

### Q13.5 多证件怎么支持?港澳台走什么通道?

- 证件类型:大陆身份证、港澳台居民居住证、港澳居民来往内地通行证(回乡证)、台湾居民来往大陆通行证(台胞证)、护照 5+ 类;
- 适配器模式:定义统一核验接口,按证件类型路由不同实现——身份证走公安人口库通道,居住证/回乡证/台胞证走出入境证件核验通道,护照走对应通道;OCR 识别模板按证件类型分别配置(字段位置、版式不同);
- 新增证件类型 = 新增一个适配器 + 配置规则,不改主流程(开闭原则)。

### Q13.6 活体检测怎么做?"验证是否真实人脸"?

- 动作活体(眨眼/摇头/张嘴)防静态照片;静默活体(无感采集,算法分析纹理/摩尔纹/3D 景深)防照片翻拍、视频回放、面具/3D 头模;双模式结合;
- 设备环境检测(root/模拟器/多开/注入框架)+ 高频尝试限流 + 风控;
- "真实人脸"结论 = 活体通过 + 人脸比对通过,两者缺一不可。

### Q13.7 生存核验 / 死亡核验是什么?怎么实现?

- 生存核验(满期生存金、年金给付前):确认被保人**仍生存且本人**,线上 = 三要素 + 活体(本人实时操作)+ 对接权威数据源的生存状态查询,替代柜面生存证明;防的是被保人身故后他人冒领;
- 死亡核验(理赔身故):死亡证明 OCR + 权威数据核对,辅助理赔定责;
- 结果进核验凭证,业务方据此放行/拦截;核验不通过转人工。

### Q13.8 比对分数阈值怎么定的?拍脑袋吗?

- 数据驱动:初版按厂商建议值,上线后用**断点平台**的失败分布数据校准——发现老年客户活体/比对失败率显著偏高(光线、皱纹、操作不熟练),按年龄分层调阈值 + 增加交互引导(光线提示、重试指引),通过率 +20% 且欺诈率无上升;
- 阈值按场景风险分级:高风险(退保、贷款、满期给付)高阈值,低风险(信息变更)低阈值;每次调整看 A/B 数据。

### Q13.9 主厂商挂了怎么办?

- 多厂商适配器 + 熔断(超时/错误率超阈值自动切备用);不同厂商分数体系不同,阈值按厂商分别配置;凭证记录实际厂商;双厂商均不可用时高风险业务转柜面、低风险可延后;厂商调用按次计费统一对账。

### Q13.10 凭证怎么防伪造、防重放?

- 服务端签发带签名,业务方存凭证 ID,使用时回中台校验(状态/有效期/业务流水绑定/使用次数);关键业务一次性有效。

### Q13.11 OCR 识别错了怎么办?

- OCR 只是录入辅助,关键字段以要素核验结果为准;结果页可人工修改;低置信字段标黄;分证件模板持续用识别失败 badcase 优化(断点平台发现港澳台模板缺失问题)。

### Q13.12 生物信息合规?

- 单独授权弹窗(不捆绑用户协议)、最小化采集、加密传输存储、限期删除原始生物数据只留凭证与审计、权限最小化 + 全审计、等保测评、供应商签 DPA。

## 14. 项目四:业务流程断点分析平台与流程标准化连环问

### Q14.1 这个项目解决什么问题?

- 线上流程(投保、保全、续期缴费、满期金领取、理赔)环节多、依赖多(OCR、人脸、银行卡、支付、核心),以前客户"卡在哪、为什么失败"靠客诉和客服猜;各业务线节点定义、错误码、埋点口径不统一,数据没法横向对比。
- 目标:全流程节点埋点 → 漏斗转化与失败归因 → 数据驱动流程优化;同时把节点/错误码/接入流程标准化。

### Q14.2 数据怎么采集的?埋点方案?

- 先定标准:统一节点事件模型——流程类型、节点编码、节点结果(成功/失败/放弃)、失败码、耗时、渠道、用户标识(脱敏);
- 后端:统一注解 + 拦截器/切面在关键节点(核验、支付、核心调用)自动上报,业务代码零侵入;前端:页面/按钮按同口径埋点(放弃行为只能前端采);
- 异步发送 + 本地缓冲,上报失败不影响主流程。

### Q14.3 数据链路?为什么用 ClickHouse?

- 节点事件 → RocketMQ 削峰 → 消费写 ClickHouse(明细)+ XXL-Job 按天聚合(漏斗、节点成功率、失败原因分布、P90 耗时)→ 看板(ECharts);
- 选 ClickHouse:事件量大(日千万级)、按天/流程类型聚合分析为主、写入远多于更新——列存 + 高压缩比 + 聚合查询快,MySQL 做这个量级聚合慢;不涉及事务更新,正好避开 ClickHouse 短板。

### Q14.4 断点怎么定义?漏斗怎么算?

- 流程标准化为有序节点列表(如满期领取:登录 → 证件 OCR → 要素核验 → 活体 → 比对 → 生存核验 → 金额确认 → 签名 → 给付提交);
- 漏斗:进入节点 N 的人数 / 进入节点 N-1 的人数 = 节点通过率;断点 = 通过率显著低于基线的节点,自动排行;
- "放弃"与"失败"分开统计:失败(系统/依赖错误)看失败码,放弃(用户主动离开)看交互设计问题。

### Q14.5 失败原因怎么归因?

- 统一错误码字典是前提(标准化产物):大类按依赖分(OCR/人脸/要素/银行卡/支付/核心/业务规则),每类细分(人脸:活体失败/比对分低/要素不一致;OCR:证件不支持/识别模糊;支付:余额不足/卡失效/通道超时);
- 归因报表:节点 × 失败码 × 渠道 × 时间段交叉;TOP 断点自动生成周报和工单,按失败码直接派给责任系统(厂商/业务/核心)。

### Q14.6 讲几个真实优化案例(必准备)

1. **港澳台客户断点集中在 OCR**:数据发现回乡证/台胞证识别失败率 40%+ → 定位为 OCR 厂商缺该类证件模板 → 推动厂商补齐 + 增加手动录入兜底,该类客户断点下降 60%;
2. **活体环节老年客户流失**:失败率随年龄陡增 → 按年龄分层阈值 + 前置光线/佩戴提示 + 操作引导动画,通过率 +20%,欺诈率无变化;
3. **某银行卡支付失败集中**:失败码聚合发现某行通道超时率高 → 支付路由临时切流 + 联系渠道修复;
4. **满期领取"金额确认"页放弃率高**:断点定位发现是客户看不懂账户价值构成 → 联动 AI 同事在该页接入解释问答,放弃率下降。

### Q14.7 流程标准化具体做了什么?

- 三件事:① 节点规范(流程节点命名、节点模型、埋点口径统一,新流程按标准接入才能被统计);② 错误码字典(全公司统一错误码分段规范,跨系统失败可归因);③ 接入 SOP 与模板(新业务线接入核验中台、埋点、看板的 checklist 和代码模板)。
- 顺序上**先立标准再建平台**:没有统一口径,统计数据不可信;标准化是断点平台的地基。

### Q14.8 怎么推动各业务线接入和执行标准?(管理向)

- 痛点:埋点和错误码改造对业务线是"额外工作";
- 做法:① 让业务线先尝到甜头——先拿满期领取一个流程做样板,用数据定位问题、转化率提升说话,其他线主动来接;② 平台化降低成本:注解+模板接入半天搞定;③ 机制固化:新流程上线 checklist 里加"埋点+错误码"项,架构评审卡口;④ 周报抄送业务负责人,数据透明形成推动力。

### Q14.9 这个项目你的角色和价值?

- 从 0 设计并主导落地:定标准、建平台、跑闭环;价值口径:覆盖 10+ 流程、80+ 节点,流程问题从"客诉驱动(周级)"变"数据驱动(天级)",核心线上办理转化率 +15%,标准沉淀为团队规范。

## 15. 项目五:香港保险 App(项目经理角色)连环问

> 定位:这是管理面/主管面的弹药,不是技术主战场。小项目主动承认"体量不大",但强调角色完整性——第一次完整跑"业务诉求 → 范围管理 → 排期协调 → 风险控制 → 按期交付"闭环,且协调复杂度高(两地、跨职能、对接核心)。

### Q15.1 你在这个项目里具体是什么角色?和技术负责人有什么区别?

- 区别:技术负责人对"方案和代码"负责,PM 对"按期上线"负责——需求范围、里程碑、资源排期、风险台账、跨方沟通会都是我的主线动作;技术方案我兼着盯,但管理动作占了主要精力;
- 一句话:平时我管"怎么把系统做对",这个项目我还管"做什么、什么时候做完、谁来做、卡住了怎么办"。

### Q15.2 项目这么小,为什么值得拿出来讲?

- 不拼规模拼三点:① 角色完整,0→1 全流程独立扛;② 协调复杂度不低——香港业务/产品方、内地核心团队、支付渠道、测试,两地异步;③ 新市场冷启动,没有现成流程,SOP 是我建的;
- 结果不只是"上线了",而是沉淀了《新区域接入 SOP》(差异清单、核心对接清单、联调/UAT 流程),后来同类区域可复用。

### Q15.3 两地需求差异怎么管理?举一个真实冲突及怎么解决的(必准备)

- 方法:需求澄清阶段输出"内地中台复用 vs 香港定制"差异清单,维度:产品规则、保全项目、缴费方式、合规、多语言;逐项标"复用/配置/定制",作为范围基线;
- 冲突模板(按真实经历替换):香港方要求的某保全项/缴费方式内地中台不支持、核心无现成接口 → 不给领导抛问答题,给选择题:① 核心改造(排期 X 周,影响上线日)② 二期交付,首期走【线下/简化流程】过渡 ③ 换替代方案;拉香港产品 + 核心主管评审,按业务价值和排期影响拍板,结论和取舍邮件留痕;
- 原则:**带着选项升级,不带着问题升级**(与 Q17.3 跨团队方法论一致)。

### Q15.4 香港方频繁提需求变更/范围蔓延怎么控?

- 设需求冻结点:冻结前充分澄清,冻结后变更走评审——必须说清对排期/成本的影响,小变更插当前迭代、大变更进二期;
- 关键不是"拒绝",而是让香港方自己做取舍:把变更的代价(延期几天、挤占哪个功能)摆出来,业务方决策;
- 所有变更书面确认(邮件/会议纪要),口头需求不认。

### Q15.5 核心系统团队排期冲突/不配合怎么推?

- 复用 Q17.3 方法论:换位思考(核心 KPI 是稳定,我的需求对他们是风险)→ 把改造尽量收敛在我方适配层,核心少动甚至零动;
- 接口契约先行:核心接口没好之前我方按契约 mock 联调,不占对方时间也不阻塞自己;
- 提前对齐:项目启动就和核心主管锁定接口清单和排期窗口,而不是临联调才提;推不动时先技术层达成共识,再双方主管对齐优先级。

### Q15.6 异地、异步沟通效率低怎么办?

- 机制:固定两地例会(短、有议程)、需求/缺陷统一看板双方可见、接口契约文档化、专用联调环境;
- 纪律:关键结论必出会议纪要邮件确认;需求不接受口头传话(香港方 → 产品 → 开发链路口径易失真),全部落到工单;
- 语言:术语对齐(同一保全项两地叫法不同),做了术语对照表。

### Q15.7 进度和风险怎么管?

- 里程碑:需求冻结 → 接口联调 → 两地 UAT → 试运行 → 正式上线,每个里程碑有准入准出;
- 风险台账:依赖项、责任人、截止时间、状态(红黄绿),每周过;关键路径(核心接口、支付渠道)重点盯,缓冲时间预留在联调和 UAT;
- 预警不瞒报:风险提前暴露,宁可上线日之前谈延期,不可上线当天翻车。

### Q15.8 质量和上线怎么保障?

- 两地分工 UAT:香港侧按本地业务规则主导验收(他们最懂香港产品和合规),内地侧保障接口、资金链路与回归;
- 上线:小流量试运行 → 正式开放;回滚预案 + 上线首周两地联合保驾值班;资金相关功能上线前必过对账验证。

### Q15.9 香港保险有什么合规特殊性?你做了什么?

- 认知层面能讲:香港适用《个人资料(私隐)条例》(PDPO),个人资料收集需告知用途、限目的使用;产品需香港保监局认可的在售产品;多语言(繁/英)保单与界面;缴费走香港本地渠道(FPS 转数快/信用卡/香港银行账户等);
- 落地层面诚实:合规细则由香港业务和法务主导把控,技术侧负责落实——数据加密、授权留痕、最小化采集、审计日志,和内地核验中台的合规思路一致。

### Q15.10 做了项目经理,以后还想不想写代码?(必问,表忠心)

- 口径:这个角色是**业务需要我顶上去的补位**,不是转岗信号;恰恰相反,做完更确认自己的定位是技术负责人——PM 经历让我做技术决策时更懂排期代价、跨方沟通成本和业务语言,反过来提升技术方案的落地成功率;
- 证据:项目期间核心攻坚我一直没放手(缴费资金链路、核验规则引擎、AI 集成都是我在盯),管理和技术是叠加不是替换。

### Q15.11 最大的教训是什么?

- 早期两地需求靠会议口头沟通,一次理解偏差(一个保全项的业务规则双方理解不同)做到联调才发现,返工一周;

## 16.1 设计一个金融业务智能问答平台(满期金 RAG + 工具调用)

## 16.2 设计一个续期缴费与对账系统

- 核心域:保单/应缴计划(核心为准)、缴费单(状态机:待支付→已支付→已入账/已关闭/退款中)、渠道适配、对账;满期给付走状态机 + 生存核验;
- 关键设计:金额以核心应收为准;回调三幂等;本地消息表驱动入账;主动查单 + T+1 三方对账;长短款自动分类工单;批量代扣分片调度;催缴延迟消息;
- 高可用:渠道多通道路由、核心降级受理异步化、MQ 削峰;

## 16.3 设计一个规则引擎驱动的多证件身份核验中台

- 需求澄清:核验场景数(20+)、证件类型(5+)、合规要求(个保法/生物数据)、SLA;
- 核心组件:
  1. **规则引擎**:决策表(场景 + 证件类型 → 核验项组合/分数阈值/重试/降级)存 DB 管理后台配置,Nacos 热生效、版本化、灰度;复杂条件 QLExpress 表达式;规则执行留痕可审计;
  2. **核验执行引擎**:责任链(OCR → 要素 → 活体 → 比对 → 生存/死亡核验)按规则动态裁剪;
  3. **证件/厂商适配器**:5+ 证件路由(公安人口库/出入境通道)、OCR 分证件模板、厂商主备熔断,新增证件开闭原则;
  4. **凭证中心**:签发/校验/失效,绑业务流水、限时、签名防重放;
  5. **流水与合规**:调用流水计费对账、生物数据加密 + 限期删除、单独授权、审计、等保;
- 高可用:双厂商熔断、人工柜面兜底;
- 可运营:核验失败明细进断点平台,阈值数据驱动校准(老年分层)。

## 16.4 设计一个业务流程断点分析与埋点平台

- 需求澄清:覆盖流程数、日事件量级(千万级)、实时性要求(天级足够)、谁用(业务/研发/运营);
- 架构:
  1. 采集层:统一节点事件模型(流程类型/节点编码/结果/失败码/耗时/渠道),注解 + 拦截器零侵入上报,异步 + 缓冲不影响主流程,前端埋点补"放弃"行为;
  2. 传输层:RocketMQ 削峰;
  3. 存储层:ClickHouse 存明细(列存/高压缩/聚合快),MySQL 存流程定义、错误码字典、聚合结果;
  4. 计算层:XXL-Job 按天聚合漏斗、节点成功率、失败码分布、P90;
  5. 应用层:ECharts 看板、断点 TOP 排行、周报、失败码自动派单到责任系统;
- 前置工程:**标准化先行**——节点规范 + 统一错误码字典,否则数据不可信;
- 权衡:ClickHouse 不支持事务更新 → 事件不可变 + 迟到事件按天重跑修正;不引入 Flink 是因为天级聚合 XXL-Job 足够,不过度设计。

## 16.5 设计题通用框架

1. 需求澄清(功能边界、读写比、量级、一致性/合规要求);2. 容量估算;3. 分层架构;4. 核心时序;5. 三高 + 一致性/合规深入;6. 主动讲权衡("选 X 牺牲 Y,因为约束 Z")。

# 第四篇 · 管理面 / 主管面 + HR 面

## 17. 技术管理面(投 TL/管理岗重点准备)

### Q17.1 你带团队怎么做技术规划?

- 口径:技术规划不写"用什么技术",而是从业务目标倒推:
  1. 看清业务:今年业务重点(如续期率提升、AI 降本、线上转化)→ 系统要支撑什么;
  2. 盘点现状:稳定性(事故/对账差异)、效率(交付周期)、成本(资源/厂商计费)三张账;
  3. 定项目:按"价值 × 紧急"排序,分三类——稳定性兜底(对账、监控、压测)、业务支撑(缴费/核验中台)、数据与未来投入(断点平台、AI 同事,当年看是创新,第二年成标杆);
  4. 落地:季度 roadmap 拆到人,月度复盘;向上对齐资源和预期。
- 举例:AI 同事项目就是把"满期金客户重复咨询多、客服要跨系统查账户、新人上手慢"的业务痛点,包装成可量化(转人工率/AHT/领取转化率)的项目向公司申请资源做成的。

### Q17.2 怎么带 5~8 个人?

- 任务分配:按能力梯队派活——核心链路自己盯或给资深,新人从明确任务起步配 mentor;
- 质量把关:架构评审(方案必须写清备选和取舍)、Code Review(资金/AI/合规相关代码必 review)、发布 checklist;
- 成长:1v1 月度沟通,每人有成长方向(有人深挖技术、有人往业务/管理);新人 30/60/90 天计划;
- 激励:结果公开认可,出问题先担责后复盘(对事不对人,复盘找流程问题不找人背锅)。

### Q17.3 跨团队协作推不动怎么办?(核心系统/业务线不配合)

- 口径:① 先换位思考——核心团队的 KPI 是稳定,你的需求对他们是风险,要带上"对他们的好处"(如我们适配层把改造收敛在自己侧,核心零改动);② 用数据和方案说话,不空谈:准备好接口方案、风险评估、回滚预案;③ 升级有技巧:先和对接人达成技术共识,再通过双方主管对齐优先级,而不是一开始就告状;④ 长期看:建立例行机制(双周对接会、联调环境),关系前置。
- 例子一:核验中台推四条业务线接入,先拿"退保/满期给付"高风险场景做样板(自助率数据说话),其他线主动来接;
- 例子二:断点平台要各线改埋点和错误码,先拿满期领取一个流程跑出"转化率提升"的样板,再做成注解+模板把接入成本降到半天,最后用架构评审 checklist 固化;
- 例子三:香港 App 对接核心系统,启动会就锁定接口清单和排期窗口,契约先行 + mock 联调不互相等待,改造尽量收敛在我方适配层。

### Q17.4 项目延期/线上事故怎么处理?

- 延期:先预警不瞒报,评估影响范围 → 砍范围保里程碑(按 MVP 切,先上主流程)→ 加人要慎重(布鲁克斯法则,后期加人反而慢),优先消除阻塞;
- 事故:止血优先(回滚/降级)→ 恢复后复盘:时间线、根因、为什么监控没提前发现、为什么预案没覆盖 → action item 到人到时间,重点修机制(防再发),不追责个人。

### Q17.5 招人你看重什么?

- 后端岗:基础扎实(并发/数据库/事务说的清)、有"代价意识"(选型讲得出取舍)、诚实(不会的不编);有 AI 应用经验或强学习意愿加分;
- 面试方法:让他讲自己做过的项目,连环追问细节,真做过的人越问越细,包装的人越问越虚。

### Q17.6 团队怎么拥抱 AI?

- 推 AI 辅助编码(日常 CRUD、单测、代码解释提效,但核心逻辑和资金代码必须人审);
- 把团队知识沉淀进 AI 同事(让项目文档、排障手册可问答);
- 要求骨干理解 RAG/评测/规则引擎等工程方法,把 AI 当新组件纳入架构设计。
