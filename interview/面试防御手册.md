## 1. Java 集合与基础

### Q1.1 HashMap 底层原理?为什么线程不安全?

- **结构**:JDK8 数组 + 链表 + 红黑树。默认容量 16、负载因子 0.75;链表长度 ≥ 8 **且**数组长度 ≥ 64 才树化(不足 64 优先扩容),节点 ≤ 6 退化回链表。
- **put 流程**:hash 扰动(`(h=key.hashCode()) ^ (h>>>16)`)→ `(n-1)&hash` 定位桶 → 空桶直接放;否则比较 key(地址/equals),相同覆盖;不同尾插链表;树化判断 → 扩容判断。
- **扩容**:2 倍扩容;JDK8 不用重新算 hash,用 `e.hash & oldCap` 判断元素留在原位还是移到 `原位+oldCap`。
- **为什么不安全**:JDK7 头插法并发扩容产生环形链表,get 时 CPU 100%;JDK8 改尾插解决死循环,但并发 put 仍有数据覆盖丢失。→ 用 ConcurrentHashMap。

### Q1.2 ConcurrentHashMap 1.7 与 1.8 区别?

- 1.7:Segment 分段锁(默认 16 段),每段是一把 ReentrantLock + 一个小 HashMap,并发度 = 段数。
- 1.8:废弃 Segment,**CAS + synchronized 锁桶头节点**,锁粒度更细;保留红黑树;`size` 用 baseCount + CounterCell 分散计数(类似 LongAdder 思想)。
- 面试加分:put 时空桶用 CAS 插入(无锁),非空才 synchronized 锁头节点——锁竞争概率低。

### Q1.3 ArrayList 扩容?和 LinkedList 区别?

- ArrayList:数组,初始 10(懒创建),扩容 `oldCap + oldCap>>1`(1.5 倍),Arrays.copyOf 拷贝;随机访问 O(1),尾插均摊 O(1),中间插入 O(n)。
- LinkedList:双向链表,头尾插删 O(1),按下标访问 O(n);内存额外开销是节点对象。实际开发几乎不用 LinkedList(数组缓存友好,连顺序插入 ArrayList 也常更快)。

### Q1.4 String 相关

- `String` 不可变(char[]/byte[] final + 类 final):可缓存 hash、线程安全、字符串常量池前提。
- `String.intern()`:JDK7+ 常量池在堆中,首次遇到的堆字符串放引用(不是复制对象)。
- `==` 比地址,`equals` 比值;`StringBuilder` 非同步快,`StringBuffer` 方法级 synchronized(基本不用)。

## 2. 并发编程

### Q2.1 volatile 解决什么?能保证原子性吗?

- 两个语义:**可见性**(写完刷主存 + 使其他 CPU 缓存行失效,MESI 协议)+ **禁止指令重排**(插入内存屏障:StoreStore / LoadLoad / StoreLoad 等)。
- **不保证原子性**:`volatile int i; i++` 仍线程不安全(读-改-写三步)。原子用 AtomicInteger(CAS)或加锁。
- 典型场景:状态标志位(`boolean running`)、DCL 单例(禁止 `new` 对象时"分配内存→赋值引用→初始化"的重排,防止拿到未初始化对象)。
- 挂简历:秒杀里"活动开关位"用 volatile 修饰,配置中心推送后所有线程立即可见。

### Q2.2 synchronized 锁升级过程?

- 锁状态记录在对象头 Mark Word:**无锁 → 偏向锁 → 轻量级锁 → 重量级锁**,只升不降。
- **偏向锁**:首个线程进入,CAS 把线程 ID 写入 Mark Word,之后该线程进入无需同步;出现第二个线程竞争时撤销。
- **轻量级锁**:多线程交替执行、竞争不激烈,栈帧中建锁记录,CAS 把 Mark Word 指向锁记录;失败自旋等待(自适应自旋)。
- **重量级锁**:自旋失败/竞争激烈,升级为 ObjectMonitor,未抢到的线程阻塞挂起(用户态→内核态切换开销大)。
- 为什么这么设计:大部分锁在实际运行中无竞争或低竞争,分级用最小代价覆盖不同竞争程度。

### Q2.3 synchronized 和 ReentrantLock 区别?

| 维度 | synchronized | ReentrantLock |
|------|-------------|---------------|
| 实现 | JVM 关键字,Monitor | JDK 类,AQS |
| 释放 | 自动出作用域 | 必须 finally 手动 unlock |
| 能力 | 可重入、非公平 | 可重入、**可公平/非公平**、可响应中断 `lockInterruptibly`、可超时 `tryLock`、多 Condition 条件队列 |
| 锁升级 | 偏向→轻量→重量 | 只有重量级(基于 AQS 队列) |

- 选型:简单同步用 synchronized(JVM 持续优化,够用);需要超时、中断、公平、多条件队列用 ReentrantLock。

### Q2.4 AQS 原理?

- 核心:`volatile int state`(同步状态)+ CLH 变体的**双向等待队列** + CAS。
- 线程 CAS 抢 state 失败 → 封装 Node 入队 → 前驱出队后唤醒;LockSupport.park/unpark 挂起唤醒。
- 独占模式:ReentrantLock(state=0/重入计数);共享模式:CountDownLatch(state=计数,countDown 减到 0 唤醒所有)、Semaphore(state=许可数)、ReentrantReadWriteLock(高16位读/低16位写)。
- 一句话:**用一个 volatile 变量 + CAS 更新 + 一个 FIFO 队列管排队**,JUC 锁和同步器的共同骨架。

### Q2.5 线程池七大参数?执行流程?拒绝策略?为什么不用 Executors?

- 七参数:`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`unit`、`workQueue`、`threadFactory`、`handler`。
- 流程:核心线程未满→建核心线程;满了→入队列;队列满→建非核心线程直到 max;还满→**拒绝策略**。
- 四种拒绝策略:AbortPolicy(默认,抛异常)、CallerRunsPolicy(调用者线程执行,天然背压限流)、DiscardPolicy(静默丢弃)、DiscardOldestPolicy(丢队头再试)。
- **不用 Executors**:FixedThreadPool/SingleThreadPool 用无界 LinkedBlockingQueue(Integer.MAX_VALUE)→ 任务堆积 OOM;CachedThreadPool 线程数无上限 → 创建大量线程 OOM。必须用 `ThreadPoolExecutor` 显式控制。
- 参数怎么定:CPU 密集型 `核数+1`;IO 密集型 `核数×2` 或 `核数/(1-阻塞系数)`;**工程上不靠公式靠压测**:按 目标QPS × 单任务RT 估算所需线程数,压测调优,重点监控队列长度和拒绝数。
- 挂简历:秒杀链路用独立线程池(舱壁隔离),下单消费线程池按 DB 承载能力压测定参;核心线程池都有监控告警(队列积压、拒绝次数)。

### Q2.6 ThreadLocal 原理?内存泄漏?

- 每个 `Thread` 持有一个 `ThreadLocalMap`,key 是 ThreadLocal 对象(**弱引用**),value 是线程变量(**强引用**)。
- 泄漏点:ThreadLocal 对象被回收后 key 变 null,但 value 在线程(尤其线程池长生命周期)上一直被强引用 → 泄漏。
- 规范:**用完必须 `remove()`**(finally 里)。线程池场景还会串数据(前一个用户的 traceId/用户信息被后一个请求读到)。
- 跨线程池传递用 TransmittableThreadLocal(阿里 TTL)。挂简历:全链路压测的压测标记就是用 TTL 跨线程池透传。

### Q2.7 CAS 与 ABA

- CAS(Compare And Swap):三个操作数 内存值/期望值/新值,相等才更新,CPU 原子指令(锁总线/锁缓存行)。
- 问题:① ABA(值从 A→B→A,看不出来)→ 加版本号,AtomicStampedReference;② 自旋开销大(竞争激烈时空转)→ LongAdder(分段 Cell 热分散);③ 只能保证一个变量 → AtomicReference 打包对象。

## 3. JVM

### Q3.1 运行时数据区?

- **线程私有**:程序计数器(当前线程执行字节码行号,唯一无 OOM)、虚拟机栈(栈帧:局部变量表、操作数栈、动态链接、返回地址;StackOverflowError/OOM)、本地方法栈。
- **线程共享**:堆(对象分配主区域,GC 主战场,新生代 Eden:S0:S1 = 8:1:1 + 老年代)、方法区(JDK8 后为元空间,用本地内存:类元信息、运行时常量池、静态变量)。

### Q3.2 对象怎么判断死亡?GC 算法?

- 可达性分析:从 **GC Roots**(虚拟机栈中引用、静态字段、常量、JNI 引用)出发不可达的对象可回收(第一次标记 + finalize 兜底,基本不用)。
- 算法:标记-清除(碎片)、标记-复制(新生代,Eden+S 存活复制)、标记-整理(老年代,移动对象无碎片)。分代收集 = 新生代复制 + 老年代标记整理。

### Q3.3 CMS 与 G1 区别?

- **CMS**(老年代,标记-清除):初始标记(STW,只标 GC Roots 直接关联)→ 并发标记 → 重新标记(STW,增量更新修正)→ 并发清除。优点并发低停顿;缺点:CPU 敏感、浮动垃圾、标记-清除产生碎片(碎片风险 Full GC)。JDK9 废弃。
- **G1**(整堆,Region 化):把堆分成多个 Region(逻辑上分 Eden/Survivor/Old/Humongous),标记-复制(在 Region 间复制,整体无碎片);**可预测停顿模型**(`-XX:MaxGCPauseMillis`,按回收价值排序垃圾最多的 Region,Garbage First);用 SATB(原始快照)处理并发标记漏标;大对象进 Humongous Region。
- 选型:堆小(<6G)CMS/Parallel;大堆、要求可控停顿用 G1;追求亚毫秒级停顿看 ZGC(染色指针 + 读屏障)。

### Q3.4 什么时候会 Full GC?

- 老年代空间不足(大对象直接进老年代、内存泄漏、晋升过快);元空间不足(动态类加载);CMS 的 promotion failed / concurrent mode failure;空间分配担保失败(Minor GC 前老年代放不下存活对象);显式 `System.gc()`(可 -XX:+DisableExplicitGC)。

### Q3.5 线上问题排查三板斧(必问,简历写了"排查经验")

- **CPU 100%**:`top` 找高 CPU 进程 → `top -Hp <pid>` 找高 CPU 线程 → 线程 id 转 16 进制 → `jstack <pid>` 找对应线程栈,定位死循环/正则/频繁 GC。
- **OOM/内存泄漏**:`jmap -dump:format=b,file=xxx.hprof <pid>`(或启动加 `-XX:+HeapDumpOnOutOfMemoryError`)→ MAT/VisualVM 看支配树(Dominator Tree),找占用最大的对象和引用链。
- **频繁 Full GC**:`jstat -gcutil <pid> 1s` 看各代增长速率 → 结合 dump 判断是大对象、元空间还是内存泄漏;常见:ThreadLocal 没 remove、静态集合无限增长、线程池队列堆积。
- 挂简历:大促前压测时发现过 Full GC 频繁,定位是订单导出大对象 + 静态缓存无淘汰,改成流式查询 + Caffeine 限容后解决。

### Q3.6 类加载过程?双亲委派?为什么要打破?

- 过程:**加载 → 验证 → 准备(静态变量赋零值)→ 解析(符号引用→直接引用)→ 初始化(静态赋值、static 块)**;使用、卸载。
- 双亲委派:类加载请求先委托父加载器(Bootstrap → Extension → Application),父加载不到才自己加载。意义:防止核心类被篡改(自己写 `java.lang.String` 不会被加载)+ 避免重复加载。
- 打破场景:JDBC SPI(核心类 rt.jar 中的 DriverManager 要加载 classpath 下的驱动,用**线程上下文类加载器**反向委托)、Tomcat(每个 webapp 独立 ClassLoader 实现应用隔离)、OSGi 网状委派。

## 4. Spring

### Q4.1 Bean 的生命周期?

1. 实例化(构造器/工厂方法)
2. 属性填充(依赖注入,@Autowired)
3. Aware 回调(BeanNameAware、BeanFactoryAware、ApplicationContextAware)
4. BeanPostProcessor.**postProcessBeforeInitialization**(如 @PostConstruct、@Value 处理在此阶段附近)
5. 初始化(InitializingBean.afterPropertiesSet → 自定义 init-method)
6. BeanPostProcessor.**postProcessAfterInitialization**(**AOP 代理在此生成**,返回的可能是代理对象)
7. 使用
8. 销毁(@PreDestroy / DisposableBean.destroy / destroy-method)

### Q4.2 循环依赖为什么用三级缓存?二级行不行?

- 三级缓存:① `singletonObjects`(成品 Bean)② `earlySingletonObjects`(早期半成品对象)③ `singletonFactories`(ObjectFactory,**lambda 里决定是否提前生成 AOP 代理**)。
- 流程:A 创建→实例化后把工厂放入三级缓存→给 A 注入 B→B 创建→注入 A 时从三级缓存拿到工厂,调 getObject 得到早期引用(若需代理此时生成代理),放入二级缓存→B 完成→A 拿到 B 完成;A 初始化后若发现已生成代理则用代理。
- **为什么三级**:保证 AOP 场景下被循环依赖的 Bean 整个容器中**代理对象唯一**——代理的生成提前到工厂第一次被调用时,且只生成一次。二级缓存也能做(提前无条件生成代理),但 Spring 选择"工厂延迟决策",不需要代理的对象不提前暴露代理。
- 边界:**构造器注入的循环依赖无法解决**(实例化都没完成,没有早期引用)→ 改 setter/字段注入,或 @Lazy。
- prototype 作用域不缓存,不支持循环依赖。

### Q4.3 AOP 实现?JDK 动态代理 vs CGLIB?

- JDK 动态代理:基于接口,Proxy.newProxyInstance + InvocationHandler,运行期生成接口实现类。
- CGLIB:基于继承,ASM 生成目标类子类,重写非 final 方法织入通知。
- Spring AOP:有接口默认 JDK 代理,无接口 CGLIB;Spring Boot 2.x 起默认 CGLIB(spring.aop.proxy-target-class=true)。
- 这就是"自调用失效"和"事务失效"的根因:调用走的是 this 原对象而非代理对象。

### Q4.4 Spring 事务在哪些场景失效?

1. **自调用**:同类中 this.method() 调 @Transactional 方法,绕过代理(解决:注入自己/AopContext.currentProxy/拆类)。
2. 方法非 public(Spring 默认只代理 public)。
3. 异常被 try-catch 吞掉,没抛出去。
4. 默认只回滚 RuntimeException,受检异常需 `rollbackFor = Exception.class`。
5. 多线程:新线程不在同一事务(事务上下文在 ThreadLocal)。
6. 数据库引擎不支持事务(MyISAM)。
7. 传播行为用错:NOT_SUPPORTED / NEVER 以非事务运行。
- 传播行为常考:REQUIRED(默认,有则加入无则新建)、REQUIRES_NEW(挂起当前,独立新事务)、NESTED(保存点,内层失败回滚到保存点)。

### Q4.5 SpringBoot 自动配置原理?

- `@SpringBootApplication` = `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`。
- @EnableAutoConfiguration 通过 Import(AutoConfigurationImportSelector)读取 classpath 下 `META-INF/spring.factories`(2.7+ 为 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`)中声明的自动配置类。
- 配置类上一堆 `@Conditional`(@ConditionalOnClass / @ConditionalOnMissingBean / @ConditionalOnProperty)按条件装配:classpath 有对应类、用户没自定义 Bean 时才生效。
- 一句话:约定优于配置,按 classpath 和条件注解"按需装配"一整套 Bean。

### Q4.6 SpringMVC 请求流程

- 请求 → DispatcherServlet → HandlerMapping 找到 Handler(+拦截器链)→ HandlerAdapter 适配执行 → 参数解析器解析参数(@RequestParam/@RequestBody)→ Controller 返回 → 返回值处理器处理(@ResponseBody 经 HttpMessageConverter 转 JSON;否则 ModelAndView 视图渲染)。

## 5. MySQL

### Q5.1 为什么索引用 B+ 树,不用 B 树/哈希?

- B+ 树:非叶子节点只存键不存数据 → 单节点能放更多键 → 树更矮(千万级数据 3~4 层,3~4 次磁盘 IO);叶子节点按键有序双向链表 → 范围查询/排序天然友好。
- B 树:每个节点都存数据,扇出低,树更高;范围查询要中序遍历。
- 哈希:等值 O(1) 但不支持范围、排序、最左前缀;哈希冲突。
- 挂简历:分库分表后单表控制在 800~1000 万,正是为了让 B+ 树高度稳定在 3 层。

### Q5.2 聚簇索引/回表/覆盖索引/最左前缀?

- **聚簇索引**:叶子节点存整行数据(主键索引);二级索引叶子存主键值。
- **回表**:二级索引查到主键值,再回主键索引查整行。
- **覆盖索引**:查询列都在索引里,无需回表(EXPLAIN  Extra 显示 Using index)。
- **最左前缀**:联合索引 (a,b,c),条件必须从最左列开始连续;遇到范围查询(>、<、between、like 左模糊)右侧列无法走索引。
- 索引下推 ICP(5.6):联合索引中服务端原本只按最左前缀,剩余条件回表后过滤;ICP 把剩余条件下推到引擎层用索引过滤,减少回表次数(Extra: Using index condition)。

### Q5.3 事务隔离级别?可重复读怎么解决幻读?

- 四种:读未提交、读已提交(RC)、可重复读(RR,InnoDB 默认)、串行化。
- 脏读/不可重复读/幻读对应逐级解决。
- InnoDB 在 RR 下通过 **MVCC(快照读)** + **临键锁(当前读)** 解决幻读:普通 select 走 MVCC 快照,事务内视图一致;`select for update`/update 等当前读加临键锁锁住记录和间隙,挡住别的事务插入。

### Q5.4 MVCC 原理?

- 每行隐藏字段:`trx_id`(最后修改的事务 id)、`roll_pointer`(指向 undo log 中的上一版本,形成版本链)。
- ReadView 四个值:创建者事务 id、活跃事务列表 m_ids、最小活跃 id、下一个将分配 id。
- 可见性判断:版本 trx_id < min → 可见;≥ max → 不可见(未来事务);在 min~max 之间 → 在 m_ids 中说明是活跃未提交事务,不可见,沿版本链往前找。
- **RC 每次 select 生成新 ReadView**(所以能读到别人已提交的新数据);**RR 事务第一次 select 生成并复用**(所以可重复读)。

### Q5.5 InnoDB 锁体系?

- 记录锁:锁单行(唯一索引等值命中)。
- 间隙锁:锁索引记录之间的开区间,防插入,只在 RR 下存在(解决幻读)。
- 临键锁:记录锁 + 前面的间隙,InnoDB 行锁默认算法;唯一索引等值未命中退化为间隙锁。
- **行锁是加在索引上的**:更新条件没走索引 → 锁不到索引 → 退化为锁全部记录(表现像表锁)。
- 意向锁:表级 IS/IX,用于快速判断表上有没有行锁,避免加表锁时逐行检查。
- 死锁:互相等待对方的锁;InnoDB 有死锁检测(等待图),回滚代价小的事务;预防:固定加锁顺序、缩短事务、降低隔离级别到 RC(间隙锁少)。

### Q5.6 redo log、undo log、binlog?两阶段提交?

- **redo log**(InnoDB,物理日志,记"某页某偏移改成什么"):WAL 先写日志再写盘,crash recovery;循环写、固定大小。
- **undo log**(逻辑日志,记反向操作):事务回滚 + MVCC 版本链。
- **binlog**(Server 层,逻辑日志,记语句/行变更):主从复制、数据归档;追加写。
- **两阶段提交**:① InnoDB 写 redo log(prepare 状态)→ ② 写 binlog → ③ redo log commit。崩溃恢复时:redo 有 commit 直接提交;只有 prepare 则看 binlog 是否完整(完整则提交,不完整回滚)。保证 redo 与 binlog 一致,主从数据一致。
- `innodb_flush_log_at_trx_commit=1`(每次事务刷 redo)、`sync_binlog=1`(每次事务刷 binlog)= 双 1,最安全。

### Q5.7 慢 SQL 怎么排查优化?(简历有"治理 200+ 慢 SQL")

- 发现:开启慢查询日志 / pt-query-digest 聚合 / 监控平台。
- 诊断:`EXPLAIN` 看 type(const/eq_ref/ref > range > index > ALL)、key(实际用的索引)、rows(扫描行数)、Extra(Using filesort / Using temporary 是危险信号)。
- 优化手段:
  1. 建/改索引:联合索引对齐 where + order by,覆盖索引免回表;
  2. 改写 SQL:避免 select *、避免函数/隐式转换使索引失效、深分页用延迟关联(`where id >= (select id from t order by id limit 100000,1)`);
  3. 架构层:缓存、ES 异构(订单列表)、分库分表。
- 挂案例:商家订单列表按"店铺+状态+时间"分页,原 SQL 扫描百万行 → 建 (shop_id, status, create_time) 联合索引 + 深分页改延迟关联,P99 从 1.2s 降到 150ms;运营端复杂检索直接走 ES。

### Q5.8 分库分表相关(项目一核心,必被连环问)

- **垂直拆分**:按业务拆库(订单库、商品库);**水平拆分**:同表数据按规则打散。
- **分片键怎么选**:选最高频查询维度 + 数据分布均匀。订单选 user_id——C 端 80% 查询是"我的订单",买家维度单库命中;写流量按用户天然均匀。
- **非分片键查询怎么办**:
  - 按订单号查:订单号用雪花算法 + **基因法**——生成订单号时把 `user_id % 64` 的分片基因嵌入 id 末几位,拿到订单号能反算出分片,直达目标库表;
  - 商家/运营维度:Canal 监听 binlog 异构到 ES,多条件检索走 ES;
  - 配置类/字典表:广播表,每个库全量一份。
- **分片规划**:16 库 64 表(每库 4 表),`表号 = user_id % 64`,`库号 = 表号 / 4`;单表目标 800~1000 万,64 表可承 5~6 亿订单,按增速预留 3~5 年。
- **扩容**:预留逻辑分片(逻辑 64 表起步),物理扩容时把整表迁移到新库、改路由映射即可;若按 2 倍扩容,50% 数据迁移;迁移用双写 + 校验 + 切流。
- **分布式 ID**:雪花算法(见 Q8.6)。
- 带来的代价:跨片事务、跨片 join/聚合(归并排序/聚合)、唯一索引退化为局部唯一、运维复杂度——所以"能不拆就不拆,先优化索引和归档"。

## 6. Redis

### Q6.1 Redis 为什么快?

- 纯内存操作;单线程执行命令(无锁竞争、无线程切换、无并发安全问题);IO 多路复用(epoll,单线程监听大量连接);高效数据结构(SDS、跳表、压缩列表)。
- Redis 6.0 多线程:**网络读写和协议解析多线程,命令执行仍单线程**——瓶颈在网络 IO 时提速,不破坏单线程模型。

### Q6.2 五种数据结构及底层编码?

- String:SDS(动态字符串,O(1) 取长度、预分配/惰性释放、二进制安全)。
- List:quicklist(双向链表,每个节点是 listpack;7.0 前为 ziplist)。
- Hash:元素少用 listpack,多用 hashtable。
- Set:全整数用 intset,否则 hashtable。
- ZSet:元素少用 listpack,多用 **skiplist + hashtable**:跳表按分值有序(O(logN) 范围查询),hashtable 存 member→score(O(1) 取分值)。
- 跳表:多层有序链表,上层是下层的"快速通道",查询从顶层往下跳,平均 O(logN);相比红黑树实现简单、范围查询友好、并发控制容易。

### Q6.3 RDB vs AOF?

- RDB:bgsave fork 子进程做内存快照(COW 写时复制),文件小、恢复快;缺点是丢最后一次快照后的数据,适合备份/灾备。
- AOF:追加每条写命令,appendfsync:always(每条,安全但慢)/ **everysec(默认,最多丢 1 秒)**/no(靠 OS)。AOF 重写压缩体积。
- 4.0 混合持久化:重写时 RDB 全量 + AOF 增量,兼顾恢复速度和数据安全。生产一般:从节点开 RDB 备份 + 主节点 AOF everysec。

### Q6.4 过期 key 怎么删?内存满了怎么办?

- 过期删除:**惰性删除**(访问时检查过期才删)+ **定期删除**(每 100ms 随机抽样,删除过期 key,比例高就继续)。
- 内存淘汰(达 maxmemory):noeviction(默认,写报错)、allkeys-lru、volatile-lru(仅设过期的)、allkeys-random、volatile-ttl、allkeys-lfu/volatile-lfu(4.0,按访问频率)。缓存场景用 allkeys-lru。

### Q6.5 缓存穿透、击穿、雪崩?

- **穿透**:查不存在的数据,缓存和 DB 都没有,每次打 DB。→ 缓存空值(短 TTL)/ 布隆过滤器(拦截不存在的 key,有误判但不漏判)。
- **击穿**:某个**热点 key 过期**瞬间大量请求打到 DB。→ 互斥锁(setnx 抢锁,只放一个线程回源重建)/ 逻辑过期(value 里带过期时间,过期后异步线程刷新,期间返回旧值)。
- **雪崩**:大量 key **同时过期**或 Redis 整体宕机。→ TTL 加随机打散、多级缓存(本地 Caffeine 兜底)、限流降级、Redis 集群高可用。
- 挂简历:秒杀商品缓存 TTL 基础值 + 随机 0~300s;热点商品走逻辑过期不设硬 TTL。

### Q6.6 缓存与数据库一致性?(高频)

- 标准方案 **Cache Aside**:读先查缓存,miss 查 DB 并回种;写操作**先更新 DB,再删除缓存**。
- 为什么是删缓存而不是更新缓存:① 并发写 A/B 顺序不可控,更新缓存可能写脏(删是幂等的,下次读懒加载最新值);② 缓存可能是复杂计算结果,懒加载避免无效计算。
- 为什么先 DB 后缓存:先删缓存再更 DB,删完后有读请求把旧值回种,DB 却还没更新完 → 脏数据窗口更长。先更 DB 后删缓存,极端不一致(读请求在 DB 更新前读到旧值并回种)概率低(要求读比写慢且恰好卡住)。
- 兜底:**延时双删**(更新 DB 后删缓存,延迟几百 ms 再删一次)/ **Canal 订阅 binlog 异步删缓存**(消息重试保证最终一致)+ 定时对账。
- 结论:缓存方案只能保证**最终一致**,强一致场景要么加分布式锁串行化,要么不走缓存。简历里订单详情走 DB、列表搜索走 ES(容忍秒级延迟)就是这个取舍。

### Q6.7 分布式锁怎么实现?Redisson 看门狗?Redlock 争议?

- 基础版:`SET key uniqueValue NX EX 30`;释放锁用 **Lua 脚本**(判断 value 是自己的才删,防误删别人的锁);value 用 UUID/线程标识。
- 问题:业务执行超过 30s 锁自动释放 → 别人拿到锁 → 并发。Redisson **看门狗(watchdog)**:加锁默认 30s,后台线程每 10s(1/3)续期到 30s;业务执行完主动释放;客户端宕机不再续期,锁到期自动释放(不会死锁)。可重入靠 hash 结构记重入次数。
- **Redlock**:N 个独立 Redis 主节点,向多数(N/2+1)加锁成功且耗时小于有效期才算成功。
- 争议(Martin Kleppmann):依赖各节点时钟,时钟跳跃/GC 停顿/网络延迟下仍可能两个客户端同时持锁;分布式锁的正确性本质需要 fencing token(单调递增令牌,资源端拒绝旧令牌)。
- 工程实践:绝大多数场景单 Redis(主从+持久化)+ Redisson 足够;要求 CP 用 ZooKeeper/etcd(临时顺序节点,会话失效自动释放)。简历统一 Redisson 组件就是落地这个选型。

### Q6.8 哨兵 vs Cluster?

- **哨兵(Sentinel)**:主从基础上,哨兵集群负责监控 + 自动故障转移。主观下线(单个哨兵认为)→ 客观下线(quorum 个确认)→ 哨兵中选一个 leader(Raft)→ 选新主(slave-priority 优先级、复制 offset 最大、runid 最小)→ 通知客户端。
- **Cluster**:数据分片,**16384 个槽**,`CRC16(key) % 16384` 定位槽,槽分布在多个主节点(至少 3 主 3 从);节点间 Gossip 通信;客户端收到 MOVED(槽已迁移,永久重定向)/ASK(临时)重定向。
- 选型:数据量不大、要高可用用哨兵;数据量大要水平扩展用 Cluster。

### Q6.9 大 key / 热 key 怎么治理?

- 大 key(单个 value 过大:几百 MB 的 hash/list):危害——阻塞主线程(删除大 key)、迁移/删除卡顿、网卡打满、集群倾斜。发现:`--bigkeys`、MEMORY USAGE、监控。治理:拆分(大 hash 按字段拆 key、list 拆段)、压缩、**异步删除 UNLINK**;设计上避免。
- 热 key(单 key 访问量打爆一个节点):发现:monitor(慎用)、redis-faina、proxy 层统计、hotkeys 参数。治理:读热点→本地缓存 Caffeine;写热点(秒杀库存)→ **key 副本分散**(同名 key 拆 N 个,客户端随机/按 uid 路由,见项目二)。

## 7. 消息队列

### Q7.1 为什么用 MQ?有什么代价?

- 三大作用:**异步**(短信/积分等非主链路,降 RT——对应老公司 530ms→60ms)、**解耦**(下单后多个下游各自订阅,新增下游不改下单代码)、**削峰**(秒杀 10 万 QPS 入口,消费端按 DB 能力匀速消费)。
- 代价:系统可用性依赖 MQ(挂了全链路受影响)、复杂度上升(消息丢失、重复、顺序、积压)、一致性变最终一致。

### Q7.2 怎么保证消息不丢失?

- **生产端**:同步发送 + 失败重试(注意重试幂等);关键链路用本地消息表(业务数据和消息同库事务写入,后台任务扫描发送,发送成功标记)或事务消息。
- **Broker**:RocketMQ 同步刷盘(SYNC_FLUSH)+ 同步复制到从(SYNC_MASTER);Kafka `acks=all`(ISR 全部确认)+ `retries`、`min.insync.replicas≥2`、`unclean.leader.election.enable=false`。
- **消费端**:**手动 ACK**,业务处理成功后再提交 offset / 返回 CONSUME_SUCCESS;失败走重试(RocketMQ 最多 16 次退避重试),最终进**死信队列** + 告警 + 人工/对账兜底。
- 挂简历:订单链路消息消费全部幂等 + 死信告警 + 每日对账任务三重保障。

### Q7.3 重复消费怎么处理(幂等)?

- 本质:MQ 至少一次投递(at-least-once),重复不可避免,靠消费端幂等。
- 手段:业务唯一键(订单号)+ 去重表(唯一索引 insert 成功才处理)/ Redis SETNX 判重;状态机幂等(只允许合法状态流转,已处理直接返回成功)。

### Q7.4 顺序消息怎么做?

- 全局有序牺牲并发,实际只需**局部有序**(同一订单的事件有序)。
- 发送:同一业务 key(orderId/skuId)hash 到**同一个 queue/partition**。
- 消费:RocketMQ 用 MessageListenerOrderly(对 queue 加锁,单线程顺序消费该 queue,失败不会跳过而是阻塞重试);Kafka 单分区单消费者线程。
- 坑点:queue 数限制并发度;消费失败不能跳过(否则乱序),所以消息体要保证可重放。

### Q7.5 消息积压怎么处理?

- 先定位:消费慢(GC/锁/下游接口 RT 高)、消费者挂了、突增流量。
- 应急:① 扩消费者实例(注意不能超过 queue/partition 数,超过的实例闲置 → 需先临时扩 queue 数);② 临时新建多队列 topic,把积压消息批量转发分散,部署数倍消费者并行消费;③ 坏消息(毒丸消息)导致反复重试 → 跳过进死信,后续补处理;④ 非核心消息临时降级丢弃。
- 恢复后:补数/对账。预防:消费 lag 监控告警 + 消费端做好批量消费和异步化。

### Q7.6 RocketMQ 事务消息原理?(简历明确写了,必问)

- 流程:
  1. 生产者发送 **half 消息**(对消费者不可见,存在内部 topic);
  2. Broker 存储成功后回调生产者执行**本地事务**(创建订单);
  3. 本地事务成功 → Commit(Broker 把消息投递到真实 topic,消费者可见);失败 → Rollback(删除);
  4. 若长时间未收到二次确认(生产者宕机),Broker **回查**生产者(查订单是否存在),按结果 Commit/Rollback;默认回查 15 次,仍未知告警人工介入。
- 解决的问题:本地事务和发消息的原子性(要么订单创建了且消息一定发出去,要么都不发生)。
- 对比本地消息表:事务消息不用建消息表、少一次扫表,但强依赖 MQ 事务特性(RocketMQ 原生,Kafka 需自己实现)。

### Q7.7 Kafka 为什么吞吐高?

- 顺序写磁盘(追加写 CommitLog,速度接近内存)+ Page Cache 利用(读写都过 OS 缓存);
- **零拷贝** sendfile(数据从页缓存直接到网卡,不经过用户态);
- 批量发送 + 压缩(snappy/lz4);
- 分区并行,消费组水平扩展;
- 稀疏索引(不每条建索引)。
- ISR 机制:leader 维护"同步副本集合 ISR",follower 落后过多(延迟/时间阈值)被踢出;HW(高水位,所有 ISR 都复制到的 offset,消费者可见边界)与 LEO(日志末端);leader 挂了只从 ISR 中选新 leader,保证不丢已提交消息。

### Q7.8 RocketMQ 延迟消息原理?(订单超时用了)

- 开源版固定 **18 个延迟等级**(1s 5s 10s ... 2h),任意时间延迟是商业版/5.x 特性。
- 原理:延迟消息先发到内部 topic `SCHEDULE_TOPIC_XXXX`(每个等级一个 queue),定时任务扫描到期消息,还原原 topic 投递。
- 为什么不自己写定时任务扫表:分库分表后扫表 QPS 高、分布式调度麻烦、取消延迟随表量波动;延迟消息把"定时触发"交给 MQ,且天然分布式。简历里仍保留**低频定时扫描做兜底**(防消息丢失),双保险。

## 8. 分布式

### Q8.1 CAP 和 BASE?

- CAP:一致性(C)、可用性(A)、分区容错(P);网络分区在分布式下必然发生 → P 必选,只能在 C/A 间取舍:ZK/etcd 偏 CP(选举时不可用),Eureka/Nacos 临时实例偏 AP(注册中心要保可用,服务列表旧一点能接受)。
- BASE:Basically Available(基本可用,故障时降级)、Soft state(软状态,允许中间态)、Eventually consistent(最终一致)。
- 落地:互联网交易链路整体 AP + 关键节点(库存、资金)用强一致手段兜底,最终一致 + 对账是常态。

### Q8.2 分布式事务方案怎么选?

| 方案 | 一致性 | 侵入性 | 适用 |
|------|--------|--------|------|
| 2PC/Seata AT | 强一致(AT 默认读未提交) | 低(自动 undo log + 全局锁) | 短事务、同构服务、高并发要评估全局锁性能 |
| TCC | 强一致 | 高(Try/Confirm/Cancel 三段) | 资金、库存等核心资源;需处理空回滚/悬挂/幂等 |
| 本地消息表 | 最终一致 | 中(建表+扫描任务) | 跨服务通知,最通用稳妥 |
| 事务消息 | 最终一致 | 低 | 用 RocketMQ 时首选 |
| Saga | 最终一致 | 中(正向+补偿) | 长事务、跨多步流程 |

- 简历口径:下单主链路(订单+库存+优惠券+积分)用 **RocketMQ 事务消息**(可接受秒级最终一致,性能好);支付/强一致短事务用 **Seata AT**;资金扣减评估过 TCC 后用**本地消息表 + 对账**兜底。
- **Seata AT 原理**:一阶段执行业务 SQL 时,Rm 记录前后镜像到 undo log 并注册分支、获取**全局锁**(锁主键值);二阶段成功异步删 undo log,失败按 undo log 反向补偿。全局锁保证不会有两个全局事务同时改同一行。
- **TCC 三个坑**:空回滚(Try 没到 Cancel 先到,Cancel 要识别并记录)、悬挂(Cancel 之后 Try 才到,Try 要检查已回滚则不执行)、幂等(Confirm/Cancel 可能重复)。

### Q8.3 接口幂等方案?

- ① Token 机制:进入页面发 token(Redis),提交时 Lua 原子校验+删除,重复提交 token 已不存在——防前端重复点击/网络重发;
- ② 数据库唯一索引(订单号、业务流水号):冲突即重复,捕获后查询返回原结果;
- ③ 去重表(唯一键 + 处理状态),本质同②但与业务表解耦;
- ④ 状态机:只允许合法前置状态流转(待支付→已支付 只能一次);
- ⑤ 乐观锁 version(update ... where version=?)。
- 简历口径:三层幂等 = token(入口) + 唯一索引(落库) + 状态机乐观锁(流转),分别挡不同环节的重复。

### Q8.4 限流算法?熔断?

- 限流:
  - 固定窗口:简单,但临界处可能 2 倍突刺;
  - 滑动窗口:把窗口切小片滚动统计,平滑(1s 切 10 格);
  - 漏桶:请求进桶,恒定速率流出,**强制平滑不允许突发**;
  - **令牌桶**:恒定速率往桶里放令牌,请求拿令牌,桶满令牌丢弃——**允许一定突发**(桶里攒了令牌)。Guava RateLimiter、Sentinel 默认行为类似令牌桶;Sentinel 还有匀速排队(漏桶思想)。
- 熔断(断路器三态):closed(正常统计)→ open(错误率/慢调用比例超阈值,直接快速失败,经过冷却时间)→ half-open(放少量请求探测)→ 成功回 closed / 失败回 open。Sentinel 支持慢调用比例、异常比例、异常数三类规则。
- 降级:非核心接口/功能在压力下关闭(推荐、评价、文案),保核心交易。
- 简历口径:网关层 IP/用户限流 + Sentinel 集群限流(活动总 QPS,Token Server 集中发令牌,解决"单机阈值×机器数"放大问题)+ Redis 库存信号量三级漏斗;降级预案 30+ 并演练。

### Q8.5 分布式锁三种实现对比?

- Redis:性能最好(万级 QPS),AP 模型,主从切换极端情况可能丢锁;适合高并发业务锁(秒杀、幂等)。
- ZooKeeper/etcd:临时顺序节点 + Watch,锁释放/会话失效自动删锁,CP,强一致但性能低(万级以下);适合要求绝对正确的协调场景(选主、分布式任务调度)。
- MySQL:唯一键插入/for update,重、性能差,适合不频繁的场景或历史包袱。

### Q8.6 雪花算法?时钟回拨怎么办?

- 64 位:1 符号位 + 41 位时间戳(毫秒,可用 69 年)+ 10 位机器位(5 数据中心+5 节点,1024 台)+ 12 位序列号(单节点每毫秒 4096 个)。
- 优点:本地生成无网络开销、趋势递增(对 B+ 树索引友好,不会像 UUID 随机导致页分裂)。
- 时钟回拨:小幅度回拨(如 <50ms)等待追平;大幅度直接报错拒绝服务并告警;或用历史最大时间兜底、切换 workerId;美团 Leaf(号段模式 + 雪花双模式)是工业级方案。
- 挂简历:订单号在雪花 id 末几位嵌入 `user_id % 64` 分片基因(见 Q5.8),既是全局 id 又携带路由信息。

## 9. 项目一:订单中心连环问

### Q9.1 先讲一下订单创建的完整链路

```
用户提交 → 网关(鉴权/限流) → 订单服务
  ① 防重令牌校验(Redis Lua 原子 GET+DEL)
  ② 风控/参数校验
  ③ 价格/优惠实时计算(调商品、营销)
  ④ 发 RocketMQ half 事务消息
  ⑤ 本地事务:创建订单(状态=待支付,雪花id含基因) → 本地事务提交
  ⑥ commit 消息
  ⑦ 库存服务消费:Redis 预扣 + DB 库存扣减(乐观锁)
  ⑧ 优惠券/积分服务消费:各自幂等扣减
  ⑨ 返回下单成功 → 唤起支付
支付成功回调 → 状态机流转 待支付→已支付 → 发已支付事件(履约/通知)
30分钟未支付 → 延迟消息 → 状态机流转 待支付→已取消 → 回补库存/退券
```

### Q9.2 状态机怎么设计的?为什么不用 if-else?

- 模型四要素:**State(状态)、Event(事件)、Transition(from→to, 含 condition 条件和 action 动作)**,全部用枚举/配置声明,如 `待支付 --支付成功事件--> 已支付`。
- 入口统一:`stateMachine.fire(orderId, event, context)`,引擎先查当前状态,查迁移表:无合法迁移直接抛异常(非法流转在引擎层拦截);有则执行 condition → action(业务逻辑)→ 持久化(`update ... where id=? and status=旧值 and version=?` 乐观锁)→ 发领域事件。
- 不用 if-else 的原因:20+ 状态 × 多事件组合爆炸,流转规则散落在十几个方法里,新增一个业务渠道(虚拟商品)要全局找分支,漏一个就是线上资损;状态机让迁移规则集中、可枚举、可评审,**非法流转不可能发生**(白名单机制)。
- 深挖:为什么不用 Spring StateMachine?——它功能全但重(有状态管理器、持久化复杂),我们只需要"迁移表 + 分发",自研轻量实现 200 行核心代码,无额外依赖,团队好维护。
- 重复事件天然幂等:消息重复投递时,当前状态已是目标态,迁移不匹配 → 返回"已处理成功"。

### Q9.3 三层幂等分别挡什么?

- **token**:挡入口层重复——用户狂点按钮、网络重试、前端重发。进页面时发 token(Redis,5min),提交时 Lua `GET+DEL` 原子操作:删除成功才放行。
- **唯一索引(订单号)**:挡落库层重复——服务重试、消息重投导致同单 insert 两次,唯一索引冲突捕获 DuplicateKeyException,转查询返回原订单。
- **状态机乐观锁(version)**:挡状态流转层重复——支付回调重复、取消事件重复,`where status=? and version=?` 影响行数为 0 即已处理过。
- 关键认知:三层不是冗余,是挡**不同环节、不同来源**的重复请求;少任何一层都有漏网场景。

### Q9.4 分库分表为什么按 user_id?按订单号不行吗?

- 查询分布:C 端 80% 是"我的订单"(user_id 维度),按 user_id 分片,买家查询单库命中,不用广播;
- 写均匀:user_id 天然离散,不会热点;
- 按订单号哈希的问题:用户查"我的订单"时没有订单号,要广播 64 张表归并,DB 压力放大 64 倍。
- 按 user_id 分片的代价是"按订单号查"和"商家维度查":前者用**基因法**解决,后者用 **Canal → ES** 异构解决(见 Q5.8)。

### Q9.5 基因法具体怎么把 user_id 放进订单号?

- 雪花 id 64 位,末 12 位是毫秒内序列号(单毫秒 4096 容量,实际用不满),取其中低 6 位(64 = 64 张表)写入 `user_id % 64`;
- 生成订单时 user_id 必然已知,生成时嵌入;
- 按订单号查询:从 id 末 6 位直接取出表号 → `表号/4` 得库号,直达分片,不广播;
- 容量校验:6 位基因仍剩 6 位序列 = 单毫秒 64 个订单/单节点,压测峰值远不到,够用。
- 一句话:**让 id 自己携带路由信息**,这是分库分表后解决"非分片键点查"的主流做法(电商订单号常用)。

### Q9.6 16 库 64 表怎么来的?以后扩容怎么办?

- 容量反推:单表健康线 800~1000 万(B+ 树 3 层);日订单 300 万,年增约 11 亿——但订单冷热分离,热数据(近 6 个月)约 5 亿,64 表 × 800 万 ≈ 5 亿,够 3 年;冷数据归档到历史库。
- 库表关系:64 张逻辑表,初期物理可落在 4~8 个库,逐步扩到 16 库;路由 `table = userId % 64`,`db = table / (64/库数)`。
- 扩容:逻辑分片数固定 64(2 的幂),扩容只做"表搬家"——把部分表整体迁到新库,改路由映射,不用 rehash 重分布数据;迁移用双写(新老库同时写)+ 数据校验 + 读切流 + 下线老库。

### Q9.7 下单用事务消息,如果库存扣减一直失败怎么办?

- 库存消费失败按 RocketMQ 重试机制退避重试(1s、5s...最多 16 次);
- 重试期间订单状态保持"待支付/处理中",前端展示"订单确认中";
- 16 次仍失败 → 死信队列 + 告警;
- 兜底:对账任务每 15 分钟扫描"已创建但库存未扣"的订单,触发补偿;补偿失败(确实无库存)→ 走订单取消流程并通知用户(业务上等同于下单失败退款)。
- 关键认知:最终一致不是"放任不一致",是"异步重试 + 死信告警 + 对账兜底"三层收敛。

### Q9.8 回查逻辑怎么写的?回查一直未知怎么办?

- Broker 回查"订单是否存在":查订单库(本地事务表/订单表),存在且状态合法 → COMMIT;不存在 → ROLLBACK;查询异常(DB 抖了)→ 返回 UNKNOWN,等下次回查。
- 注意回查接口必须**幂等且只读**(不能在回查里创建订单)。
- 默认回查 15 次仍 UNKNOWN,RocketMQ 会发告警/记日志,人工介入;工程上把回查失败率做成监控大盘指标。

### Q9.9 Seata AT 为什么不放在下单主链路?

- AT 一阶段要拿**全局锁**(锁主键值直到二阶段结束),跨 4 个服务的长链路持锁时间 = RPC 时间之和,高并发下热点商品行锁冲突严重,TPS 上不去;
- AT 二阶段回滚靠 undo log,要求所有分支都支持本地事务且 SQL 能被解析(同类框架限制);
- 下单对库存/积分的一致性容忍秒级延迟(用户下完单晚 1 秒看到优惠券扣减无感),所以选事务消息;支付回调涉及钱、链路短(订单+支付流水),用 AT 可接受。

### Q9.10 订单超时为什么不用 Redis 过期监听/定时任务?

- Redis keyspace notification 不可靠(过期事件会丢,不保证投递);
- 定时扫表:分库分表后要扫 64 张表,为了不漏单扫描间隔短 → 大量无效扫描 QPS;间隔长 → 取消延迟不可控;且扫到未支付订单要加锁防重复取消,互相竞争;
- RocketMQ 延迟消息:事件驱动,到点才触发,零无效扫描,天然分布式、可重试;
- 兜底:保留一个**低频**(每 5 分钟)扫描任务,只扫"创建时间接近超时临界点"的小窗口数据,防止消息极端丢失。双保险,主链路不依赖扫表。

### Q9.11 Canal 同步 ES,延迟多少?丢消息/不一致怎么办?

- 链路:Canal 伪装 MySQL 从库拉 binlog → 解析后发 RocketMQ → 消费端写 ES;正常延迟 1 秒以内。
- 顺序:按主键 hash 到同一 queue,同一订单的变更按 binlog 顺序消费,避免旧值覆盖新值。
- 丢消息:消费失败重试 → 死信告警;
- 不一致兜底:① 详情页/强一致查询走 DB,只有列表搜索走 ES(业务可接受秒级延迟);② 定时对账任务按 update_time 增量比对 DB 与 ES,差异修复。

### Q9.12 ES 做订单搜索,深分页怎么处理?

- ES from+size 深分页(from+size > 10000)要在各分片排序取 from+size 条再归并,内存爆炸;
- 用 search_after(用上一页最后一条的排序值游标翻页,适合无限滚动)或 scroll(适合全量导出);业务上运营后台强制带时间范围 + 限制最大翻页深度。

## 10. 项目二:秒杀系统连环问

### Q10.1 完整讲一下秒杀链路

```
活动前:商品静态页 CDN;库存/活动数据预热到 Redis;本地缓存 Caffeine 加载热点
请求阶段:
  ① 答题/验证码(拉长峰值 + 挡机器人)
  ② Nginx(OpenResty)层:IP/uid 限流 + 黑名单
  ③ 网关 → 应用:Sentinel 集群限流(活动维度总 QPS 阈值)
  ④ 校验:登录态、活动时间、风控/设备指纹
  ⑤ Redis Lua 原子操作:一人一单判断(set 去重)→ 库存判断 → 预扣
     失败:已购/售罄直接返回;成功:返回"排队中"
  ⑥ 扣减成功 → 发 MQ(下单消息)→ 接口立即返回(不等落库)
  ⑦ 消费端:幂等创建订单(唯一索引)→ DB 乐观锁扣真实库存
  ⑧ 前端轮询/长连接查结果:成功→支付;失败→提示
超时未支付:延迟消息 → 取消订单 → 回补 Redis 库存(incr)+ 移除一人一单标记(srem)
```

### Q10.2 Lua 脚本写一下?为什么 Lua 能保证原子?

```lua
-- KEYS[1]=库存key  KEYS[2]=已购用户set  ARGV[1]=uid
if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then
    return 1   -- 重复购买
end
if tonumber(redis.call('get', KEYS[1]) or '0') <= 0 then
    return 0   -- 售罄
end
redis.call('decr', KEYS[1])
redis.call('sadd', KEYS[2], ARGV[1])
return 2       -- 成功
```

- Redis 执行 Lua 是**单线程串行执行**,整个脚本作为一个命令执行期间不会被其他命令打断 → 原子;脚本不要写循环/外部调用,防阻塞。

### Q10.3 Redis 预扣了库存,但下单消息丢了/服务宕机,库存不回补怎么办?

- 消息丢失防线:生产端同步发送 + 失败重试(本地兜底重试);Broker 同步刷盘 + 主从;消费端手动 ACK——消息走到消费成功才确认,宕机未确认的消息会重新投递;
- 消费失败:catch 异常发"库存回补消息" + 原消息重试(消费幂等,不会重复扣);
- 超时未支付:延迟消息触发取消 + 回补;
- 终极兜底:对账任务比对 Redis 预扣量与 DB 实际订单量,差异自动修正/告警。

### Q10.4 回补库存怎么保证不回补多了(一人一单标记)?

- 回补动作也要原子且幂等:Lua 脚本里先判断订单状态为"已取消"才 `incr 库存 + srem 已购标记`;
- 状态机保证只有 待支付→已取消 一次流转成功,重复回补消息影响行数/状态判断不通过,直接返回成功丢弃。

### Q10.5 有 Redis 预扣了,为什么 DB 还要乐观锁?

- Redis 和 DB 是两套数据,Redis 预扣成功但 DB 落库可能因重试、旁路任务(后台补库存)、人工修数据等出现不一致;
- DB 是库存事实源,最后一道防线:`update stock set stock=stock-1 where sku_id=? and stock>0`,影响行数 0 即超卖,订单置失败 + 回补 Redis;
- 防御纵深思想:任何一层都可能出问题,关键资损点(库存=钱)必须层层兜底。

### Q10.6 三级限流的阈值怎么定的?Sentinel 集群限流解决什么?

- 阈值来源:**压测**。压测得出应用集群安全水位(如 5 万 QPS,CPU 60%),Redis 集群水位,DB 写入水位 2000 TPS;按水位反推各级阈值,留 20% buffer。
- 单机限流问题:每台机器限流 1000 QPS,100 台机器集群总放 10 万——机器扩容/缩容时总量漂移,且热点流量在机器间不均匀(某台被打满,其他台空闲却还在放行)。
- 集群限流:Sentinel Token Server 集中发放令牌(内嵌/独立部署),所有实例先向 token server 取令牌,保证**全局总 QPS 精确受控**;token server 故障降级回单机限流(可配)。

### Q10.7 单个热点商品 10 万 QPS,Redis 单节点扛不住怎么办?

- 读热点:本地缓存 Caffeine 兜大部分读(活动信息、商品信息);
- 写热点(库存 key 集中在一个槽/一个节点):**库存副本分散**——把 1000 件库存拆到 N 个 key(`stock:sku:1` ... `stock:sku:N`,各存 1000/N),客户端按 uid 哈希/随机选一个 key 扣减;单 key 压力降到 1/N,且 N 个 key 落在 Cluster 不同节点。
  - 细节:某副本扣完了怎么办?→ Lua 返回售罄后客户端尝试其他副本(设尝试上限 2~3 次,避免放大);一人一单的 set 是全局 key(不拆),按 uid 判定不受影响;
  - 回补时按记录的副本号回补对应 key。
- 备选:服务端本地预扣 + 异步同步(更复杂,我们用副本法,运维简单且可控)。

### Q10.8 异步下单,用户怎么知道结果?会不会觉得卡?

- 接口在 Redis 预扣成功后立即返回"抢购成功,排队下单中"(HTTP 202 语义),前端进入等待页;
- 前端轮询订单查询接口(或 WebSocket 推送),拿到订单 → 跳支付;超时(如 5s)没拿到 → 提示"下单确认中,稍后在订单列表查看";
- MQ 消费正常秒级完成,99% 用户在 1~2 秒轮询内拿到结果;
- 体验权衡:用秒级"排队中"换 DB 不被打挂,比"转圈 30 秒后 502"好得多,大促用户预期也接受排队。

### Q10.9 答题/验证码为什么能削峰?

- 把"同一秒 10 万人同时点"打散成"10 万人花 3~10 秒答题后陆续点",瞬时峰值拉平约 30%;
- 同时挡脚本机器人(无差别请求直接发答案的刷子在答题环节被拦),配合设备指纹/黑名单,拦截约 40% 刷子流量。

### Q10.10 秒杀和主交易链路怎么隔离?

- **线程池隔离**:秒杀独立 Tomcat 业务线程池?——实际是独立服务集群 + 独立线程池(Hystrix/ Sentinel 舱壁模式),秒杀接口不占用主下单线程池;
- **Redis 隔离**:秒杀 key 用独立逻辑分片/专属集群,避免把共享 Redis 打满影响主站;
- **DB 隔离**:秒杀订单写独立表/独立库(活动结束后归并);MQ 用独立 topic + 独立消费组;
- **限流降级兜底**:秒杀顶不住时可一键降级(关闭秒杀入口),主站交易不受影响——故障域隔离。

## 11. 项目三:稳定性建设连环问

### Q11.1 全链路压测怎么做?压测数据怎么隔离?

- 流量构造:线上流量录制(网关日志/代理层录制真实请求)→ JMeter/自研平台按比例(1:1、3:1、5:1)回放;
- **压测标记透传**:请求头加压测标识 → 网关入口放入 ThreadLocal → RPC(Feign 拦截器放 attachment)→ HTTP header → MQ(消息属性)→ 子线程(TransmittableThreadLocal),全链路透传;
- 存储隔离:DB 路由**影子表**(表名后缀 _press,同库或影子库,压测流量 CRUD 都路由影子表);Redis key 加 press 前缀;MQ 用压测 topic + 压测消费组;第三方调用(支付/短信)mock 或白名单拦截;
- 压测中盯:CPU/RT/错误率/连接池/线程池队列/慢 SQL,水位安全线 CPU 70%、RT 不超 SLA;发现瓶颈(如 Redis 连接池打满、热点 key、某条 SQL)当场记录,压后复盘整改,共修复 40+ 瓶颈点。

### Q11.2 降级预案怎么演练?

- 预案清单:每个核心接口/依赖都有开关(配置中心 Nacos 热推送),如"关闭推荐""关闭营销计算""库存只查缓存""评论降级兜底文案",30+ 预案文档化(触发条件、开关位置、影响面、回滚步骤);
- 演练:大促前 2 周开始**常态化演练**,每周随机在预发/灰度环境触发预案,验证开关生效、监控告警联动、回滚正常;
- 关键认知:没演练过的预案等于没有——开关位置忘了、配错 key、降级后 NPE 都是真实踩过的坑。

### Q11.3 讲一个你排查过的最棘手的线上问题(STAR)

- 模板(结合真实经历微调):大促演练时订单接口 P99 间歇性飙到 2s。
  - S:压测到 3 万 QPS 时,平均 RT 正常但 P99 周期性抖动;
  - T:我负责定位;
  - A:① SkyWalking 链路发现慢在 Redis 调用(不是 DB);② Redis 监控发现单节点 CPU 偶发 100%——定位到一个**大 key**(运营把 5000 个 sku 的活动配置塞一个 hash);③ 同时慢日志里发现 KEYS 命令(某定时任务);④ 整改:大 key 拆分 + 换成 HSCAN 遍历 + Caffeine 本地缓存;⑤ 加 Redis 命令耗时监控和大 key 扫描常态化;
  - R:P99 稳定在 50ms 内,沉淀为 Redis 使用规范(禁用 KEYS/FLUSHALL、value 大小红线)。
- 备选素材:GC 问题(Q3.5)、慢 SQL(Q5.7)任选,核心是**有排查路径、有工具、有沉淀**。

### Q11.4 慢 SQL 治理机制怎么运转的?

- 发现:pt-query-digest 每日聚合慢日志 + 监控平台慢 SQL 数实时告警;
- 流程:周报通报 TOP20 → 提单到对应开发 → DBA 协助 explain 分析 → 优化(索引/SQL 改写/架构)→ 上线后对比 RT 闭环;
- 预防:Code Review checklist(新 SQL 必 explain、禁止 select *、深分页规范)+ 发布前静态扫描(MyBatis mapper 规则检查)。

### Q11.5 监控告警怎么设计?告警风暴怎么办?

- 三个层次:基础设施(主机/容器 CPU、内存、磁盘)、中间件(MySQL/Redis/MQ 连接数、慢查询、积压)、业务(下单 TPS、成功率、RT、支付回调延迟)——业务指标最救命;
- 告警分级:P1 电话+飞书、P2 飞书群、P3 仅大盘;
- 防风暴:告警聚合(同服务 5 分钟内同类合并)、依赖抑制(下游 DB 挂了,上层 100 个接口告警合并成根因一条)、配 runbook 处理手册;
- MTTD 从 15 分钟(等用户投诉)降到 1 分钟。

# 第三篇 · 三面:系统设计面

> 考察上限。套路:**先澄清需求(别上来就画架构)→ 容量估算 → 整体架构 → 核心链路 → 高并发/高可用/一致性深入 → 演进与权衡**。
> 不会给标准答案的题,看的是思考过程。以下四题为高频题,直接复用简历项目素材。

## 12.1 设计一个秒杀系统

- 直接用项目二全链路作答(Q10.1),再补充容量估算模板:
  - 假设 100 万人抢 1 万件商品:峰值 QPS 估 10 万(读)/ 写峰值(答题打散后)约 2~3 万;
  - 机器:应用层按单机 2000 QPS → 15~20 台;Redis Cluster 6 主 6 从;MQ 按峰值写入 + 消费速率 2000 TPS 反推消费者 8~10 台;
- 加分点:静态化 CDN(读流量根本不进系统)、作弊防控、库存预热、限流阈值压测定、故障演练。

## 12.2 设计短链接系统

- 需求澄清:日均生成量?跳转 QPS?是否需要自定义短码?统计分析?
- 发号:分布式 ID 生成器(雪花/号段模式取号)→ Base62 映射(6 位短码 ≈ 568 亿容量);自定义短码走唯一约束冲突检测;
- 存储:短码→长链映射,数据量大按短码哈希分库分表;前面加 Redis 缓存热点短链;
- 跳转:302(临时重定向,每次请求到服务端,可统计 PV/UV)vs 301(永久,浏览器缓存,省资源但丢统计)——统计诉求选 302;
- 高并发:热点短链(营销短信)走 CDN/边缘缓存 + Redis;布隆过滤器挡恶意短码扫描。

## 12.3 设计 Feed 流(信息流)

- 推拉模式:
  - 推模式(写扩散):发博时 fanout 写到所有粉丝的收件箱(feed 表按 uid 分片),读一次拿;写放大(大 V 一条推千万人),读快;
  - 拉模式(读扩散):读时实时拉关注人的博文合并排序;写轻,读重(大 V 读放大);
  - **推拉结合**:普通用户推,大 V 不推(粉丝读时单独拉大 V 再 merge),业界通用方案;
- 计数(赞/评/转):Redis 计数器 + 异步落库;
- 排序:时间线用拉模式 + 分页游标;推荐流走推荐系统服务(另一个话题)。

## 12.4 设计微信红包/点赞计数

- 红包:发红包(金额拆成 N 份用**二倍均值法**:每次随机 [0.01, 剩余均值×2],保证均匀)→ 拆好的明细存 Redis(list/队列)→ 抢红包 Lua 原子(判重复 uid + 取份)→ 异步落库写流水 → 24 小时未抢完回退余额;
- 计数:点赞 Redis hash/set 记录关系(防重复)+ 计数器;高赞内容计数用 Redis 分片计数或本地批量聚合后刷库;读多写少走缓存。

## 12.5 设计题通用框架(套任何题)

1. **需求澄清**(3 分钟):功能范围、读写比、QPS/数据量级、一致性要求;
2. **容量估算**:QPS、存储、带宽,量级对即可;
3. **架构分层**:客户端/CDN → 网关 → 服务拆分 → 存储选型;
4. **核心流程**:时序图级别讲一遍;
5. **三高深入**:高并发(缓存/异步/分片/限流)、高可用(主从/集群/降级/多活)、一致性(缓存一致/分布式事务/对账);
6. **权衡**:主动说"这里我选了 X 牺牲了 Y,因为约束是 Z"。
