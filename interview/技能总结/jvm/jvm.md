**手动碰到 JVM = 你给 JVM 下达指令，观察它的行为，甚至看它内部的数据，亲眼验证规范。**

> JDK 自带一整套工具，就是留给你 “触摸虚拟机” 的入口：`jps、jstat、jmap、jhat、jvisualvm、hsdis`，外加 JVM 启动参数。
>
> &#x20;你写 Java 代码，加上启动参数，就能控制 JVM 的行为；工具可以偷看 JVM 内部状态。

## 一、最简单的触摸方式：JVM 启动参数（你直接给 JVM 下命令）

你写 main 方法，启动程序的时候，在 VM options 里传参数，**直接配置 JVM**，这就是第一层接触。

&#x20;前面 OOM 例子的参数：

plaintext

```
-Xms20m -Xmx20m

```

含义：告诉 HotSpot，堆初始 20M，最大 20M。

&#x20;你修改这个值，JVM 的行为直接改变。

&#x20;还有这些你后面会用到：

- `-XX:+PrintGCDetails`：打印 GC 详细日志（看垃圾收集器干活）
- `-XX:+UseSerialGC`：强制指定 GC 收集器
- `-Xss256k`：修改虚拟机栈大小（会直接改变递归 StackOverflow 的深度）

👉 这个动作，就是你**直接跟 JVM 对话**。你改参数，JVM 就按你的规则跑。

## 二、JDK 自带工具集：扒开 JVM 外壳，看里面的状态（真正 “触摸”）

> 所有工具都在`JDK/bin`目录，不需要额外安装。

### 1. jps（Java Virtual Machine Process Status Tool）

作用：列出当前正在运行的 Java 进程，拿到进程 PID。

shell

```
jps

```

拿到 PID，后面所有工具都靠这个 PID 去附着到正在运行的 JVM 实例上。

> 含义：找到操作系统上正在跑的那个 JVM 进程。

### 2. jstat（看运行时统计：GC、内存）

实时观测 JVM 堆、GC 次数、内存占用。

shell

```
# pid换成你的进程号，每1000毫秒打印一次
jstat -gc 12345 1000

```

你启动那个堆 OOM 程序，一边跑一边开 jstat，**亲眼看见 Eden 区内存慢慢涨满，发生 GC**。

&#x20;不再是书上写的 “Eden 区放新生对象”，你能看到数字变化。

### 3. jmap（快照，抓取堆内存 dump）

把当前 JVM 整个堆里面所有对象，导出成文件。

shell

```
jmap -dump:format=b,file=heap.hprof 12345

```

拿到`heap.hprof`堆转储文件，里面存着 JVM 堆里全部对象实例。

&#x20;之后用 jhat 或者 VisualVM 打开：

&#x20;你能看到：有多少个 OOMObject 实例，占用多少内存。

> 相当于：暂停 JVM，打开堆，翻看里面所有对象。

### 4. jvisualvm（图形界面，最适合新手触摸）

直接在命令行输入：

shell

```
jvisualvm

```

图形窗口，可以：

1. 挂载本地正在运行的 Java 进程
2. 实时看堆内存曲线、线程数量、类加载数量
3. 手动触发 Full GC
4. 一键 dump 堆快照，浏览堆里所有对象

   &#x20;✅ **这个是新手首选！可视化，不用死记命令。**

   &#x20;你跑递归栈溢出 demo，打开 visualvm 看线程栈；跑堆 OOM，看堆内存持续上涨。

## 三、更深一层触摸：看字节码（javap）

你写一段简单 Java 代码：

java

运行

```
public class Demo {
    int a = 10;
    public void test(){
        int b = 20;
    }
}

```

编译后，执行：

shell

```
javap -c Demo.class

```

输出字节码指令。

&#x20;Java 源码 → 编译器编译成字节码，**字节码就是 JVM 能看懂的指令集**。

&#x20;JVM 执行的不是 Java 源码，是这些字节码。

> 你可以读懂字节码，看 JVM 一步一步执行指令。
>
> &#x20;这就是直接看 JVM 要执行的指令。

## 五、一个非常重要的认知：JVM 是什么？

JVM 本质就是**操作系统上跑的一个普通进程**。

&#x20;你启动 main 函数，操作系统拉起一个 HotSpot 进程，这就是你的 JVM。

- 你可以给它传启动参数（配置它）
- 你可以 attach 上去，读取它内部内存统计（观测它）
- 你可以让它导出堆快照（偷看里面所有对象）
- 你可以杀死这个进程（直接关掉 JVM）

> 看书是看理论；**跑 demo + 工具观测，才是伸手摸到 JVM 本身。**

# 一句话结论

**JMM（Java 内存模型）本身是 JLS 定义的一套抽象契约，你不能直接 “看见 JMM”；但是 JMM 在 HotSpot 上的实现现象，可以写 Demo + 工具去观测、复现。**

先分清两个东西，别混在一起：

1. **JMM（Java Memory Model）**：JLS 规范，**逻辑规则**。

   &#x20;规定：多线程之间，**可见性、原子性、有序性**的语义，happens-before。
   > 它不是 JVM 里一块内存区域，不是硬件，没有实体。就像法律条文，你看不到法律本身，只能看到**违法 / 守法产生的行为现象**。
2. **HotSpot 对 JMM 的实现**：HotSpot 用**内存屏障、CPU 缓存、指令重排**去实现 JMM 这套规则。

   &#x20;这一层的现象，**可以写代码复现**；底层的内存屏障指令，可以看汇编。

## 能看到什么（分层次）

### ✅ 第一层：能亲眼看到【JMM 的现象】（最推荐，现阶段上手）

写经典的**指令重排 Demo（DCL、双重检查锁的那个复现代码）**，在 HotSpot 上复现：

&#x20;一个线程写，另一个线程读到**半初始化对象**。

> 这个现象，就是 JMM 允许指令重排带来的结果。
>
> &#x20;加上`volatile`之后，现象消失。
>
> &#x20;👉 你不是看到 JMM，而是**看到 JMM 规则带来的行为差异**。
>
> &#x20;这就是触摸 JMM 最直接的方式。

> 注意：这个复现比较玄学，不是每次运行都必出现，因为 CPU、JIT 随机。要循环大量次数才能复现。

### ✅ 第二层：看到 HotSpot 用来实现 JMM 的【内存屏障】

JVM 在 volatile 读写、synchronized 出入 monitor 的时候，会插入内存屏障。

&#x20;使用`-XX:+PrintAssembly` + hsdis 插件，可以**查看 JIT 编译后的 CPU 汇编指令**。

&#x20;你能看到：volatile 写后面，会出现`lock`指令（x86 平台），这就是内存屏障。

> 这个就是 HotSpot 兑现 JMM 契约的硬件指令。
>
> &#x20;👉 这已经摸到 JMM 在 CPU 层面的实现。

缺点：

- 配置 hsdis 麻烦；
- 汇编门槛高；
- 不同 CPU 架构（ARM）指令不一样。

  **现阶段不建议优先搞这个。**

### ❌ 不能看到的

你不能在 jvisualvm/jmap/jstat 里面找到一个叫 “JMM” 的模块或者区域。

&#x20;jmap、jvisualvm 看的是**堆、线程、对象**；它们看不到逻辑上的内存可见性规则。

&#x20;JMM 不是一块实体内存，是**多线程之间读写的约束规则**。

## 对比前面的 JVM 内存区，帮你理解区别

- 运行时数据区（堆、虚拟机栈）：**实体存储区域**，可以用 jmap/jvisualvm 直接观测里面对象、内存大小。
- JMM：**多线程访问内存的行为契约**，没有实体，只能观测行为现象。

## 举个类比

- 运行时数据区 = 一间屋子，你可以推门进去，看家具、测量大小（jvisualvm）
- JMM = 这间屋子的**人与人之间传递物品的规则**：

  &#x20;规定 A 放东西，B 什么时候一定能看见；

  &#x20;规则本身看不见，但是你可以做实验，看什么时候 B 看不到 A 放的东西（可见性问题）。

## 学习顺序建议（贴合你现在的节奏）

1. 先搞定运行时数据区 + 对象创建，熟练用 jvisualvm 观察堆、线程。
2. 然后写 Demo 复现**指令重排**，感受 JMM 现象（只看行为，不看汇编）。
3. 等你理解 happens-before 之后，**有兴趣再去看 PrintAssembly 汇编，看内存屏障指令**。

## 补充一个关键坑（面试高频）

很多人会混淆：

> JMM ≠ CPU 缓存模型
>
> &#x20;JMM 是 Java 语言层契约；CPU MESI、缓存是硬件。HotSpot 用硬件能力实现 JMM，但二者不是一回事。
>
> &#x20;复现代码看到的是 JMM 现象；汇编看到的是 HotSpot 为实现 JMM 发出的 CPU 指令。
