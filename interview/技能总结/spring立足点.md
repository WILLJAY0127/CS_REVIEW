# 先说你的感受：Spring 没有像 JVM / JLS 那种 “硬标准规范” 的立足点，根源在这里

JVM 有 JVMS、Java 并发有 JLS，是**语言虚拟机的硬性规范，是定义 “必须是什么行为”**。

&#x20;但 Spring 是**应用层框架，是一个代码库，不是语言标准**。

&#x20;Spring 官方文档，写的是**这个框架对外承诺的行为**，不是编程语言强制规则。

> 一句话区分：
>
> &#x20;JLS/JVMS：你写 Java 代码，只要跑在任何合规 JVM 上，都必须遵守这套规则。
>
> &#x20;Spring 官方文档：**只有你用 Spring 框架，才遵守它定义的行为；换 Guice、Micronaut，规则就完全不一样。**
>
> &#x20;网上大量 Spring 面试题，很多是**Spring 内部源码实现细节**（三级缓存、后置处理器执行顺序），官方文档根本不写源码内部实现，只描述对外表现。
>
> &#x20;👉 这就是你感觉 “没有立足点” 的核心原因。

## 怎么建立立足点：把 Spring 拆成两层，严格分开

### 第一层：【契约层】—— 官方文档，唯一立足点（必须优先抓住）

> 这一层是 Spring 对外承诺的**行为契约**，写在 reference 文档，不会随便改，面试回答的基准。
>
> &#x20;只关心：调用框架组件，**外部看到什么效果**，不关心里面怎么实现。
>
> &#x20;包含：

1. IOC 容器契约：Bean 作用域、生命周期回调接口（`InitializingBean/@PostConstruct`）、依赖注入规则。
   - 契约：单例 Bean 在容器中只一份；`@PostConstruct` 在属性填充完成之后执行。
   - 官方文档保证这个行为，**不管底层源码怎么改，对外行为不变**。
2. AOP 契约：通知执行顺序、代理生效前提；只有被容器管理的 Bean，切面才生效。
3. 事务契约 `PlatformTransactionManager`：
   - 传播行为、隔离级别、事务状态的行为定义，这是接口契约。

     &#x20;REQUIRES\_NEW 的契约：挂起当前事务，创建全新独立事务。这是文档写死的行为。

> ✅ 这一层，是你回答面试题的**立足点**，争议全部回官方 reference 核对。

### 第二层：【实现层】—— Spring 源码内部方案（属于实现，不是契约！可替换、可修改）

> 这就是网上面试题疯狂讲的东西，**不属于官方契约，只是 Spring 当前版本为了实现上面契约选用的方案**。
>
> &#x20;这一层可以换方案，只要对外行为不变。
>
> &#x20;例子：

- 三级缓存：**实现层**。目的是实现【单例 setter 循环依赖可以解决】这个契约行为。
  > 重点：契约只说 “setter 注入单例循环依赖可以解决”，**没有规定必须用三级缓存**。Spring 完全可以换别的方式实现，只要外部行为不变。
  >
  > &#x20;所以面试回答的逻辑顺序：
  >
  > &#x20;① 先讲契约：Spring 支持 setter 单例循环依赖，不支持构造注入循环依赖（官方文档行为）
  >
  > &#x20;② 再补充：当前版本 Spring 内部是靠三级缓存这个实现方案做到的
- BeanPostProcessor 执行顺序、JDK/CGLIB 代理选择逻辑，都是**实现细节**。

> 很多学习 Spring 的人踩坑：**直接上来啃第二层源码实现，跳过第一层契约。**
>
> &#x20;就会感觉飘在空中，没有根基，各种说法打架，这就是你现在的感受。

## 学习 Spring 的新范式（适配你喜欢 “标准、有依据” 的风格）

固定顺序，**先契约，后实现**

1. 打开 Spring reference 文档，阅读对应模块，提炼【对外行为契约】，这是你的基准。
2. 写 Demo 验证这个契约（最重要！Demo 用来验证文档描述的行为，Demo 结果 = 事实）
3. 再去看源码，理解 Spring**用什么内部方案完成这个契约**
4. 区分：哪些是契约（必须遵守），哪些是内部实现（只是一种方案，有取舍）
5. 遇到网上冲突的说法：**以文档描述行为 + Demo 运行结果为准，源码只是实现手段**

举个例子：循环依赖，按这套范式组织回答

1. 契约（文档 + Demo 验证）

   &#x20;Spring IOC 支持**单例 Bean、setter 注入**的循环依赖；

   &#x20;构造器注入 /prototype 作用域，无法解决循环依赖，启动直接报错。
2. 实现（源码方案，只是手段）

   &#x20;Spring 用三级缓存机制来实现这个能力。

   &#x20;解释每一层缓存的作用；追问：二级缓存行不行？回答：单纯二级缓存无法处理 AOP 代理对象场景，所以引入第三层。
3. 边界：这个实现有局限，局限就是契约写的不支持的场景。

> 重点：**契约是不变的锚点；源码实现是可变的手段**。
>
> &#x20;面试的时候，先讲契约行为，再讲实现方案。面试官追问底层，再切入源码细节。
>
> &#x20;不要一上来就直接讲三级缓存，那样就会变成背源码，没有根基。

## 再举事务的例子，体会这套锚点思路

1. 事务契约（官方文档）

   &#x20;@Transactional 基于 AOP 代理生效；7 种传播行为定义的事务挂起 / 新建规则；异常回滚规则。
2. Demo 验证：写代码测试 REQUIRES\_NEW、同类自调用事务失效，看运行结果。
3. 实现：底层用 AOP 拦截方法，在方法前后调用 PlatformTransactionManager 接口。

> 事务失效，本质是**破坏了 AOP 代理的契约**，不是什么玄学。

## 🧪 实操的定位（Spring 里实操比读源码更像 “立足点”）

JVM 我们可以写代码，观察 JVM 按照 JVMS 规范运行；

&#x20;Spring 也一样：**Demo 运行结果，就是事实标准，用来校验网上各种说法**。

> 网上很多 Spring 面试结论是错的，跑一遍 demo 就能直接证伪。
>
> &#x20;例如：很多人说`@PostConstruct`是初始化第一回调。写 Demo，同时写上`InitializingBean`、xml init-method，打印顺序，你就能拿到事实。

## 学习优先级调整（解决 “飘着” 的问题）

1. 先吃透【IOC 容器契约】，用 demo 验证 Bean 生命周期回调顺序，建立第一个锚点
2. 然后 AOP 契约，demo 验证代理生效 / 失效规则，第二个锚点
3. 然后事务契约，demo 复现各种事务失效、嵌套传播场景，第三个锚点
4. 最后，再去看源码实现（三级缓存、后置处理器），源码只是用来解释 “Spring 怎么实现这个契约”

## 下一步选择

A：我们从**IOC Bean 生命周期**开始，先提炼官方文档的【契约】，然后写 Demo 验证生命周期回调顺序，建立 Spring 第一个锚点。

&#x20;B：直接从 AOP 契约入手，复现 AOP 失效场景（同类内自调用）。
