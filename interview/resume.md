## 四、项目经历

### 项目一:交易中台 — 订单中心重构(2022.03 — 2022.12)

**项目背景**:老订单系统为单体架构,订单状态流转散落大量 if-else,线上状态流转 BUG 频发;订单表单表数据超 2 亿,大促期间慢查询告警不断;多业务方(自营、POP、虚拟商品)接入订单逻辑耦合严重。

**技术栈**:Spring Cloud Alibaba · MySQL · ShardingSphere · Redis · RocketMQ · Elasticsearch · Canal

**核心职责与成果**:

1. **订单状态机引擎**:抽象「状态 + 事件 + 动作 + 条件」模型,自研轻量状态机(参考 Spring StateMachine 思想),订单 20+ 状态流转全部配置化,消灭散落的 if-else 分支,状态流转相关线上 BUG 率下降 90%。
2. **三层幂等体系**:前端防重令牌(Redis token + Lua 原子校验)+ 业务唯一索引(订单号)+ 状态机乐观锁(version 字段),彻底解决重复下单、重复支付、重复回调问题。
3. **订单库分库分表**:采用 ShardingSphere 按 `user_id` Hash 分 16 库 64 表,单表数据 2 亿+ 降至 800 万,核心查询 P99 从 1.2s 降至 150ms;订单号采用雪花算法并**基因法嵌入 user_id 分片基因**,解决按订单号直达分片的问题;商家/运营维度查询通过 Canal 异构 ES 解决。
4. **分布式事务**:下单链路(订单 + 库存 + 优惠券 + 积分)采用 **RocketMQ 事务消息**保证最终一致;支付等强一致场景用 **Seata AT**;资金扣减场景评估过 TCC 方案后采用本地消息表对账兜底。
5. **订单超时处理**:基于 RocketMQ 延迟消息实现 30 分钟未支付自动取消订单 + 库存回补,替代原定时任务扫表方案(扫表 QPS 高、取消延迟不可控),取消延迟从分钟级波动收敛到秒级。
6. **订单列表 ES 异构**:Canal 监听 binlog → RocketMQ → ES,订单多条件组合检索 RT 从 800ms 降至 50ms,主库读压力下降 70%。

**项目成果**:订单创建 RT 350ms → 80ms;需求交付周期缩短 40%;连续两届大促零事故;支撑日订单 300 万+。

### 项目二:大促秒杀与高并发营销系统(2023.06 — 2023.10)

**项目背景**:大促峰值流量为日常 30 倍,头部热点商品瞬时并发达 10 万+ QPS,老链路下单全部直打 DB,大促演练时数据库连接池被打满、主库 RT 飙升。

**技术栈**:Redis · Lua · RocketMQ · Sentinel · Caffeine · Nginx(OpenResty)

**核心职责与成果**:

1. **流量漏斗三级限流**:网关层 Nginx+Lua 按 IP/用户维度限流;应用层 Sentinel **集群限流**按活动维度控制总 QPS;数据层 Redis 库存信号量兜底。超量请求快速失败,返回"活动太火爆",绝不放流量打到 DB。
2. **库存防超卖**:Redis + Lua 脚本实现「查库存 → 判重复购买 → 扣减」原子预扣;扣减成功发 MQ 异步下单,消费端落库时 DB 乐观锁(`stock > 0` + version)兜底;下单失败或超时未支付通过 MQ 回补 Redis 库存。大促全程零超卖。
3. **热点商品治理**:本地缓存 Caffeine + Redis Cluster 分片;对单热点 key 做**副本分散**(`stock:{skuId}:{1..N}`,客户端随机路由 + 扣减结果汇总),单热点商品支撑 10 万 QPS;热点数据通过配置中心主动推送。
4. **异步削峰**:答题/验证码拉长峰值(削平瞬时约 30%),下单请求全部写入 MQ,消费端按 DB 承载能力匀速拉取消费,将 10 万 QPS 入口流量收敛为约 2000 TPS 的 DB 写入。
5. **舱壁隔离**:秒杀链路独立线程池 + 独立 Redis 逻辑分片,与主交易链路物理隔离,秒杀故障不传染主站交易。
6. **防刷风控**:令牌桶防刷 + 设备指纹 + 黑名单 + 风控规则校验,拦截刷子流量约 40%。

**项目成果**:秒杀接口平均 RT 30ms,链路可用性 99.99%,双 11 当天零超卖、零 P0/P1 事故。

### 项目三:微服务治理与稳定性体系建设(2024.01 — 2024.09)

**项目背景**:微服务规模 100+ 后,问题集中暴露:大促容量靠拍脑袋、慢 SQL 反复出现、故障发现靠用户投诉、限流降级各团队做法不一。

**核心职责与成果**:

1. **全链路压测**:基于 JMeter + 线上流量录制回放搭建压测体系,压测流量打标透传(影子库/影子表),大促前完成核心链路容量摸底,识别并修复瓶颈点 40+ 处(含连接池、线程池、热点 key、慢 SQL)。
2. **限流降级预案**:Sentinel 统一接入网关层与应用层,核心接口配置 QPS 阈值与 RT 熔断规则,沉淀降级预案 30+ 个并常态化演练(预案开关、参数、回滚步骤全部文档化)。
3. **慢 SQL 治理机制**:建立「慢 SQL 监控(pt-query-digest + explain)→ 周报通报 → 开发/DBA 联合治理」闭环,累计治理慢 SQL 200+ 条,核心库 P99 RT 下降 60%。
4. **可观测体系**:Prometheus + Grafana 业务监控大盘 + SkyWalking 全链路 Trace + ELK 日志,告警接入飞书;故障平均发现时间(MTTD)从 15 分钟缩短至 1 分钟。
5. **分布式锁组件化**:统一封装 Redisson 锁组件,强制锁粒度、超时时间、看门狗续期规范,消灭此前多次发生的锁超时失效事故。

**项目成果**:核心交易链路可用性 99.99%,大促零 P0/P1 事故,团队大促值班压力显著下降。
