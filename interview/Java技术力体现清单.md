# Java 后端技术力体现清单(面试自查用)

> 核心问题:Java 后端的哪些"动作"能体现技术力?
> 用法:对照简历,每个项目至少覆盖"选型取舍 / 边界处理 / 可观测治理"三力中的两项;面试时主动把话题引到这些动作上。

---

## 总览:技术力体现在三个层次

1. **选型取舍**:为什么用 A 不用 B,代价是什么
2. **边界处理**:异常、并发、一致性、降级怎么兜
3. **可观测与治理**:埋点、监控、对账、容量规划

面试官判断"是不是真做过",就看说一个技术点时:
- 能不能讲出**代价**(用了 A 牺牲 B,因为约束 C)—— 选型力
- 能不能讲出**异常路径**(失败/超时/并发/重复怎么走)—— 边界力
- 能不能讲出**怎么证明它 work**(监控指标、对账、压测)—— 治理力

---

## 1. 并发编程

| 动作 | 体现的技术力 |
|------|------------|
| 锁的选型(synchronized / ReentrantLock / 读写锁 / Redisson) | 知道各锁代价(重量级、可中断、公平、读多写少),按场景选 |
| CAS / AtomicXxx 代替锁 | 理解无锁原理、ABA 问题、自旋开销 |
| 自定义线程池参数(核心数、有界队列、拒绝策略、监控) | 不用 `Executors.newFixedThreadPool`(OOM 隐患) |
| ThreadLocal 用完主动 remove | 知道线程池复用导致脏数据/内存泄漏 |
| 分布式锁带续期、防误删、可重入 | 不是裸 setnx,考虑看门狗续期、客户端宕机 |

**金融场景加分动作**:资金类操作用"状态机 + 乐观锁(影响行数=0 判定重复处理)",而不是分布式锁一把梭——锁会掩盖并发问题,乐观锁更符合幂等语义。

## 2. JVM 与线上排查

| 动作 | 体现的技术力 |
|------|------------|
| OOM/CPU 100% 三板斧排查 | `top + top -Hp + jstack` 找线程、`jmap` 找堆、arthas 在线诊断 |
| 能讲清为什么选 G1 不选 CMS | 停顿、吞吐、Region、混合回收的权衡 |
| 定位 Full GC 频繁根因 | 大对象、内存泄漏、Metaspace、System.gc() |
| 线上不重启热更新(arthas redefine) | 应急能力 |

---

## 3. Spring

| 动作 | 体现的技术力 |
|------|------------|
| AOP 自定义切面做审计/限流/脱敏 | 理解动态代理(JDK vs CGLIB)、切点、性能影响 |
| `@Transactional` 失效场景列全 | 自调用、非 public、异常被吞、传播行为错——懂 AOP 代理原理 |
| 事件机制解耦(ApplicationEvent) | 同步事务内发布 → `@TransactionalEventListener` 异步解耦 |
| 自定义 starter / 自动配置 | 理解 Boot SPI,能做二方库封装 |

---

## 4. MySQL

| 动作 | 体现的技术力 |
|------|------------|
| 索引设计:覆盖索引、最左匹配、避免回表 | 看执行计划 `Extra` 判断,不是"加个索引" |
| 慢 SQL 看懂执行计划 | type/key/rows/Extra,filesort、临时表 |
| 分库分表:分片键、跨片查询、扩容 | 范围 vs 哈希分片、分库 vs 分表、全局 ID |
| 避免大事务/长事务 | 持锁、占 undo log、影响 MVCC |
| 乐观锁/悲观锁恰当使用 | 高并发扣减用乐观锁+重试,资金对账用悲观锁 |

---

## 5. Redis

| 动作 | 体现的技术力 |
|------|------------|
| 穿透/击穿/雪崩三件套防护 | 布隆过滤器、互斥重建、逻辑过期、随机过期 |
| 分布式锁讲到 RedLock 争议 | 主从异步复制丢锁、RedLock 争议点、自己怎么取舍 |
| 缓存一致性(延迟双删 / 订阅 binlog) | 知道 Cache Aside、先删缓存再更新库的坑 |
| 热 key 本地缓存 + 大 key 拆分 | 知道 Redis 的边界 |
| Lua 保证原子性 | 扣减库存、限流计数的多步原子操作 |

---

## 6. 消息队列

| 动作 | 体现的技术力 |
|------|------------|
| 不丢不重三幂等 | 消费端幂等(唯一 ID+去重表/状态机)、生产重试、broker 持久化 |
| 顺序消息场景识别 | 同 key 同队列,知道代价(牺牲并行度) |
| 事务消息 / 本地消息表 | 最终一致性,业务侧有兜底对账 |
| 积压处理(扩消费者、临时 Topic、降级) | 不只会用,还会救火 |
| 延迟消息替代定时扫表 | 知道扫表压力与不精确 |

**保险缴费场景**:支付回调用 MQ 削峰 + 消费端按缴费单号去重 + 本地消息表驱动核心入账——三个动作串起"幂等 + 削峰 + 最终一致"的技术力闭环。

---

## 7. 分布式

| 动作 | 体现的技术力 |
|------|------------|
| 分布式事务选型(TCC/Saga/本地消息表/Seata AT) | 知道各方案代价(TCC 写补偿、Saga 长事务、AT 全局锁) |
| 幂等设计(幂等键/状态机/唯一索引) | 从协议层保证,不是"加个 if" |
| 限流(令牌桶/漏桶/滑动窗口)+ 熔断 + 降级 | 三者联动,不只是会用 Sentinel |
| 分布式 ID(雪花、Leaf、号段) | 时钟回拨、性能、趋势递增的取舍 |
| 服务治理(注册发现、配置中心、链路追踪) | 可观测性三件套 |

## 8. 架构与系统设计

| 动作 | 体现的技术力 |
|------|------------|
| 防腐层(ACL)隔离老系统 | 保险核心老、协议乱,适配层收敛变化——隔离与演进 |
| 状态机建模 | 缴费单/保单流转,防非法跳转,天然幂等 |
| 对账体系 | 三方对账(渠道账单 ↔ 平台流水 ↔ 核心应收),长短款自动分类 |
| 异步化 + 削峰 + 缓存降级组合拳 | 知道什么时候不该异步(强一致场景) |
| 灰度 / 回滚 / 降级预案 | 上线不是赌,有逃生通道 |

## 9. 工程素养(TL 岗加分,多数人忽略)

| 动作 | 体现的技术力 |
|------|------------|
| 统一异常处理 + 统一返回结构 | 不在每个 Controller 写 try-catch |
| 日志规范(traceId 贯穿、级别用对、不打敏感信息) | 可观测性基础 |
| 单测 + 集成测试分层 | 关键路径必测,不是"没时间写" |
| 注解 + 切面零侵入埋点 | 架构抽象能力(断点平台的做法) |
| 错误码字典统一 | 跨系统失败可归因——标准化能力 |

## 10. 性能优化(最容易被深挖)

| 动作 | 体现的技术力 |
|------|------------|
| 批量代替循环单条 | N+1 查询、批量 insert |
| 异步化(MQ / CompletableFuture / WebAsync) | RT 与吞吐的权衡 |
| 多级缓存(本地 + Redis + DB) | 知道一致性边界 |
| 连接池/线程池压测调优 | 不拍脑袋,压测数据说话 |
| 慢 SQL、大 key、深分页优化 | 能定位 + 能优化 + 能讲原理 |

---

## 一句话总结

**技术力 = 选型有取舍 + 边界有兜底 + 全程可观测**

四个项目对三力的覆盖:
- **缴费平台**:一致性/对账 → 边界 + 治理
- **规则引擎核验中台**:决策表选型(Drools vs 轻量)→ 选型
- **AI 同事**:评测/降级/红线 → 治理
- **断点平台**:埋点/标准化 → 可观测

> 准备方法:每个项目挑出最体现三力的 1 个动作背熟,自我介绍时刻意停顿在这些点上,引面试官来问。
