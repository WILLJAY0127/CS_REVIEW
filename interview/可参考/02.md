## 项目经历

### 一、人脸识别核身平台（三代架构演进 + 风控体系）
**角色**：核心开发/模块负责人 | **时间**：【20XX.XX - 至今】

**背景**：保险投保/保全/回访/贷款专区等场景强依赖实名核身，需对接第三方人脸平台（本地库1:1比对、公安库、出入境库三源比对），并叠加活体检测、防欺诈风控。

**架构演进主线**（由我主导/深度参与三代设计）：

1. **V1 适配层（facialAdapter）**：以适配器模式屏蔽三方人脸平台差异，统一注册/本地比对/公安库/出入境库四类API；加密/非加密双通道，MD5签名鉴权；Nacos + `@RefreshScope` 配置动态刷新，密钥与URL零重启变更
2. **V2 引擎化重构（faceRecognition2）**：
   - 设计**"责任链 + 策略选择器"双引擎**：核身路径责任链（本地库优先 → 按证件类型路由公安库/出入境库 → 成功后回注本地库），通过 `ApplicationContextAware` 按Bean名动态组链；比对源通过 `BusinessHandlerChooser` 策略路由
   - **前置/后置校验链**：前置按日失败次数拦截（Redis按天计数），后置失败计数+剩余次数文案+超限封禁
   - **后置风控层**：视频辅助识别检测（防他人协助刷脸）+ 死亡状态校验（对接公安侧状态，hr_status拦截），采用"风控异常放行、明确命中拦截"的可用性优先策略
   - 全链路开关化降级（真实人脸开关/风控开关/视频校验开关/死亡校验开关，均配置中心动态下发）
3. **V3 DDD + 规则引擎（insure-front facialArea）**：
   - 落地五层DDD结构：`controller → app → appDomainAdapter(防腐层) → domain → infrastructure`
   - 自研**泛型责任链组件**（`AbstractChainHandler<T,V> + FilterChain + HandlerChainContext`），配合 `SpringContextUtils.getBeanWithGeneric` 按泛型从容器取Handler，规则前置/后置链完全由**DB配置驱动**（动作检测次数、活体开关、本地库/公安库阈值、每日失败上限），新业务接入零代码
   - **双规则引擎**：BusinessRuleEngine（业务维度匹配）→ CoreRuleEngine（核心执行规则）
   - **高风险客户体系**：失败记录沉淀 → 高风险识别 → 动态加强活体动作检测（随机动作码，防脚本固化）

**技术亮点**：
- 票据（ticket）机制：核身通过后生成20分钟时效票据存Redis，下游业务凭票据换取人脸图片，避免敏感数据多次传输
- 跨服务全链路：业务前台（DDD分层）--Feign--> 核身引擎（责任链）--RestTemplate--> 三方平台，两层各司其职
- 场景码、业务配置DB化 + Redis缓存（60min），配置变更分钟级生效

**量化成果**：【日均调用量、支撑业务线数、接入业务接入成本从X天降到Y天、风控拦截率等——填真实数据】

### 二、AI智能查询助手"小太同学"（Dify Workflow + Java双端）
**角色**：后端负责人 | **时间**：【20XX.XX - 至今】

**背景**：保险App内对话式查询助手，用户用自然语言查询投连账户资金、保险理赔进展。核心挑战：**大模型是概率机器，金融场景要求答案100%准确**。

**Java侧（tlife-ai-query）**：
- 设计投连**聚合查询服务**：用户/保单/账户三维聚合 + 多级缓存；意图码→查询维度映射（`IntentCodeMapper`）；条件查询的**条件补全**（User→Account维度推导、时间范围前推）+ 响应裁剪；历史数据（收益5年/净值3年/交易不限）**按需加载**，避免无谓的重量级查询
- **异步语义日志**：全量记录"问题→API调用→响应→耗时"，为后续构建Golden Set评测集提供数据基础
- 配套理赔查询的EBA/保单等服务，支撑理赔工作流取数

**Dify工作流侧**：
- 投连助手：40+节点、8400+行YAML，7类意图+澄清+拒答9类兜底；**反向排除法**意图识别（先排除不可能的，不确定的进澄清，宁可不答不可答错）；置信度<0.65强制澄清；保单归属验证（防查他人保单）；概念混淆词（利息/分红/保底收益）代码级强制拒答
- **预加载机制**：12个预取节点在意图分支前并行取数，避免分支后重复调用；取数层 `ThreadPoolExecutor(10)` 并发拉取多账户数据
- **模型分工策略**：意图/参数抽取用 qwen（temperature=0，要确定性），回答生成用 deepseek（temperature=0.3，要表达力）

**方法论沉淀（理赔V3验证）**：
- **两次洗数理论**：LLM识别意图后，由代码"洗"出两路——取数入参（给API）和回答上下文（给LLM），raw data再经代码洗成slots，LLM只做填空——把LLM压缩到只做"它必须做的事"
- **五层准确性架构**：规则直出(100%) → 纯代码模板(100%) → 混合模板(≈100%) → 生成+校验降级(90%+) → 拒答兜底(100%安全)，"能不用LLM就不用LLM"
- 建立发布流水线：build → check → publish 自动化，YML注入式构建

**量化成果**：【问题覆盖量、准确率、日均调用量、转人工率等——填真实数据】
