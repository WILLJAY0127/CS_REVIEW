## 📋 题目描述

给定一个整数数组 `nums` 和一个整数目标值 `target`，请你在该数组中找出 **和为目标值 `target`** 的那 **两个** 整数，并返回它们的**下标**（数组下标，不是元素值本身！）。

### 题目隐含三大前提（决定用什么解法）

| 前提 | 说明 | 没满足会怎样 |
|------|------|-------------|
| **每种输入有且只有一个答案** | **只会有恰好 1 个下标二元组**满足 nums[i]+nums[j]==target（不会有 2 对、3 对多个不同解同时成立）| 不用考虑多解怎么排序、怎么选、要不要去重，找到立刻 return 就行 |
| **不能重复使用同一个元素** | `nums[i]` 和 `nums[j]` 必须 **i ≠ j**，哪怕数值相等也必须是两个不同位置（比如 `[3,3], target=6` → `[0,1]` 才对，`[0,0]` 错）| 两数用同一个会踩坑 |
| **返回下标顺序随意** | `[0,1]` 和 `[1,0]` 都判对 | 不用再做最后翻转 |

### 经典示例

| 例 | nums | target | 正确答案 | 说明 |
|----|------|--------|---------|------|
| 1 | `[2,7,11,15]` | 9 | `[0,1]` | nums[0]+nums[1]=2+7=9 |
| 2 | `[3,2,4]` | 6 | `[1,2]` | nums[1]+nums[2]=2+4=6（**注意不是 [0,0]**，不能重复用第一个 3！）|
| 3 | `[3,3]` | 6 | `[0,1]` | 同一个数字出现两次在不同位置，返回两个下标 **0 和 1** |

## 思路 0：纯暴力双重循环（最差，仅对比用）❌

先扫一眼作为基准。两个 for 嵌套，枚举所有 i<j 配对：

```python
def twoSum(nums, target):
    n = len(nums)
    for i in range(n):
        for j in range(i + 1, n):
            if nums[i] + nums[j] == target:
                return [i, j]
    return []
```

- 时间 **O(n²)**：n=1w 就要比较 1 亿次，秒不过
- 空间 O(1)
- 问题：完全不符合「哈希空间换时间」的优化目标

## 思路 1：两趟遍历哈希（你的直觉版 ✅，完全正确）

### 第一步：先想清楚哈希表要存什么

| 存什么？ | 键 key | 值 value | 为什么？ |
|---------|--------|---------|---------|
| **元素 ↔ 下标** 映射 | 数组里的数值 `nums[i]` | 这个数所在的**下标 `i`** | 题目最后要返回**下标**，不是返回值本身。如果只存"有没有这个数"就拿不到下标了，所以必须用 **Dict 不是 Set** |

> 🎯 选型铁则命中：[LC349 铁则 2](../2.两个数组的交集/349_两个数组的交集.md#L372-L374) —— 需要存「键值对应关系（值→下标映射）」 → 用 **Dict / HashMap**

---

### 思路 1 具体流程（2-pass）

```
Pass 1：先遍历数组一遍，把「每个数字 → 它的下标」全存进 num_map 字典
         （就是你说的「先都放 dict」）

Pass 2：再遍历一遍数组，对每个 nums[i]：
           我希望找到的互补数 = diff = target - nums[i]
           查 num_map 里有没有 diff
           有 → 返回 [i, num_map[diff]]
```

### ⚠️ ❗ 2-pass 版本最容易踩的致命坑：不能同一个元素自己加自己

**如果 2-pass 写成这样会出 bug：**

```python
# ❌ 错误版：没加「下标不能相同」判断
def twoSum(nums, target):
    num_map = {}
    for i, v in enumerate(nums):
        num_map[v] = i          # Pass1：全存
    for i, v in enumerate(nums):
        diff = target - v
        if diff in num_map:     # ⚠️ diff 很可能就是 v 本身！
            return [i, num_map[diff]]
    return []
```

**反例翻车：nums=[3,2,4], target=6**
```
Pass1存完：num_map = {3:0, 2:1, 4:2}

Pass2 i=0, v=3: diff=6-3=3 → 3 in num_map ✅ → return [0, 0] ❌ 错！
（i=0 和 num_map[3]=0 是同一个下标！重复用了同一个 3，违反「不能重复用同一元素」规则）
```

### ✅ 正确的 2-pass 写法（加一行判断）

```python
def twoSum(nums, target):
    num_map = {}
    # ────────── Pass 1：一次性把所有 值→下标 存字典 ──────────
    for i, v in enumerate(nums):
        num_map[v] = i              # 相同值会被后出现的下标覆盖，没关系（题目恰好只有一个解）

    # ────────── Pass 2：再扫一遍，查互补 diff  ──────────
    for i, v in enumerate(nums):
        diff = target - v
        if diff in num_map and num_map[diff] != i:   # ✅ 关键：不能是同一个下标！
            return [i, num_map[diff]]
    return []
```

**上面翻车险情再走一遍正确版：**
```
i=0, v=3, diff=3:
  diff in num_map → True，但 num_map[diff]==0 == i==0 → ❌ 条件不成立，不返回
i=1, v=2, diff=4:
  diff in num_map → True，num_map[4]=2 ≠ 1 → ✅ 成立，return [1,2]
```

### 🧩 深度 FAQ：[3,3] 这种相同数值 Pass1 存字典时「下标被覆盖」，为什么答案还对？

这就是你问的那个点，**结论先说：2-pass 版完全正确，不会因为覆盖而出错。**
那个 AI 说"存 dict 只会存一个 value 所以不对"——**前提是它忘了你加了 `num_map[diff] != i` 这一行判断，也没考虑题目「恰好一个答案」的双重保护。**

#### 先承认事实：Python 字典 key 唯一，相同数值确实只能存一个下标（后面会覆盖前面）

比如 `nums = [3, 3]`，Pass1 跑完：
```
i=0: num_map[3] = 0
i=1: num_map[3] = 1   ← 覆盖掉了！最终 num_map = {3: 1}，下标 0 "丢了"
```

✅ **但覆盖根本不影响答案正确性！因为有两层保护：**

---

#### 🔰 保护 1：`num_map[diff] != i` 判断（挡住自己加自己）

拿 nums=[3,3], target=6 按正确版 2-pass 一步一步跑：
```
Pass1 存完：num_map = {3: 1}   (被覆盖成第二个 3 的下标 1)

Pass2 开始：
  i=0, v=3:
    diff = 6 - 3 = 3
    3 in num_map ✅ → num_map[3] = 1
    然后判断：1 != i=0 ？ ✅ 成立！ → return [0, 1] （这就是标准答案！）
```

**解释：** 虽然下标 0 在 dict 里被覆盖没了，但没关系——当我们站在**左脚 i=0** 查 diff 的时候，dict 里存的是**右脚 1**，两下标不同（保护1命中）、加起来又等于 target，直接就是正确答案。就算覆盖让 dict 里只留下右脚也完全够用，因为"一对"只要能凑出来就行，不在乎 dict 里留的是左脚还是右脚的下标。

---

#### 🔰 保护 2：题目「恰好一个答案」的承诺（保证你不会选到"另一个合法但另一个解"的问题）

再极端一点：`nums = [3, 3, 3, 3]`，四个下标都是 3，target = 6。
Pass1 存完：`num_map = {3: 3}`（只有最后一个下标 3 活在 dict 里，前 0、1、2 全被覆盖丢了）

正确版 2-pass 再跑一遍：
```
Pass2:
  i=0, v=3: diff=3 in num_map ✅，num_map[3]=3 ≠ 0 ✅ → return [0, 3]
```

`[0,3]` 合法吗？ **完全合法**——nums[0]+nums[3]=3+3=6，0≠3。
OJ 根本不在乎你返回 [0,1]、[0,3]、[1,2]、[2,3] 中哪一个，只要满足 `nums[a]+nums[b]==target && a≠b` 就判对。
而「恰好一个答案」就是在给打包票：**不会出现"值层面不同的多对"**（比如 [1,4] 和 [2,3] 同时等于 target=5 那种真的两个不同解），但相同数值在不同位置重复出现形成的多组"下标对"，都算作同一个答案，返回任意一个合法下标对都可以。

---

#### ❗ 什么时候覆盖真的会出 bug？

只有一种极端情况：**你把保护 1 的 `!= i` 判断丢了，而且题面又没有「同一值重复出现多次」。**
那就是文档前面的自杀 bug 例子：`nums=[3,2,4], target=6` → i=0 查 diff=3，dict 里有自己，没保护就返回 [0,0]。和"覆盖"无关，是没加 `!= i` 判断的锅。

**覆盖 + 没加保护，最坏情形是什么？** nums=[3,3], target=6，没加保护：
```
Pass2 i=0, v=3, diff=3: num_map[3]=1 → 1≠0，其实居然也对（碰巧没自己加自己，因为被覆盖了）
但如果是 nums=[3,2,4] 只有一个 3，没被覆盖，num_map[3]=0，i=0 时就自杀 [0,0]
```
所以结论：**覆盖本身不是问题，真正的问题是忘记加 `num_map[diff] != i` 这一行保护。**

---

### 复杂度

- 时间：O(n)（Pass1 一次 n + Pass2 一次 n）
- 空间：O(n)（字典存 n 个键值对）

> ✅ **再次强调：你的直觉版完全正确，只要补上「num_map[diff] != i」这一行判断就没任何问题，OJ 100% 过。**

## 思路 2：一遍遍历边存边查（优化版 ⭐⭐⭐⭐⭐）

### 🔑 优化契机：能不能把两趟合成一趟？

从 2-pass 往下想一个问题：

> 当我们站在第 i 位处理 `nums[i]` 的时候，需要的互补数 `diff = target - nums[i]`，
> 这个 diff 的下标一定在 `0..i-1` 或 `i+1..n-1` 两种情况。
>
> **能不能我只让 "diff 在左边" 的情况被发现？ 右边那部分等轮到它自己的时候再发现？**

答案是可以！**每一对合法答案 (j, i) 都能被约定：j 在左、i 在右。**
当我们走到右脚 i 的时候，左脚 j 必然已经在前面遍历过了 → 已经被存进字典！
而 i 右边那些将来可能和 i 配对的数 → 等它们自己变成"右脚"的时候，i 作为"左脚"已经在字典里了。

这就是**边存边查**的根基：**用"左脚先入字典，右脚来查"保证任何一对只会被发现一次，而且 i 永远>j → 自然不可能同一个下标 → 连 `!=i` 判断都省了！**

---

### 🔑「签到模型」指纹触发公式（👈 你说之前缺的就是这个）

> **看到什么信号，脑子里自动弹"前辈配后辈 + 先查本子再登记"模型？**
> 任意一条命中，就可以直接套：

| 序号 | 触发信号 | 典型题目 |
|------|---------|---------|
| ① | 题目要求 **两个不同位置的元素配对**（加/减/乘/比大小都行），**明确禁止同一个元素用两次**（i≠j）| 两数之和、三数之和、四数相加 II |
| ② | 需要用哈希表存「**已经遍历过的数据**」，用"**过去的历史**匹配当前"的思路 | 两数之和（找左侧存在过的补数）|
| ③ | 本质是**单向遍历、时序不可逆**：数组从左往右扫，左边=过去，右边=未来，天然有序 | 所有「单趟哈希下标配对类」题目 |

**一句话口诀：「不同位置配对 / 禁自匹配 / 历史库匹配当前」三信号齐 → 立刻上签到模型：先查历史库，入库放最后。**

### 🏢 具象类比 1：会议室签到找搭档（1 秒吃透边存边查）

**规则：两个人组队、身高加起来等于指定高度 target，不能自己跟自己组队，只允许「先进来的老员工」和「刚进来的新人」配对。**

| 道具/流程 | 现实世界 | ≈ 两数之和算法 | 这个约束的目的 |
|----------|---------|---------------|--------------|
| 遍历顺序 | 顾客从门口按顺序依次走进去 | `for i,v in enumerate(nums)` 从左往右 | 保证时序：先进来 = 左侧已遍历索引 |
| 哈希字典 | 签到本（只登记已经走进房间的人，座位号=下标）| `num_map = {值: 下标}` | 本子里的下标永远 **< 当前 i**（i 还没写进去）|
| 步骤 ① 先查 | 新人先算"我需要多高的搭档" → 翻签到本找身高 | `diff = target - v` → `if diff in num_map` | **只找已经登记的前辈**，绝不找还没来的人 |
| 命中就返回 | 找到前辈的座位号 → 两人组队成功 | `return [num_map[diff], i]` | `num_map[diff] < i` 天然成立 → i≠j 自动满足 |
| 步骤 ② 查不到再存 | 本子里没有能搭档的前辈 → 把自己签名+座位号登记进本子 | `num_map[v] = i` | 把自己归入"前辈"，留给**后面进来的人**来找自己 |

> 🔴 反例对比：为什么"先全部登记完再挨个找人"（=2-pass）要多写一行保护？

> 所有人一次性冲进房间先写完签到本（高的人会覆盖矮的人同身高记录），然后每个人再挨个找人。
> 如果两个身高相同的人（=同一数值）一起登记，后一个人会把前一个人的记录**覆盖擦掉**；
> 第二个身高相同的人翻本子时，本子上只剩他自己那一条，一不小心就变成"自己和自己组队"自杀 bug（所以 2-pass 必须手动加 `!=i` 判断挡掉）。
> 而「签到模型」永远是"先找人、再登记自己"，当前人此刻根本不在本子上，连自杀的机会都没有。

### 🧱 底层逻辑拆解（时序隔离，为什么 i<j 是数学必然）

从「先查后写」的三步代码时序中，可以提炼出三条通用公理，以后任何单趟哈希配对题都适用：

#### 公理 1：遍历是一条单向时间轴，过去/现在/未来严格分层

```
索引方向：  0  →  1  →  2  →  3  → ... → n-1
(时间轴)  过去  过去   现在(j)  未来      未来
          ↑              ↑                ↑
     全部在 dict 里    正在处理      绝对不在dict里
```
数组遍历是一条**射线**：循环下标 j 只会越来越大，不会倒回去。
`dict` 只充当「时间轴的存档日志」—— 只存过去的索引，不包含当前 j 和未来的索引。

#### 公理 2：查询发生在写入之前，形成「闭环隔离」

固定时序永远是：**查 → 不命中才写**，顺序绝对不能反：
```python
# 查询阶段（这一时刻当前 j 绝对还没进入 dict！）
if diff in num_map:  # dict 里的所有下标，全部都严格 < j
    return [...] 
# 写入阶段（查不到的时候，才把自己加入历史库）
num_map[v] = i
```

**数学结论**：如果查到 `dict[diff] = i_hit`，必然有 `i_hit < j`。
返回 `[i_hit, j]`，两个下标天然不相等，彻底杜绝 `[j,j]` 非法答案。不需要任何手动 `!=j` 判断。

#### 公理 3：「先存后查」的 2-pass 为什么丢失这条保证？
2-pass 一次性把所有下标（包括**当前的、未来的**）全部塞进 dict：
- 把「过去/现在/未来」的时序隔离直接抹掉了
- dict[3]=0 立刻被 dict[3]=1 覆盖，位置先后信息丢了
- 第二轮遍历时，`j=1` 查到 `num_map[3]=1`，两下标可能相等（自杀）、也可能被覆盖到右脚（碰巧没自杀），全靠碰运气，所以必须手动补 `!=i` 保护。

#### 公理落地：用 [3,3] target=6 按时序逐行证明（不会自杀）
```
j=0:
  [查询阶段] dict 空 → {} 无 diff
  [写入阶段] dict[3]=0 → dict={3: 0}   (现在自己入库，成为前辈)

j=1:
  [查询阶段] diff=3 in dict ✅ → dict[3]=0，公理1保证 0 < 1
  → 直接 return [0, 1] 🎯
  [本次不执行写入]  （因为找到就 return 了，没走到写那一步）
```

### ↔️ 反向区分：什么时候**不用**「先查后存签到模型」？（避免滥用）

签到模型专门为「下标配对」类题目设计，下面这些哈希题直接一次全存就行，不需要严格遵守先查后存的顺序：

| 题型特征 | 不需要先查后存的原因 | 典型题目 | 正确做法 |
|---------|-------------------|---------|---------|
| **只统计频次**，不区分先后、不要求不同位置配对 | 只要最后计数结果对，顺序无所谓 | LC 242 有效的字母异位词 / LC 383 赎金信 | 直接全存进数组/dict计数，最后比较 |
| **只判断存在性 / 只去重**，不返回下标 | 不需要配对，不需要 i≠j | LC 349 两个数组的交集 / LC 202 快乐数 | 直接全丢进 set，`if x in set` 就行 |
| **不需要下标**，纯粹判断内容 | 没有"不能同一个元素用两次"的硬约束 | 异位词分组 LC 49 | 全存进 dict 分组，不用时序 |

### 🚦 固化的思考流水线（刷到同类题脑子里自动跑一遍）

```
拿到题目，第一步：审题两道判断题
  ├─ Q1: 是否要返回两个不同位置的元素 / 它们的下标？
  ├─ Q2: 是否明确要求「不能使用同一个元素两次」(i≠j)？
  └─ 两个都是 YES → 🔥 启用「签到模型」不用再想

启用后固定 5 步流水账：
  Step 1: 开空白哈希字典 num_map = {}（=空白签到本）
  Step 2: 开 for i, v in enumerate(nums) 从左往右遍历（= 顾客依次入场）
  Step 3: 每次先算「补数 diff = target - v」（= 算自己要的搭档）
  Step 4: 先查签到本：if diff in num_map → 直接 return [num_map[diff], i] （前辈+后辈组队成功）
  Step 5: else → num_map[v] = i 把自己登记进本子，留给后面的人
```

---

### 极简 1 句通用公理（最后刻进大脑）

> **当算法依赖遍历的先后次序、依赖前后索引的 i≠j 关系时，哈希表作为「时间轴的存档日志」，必须严格遵守「先查询日志，再写入日志」的顺序。**

```
核心不变量：站在位置 i → dict 里恰好装着 nums[0]~nums[i-1] 的 值→下标映射
                 ↓
           diff 命中 = 左脚在里面 = 配对一定是合法 (j,i) j<i
           diff 没命中 = 左脚没出现 / 没有合法左脚 → 那把当前 i 当左脚存起来，等以后的右脚
```

### 固定三步流程（每次循环）

```
① 先查：diff = target - nums[i] 在不在当前 dict 里？
         在  → 直接 return [dict[diff], 当前 i] （结束）
② 不在  → 把 nums[i] → i 存进 dict（让当前元素成为"未来右脚的左脚候选"）
③ 进入下一轮 i+1
```

### Python 完整标准代码（可直接提交，面试写这个）

```python
def twoSum(nums, target):
    num_map = {}                  # key: 值,  value: 这个值的下标
    for i, v in enumerate(nums):
        diff = target - v
        if diff in num_map:       # ① 先查：有没有左脚已经在里面
            return [num_map[diff], i]  # ✅ 自然 j < i，同一个元素 bug 永不出现
        num_map[v] = i            # ② 查不到，把自己当左脚存入，等将来的右脚
    return []
```

> 🔥 **为什么比 2-pass 更好？**
>
> 1. **少一轮完整遍历**（2n → n，常数级提速但实际很明显）
> 2. **去掉了 `num_map[diff] != i` 的判断**，代码更短、完全不会踩 2-pass 的自杀 bug
> 3. **最好情况非常快**：如果答案恰好在前两位，第一轮就 return，字典只装了 1 个数

### 🧱 1-pass 思路逐轮模拟：nums=[2,7,11,15], target=9 + 错误用例 [3,2,4] 对比

#### 例 1：nums=[2,7,11,15], target=9 → 答案 [0,1]

```
初始 num_map = {}

i=0, v=2:
  diff = 9-2 = 7，7 in {} ? ❌
  num_map[2] = 0 → num_map = {2: 0}

i=1, v=7:
  diff = 9-7 = 2，2 in {2:0} ✅
  → return [num_map[2], 1] = [0, 1] ✅ 正确！
（只遍历了 2 个元素就退出，dict 里甚至还没存 7、11、15）
```

#### 例 2：**最容易踩 2-pass 自杀 bug 的例子** nums=[3,2,4], target=6 → 答案 [1,2]

```
初始 num_map = {}

i=0, v=3:
  diff = 6-3 = 3，3 in {} ? ❌
  num_map[3] = 0 → {3:0}   (第一个 3 当左脚先存)

i=1, v=2:
  diff = 6-2 = 4，4 in {3:0} ? ❌
  num_map[2] = 1 → {3:0, 2:1}

i=2, v=4:
  diff = 6-4 = 2，2 in {3:0, 2:1} ✅
  → return [num_map[2]=1, 2] = [1, 2] ✅（正确！没有出现 i=0 和 自己配对的自杀 bug）
```

> 🔑 **为什么 1-pass 自动避免自杀 bug？**
>
> 因为当前 i 自己的值 v 我们是「先查、再存」！存 v 的动作在**查完之后**才发生。
> 轮到 i 这一回合，dict 里**绝对还没有 v 自己**，所以 diff==v 时不可能命中（想命中必须等后面另一个位置存着相同 v 的时候）。
> 对比 2-pass：提前把 v 已经存在 dict 里了，必须手动 `!= i` 排除自己。

### ➕ 例 3：nums=[3,3], target=6 → 答案 [0,1]

```
i=0 v=3: diff=3 → 不在{} → 存 {3:0}
i=1 v=3: diff=3 → 在 {3:0} ✅ → return [0, 1] ✅
```

完美处理相同数值在两个位置的情况。

| 解法 | 时间 | 空间 | 自杀 bug（自己+自己）| 遍历趟数 | 推荐度 | 定位 |
|------|------|------|-------------------|---------|--------|------|
| 暴力双重 for | O(n²) | O(1) | 自然不会（j>i 保证）| 1 趟但 n² 次 | ⭐ | 仅对比，不用 |
| **2-pass 哈希（你的直觉版）** | O(n) | O(n) | ⚠️ **容易中招，必须加 `num_map[diff] != i`** | 2 趟 | ⭐⭐⭐⭐ | 正确解，完全能写，只是 1-pass 更优 |
